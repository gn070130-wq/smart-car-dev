摘  要
本文介绍安徽理工大学“京天武迢驱”队面向第二十一届全国大学生智能汽车竞赛人工智能模型组开发的虚实融合自主智能车系统。整车自项目开始即采用C车模作为实际参赛与联调平台，技术检查资料记录整车尺寸约275 mm×180 mm×150 mm、摄像头距地约150 mm。系统以RK3588S边缘计算平台作为人工智能推理与高层决策核心，以TC264微控制器作为车辆底层执行控制器，构建“视觉感知—语义理解—行为决策—运动控制”的分层架构。上位机软件基于ROS 2组织摄像头、目标检测、语义分割、路牌视觉大模型、决策和串口节点；TC264通过UART3接收8字节控制帧，并以5 ms周期执行双编码器采样、IMU采样、视觉横向误差转向控制和左右电机速度闭环。当前工程已实现巡航、行人避让、车辆绕行、路牌语义决策、金币偏置和终点停车等主要逻辑，自主泊车强化学习、红绿灯限速与总决赛Agent任务仍属于后续扩展模块。

第一章 绪论
1.1 研究背景与赛道定位
随着视觉感知、边缘计算、强化学习和多模态大模型技术快速发展，智能驾驶系统正由传统的单一车道识别与规则控制，逐步向复杂环境理解、实时风险评估和自主策略规划方向演进。第二十一届全国大学生智能汽车竞赛人工智能模型组以现实物理赛道为基础，通过增强现实系统实时叠加虚拟行人、虚拟道路标识、虚拟障碍物、虚拟金币和任务指令等对象，形成虚实融合驾驶环境。该赛道不仅要求车辆能够稳定完成自主巡航，更强调参赛系统对视觉场景的理解能力、对突发事件的实时应对能力，以及将人工智能模型部署到车载边缘平台后的完整工程实现。
本组要求参赛者基于统一智能车平台完成感知、理解、决策和执行闭环，外部环境感知采用纯视觉方式，不依赖激光雷达、超声波、红外测距等额外环境传感器。与传统智能车竞赛相比，该赛道不再以固定赛道元素和固定触发点作为主要信息来源，而是通过随机生成或动态变化的虚拟对象考察模型的泛化能力。因此，系统设计必须同时兼顾视觉模型精度、推理实时性、决策鲁棒性、车辆运动控制稳定性和边缘算力约束。
1.2 竞赛任务与关键技术要求
线下赛围绕城市交通中具有代表性的复杂场景设置多项核心任务。车辆需要在虚拟行人突然横向进入车道时进行风险判断并采取减速、制动或绕行策略；在分叉路口识别虚拟路牌中的文字、图标或混合语义，并依据OCR和视觉大模型结果选择正确方向；在指定停车区域利用强化学习策略完成车位识别、轨迹规划和泊入；在限速区间根据红绿灯状态与速度约束进行节奏性通行；在完整赛道中兼顾安全和时间成本尽可能收集虚拟金币；全国总决赛还将加入基于文字指令的智能体规划任务。

1.3 系统总体方案
针对上述任务，本系统采用“边缘AI上位机+实时控制下位机”的分层架构。RK3588S负责摄像头图像采集后的深度学习推理、目标状态融合、OCR与大模型交互、任务状态机以及高层行为决策；TC264负责舵机、电机、编码器和惯性状态的实时控制。两级控制器通过有线串口交换期望速度、目标横向位置、模式状态及必要反馈信息。该结构将计算量较大的人工智能模型与高频底层控制解耦，使视觉模型更新不会直接影响电机闭环的实时性，同时便于分别调试感知算法与车辆控制参数。
系统运行时，摄像头持续获取车前方真实赛道及增强现实叠加图像，感知节点根据当前任务并行完成赛道分割和目标检测；决策节点将检测结果与车辆运行状态进行融合，判断当前是否处于行人避让、路牌识别、信号灯、金币收集、停车或普通巡航阶段。对于需要语义理解的路牌任务，系统截取目标区域并调用OCR或视觉大模型服务得到结构化方向指令；对于需要连续策略输出的泊车任务，则由训练得到的强化学习策略根据视觉状态量生成控制动作。最终的目标速度和横向/转向控制量经过限幅与安全检查后通过串口发送至TC264，由下位机完成执行。

1.4 软件架构与工程组织
上位机软件采用ROS 2进行模块化组织。工程按照硬件接入、消息接口、视觉感知、高层决策和整车启动进行划分，其中car_hardware负责摄像头与串口节点，car_perception负责目标检测、OCR和语义分割模型，car_decision负责任务状态机、轨迹平滑和大模型服务，car_interfaces定义车辆控制与赛道信息消息以及大模型任务服务，car_bringup用于整车节点统一启动。该结构使每个模块具有明确输入输出接口，方便单独运行、录制数据、替换模型和定位故障。
整车启动后，摄像头节点首先建立图像数据流，感知节点加载RKNN模型并进入推理循环，串口节点建立与TC264的通信链路，决策节点订阅感知结果并发布控制信息，大模型服务在收到路牌或智能体任务请求时执行语义推理。各模块通过时间戳、状态标志与超时机制避免使用过期信息，从而提高模型推理波动或局部通信异常情况下的系统安全性。

第二章 车模机械结构与平台布置
2.1 C车模与整车结构
本项目自设计与调试初期即采用C车模，当前代码、PCB、整车照片及技术检查资料均对应同一C车模平台。现有技术检查资料记录整车长约275 mm、宽约180 mm、高约150 mm，摄像头距地约150 mm；车辆配置1个前视摄像头、2个编码器、RA660惯性传感器、RK3588S上位计算平台、无线串口以及2块自制PCB。该车模直接用于完成视觉算法、上下位机通信、电机驱动、转向控制和整车任务逻辑的开发、联调与比赛准备。
C车模整车结构如图所示。RK3588S及散热组件布置在车体中部上方，自制核心板与驱动板位于底盘中部，摄像头安装在车体前端支架，电池和功率线束尽量靠近底盘布置。现有结构能够满足当前联调与比赛任务需求；从照片可见线束数量较多、部分连接线跨越计算平台和转向机构附近，因此后续机械优化重点应放在线束固定、USB及供电接口防松、串口与编码器信号线缩短，以及功率线与弱信号线分离布置，而不是更换车模平台。

2.2 摄像头安装与视觉视场
外部环境信息由前视摄像头获取，现有C车模技术检查资料记录镜头距地约150 mm。摄像头视场应同时覆盖近处道路边界、分叉路牌、虚拟行人出现区域以及后续停车任务所需的视觉标识，避免近处盲区过大或远处目标像素不足。后续如调整摄像头支架或外壳位置，应重新测量安装高度和俯仰角，并同步重新标定视觉控制参数。
调试阶段可利用实时图像显示工具观察分割区域、目标框和图像中心线，并以典型任务距离为参考调整镜头角度。对于路牌识别任务，应重点保证分叉口前的路牌ROI具有足够清晰度；对于行人避让任务，应保证道路两侧虚拟行人的出现区域处于有效视场；对于金币收集，应兼顾较宽横向视野，以便提前规划轻微路径偏置。摄像头最终安装高度和角度应在报告图片及技术检查表中记录。
2.3 上位计算平台与散热
RK3588S承担深度学习推理、ROS 2通信和高层决策，是整车计算量最大的模块。为保证连续运行时的推理频率稳定，计算平台采用刚性固定，并为处理器和电源芯片预留散热空间。布置时避免将上位机紧贴电池或电机驱动功率器件，以减少热量叠加；同时保证USB摄像头、串口转换模块和供电线具有足够弯曲余量，避免车辆振动造成接口接触不良。
在正式比赛前应分别在普通巡航、双模型并行推理和大模型任务触发条件下记录处理器温度、CPU/NPU占用及推理帧率。若温升导致推理频率下降，应优先通过模型量化、输入尺寸优化和线程调度降低计算负载，再结合散热片或风冷结构改善热环境。
2.4 PCB、供电与线束布置
系统采用自制核心板和驱动板完成主控接口、电源变换和电机驱动。核心板集中布置TC264核心板针座、姿态传感器接口、编码器接口、舵机接口、蜂鸣器、屏幕按键、USART及电源扩展接口；驱动板完成左右电机功率输出和板卡供电。机械安装时将低功耗信号线与电机大电流线尽量分离，并将串口、编码器等敏感信号线控制在较短长度，降低开关噪声耦合。
整车使用1块3300 mAh航模电池，核心板、驱动板、RK3588S和执行机构由车载电源系统供电。电池固定与线束走向应结合C车模底盘空间进行优化，保证高速转向、急加速和制动过程中电源连接可靠，同时避免功率线束干涉转向机构或车轮。现有PCB与上、下位机的功能分工保持不变。
第三章 硬件系统设计
3.1 硬件总体架构
整车硬件由RK3588S边缘计算平台、TC264实时控制器、前视摄像头、自制核心板、自制电机驱动板、转向舵机、左右驱动电机、双编码器、IMU660RA/RA660惯性传感器及航模电池组成。当前平台通过RK3588S完成视觉与高层决策，通过TC264完成5 ms级实时执行，二者之间由UART3有线串口连接。

3.2 TC264核心控制与接口板
下位机采用TC264微控制器作为车辆实时控制核心。结合现有2026lyy工程核对，all_init()初始化UART2和UART3，波特率均为115200 bit/s，其中UART3（P15_6/P15_7）用于接收RK3588S控制数据，UART2（P10_5/P10_6）保留给无线串口；同时初始化舵机PWM、IMU660RA、左右编码器、左右电机PWM/方向输出以及5 ms周期定时器。核心板ver-1.2则将上述接口集中到同一PCB，便于整车接线与调试。
TC264的实时任务由CCU60 5 ms定时中断置位，CPU1主循环调用start_task_process0()执行task0_5ms()。当前有效调用顺序为：左右编码器采样、IMU数据读取、转向控制、目标速度分配、左右电机速度控制以及调试数据发送。该结构使底层控制周期与Linux端视觉推理周期解耦，视觉帧率波动不会改变TC264的基本执行周期。

图3.1 TC264核心板 ver-1.2 原理图
 
3.3 RK3588S边缘计算平台
RK3588S作为AI上位机运行Linux和ROS 2环境，并利用NPU完成RKNN模型推理。系统将训练完成的目标检测和语义分割模型转换为RKNN格式，在车端直接加载推理，从而降低CPU占用并提高实时性。上位机同时承担路牌ROI截取、OCR识别、视觉大模型请求、任务状态融合和控制目标发布，因此需要合理控制模型数量、输入分辨率和并发线程。
为了保证决策链路具有可维护性，各AI功能不直接操作电机，而是统一输出结构化感知结果或高层控制目标。例如目标检测节点输出目标类别、边界框和置信度，赛道分割模块输出可行驶区域和参考中心，路牌语义模块输出方向意图，决策节点再根据当前状态生成速度与横向目标。通过这种接口化设计，可以在不修改底层控制代码的情况下更换模型或优化策略。
3.4 电源设计
车辆由航模电池统一供电，自制核心板和驱动板根据不同负载进行多级稳压。核心板电路包含5 V和3.3 V供电支路，部分降压电路采用TPS5450系列器件，3.3 V支路采用低压稳压器供给逻辑和传感接口。驱动板设置独立的板卡供电与功率输入，并配置大容量电容、保险/保护器件和瞬态抑制元件，用于降低电机启动、制动和换向时的电源波动。
电源设计调试重点包括三方面：一是电机大电流变化时上位机和TC264不得复位；二是舵机快速动作时逻辑电源压降不得影响串口和传感器；三是RK3588S满负载推理时供电应保持稳定。实际测试时应在电机堵转风险可控的条件下逐步增加负载，并使用示波器检查5 V、3.3 V及主电源纹波。
3.5 电机驱动板
驱动板ver-1.2采用两路DRV8701E栅极驱动器配合外部MOSFET功率级构成电机驱动通道。DRV8701E支持PH/EN控制方式，可由TC264输出方向与PWM使能信号；外部MOSFET承担主要功率开关，提高驱动能力并便于根据电机电流选择器件。板上同时配置驱动使能、睡眠控制、电源指示和保护电路。
当前下位机电机输出通过PwmOut_l()和PwmOut_r()分别控制方向GPIO与PWM，占空控制量在速度控制程序中限制在±5000。左右电机分别采用带前馈的速度闭环控制：左侧参数当前为kp=1.6、ki=0.06、kd=0.5，右侧为kp=2.0、ki=0.06、kd=0.2，前馈系数均为0.6。需要说明的是，现有代码中尚未实现独立的换向死区、方向切换延时或速度斜坡保护，因此报告不再将这些功能描述为“已实现”；正式高速调试前建议在程序中补充换向保护与急停策略。

3.6 编码器与惯性状态反馈
编码器和IMU660RA/RA660仅用于车辆自身状态采样，不参与外部道路、障碍物或虚拟对象识别。当前程序每5 ms读取左右编码器计数，采用“0.9×历史值+0.1×当前计数”的一阶低通滤波后得到realspeed；右侧编码器在软件中进行符号反向，以统一车辆前进方向的速度正负号。IMU数据也在同一周期读取，但当前转向函数中的陀螺仪阻尼系数g_kd设置为0，因此IMU尚未实际参与转向闭环。
自身状态反馈与纯视觉外部感知的功能边界在软件中保持明确：道路中心、行人、车辆、路牌、金币等信息来自摄像头与视觉模型；编码器用于电机速度闭环，IMU当前主要完成数据采集和后续融合预留。因现有代码尚未启用IMU转向补偿，本文将其描述为“已采样、待融合”，避免把预留功能写成已完成闭环。
3.7 上下位机串口通信
RK3588S与TC264之间采用UART3有线串口通信，当前工程波特率为115200 bit/s、8N1。uart_node订阅/decision/cmd_val后，将desired_speed乘1000转换为16位整数，并将target_x直接转换为16位整数。这里的target_x是图像横向目标像素坐标，而不是前轮转角；下位机以图像中心320像素为参考计算转向误差。控制帧固定为8字节：0xAA、0x55、Speed高字节、Speed低字节、Target X高字节、Target X低字节、校验和、0xFF；校验和为4个数据字节之和的低8位。TC264在UART3接收中断中逐字节调用get_uartdata()状态机完成帧头、数据、校验和帧尾检查。

当前代码中Uart2data.rec_ok在成功解析一帧后会置1，但尚未发现基于该标志或时间戳实现的“控制帧超时自动停车”逻辑；因此原报告中关于下位机通信看门狗、超时降速和自动停止的描述不准确，现已删除。另一个关键点是，UART3控制帧只更新Speed与Image_Center，电机是否真正输出还受motor_flag使能门控，motor_flag目前由无线调试/参数协议等路径置位。正式比赛版本建议将上位机心跳与motor_flag联动，并增加100~200 ms级通信超时急停。
第四章 人工智能感知与语义理解
4.1 视觉感知总体流程
视觉感知模块以摄像头图像为唯一外部环境输入。每帧图像首先完成格式转换和必要的缩放处理，随后根据任务需求进入语义分割、目标检测以及OCR/VLM处理分支。语义分割主要提供道路可行驶区域和巡航参考；目标检测用于识别行人、车辆、金币、拱门、停车相关标志、路牌及其他赛道对象；OCR和视觉大模型仅在需要语义理解时触发，以降低持续调用大模型造成的计算与时延开销。
当前工程在RK3588S端部署RKNN格式的检测模型和PP-LiteSeg语义分割模型，并将感知结果统一交给上层分析模块。模型推理与决策尽量解耦，决策节点不依赖某一具体网络输出格式，而是使用类别、置信度、目标中心、边界框、可行驶区域中心等规范化信息。这样可以在后续更换PaddlePaddle训练模型、调整输入尺寸或重新量化时保持上层状态机基本不变。
4.2 赛道语义分割与巡航参考
普通巡航阶段需要持续估计车辆相对于可行驶区域的位置。系统使用轻量化语义分割网络对前视图像进行像素级分类，提取道路或赛道区域。为降低近处透视畸变和远处噪声影响，可在图像下半部分设置若干横向采样行，计算每一行有效区域的左右边界和中心位置，再根据距离权重融合得到目标中心线。若局部出现虚拟对象遮挡，则优先利用剩余连续区域和历史中心线维持短时稳定。
相比单纯基于灰度阈值的传统巡线方法，语义分割对虚实融合画面中的颜色变化、阴影和虚拟特效具有更强适应性。为了满足实时性要求，训练阶段需要控制模型规模并进行数据增强，部署阶段通过RKNN量化和NPU推理降低计算耗时。最终用于控制的不是整幅分割掩膜，而是经过几何处理后的道路中心、曲率趋势和有效性标志，从而减少决策节点的数据量。
4.3 目标检测与多任务对象识别
当前目标检测模块在PerceptionAnalyzer中定义的主要类别为NOTICEBOARD（提示牌）、STOP（停车标志）、ARCH（拱门）、HUMAN（行人）、GOLD（金币）和CAR（车辆）。每个检测框保留类别、位置和尺寸信息，并由感知分析器进一步形成TrackInfo中的行人、车辆、拱门、停车标志、金币与路牌状态。红绿灯、车位等类别尚未出现在当前有效枚举中，后续任务扩展时再增加。
为减少误检对车辆控制的直接影响，系统不采用“单帧检测即触发”的方式，而是结合连续帧确认、置信度阈值和空间位置条件形成事件。对于虚拟对象突然出现的场景，连续帧阈值不能过高，否则会增加响应延迟；因此行人等安全相关目标采用更灵敏的触发策略，而金币等非安全目标允许更严格的稳定确认。
4.4 虚拟行人识别与“鬼探头”避让
“鬼探头”任务的核心并非在固定位置执行制动，而是实时判断虚拟行人与车辆路径是否存在冲突。系统首先通过目标检测获得行人边界框，并利用连续帧中目标中心位置、框面积变化和相对道路位置估计其横向运动趋势与接近程度。当行人位于车道外且风险较低时，车辆保持巡航或适度降低速度；当行人接近道路边界时进入预警状态；当预测路径与车辆前进区域发生明显重叠时，系统进入避让状态。
避让策略遵循安全优先原则。当道路另一侧存在足够可行驶空间且横向绕行不会引入新的碰撞风险时，可生成绕行方向并降低速度通过；若可行驶空间不足、行人已进入车辆前方或目标出现过于突然，则优先紧急制动并等待行人通过。状态机只有在连续若干帧确认行人离开危险区域后才恢复普通巡航，避免由于短时漏检出现反复加速。
4.5 路牌OCR与视觉大模型语义理解
分叉路口任务要求车辆理解虚拟路牌中可能同时出现的文字、图标和符号信息。系统在目标检测发现路牌后，先根据边界框裁剪ROI，并进行适度放大、透视或亮度处理。对于文字信息较明确的场景，使用PaddleOCR得到字符结果，再进行关键词与方向词解析；对于图文混合、语义组合或仅依靠OCR难以判断的情况，则将路牌图像提交给文心视觉大模型，并要求模型按照预定义格式输出“LEFT、RIGHT、STRAIGHT”等有限方向结果。
为避免大模型自然语言输出直接驱动车辆，LLM服务层对返回内容进行二次解析，仅允许映射到有限动作集合。若返回结果不在允许范围、请求超时或置信信息不足，则车辆在分叉前进入低速等待或重新采集路牌图像。得到可靠方向指令后，状态机进入LLM_EXECUTE模式，在预定的分叉几何区间内根据道路分割结果执行对应方向，完成后退出该模式并恢复普通巡航。
4.6 自主泊车强化学习策略
自主泊车任务在竞赛要求中必须采用强化学习策略，但当前src工程的decision_node状态枚举中尚无PARKING_MODE，现有感知消息和检测类别也未形成完整泊车输入，因此本节属于后续实现方案而非已完成代码。计划按照组委会提供的强化学习仿真环境与PaddlePaddle工具链建立训练流程，并在视觉端使用允许数量范围内的AprilTag辅助获取车位相对状态。
后续强化学习奖励函数可围绕目标位姿误差、航向误差、动作平滑性、碰撞惩罚和成功奖励设计，策略部署后仍只输出期望速度与转向目标，由TC264底层闭环执行。网络结构、训练轮数、垂直/平行车位成功率等内容必须在实际完成训练与实车验证后再填写。
4.7 红绿灯识别与区间速度规划
限速与红绿灯任务属于当前工程尚未完成的扩展模块。现有PerceptionAnalyzer检测类别主要包括提示牌、停车标志、拱门、行人、金币和车辆，decision_node状态枚举中也尚无独立红绿灯状态，因此报告不将该功能描述为已实现。后续需增加红绿灯视觉类别/状态信息，并根据正式发布的最低速度、最高速度和灯态约束加入速度规划状态。
实现时应以实时视觉灯态为主要依据，而不是固定时间或固定赛道位置触发。速度上下限建议配置化，并在进入限速区间后由状态机根据当前速度、视觉灯态和可通行条件生成目标速度。正式报告中的识别准确率和通过策略应以完成代码和实车测试后的结果为准。
4.8 金币感知与全局巡航策略
金币属于奖励目标，其优先级低于道路安全和其他强制任务。目标检测获得金币位置后，决策模块判断金币是否位于可行驶区域、车辆是否有足够横向空间，以及偏离基准路径后是否会影响即将到来的行人、路口或停车任务。当条件满足时，系统对道路中心参考加入有限的横向偏置，使车辆以平滑轨迹经过金币区域；若金币位于高风险位置，则直接放弃收集。
全局策略通过“任务优先级+局部收益”实现，不以收集数量作为唯一目标。安全相关事件最高优先，路牌、红绿灯和停车等强制任务次之，金币收集只在普通巡航且不会显著增加时间和风险时启用。该逻辑能够避免车辆为了单个金币做出大幅横移或急转弯，符合比赛对安全与任务完成质量的综合评价原则。
4.9 智能体文字指令规划接口
全国总决赛神秘任务需要基于文字指令进行高层规划。当前工程已有LLMTask服务，但其实际用途是路牌截图的VLM语义决策，尚未形成通用Agent动作序列规划器。因此本节作为扩展接口设计：后续可复用OCR/VLM服务，将自然语言任务解析为有限动作序列，再交由现有状态机逐项执行。
后续Agent仍应只负责高层任务分解，不直接产生电机PWM；输出必须映射到有限、可验证的动作集合，并设置完成条件、超时和安全中止条件。当前代码没有这一完整链路，终版报告应在实际实现后再补充接口、状态与测试结果。
第五章 决策规划与车辆运动控制
5.1 ROS 2节点与数据流
整车软件通过ROS 2话题与服务组织数据流。摄像头节点发布图像，感知节点订阅图像并输出赛道与目标信息，决策节点订阅感知结果后生成ControlInfo类控制消息，串口节点负责将控制消息编码后发送至TC264。对于路牌和Agent等低频语义任务，使用服务接口触发大模型推理，避免持续占用主控制回路。整车启动文件统一加载各节点和全局参数，减少比赛现场重复配置。
5.2 事件驱动状态机
为了避免多个任务同时修改速度或转向指令，系统采用事件驱动状态机统一管理控制权。普通情况下车辆处于CRUISE状态，以道路中心和速度目标进行巡航；检测到高风险行人后切换到PEDESTRIAN_MODE；检测到需要避让的车辆目标时进入CAR_AVOID_MODE；发现有效路牌后依次经过SIGNAL_BOARD_TRIGGER、WAITING、CAPTURE和LLM_EXECUTE阶段；目标丢失时进入LOST或保守恢复状态；收到停止条件时进入STOP_MODE。后续泊车、红绿灯和Agent任务同样以独立状态扩展。

5.3 巡航转向与速度指令生成
普通巡航中，decision_node并不直接输出舵机角度，而是把语义分割得到的道路目标横坐标作为ControlInfo.target_x发布；行人避让、车辆绕行和金币收集通过在该像素坐标上叠加平滑偏置改变车辆目标路径。基础速度由lap1_speed、lap2_speed和lap3_speed参数决定。当前配置文件三圈速度均设为3.2，上位机再将该数值乘1000后发送给TC264。
当赛道丢失时，现有decision_node根据最近可靠target_x选择-50或image_width+50的极限寻线目标，并将速度降至基础速度的0.45；终点STOP_MODE在触发后的前1 s保持基础速度冲线，随后输出0速度。路牌任务使用SIGNAL_BOARD_TRIGGER、WAITING、CAPTURE与LLM_EXECUTE等状态，大模型结果只映射为有限的直行/右侧分叉动作，不直接产生电机PWM。
5.4 下位机速度与转向控制
TC264接收有效控制帧后更新Uart2data.Speed与Uart2data.Image_Center。task0_5ms()在5 ms周期内先更新编码器和IMU，再执行Attitude_Control()：当前设定目标图像中心为320，误差err=320-Image_Center，实际启用参数为kp=1.1，而二次项kp2、视觉微分kd和陀螺仪阻尼g_kd均为0，因而当前转向本质上是比例控制；输出加到舵机中心值4790，并由4200~5400的软件机械限幅约束。
随后kinematics_task()根据Uart2data.Speed生成左右电机目标速度。虽然工程保留了阿克曼主动差速函数，但其中factor当前被固定为0，因此左右基准目标速度实际相同，并未启用基于转角的主动差速。Motor_Run()再依据motor_flag决定是否执行左右独立速度闭环：motor_flag=1时以g_target_speed_l/r为目标，motor_flag=0时目标速度置0。现有代码没有实现控制帧超时、编码器异常自动停车或独立换向保护，这些功能应作为正式比赛前的安全增强项，而不应在报告中写成已完成。

5.5 安全优先级与冲突处理
不同任务可能在同一时间出现，例如巡航过程中同时检测到金币与行人，或分叉路牌附近出现红绿灯。系统通过优先级管理避免控制冲突：紧急行人/碰撞风险具有最高优先级，其次为红灯停车等安全约束，再次为必须完成的路牌、停车和Agent任务，金币收集优先级最低。当高优先事件触发时，低优先任务的路径偏置和速度增益立即失效。
状态机切换采用“进入条件+保持条件+退出条件”三段式逻辑，并设置最短保持时间和连续帧确认，减少目标检测抖动造成的频繁切换。任何AI模块只负责提出事件或目标，不可绕过状态机直接控制电机，这一原则保证了整车控制链路的可解释性和可调试性。
第六章 系统开发与调试
6.1 开发环境与调试工具
上位机开发环境以Linux、ROS 2、C++/Python和RKNN运行时为主，深度学习训练和数据处理采用PaddlePaddle相关工具链。视觉模型在训练端完成数据标注、训练、验证和导出，再转换为适合RK3588S NPU运行的RKNN模型。下位机使用TC264配套编译与下载环境完成PWM、编码器、串口、舵机和惯性传感器驱动开发。
调试工具包括ROS 2话题查看、图像叠加显示、串口日志、模型离线测试脚本和参数配置文件。为了提高问题定位效率，调试过程中尽量同步记录原始图像、感知输出、状态机状态、上位机控制目标和下位机实际反馈，使一次异常能够还原完整数据链。
6.2 数据采集、标注与模型训练
由于增强现实虚拟对象与真实赛道背景同时出现在摄像头画面中，训练数据需要覆盖不同光照、摄像头角度、赛道纹理和虚拟对象位置。目标检测数据应重点覆盖行人、路牌、金币、红绿灯、停车标志等关键类别，并保留目标尺寸较小、部分遮挡和靠近图像边缘的样本。赛道分割数据则需覆盖直道、弯道、分叉、遮挡及虚拟特效叠加区域。
训练阶段采用随机亮度、对比度、缩放、裁剪和轻微模糊等增强方式提高泛化能力，但不使用会改变任务语义的过强变换。模型评价除常规检测精度或分割指标外，还需关注“任务触发可靠性”，例如行人是否能在足够提前量被发现、路牌ROI是否可供OCR读取、金币误检是否会导致不必要横移。最终模型选择以实车任务表现而非单一离线指标为依据。
6.3 RKNN模型转换与边缘部署
模型部署到RK3588S前，需要完成输入尺寸固定、算子兼容性检查、量化校准和RKNN转换。量化数据集应尽量来自真实摄像头采集画面，避免使用与比赛环境差异较大的通用图片。转换后分别比较浮点模型与RKNN模型在相同验证集上的输出，确认量化没有造成关键目标明显漏检。
车端运行时同时加载目标检测和语义分割模型，因此需控制内存占用和线程并发。可将检测与分割安排在独立工作线程，通过最新帧覆盖方式防止图像队列无限积压；决策节点只使用时间上最新的有效结果。对于OCR和视觉大模型等低频任务，采用事件触发，只有在路牌稳定进入指定区域后才执行，避免持续推理影响主视觉链路。
6.4 单模块调试
整车调试按照由底层到上层的顺序进行。首先在车轮悬空条件下验证电源、舵机、电机方向、编码器正负号和串口通信；随后在低速直线场景中整定速度环和转向中心；再独立测试摄像头帧率、目标检测和语义分割结果；确认单模块稳定后，才接入状态机和AI任务逻辑。每次只改变一类参数，避免模型阈值、速度增益和舵机参数互相掩盖问题。
对于路牌大模型任务，应先离线验证相同截图在OCR与VLM服务中的输出稳定性，再接入车辆状态机；对于行人任务，应在低速条件下多次改变行人出现时机和横向位置，检查触发距离与制动提前量；对于金币任务，应优先验证车辆在放弃金币时仍能稳定巡航，防止奖励目标影响基础能力。
6.5 整车联调与典型异常处理
整车联调重点观察从“目标出现”到“车辆动作”的端到端延迟。该延迟包含摄像头采集、模型推理、状态机确认、串口发送和底层执行多个环节。对于行人避让等安全任务，应以最不利的推理帧率和车辆速度估算安全余量；若余量不足，应优先降低触发阈值、提高安全任务推理频率或限制最高速度，而不是单纯提高控制增益。
常见异常包括短时漏检、误检、图像卡顿、大模型超时、串口丢帧、车辆打滑和转向饱和。系统分别采用连续帧确认与短时保活、类别和区域过滤、图像超时检测、LLM超时回退、串口校验与看门狗、速度限幅以及舵机机械/软件双限位进行处理。比赛前应针对每类异常进行重复测试，验证车辆能够进入可预测的安全状态。
6.6 各任务测试记录建议
为了避免在尚未完成最终赛道实测前虚构定量结果，本报告现阶段不填写未经验证的成功率、平均时间或模型精度。正式提交前建议按照统一模板补充测试数据：每项任务至少记录测试次数、成功次数、失败原因、平均完成时间、关键模型置信度和端到端延迟；对于自主泊车，分别记录垂直式和平行式车位；对于行人避让，记录不同出现点和车辆速度；对于路牌识别，记录文字、图标和混合路牌的识别结果。

void control_callback(const car_interfaces::msg::ControlInfo::SharedPtr msg) {
    int16_t speed_cmd = static_cast<int16_t>(msg->desired_speed * 1000.0f);
    int16_t target_x  = static_cast<int16_t>(msg->target_x);

    unsigned char cmd_frame[8];
    cmd_frame[0] = 0xAA;
    cmd_frame[1] = 0x55;
    cmd_frame[2] = (speed_cmd >> 8) & 0xFF;
    cmd_frame[3] = speed_cmd & 0xFF;
    cmd_frame[4] = (target_x >> 8) & 0xFF;
    cmd_frame[5] = target_x & 0xFF;
    cmd_frame[6] = (cmd_frame[2] + cmd_frame[3] +
                    cmd_frame[4] + cmd_frame[5]) & 0xFF;
    cmd_frame[7] = 0xFF;
    serial_driver_->send_data(cmd_frame, sizeof(cmd_frame));
}

A.3 TC264控制帧状态机解析（code/communicate.c，节选）
void get_uartdata(uint8_t ch)
{
    static uint8_t state = 0;
    static uint8_t buf[8];

    if(state == 0) { if(ch == 0xAA) buf[state++] = ch; return; }
    if(state == 1) { if(ch == 0x55) buf[state++] = ch; else state = 0; return; }

    buf[state++] = ch;                 // data[2..6] and frame tail
    if(state < 8) return;

    uint8_t sum = (buf[2] + buf[3] + buf[4] + buf[5]) & 0xFF;
    if(buf[7] == 0xFF && sum == buf[6]) {
        Uart2data.Speed = (buf[2] << 8) | buf[3];
        Uart2data.Image_Center = (buf[4] << 8) | buf[5];
        Uart2data.rec_ok = 1;
    }
    state = 0;
}

void Attitude_Control(void)
{
    Yaw_angle_control.input = 320;
    Yaw_angle_control.feed_back = Uart2data.Image_Center;
    static float kp = 1.1f, kp2 = 0.0f, kd = 0.0f, g_kd = 0.0f;
    static int last_err = 0;
    int err = (int)(Yaw_angle_control.input - Yaw_angle_control.feed_back);
    int out = err * kp + err * abs(err) * kp2 +
              (err - last_err) * kd - (Yaw_Gyro * g_kd);
    last_err = err;
    steer_set_duty(out + steer.centre);
}
