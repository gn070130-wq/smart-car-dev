摘 要
全国大学生智能汽车竞赛是以智能汽车为研究对象的创意性科技竞赛，是面向全国大学生的一种具有探索性的工程实践活动，是教育部倡导的大学生科技竞赛之一。
本篇技术报告的智能车采用C型车模，香橙派5为控制核心，MCU为TC264D-40F200W的最小系统为下位机，通过在机械系统、硬件系统、软件系统的精细设计与调整，本篇技术报告给出的智能车设计方案能够较好的完成赛规要求的运行任务。 





















引    言
全国大学生智能汽车竞赛是一项面向大学生的探索性工程实践活动，以“立足培养、重在参与、鼓励探索、追求卓越”为指导思想。参赛队伍围绕智能车这一复杂工程对象，自主完成机械结构、电子线路、环境感知、运动控制、决策算法以及开发调试工具等环节的设计、制作与验证，在真实工程约束下综合运用自动控制、嵌入式系统、计算机视觉和人工智能等多学科知识。竞赛不仅考查车辆完成任务的速度和稳定性，也强调学生发现问题、分析问题、协同解决问题以及将理论转化为可复现系统的能力。
第二十一届竞赛的人工智能模型组面向未来智能驾驶关键能力培养。依据组委会发布的人工智能模型组细则，该组别以现实赛道为基础，通过增强现实系统叠加虚拟行人、道路标识、障碍物和金币等对象，形成虚实融合的驾驶环境；车辆需要建立从视觉感知、语义理解、策略决策到运动执行的完整闭环。规则强调以纯视觉方案完成外部环境感知，并将飞桨目标检测、OCR、文心大模型以及 RK3588 边缘部署等技术纳入任务体系。与仅依靠固定位置或固定时序触发的控制方式相比，该组别更关注模型对动态场景的识别、理解和泛化能力。
本队以香橙派 RK3588 平台作为上位计算单元，以摄像头图像作为主要环境信息来源，构建目标检测、道路语义分割、OCR 文字识别、文心语义推理、路径提取与车辆控制相结合的软件系统。目标检测与道路分割模型在服务器端使用 PaddlePaddle 完成训练和验证，随后转换为 RKNN 模型部署至板端 NPU；OCR 采用 PaddleOCR 检测与识别双模型，语义推理调用 ERNIE-4.5-Turbo-128K。开发阶段通过 Visual Studio Code 的 Remote-SSH 功能远程连接香橙派进行代码编写、编译和运行，并使用自研上位机软件同步观察摄像头图像、识别结果和电机波形，从而完成感知、决策与控制参数的联合调试。


第一章 系统方案设计概述
1.1系统介绍
为了充分利用赛事版卡的多核心优势，我们的程序以多线程方式并行运算，将OV13850摄像头图像采集，AI元素识别，传统赛道识别三项任务分开处理，并最终在主线程合并得到舵机转角与控制速度，之后与下位机进行通信，通过PID控制算法使得智能车在赛道上以较好的姿态快速运行[1]。 
第二章 车模整体结构设计
智能汽车各系统的控制都是在机械结构的基础上实现的，因此在设计整个软件架构和算法之前一定要对整个模型车的机械结构有一个全面清晰的认识，然后建立相应的数学模型，从而再针对具体的设计方案来调整赛车的机械结构，并在实际的调试过程中不断的改进优化和提高结构的稳定性。本章将主要介绍智能汽车模型车型车的机械结构和调整方案。
2.1基础车模介绍
C车模具有出色的对称性，便于安装舵机，且具备快速灵敏、高精度、快速响应、强劲动力、卓越抓地力、充足刚性和恰到好处的重心等多重优势。车模的尺寸为310 × 180 × 80mm，轮胎尺寸为27 × 64mm。经过适当打磨处理，车模的轮胎具备良好的减震性，从而提供更强的摩擦力。C车模采用后轮单驱方式提供动力，而前轮的舵机则用于转向控制。驱动电机选用了型号为 RS-380，额定电压为7.2V，空载转速为15000rpm，重量为60g。舵机方面，采用了 K7361 型号，供电电压为6.0V 时，额定扭矩可达24kg·cm；而在8.4V 供电时，额定扭矩则可增至30kg·cm。此外，舵机的动作速度为每60°动作0.050秒。
2.2传感器的选择  
为保证车模可以及时获取赛道信息、进行AI识别并及时作出响应，我们采用香橙派1300万像素OV13850摄像头作为寻迹传感器，配合编码器速度传感器，完成“智能模型组”的基础寻迹任务。 
2.3电池的选择  
电池方面我们选择了格氏ACE电池，型号为GS24003S30，额定电压为11.1V，放电倍率为30C，容量2400mAh足够日常调车需求，重量200g更好的分布了全车重心。
2.4小车机械结构设计 
2.4.1自制车模重心高度调整 
重心高度是影响 C 车模行驶稳定性的关键因素。若整车重心过高，车辆转弯时容易出现车轮抬升，极端情况下会发生侧翻。因此为提升 C 车模行驶稳定性，整车设计中需要尽可能压低重心，保障车辆运行可靠。
为兼顾车辆高速性能，本设计将负压模块紧贴后桥布置，使底盘及电机等大质量部件相对于车辆中心轴对称安放。该布局让主要重物尽可能贴近底盘地面，减小车辆转弯时的倾覆力矩，提升转向响应灵敏度。 
2.4.2编码器的安装
为了更为精确的获得电机转速的返回值，本次车模上安装的是龙邱4096线编码器。最终 综合考虑了读数精准和重心分布两大因素，用定制加工件和齿轮进行了安装配合，尽量使得传动齿轮轴保持平行，传动部分轻松、流畅，不存在过大噪音和丢数情况。如图 2.2 所示。

2.4.3四轮车模前轮倾角的调整
调试过程中发现，C 车模原厂前轮轴与车轮存在较大装配间隙，该间隙会显著改变车辆高速状态下的实际转向中心，引发高速过弯时的转向不足问题。
前轮定位用于保障车辆直线行驶稳定性、降低舵机转向负荷并减少轮胎磨损。C 车模阿克曼转向机构的前轮定位包含主销内倾、主销后倾、前轮外倾、前轮前束四项可调参数，以此确定转向轮、主销与前轴相对于底盘的装配位置关系。
实际调试表明，适当增大主销内倾角，能够提升转弯过程中轮胎与地面的接触面积，增大车轮与地面的摩擦力，改善转向响应特性，缓解因地面摩擦力不足带来的转向不足现象。
2.4.4底盘高度的调整
在保证顺利完赛的前提下，底盘尽量降低，从整体上降低模型车的重
心，可使模型车转弯时更加稳定、高速。
2.4.5舵机安装结构的安装
考虑到主板的安装方便以及车模转向性能，我们对舵机安装结构进行了较 大的调整。比赛车模的转向是通过舵机带动左右横拉杆实现。舵机的转动速度 和功率是一定，要想加快转向机构的响应速度，唯一的办法就是优化舵机的安 装位置及其力矩延长杆的长度。由于功率是速度与力矩乘积的函数，过分追求速度，必然要损失力矩，力矩太小也会造成转向迟钝，因此设计时就要综合考虑转向机构响应速度与舵机力矩之间的关系，通过优化得到一个最佳的转向效果。利用实际参数经计算，我们得出了一套可以稳定高效工作的参数及结构。
最终，我们设计了一套舵机连片(转向拉杆)，综合考虑了速度与力矩的关系， 并根据模型车底盘的具体结构，简化了安装方式，实现了预期目标。

2.4.7其他机械结构的安装
在 C 车模机械结构层面仍存在多处优化空间，例如车轮可靠性、传感器防护等方面。C 车模采用后轮驱动方案，车辆行驶过程中，轮胎与轮毂之间容易产生相对滑移，会造成加速过程中的驱动力损耗，进而导致整车运行状态不稳定。针对该问题，调试阶段对后轮车轮做粘胎加固处理，有效避免轮胎与轮毂发生错位，减少驱动力损失，提升动力输出的稳定性。

第三章 硬件电路设计
硬件部分是实现智能汽车各种功能的基础。比如，电机驱动部分可以控制车辆的速度和方向；电源管理部分可以保证电池的正常工作；主控部分可以协调各个部件的工作等等。没有良好的硬件支持，智能汽车就无法实现各种智能化的功能。同时，它也是提高智能汽车性能的关键。通过选用高性能的电子元器件、优化电路设计等手段，可以提高智能汽车的速度、灵敏度、稳定性等指标，从而使其更具竞争力。
在整个小车硬件系统设计过程中，我们始终遵循规范进行操作，以可靠、高效为原则，同时注重让电路板整洁美观，在确保传感器和执行器的要求得到满足的前提下，尽可能地采用原理简单、能耗低的电路

第四章 软件系统设计
高效的软件程序是智能车高速平稳自动寻线的基础我们设计的智能车系统采用 USB 摄像头进行赛道识别， 图像采集及校正处理就成了整个软件的核心内容。
在智能车的转向和速度控制方面，我们使用了鲁棒性很好的经典 PID 控制算法， 配合使用理论计算和实际参数补偿的办法， 使智能车能够稳定快速寻线。
4.1 图像初步处理
在语义分割模型提取赛道掩膜后，我们需要对其进行处理以得到赛道特征，提供尽可能多的赛道信息供决策算法使用。
4.1.1 赛道边沿提取
边沿提取算法的基本思想如下：
算法输入是分割网络输出的二值掩膜图像，赛道为白、背景为黑，阈值判定即像素值是否大于零。扫描从图像近底端的第220行开始，自下而上逐行推进。每行从左到右遍历所有列，比较相邻像素：由黑变白处记录为色块起点，由白变黑处记录为色块终点，从而将每行白色区域切分为若干色块并统计数量；对图像左右边界处的色块做单独处理，防止边界色块丢失。色块区间按行存入缓冲区，每行最多64个。此步只提取"色块区间"这一中间信息，真正的边沿在后续步骤中筛选确定。
在起始行，若存在两个宽度均不低于约20像素的色块，视为面临岔路选择，按外部给定的优先方向取左侧或右侧色块作为赛道起点；否则取最宽色块为起点，宽度不足则跳过本行继续向上寻找，直至找到有效色块。后续行中，唯一连通色块要求宽度不低于16像素，多色块择优时选中色块不低于13像素。这些最小宽度阈值用于滤除分割噪声与碎片。此外，算法记录边沿落在图像左右边缘两列内的"贴边点"供后续修正使用；在岔路真伪验证中，还会将色块映射到俯视矫正域测量真实宽度，超过65像素的"超长色块"用于排除宽路面的岔路误判。宽度信息贯穿起点选择、噪声过滤、贴边检测与岔路验证全流程。
基于赛道空间连续的先验，算法要求本行色块必须与上一行已确认的边沿区间存在横向重叠。无连通色块则判定搜索结束；只有一个连通色块则直接取其端点作为本行新边沿；出现多个连通色块时，计算各色块中心与滑动窗口中心平均值的距离，选取最近者，滑动窗口保存最近十行有效中心并取平均，避免历史信息产生惰性。重搜索模式下还会以岔路点水平位置为分界施加方向偏好惩罚，防止误选另一侧岔路色块。选中色块不满足宽度下限则跳过本行。每确认一行后更新滑动窗口并检查是否贴边，边沿点按由近及远顺序累积，为控制中心计算提供有序中线信息。
当一行出现多个连通色块且与前一行边沿的重叠长度分别达到32和40像素以上时，记录两色块交界中点为岔路点，每帧只取首个。交汇点检测在扫描完成后从远向近回溯：寻找与上一行选定边沿重叠超过20像素、且向下连续三层均有宽度不低于13像素连通区域的色块，一行存在多个时记录交界中点；右转弯场景下远端右边界连续贴边或整体偏右会诱发远端误判，据此过滤靠近远端且位于图像右侧的交汇点。若岔路点与交汇点之间存在超长色块，说明只是宽路面，清空岔路点。另有隐含交汇的识别，通过近处与中部的赛道宽度对比及近处贴边比例两阶段判断，两侧使用不同阈值。补线环节中，岔路点以下区域以可靠边沿为基准，映射到俯视域后按近端20像素到远端实测宽度线性过渡生成另一侧边沿；交汇点以上区域则以实测道路宽度做等宽偏移生成缺失边沿，参考边沿贴边段先做锚点插值修正以保证与下方边沿无缝衔接；隐含交汇则用固定20像素宽度在俯视域整体等距偏移替换另一侧边沿。这些补线手段保证了进出岔路、交汇区域及终点段边沿的连续完整，为后续规划和控制提供稳定输入。

4.2 AI视觉感知与语义理解
人工智能模型组的赛道由真实道路和增强现实任务元素共同构成，仅依靠传统的颜色阈值或固定位置判断难以稳定完成比赛任务。因此，本系统将道路语义分割、目标检测、文字识别和大模型语义理解组合为一套视觉感知方案，使车辆能够从摄像头画面中同时获得“道路在哪里”“出现了什么目标”以及“路牌表达了什么含义”等信息。各类模型在服务器上完成训练和验证，转换为 RKNN 格式后部署到香橙派 RK3588 的 NPU 上运行。
道路识别采用轻量级 PP-LiteSeg 语义分割模型，将摄像头画面中的可行驶区域与背景分离。相较于只搜索固定颜色边线的方式，语义分割能够利用道路的整体纹理和形状信息，对背景变化及局部干扰具有更好的适应性。程序对分割结果进行边界搜索、中线拟合和岔路分析，为基础循迹、避障和目标收集提供路径依据。



AI元素识别采用基于 PaddlePaddle 框架训练的 YOLO26n 轻量目标检测模型。结合比赛任务建立并标注数据集，模型主要识别车辆、行人、金币、红绿灯、引导牌、限速牌和终点标志等元素。训练过程中通过扩充不同距离、光照和背景下的样本提高模型适应性，训练完成后将模型导出并进行量化部。推理结果包含目标类别、置信度和位置，程序再结合道路区域、目标在图像中的相对位置及连续多帧结果进行判断，以减少单帧误检对车辆控制的影响。

对于引导牌等包含文字信息的任务，目标检测首先定位路牌区域，随后调用 PP-OCRv4 检测与识别模型提取文字。OCR 的板端部署参考 rknn_model_zoo，使用独立的文字检测模型、文字识别模型及字符字典。识别出的文字进一步通过 API 调用，交由 ERNIE-4.5-Turbo-128K 进行语义理解，将自然语言指令转化为明确的方向或动作信息。程序仅在确认出现引导牌后触发 OCR 与大模型请求，既减少不必要的计算与网络访问，也避免无关画面对语义判断造成干扰。
系统通过多线程流水线并行执行图像读取、道路分割、目标检测和文字识别，并在资源融合环节将同一时刻的感知结果统一交给场景状态机。车辆遇到行人或其他车辆时优先执行安全避让；识别交通信号后调整通行状态；检测到金币时在保证基础循迹安全的前提下修正目标路径；发现引导牌时等待文字与语义结果后选择道路分支。通过这种由多模型感知到任务决策的组合方式，系统能够较完整地适应人工智能模型组的虚实融合场景。
4.3 PID 控制算法介绍 
我们使用传统PID算法控制左右电机稳定在目标速度，使用PD算法控制舵机方向。
在工程实际中，应用最为广泛的调节器控制规律为比例、积分、微分控制，简称 PID 控制，又称 PID 调节。PID 控制器问世至今已有近 70 年历史，它以其结构简单、稳定性好、工作可靠、调整方便而成为工业控制的主要技术之一。当被控对象的结构和参数不能完全掌握，或得不到精确的数学模型时，控制理论的其它技术难以采用时，系统控制器的结构和参数必须依靠经验和现场调试来确定，这时应用 PID 控制技术最为方便。即当我们不完全了解一个系统和被控对象，或不能通过有效的测量手段来获得系统参数时，最适合用 PID 控制技术。
PID 控制，实际中也有 PI 和 PD 控制。 
PID 控制器是一种线性控制器，它根据给定值与实际输出值构成控制偏差。将偏差的比例(P)、积分(I)和微分(D)通过线性组合构成控制量，对被控对象进行控制，故称 PID 控制器，原理框图如图 4.12 所示。 
图 4.13 PID 控制器原理框图
简单说来，PID 控制器各校正环节的作用如下： 
比例环节：及时成比例地反映控制系统的偏差信号，偏差一旦产生，控制器立即产生控制作用，以减少偏差。积分环节：主要用于消除静差，提高系统的无差度。积分作用的强弱取决于积分时间常数，越大，积分作用越弱，反之则越强。 
微分环节：能反映偏差信号的变化趋势(变化速率)，并能在该偏差信号变得太大之前，在系统中引入一个有效的早期修正信号，从而加快系统的动作速度，减小调节时间。 
数字 PID 控制算法通常分为位置式 PID 控制算法和增量式 PID 控制算法。 
4.3.1 位置式PID 
位置式PID是最基础的PID控制算法，直接根据当前误差计算控制量的绝对输出值。它的离散公式为：u(k) = Kp·e(k) + Ki·∑e(j) + Kd·[e(k)-e(k-1)]，其中Kp比例项负责快速响应误差，Ki积分项消除稳态误差，Kd微分项抑制超调、预测变化趋势。
它的特点是输出直接对应执行机构的位置（比如舵机转角、阀门开度），结构直观，但积分项存在累积效应，遇到突发停机或设定值大幅跳变时容易产生积分饱和，导致超调或震荡，因此多用于执行机构不带积分特性的场景，比如舵机控制、温度调节等。
4.3.2 增量式PID 
增量式PID输出的是控制量的变化值，而非绝对位置。它的离散公式由位置式PID推导而来，最终形式为：
Δu(k) = Kp·[e(k)-e(k-1)] + Ki·e(k) + Kd·[e(k)-2e(k-1)+e(k-2)]
其中，Δu(k) 表示本次控制量相对于上一次的增量。它的核心特点与优势如下：
只关注误差的变化，即使系统因突发情况停机或设定值大幅跳变，也不会产生积分饱和，系统恢复时更平稳；在需要切断控制（如故障保护）时，只需停止计算增量，执行机构会保持在当前位置，不会像位置式那样直接归零或跳变到危险位置；执行机构要求：通常需配合带积分记忆功能的执行机构（如步进电机、伺服电机），通过不断累加 Δu 来更新当前位置。常应用在电机速度、位置控制等需要高安全性的工业执行器。
4.3.3 PID参数整定 
PID参数整定本质上是在系统响应速度、稳态精度与抗干扰能力之间寻找最优解。在实际工程中，整定思路远不止于传统的理论计算与经验试凑，更多时候需要结合控制对象的物理特性进行“量体裁衣”。
对于像智能车这类受物理环境干扰极大的嵌入式系统，参数整定往往遵循一种“数据驱动+物理直觉”的混合策略。由于车辆在不同速度区间和不同赛道曲率下的动力学特性差异巨大，单纯依赖一组固定的PID参数很难在全赛道保持最优表现。因此，我们的整定工作并没有局限于基础的Ziegler-Nichols方法，而是将重点放在了动态参数映射上。
我们摒弃了依赖精确数学模型的思路，转而采用基于关键特征点的工程整定法。具体操作中，不再追求全系统的理论建模，而是先通过开环测试获取执行机构（如舵机与电机）的基础响应特性，随后在实车运行中引入误差反馈机制。针对直道高速与弯道低速两种截然不同的工况，我们建立了参数与车速、偏差的映射关系表，使PID参数能够根据实时运行状态在多维空间中动态寻优。此外，为了解决积分项在跨越赛道元素时容易引发的“打滑积分累积”问题，我们在整定过程中引入了积分分离与抗积分饱和机制，确保车辆在遭遇突发扰动后能迅速回归稳定。
4.3.4转向舵机的 PID 控制算法 
本车的舵机转向控制由姿态 PD 控制器实现。整个算法的输入来自控制中心模块：系统首先对赛道分割图像提取赛道中线，其中加权控制中心以距离越近权重越大的原则对中线点横向坐标加权求和，并限制在零到639的范围内，同时限制其单帧变化量不超过一定的像素，以抑制检测结果的瞬时跳变。
舵机控制的核心环节是姿态 PD 控制器。它以控制中心相对图像中心（320）的横向偏差作为比例误差，偏差左偏为负、右偏为正；微分项则通过本帧误差减去上一帧误差得到。为防止检测偶发误检导致误差突变，算法对误差变化量做了限幅处理：当一帧内误差变化超过200像素时，将本帧误差强制修正为上一帧误差加减200像素，等效于对误差施加了变化率限制。之后根据当前场景选择不同的参数组：普通赛道、高速模式、躲车场景、金币场景和行人场景各自拥有独立的比例系数和微分系数，其中高速模式下微分系数被大幅调低，以避免高速行驶时微分项放大抖动。比例系数本身还包含一个动态分量，它与与赛道弯曲程度成正比，意味着弯道被探测得越早、距离越远，比例增益就越大，从而实现提前转向。将比例项与微分项相加后，对输出做正负250的限幅，再叠加到舵机中点值1500上，最终把结果限制在1250至1750的舵机硬件量程内，PD输出限幅与舵机满量程恰好对应。
该算法在主线程中每帧调用，调用后还会叠加引导偏移并再次限幅，在行人避障场景下则允许直接覆盖舵机值执行安全起步动作，最终与左右轮速度一起通过串口下发到下位机。整体来看，这套舵机控制方案具备场景自适应、动态前馈和多级限幅等优点，鲁棒性较好，运算量小，适合嵌入式平台；同时我们的算法也存在一些值得改进之处，例如控制器按值传参导致转向行设置无法回传且每帧拷贝点集带来开销、微分项对原始误差直接差分缺乏滤波、动态增益作用范围偏小、缺少积分环节可能产生稳态偏差，以及舵机输出没有斜率限制等，不过针对目前的场景，该算法已经能取得较好的效果。

5.1.3模型制作、安装与整车部署流程
目标检测模型的制作流程为：采集增强现实与真实赛道图像，完成 10 类目标框标注，转换并检查 YOLO 格式数据，划分训练集和验证集，加载预训练权重训练，依据验证结果补充难例并迭代，最终导出 Paddle 权重和 ONNX 模型。道路分割模型则使用多边形标注道路区域，经 PaddleSeg 数据转换工具生成分割数据集，采用 PP-LiteSeg 进行二分类训练。当前分割配置使用 STDC1 骨干网络，采用交叉熵与 Dice 组合损失，并配置辅助监督，以兼顾道路主体完整性和边界质量。
模型安装时，将转换后的 RKNN 文件复制到板端工程自创的 model 目录，随后重新编译或直接运行程序，检查模型文件权限与相对路径。配置调试开关、控制参数、API Key 以及选择调用的文心模型和接口超时等信息。完成单模块测试后，再依次接入视频源、串口与下位机，最后进行低速整车联调。
5.2 自研上位机调试软件
为提高整车调试效率，本队开发了配套上位机软件。当车辆出现偏航或任务误触发时，首先利用图像显示区判断道路掩膜、检测框和轨迹是否正确；若视觉正确而执行异常，再检查串口数据、舵机输出和电机波形；若仅在高负载时出现卡顿，则结合线程耗时、队列长度、CPU/NPU 占用和帧序列检查资源竞争。工程还将 USB 串口 latency_timer 调低，以减小通信等待时间。通过“视觉—决策—控制—执行”分层排查，可显著缩短整车问题定位周期。

            taxi.taxiStateSet(AIResult, trackForState, person.person_waiting, isAsync, suspend, mileageCounter);

        if(params.global.personEnable)
        {
            // 传入图像采集时间戳（AI资源的原始图像时刻），用于行人位置的时间加权回归
            long long imageTs = 0;
            if (isAsync && visionres.inquireID().AI.has_value())
                imageTs = visionres.inquireID().AI.value();
            else if (visionres.inquireID().road.has_value())
                imageTs = visionres.inquireID().road.value();
            person.personStateSet(AIResult, trackForState, taxi, isAsync, mileageCounter, imageTs);
        }

        if(params.global.goldEnable)
            gold.goldStateSet(AIResult, trackForState, taxi, person);

        if(params.global.trafficLightEnable)
            trafficLight_stop = trafficlight.trafficLightStop(trackForState, AIResult);
            
        if(params.global.endSingle)
            finished = endSingle.stopJudge(AIResult, mileageCounter.mileage);
        
        // 停车检查
        if(finished)
        {
            stopCnt++;
        }
        if(stopCnt>0)
        {
            endMileage += speed * duration / 1000.0f;
            if(endMileage > 1.6)
            {
                cout<<"比赛结束"<<endl;
                uart->carControl(0, 0, MID_SERVO_VALUE);
                return ThreadFunction::safeExit(threadPool);
            }
        }

        // 进行元素边界修正
        // taxi、person内部无论左右均使用正数偏移量，gold内部左右使用正负偏移量，表示方法不同
        edgeOffset = 0;

        // 车辆躲避
        if(taxi.taxi_state == Taxi::TaxiState::TaxiAvoiding ||
           taxi.taxi_state == Taxi::TaxiState::TaxiExit)
        {
            if(taxi.fitting_2(visionres.track))
            {
                scene = Scene::TaxiScene;
                edgeOffset = taxi.edgeOffset;
            }
        }

        // 行人躲避
        if(person.person_state == Person::PersonAvoiding ||
            person.person_state == Person::PersonExit)
        {
            if(person.fitting(visionres.track, taxi, ctrlCenter.controlCenter))
            {
                edgeOffset += person.edgeOffset;
                if(taxi.taxi_state != Taxi::TaxiState::TaxiAvoiding)
                    scene = Scene::PersonScene;
            }
        }

        // taxi、person对边界处理完毕后，根据修正方向改为正负偏移量，以便传递给gold进行边界拟合
        if (person.person_state == Person::PersonAvoiding || person.person_state == Person::PersonExit)
        {
            if(person.isLeft)
                edgeOffset = -edgeOffset;
        }
        else if (taxi.taxi_state == Taxi::TaxiState::TaxiAvoiding || taxi.taxi_state == Taxi::TaxiState::TaxiExit)
        {
            if(!taxi.onLeft)
                edgeOffset = -edgeOffset;
        }

        // 收集金币（GoldCollecting 和 GoldExit 都进行边界拟合）,若处于路牌减速状态则不修正，防止路牌识别失败
        if((gold.gold_state == Gold::GoldState::GoldCollecting || gold.gold_state == Gold::GoldState::GoldExit) && ocr_waiting.load() != 1 && !guide_right_edge.load())
        {
            if(gold.fitting(visionres.track, taxi, person, edgeOffset, gold_no_left.load()))
            {
                scene = Scene::GoldScene;
            }
        }

        // 计算控制中心
        ctrlCenter.fitting(visionres.track, params);
        ctrlCenter.controlCenterCalculate(params, scene,isFirstLap);

        bool fasterStop = false;
        
        // 计算控制量
        motion.poseCtrl(ctrlCenter, scene, params, isFirstLap);

        float targetSpeed = params.control.speed_high;
        if(scene == Scene::TaxiScene)
        {
            targetSpeed = params.control.speed_taxi;
            if(taxi.dangerFront)
            {
                targetSpeed *= 0.5;
                fasterStop = true;
            }
        }

        if(scene == Scene::PersonScene)
        {
            if (person.personTaxiConflict)
                targetSpeed = params.control.speed_taxi * 0.5;   // 人车方向冲突，降速通过
            else
                targetSpeed = person.near ? params.control.speed_person_over : params.control.speed_person;
            fasterStop = person.near;
        }
        

        // 进入OCR语义识别，降速停车等待
        if(ocr_waiting.load() == 1 && person.person_state != Person::PersonAvoiding && person.person_state != Person::PersonExit)
        {
            targetSpeed = std::min(targetSpeed * 0.75f, 0.75f);
            scene = Scene::StopScene;
        }
        
        // 停车场景
        if( (ocr_waiting.load() == 1 && spurroad_stop.load() == true) 
            || trafficLight_stop || person.person_waiting )
        {
            // 停车距离修正：修正期间用修正速度代替停车
            if (person.person_waiting && person.correctionActive)
            {
                targetSpeed = max(-0.5f, min(person.correctionSpeed, 0.5f));
                // 倒车时将舵机设为中值，防止舵机打角导致撞击
                if(targetSpeed<0) 
                        motion.servoPwm = MID_SERVO_VALUE;

            }
            else
            {
                targetSpeed = 0;
            }
            fasterStop = true;
            scene = Scene::StopScene;
        }
        
        if(params.global.debug)
        {
            if(params.debug.speedDebugEnable)
            {
                targetSpeed = params.debug.speedDebug;
                scene = Scene::DebugScene;
            }
            if (params.debug.servoDebugEnable)
            {
                motion.servoPwm = params.debug.servoDebug;
                scene = Scene::DebugScene;
            }
        }

        // 速度设置
        if((scene == Scene::NormalScene || scene == Scene::GoldScene) && frameID >= 15)
        {
            if(person.preSlowDown == 1)
            {
                targetSpeed = params.control.speed_safe;
                fasterStop = true;
                motion.speedTargetSet(targetSpeed, params, fasterStop);
            }
            else if(person.preSlowDown == 2)
            {
                targetSpeed = params.control.speed_person_over;
                fasterStop = false;
                motion.speedTargetSet(targetSpeed, params, fasterStop);
            }
            else
                motion.speedCtrl(ctrlCenter, params, isFirstLap);
        }
        else
        {
            motion.speedTargetSet(targetSpeed, params, fasterStop);
        }
        // 差速计算
        motion.speedDiffer_1(params);
        
        // 串口通信
        if(!params.global.debug || (params.global.debug && params.debug.vehicleMode))
        {
            
            // 发送舵机值和速度值
            uart->carControl(motion.speedLeft, motion.speedRight, motion.servoPwm);
            // 场景切换处理
            if(scene != sceneLast)
            {
                uart->PIDOption(scene);
            }
        }

        sceneLast = scene;
        
    }
    return 0;
}
