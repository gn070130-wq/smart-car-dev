摘 要
本作品面向第二十一届全国大学生智能汽车竞赛人工智能模型组任务，采用市售 RC 单电机四驱车模改装形成自制智能车模。整车以官方 RK3588 板卡作为上位机，以 TC377 作为下位机：RK3588 接收摄像头图像，完成赛道及场景目标的检测、实例分割、路牌文字识别和任务决策；TC377 接收上位机下发的控制指令，完成电机速度闭环和舵机转向执行。
系统配备独立供电板、TC377 下位机板和单路电机驱动板，形成计算、控制、驱动和供电相互分工的硬件结构。针对 AR 叠加现实场景中的行人、金币、出租车、大门、起始标注、结束标注及路牌等元素，作品构建了以自采图像数据为基础的视觉感知流程，并使用 YOLO11、实例分割模型和 PP-OCR 提取场景信息。
路牌处理采用分级识别流程：YOLO11 先在整帧画面中定位路牌，程序按检测框裁剪文字区域，再由 PP-OCR 输出文字内容。文字结果经清洗和方向约束后进入岔路决策，最终转换为舵机 PWM 与速度目标并通过串口发送至 TC377。报告围绕机械改装、三板电路、RK3588 与 TC377 协同、视觉感知和运动控制展开，并记录供电压降与 Type-C 线材造成的帧率变化。
关键词：人工智能模型；RK3588；TC377；目标检测；实例分割；PP-OCR；异构协同；智能
引 言
全国大学生智能汽车竞赛要求参赛队伍在有限的车模空间和计算资源条件下，完成环境感知、路径判断与运动控制。人工智能模型组将传统智能车的实时控制任务扩展到 AR 叠加现实场景，车辆需要从连续图像中识别具有不同奖惩含义的目标，并根据路牌文字完成路线选择。
本赛道的任务并不是单一的循迹或定速行驶。车辆需要在三圈运行过程中同时处理行人、车辆、金币、大门、起始/结束标注和路牌等信息：碰撞行人或车辆会增加罚时，获取金币可以减少时间，路牌识别结果还会影响岔路口的行驶方向。因此，系统既要具备较稳定的视觉识别能力，也要将识别结果及时转换为可执行的速度和转向指令。
针对上述需求，本作品采用 RK3588 与 TC377 的异构协同结构。RK3588 负责计算量较大的目标检测、实例分割、文字识别和高层决策，TC377 负责串口指令接收、编码器速度反馈、电机 PID 速度控制以及舵机 PWM 输出。通过计算层与执行层的分离，系统可以在保持视觉算法扩展性的同时，保证底层运动控制的实时性。
本文后续首先介绍系统总体架构，再说明自制阿克曼车模、三块电路板和供电系统的设计；随后介绍数据集、目标检测、实例分割和路牌文字识别流程，并进一步说明场景决策、上下位机通信和下位机控制；最后结合联调过程、供电问题和比赛测试结果，对系统性能和不足进行总结。
第一章 系统总体设计
1.1 竞赛任务与系统需求
人工智能模型组的比赛画面在现实赛道基础上叠加了多种 AR 元素。车辆需要连续完成三圈，并在行驶过程中识别赛道、行人、金币、车辆（比赛标注为出租车）、大门、起始标注、结束标注和路牌等目标。不同目标对应不同的驾驶策略：行人和车辆需要尽量避免碰撞，金币需要在不明显降低整体速度的前提下进行获取，路牌则需要被进一步识别为文字信息并参与岔路决策。
根据上述任务，系统设计需要满足四项基本要求：第一，视觉模型能够在 RK3588 上稳定运行；第二，感知结果能够以较低延迟传递给决策模块；第三，决策结果能够通过串口可靠地下发给 TC377；第四，电机和舵机能够在车模供电、空间和机械约束下完成连续执行。

图 1.1 人工智能模型组任务与奖惩流程
1.2 系统总体架构
整车系统由感知层、决策层、执行层和供电层组成。感知层以官方配套摄像头为输入，采集赛道和 AR 场景图像；决策层部署在 RK3588 上，完成目标检测、实例分割、PP-OCR 文字识别以及后续的任务判断；执行层由 TC377、单路电机驱动板、电机、舵机和正交编码器构成，负责将上位机指令转化为车模的速度和转向动作；供电层由独立供电板向各模块提供不同电压。
与将所有任务集中在单一主控上的方案相比，异构分层结构能够把高算力视觉任务和高实时性控制任务分开处理。RK3588 可以根据赛题需要调整模型和决策流程，TC377 则以固定周期处理编码器反馈和速度环控制，从而降低视觉算法波动对底层执行的影响。

图 1.2 RK3588-TC377 异构协同系统框图
1.3 上下位机功能分工
RK3588 作为上位机，主要承担图像采集后的算法处理。程序对输入画面进行目标检测和实例分割，识别场景中的关键元素；当画面中出现路牌时，进一步调用 PP-OCR 获取文字内容，并将文字信息送入岔路方向决策流程。上位机最终输出启动/状态信息、舵机 PWM 和电机速度环目标速度。
TC377 作为下位机，主要承担与硬件实时性相关的任务。它通过串口接收上位机指令，从正交编码器获得速度反馈，利用 PID 调整电机速度，并输出舵机 PWM。舵机目前采用开环控制，具体转向效果通过 PWM 标定和机械结构改装保证。
1.4 任务执行流程
系统启动后，首先完成各板卡供电、主控初始化和串口连接。车辆接收到启动信号后，RK3588 持续读取摄像头画面并运行感知模型；感知结果进入场景判断和路牌决策模块，形成当前时刻的速度与转向目标；TC377 接收指令后执行底层控制，并通过编码器反馈修正电机速度。该流程在三圈比赛过程中循环执行，直到检测到结束标注或收到停止状态。
任务状态采用连续帧确认方式，减少单帧误检引起的速度或转向突变。启动、正常行驶、目标处理、岔路决策和结束状态按条件切换；短时间内没有有效识别结果时，系统保持最近一次有效控制量或降低到安全速度。连续帧确认参数由上位机统一管理，用于平衡响应速度与抗干扰能力。

第二章 车模方案与硬件系统设计
本章说明车模平台、机械结构和电路系统的设计。硬件方案围绕板卡安装、重心分布、转向间隙、供电能力和线束连接展开，并结合调试中出现的问题说明相应的处理方法。
2.1 基础车模选择与方案迭代
本作品没有直接沿用往届常见的竞赛车模，而是选用市售 RC 单电机四驱车模进行改装。该车模由一个电机通过传动结构和差速器驱动四个车轮，具有完整的机械传动和阿克曼转向基础。选择这一平台的主要考虑是其结构强度、四轮驱动能力和承载空间能够适应 RK3588、三块电路板及供电模块的安装需求。
车模方案确定后，改装重点由板卡安装转向整车运行稳定性优化。在调试过程中，前轮转向虚位会放大舵机 PWM 变化对车辆轨迹的影响，因此对原有转向机构进行了针对性修改，以减小传动间隙并提高转向重复性。机构调整完成后，重新标定舵机中值和左右限位，并通过连续转向测试检查响应一致性。

图 2.1 自制车模整体外观及二层结构板布局

2.2 机械结构改装
为了在保留原有传动结构的基础上安装上位机和电路板，车模增加了二层结构板。二层结构板用于固定 RK3588、供电板、下位机板和驱动板，并兼顾整车重心、线束走向和散热空间。布置时将电机功率线与串口、编码器等弱信号线分区，并在接插件周围预留拆装空间。
前轮转向机构的改进目标是减小机械虚位，使相同 PWM 指令在不同方向变化时具有更一致的转向响应。由于舵机控制采用开环方式，机械间隙会直接影响控制效果，因此机械改装与舵机 PWM 标定需要结合进行。
车体新增的结构件均根据安装空间单独建模。二楼板形成上层安装平面，用于固定 RK3588 和三块电路板；编码器固定件限制编码器相对传动机构的位置，避免车体振动引起测量间隙变化。
摄像头固定件保持镜头姿态和安装高度，碳柱固定件连接上层结构与车体支撑柱。四类结构件采用 3D 打印制作，安装位置如图 2.2 所示。
图 2.2 3D 打印结构件及安装位置
2.3 传感器与执行机构
整车采用官方配套摄像头作为主要环境感知输入。摄像头采集的画面送入 RK3588，供目标检测、实例分割和文字识别使用。底层速度反馈由正交编码器提供，编码器信号接入 TC377，用于电机速度环 PID 控制。系统没有使用 IMU、雷达、超声波等其他感知器件，这使系统结构更简洁，但也要求视觉感知和机械控制具有较好的稳定性。
执行机构包括驱动电机和转向舵机。驱动电机通过单路电机驱动板连接到 TC377，舵机由 TC377 输出 PWM 控制。上位机不直接驱动功率器件，而是发送目标速度和舵机控制量，由下位机统一执行。
摄像头、编码器和执行机构分别连接到不同处理单元，图像数据不进入 TC377，编码器反馈也不依赖上位机轮询，从而减少跨处理器传输对实时控制的影响。系统虽然预留了 IMU 安装位置，但本次未插入模块，也未在软件中使用姿态数据；这一取舍简化了标定流程，同时要求后续测试重点关注急转弯、加减速和光照变化条件下的稳定性。
2.4 三板电路系统布局
整车电路分为供电板、TC377 下位机板和单路电机驱动板三部分。供电板负责将输入电源转换为各模块所需的电压，并实现缓启动等电源管理功能；下位机板以 TC377 为核心，集成串口、编码器、舵机和相关降压模块；电机驱动板负责将下位机输出的控制信号转换为电机驱动电流。
下位机板通过 XT30 接口直接连接供电板，电机驱动板按功率路径与供电板和驱动电机连接。三板分离使供电、控制和功率驱动的功能边界更加清晰，便于分别完成通电检查、信号测试和功率级调试。三块电路板的 PCB 图、正反面实物照片及原理图集中列于附录 B。

图 2.3 三块电路板在车模中的安装位置示意
三板电路的连接关系可以按“功率路径”和“信号路径”分别理解。供电板承载 12 V 输入、缓启动及四路降压输出；下位机板接收其中的控制电源，并以 TC377 为核心完成串口收发、编码器采集、舵机 PWM 输出和电机驱动控制；单路电机驱动板只处理驱动功率级，将下位机的控制信号转换为驱动电机所需的电流。这样的边界划分使模型计算、实时控制和大电流开关相互隔离，便于分板测试和故障定位。
RK3588 与 TC377 通过串口交换控制数据，传输内容包括启动状态、舵机 PWM 和速度环目标速度。正交编码器的 A、B 相信号直接接入 TC377，舵机控制线与电机驱动控制线由下位机统一输出。电源线、通信线、编码器线和电机功率线分区布置，减少功率回路对弱信号的干扰。
下位机板通过 XT30 接口直接插接在供电板上。XT30 在这里承担下位机板的电源正负极连接，不承担 RK3588 与 TC377 之间的通信。直接插接可以减少中间接插件和额外线束，缩短高电流供电路径，降低接触电阻和装配错误的可能性；装配时仍应由结构件承担板卡固定和振动载荷，避免把机械应力长期施加在接口焊点上。

图 2.4 供电板与下位机板 XT30 直接插接位置
TC377 下位机板与单路电机驱动板之间通过 PWM、方向和使能等控制信号连接。下位机板负责产生控制量，驱动板完成电平接口和功率放大，电机电源回路与串口、编码器等弱信号回路分开布置。图 2.5 给出两块电路板之间的功能边界。

图 2.5 TC377 下位机板与单路电机驱动板关键接口局部示意
该图表示下位机板与驱动板之间的信号方向和功率边界，具体器件连接、引脚编号和阻容参数见附录 B 中的电路板原理图。
2.5 供电方案与问题改进
供电板以 12 V 输入电源为基础设置四路降压输出，其中三路约 5 V 输出分别供给 TC377、RK3588 和下位机板上的其他模块，另一路通过降压为舵机提供约 8 V 电压。多路供电能够减少不同负载之间的相互影响，缓启动则用于降低上电瞬间对电池和降压模块的冲击。
调试过程中发现，RK3588 在数字负载约 3 A 时存在约 0.2 V 的供电压降。为保证板卡在运行视觉模型时仍有足够的电压裕量，最终将 RK3588 供电降压输出设置在约 5.2 V。除此之外，早期使用的 Type-C 线材性能不足，会导致 RK3588 功率受限并使模型运行帧率下降。更换满足供电能力要求的线材后，模型运行稳定性得到改善。
使用数字负载对 RK3588 供电支路进行测试时，负载电流约为 3 A，供电链路压降约为 0.2 V。根据该结果，将降压输出调整到约 5.2 V，并分别测量降压模块输出端和 RK3588 Type-C 输入端的电压。更换载流能力更高的 Type-C 线材后，再以视觉模型高负载工况复测板卡运行状态。

第三章 视觉感知系统设计
3.1 数据集构建与训练流程
训练数据主要来自实际赛道和相近场景的图像采集。根据比赛任务，对赛道区域、行人、金币、出租车、大门、起始标注、结束标注和路牌等目标进行分类或区域标注，并使用飞桨平台完成训练。自采数据能够覆盖车载摄像头视角、赛道背景和 AR 元素的实际变化，使模型训练目标与比赛输入保持一致。
数据处理依次完成图像采集、质量筛选、目标标注、训练集与验证集划分、模型训练和板端部署测试。标注过程统一类别名称及边界框、掩膜范围，并重点检查小目标、遮挡目标和画面边缘目标。数据集与训练任务由飞桨平台统一管理，使训练记录、模型文件和板端部署版本保持对应。

3.2 目标检测与实例分割
目标检测部分使用 YOLO11，对比赛场景中的关键目标进行识别。检测结果不仅用于判断画面中是否存在某类目标，还可以提供目标位置和置信度，为避让、获取金币和状态判断提供输入。不同目标的处理优先级应结合比赛奖惩规则确定，例如行人和车辆需要优先保证安全避让，金币则需要在不影响整体路线的情况下处理。
系统使用实例分割模型提取赛道可行驶区域和目标轮廓。分割结果用于估计可通行范围和目标占用区域，并与 YOLO11 检测框共同送入决策模块。模型输入尺寸和推理流程按 RK3588 的运行条件配置，板端测试用于确认处理速度和连续运行稳定性。

3.3 路牌文字识别
路牌属于需要进一步理解的目标。系统首先使用 YOLO11 在摄像头画面中检测路牌并获得其边界框，再按照检测框裁剪出路牌文字 ROI，最后将该区域送入 PP-OCR 进行文字识别。与直接将路牌作为一个类别相比，先定位再识别能够减少背景干扰，并为岔路口决策提供更具体、可解释的文字输入。
路牌识别结果进入后续决策模块前，需要进行文字清洗和格式统一，例如去除无关字符、判断识别结果是否完整，并区分有效方向信息和低置信度结果。识别失败时不能直接输出未经确认的方向指令，应由决策模块结合备用规则或当前状态处理。
从软件流程看，路牌处理被拆成“检测框获取—区域裁剪—PP-OCR 识别—文字清洗—方向决策”五个步骤。程序只有在检测框有效、识别文字满足方向集合约束且连续帧结果一致时，才更新当前路口状态；因此单帧误检不会直接改变舵机 PWM 或速度目标。
在处理流程中，路牌检测框首先被裁剪为文字识别区域，再按照 PP-OCR 的输入要求完成缩放和预处理。识别输出经过关键词匹配和方向集合约束后写入当前场景状态；同一路牌在连续画面中重复出现时，通过结果一致性判断减少重复处理。裁剪尺寸、置信度阈值和重复判定帧数由板端调试确定。

感知系统验证覆盖各目标类别的识别情况、模型运行速度、路牌文字识别耗时，以及遮挡、远距离、背景干扰和连续运动画面下的稳定性。测试时使用与车载摄像头视角一致的画面，并分别记录检测、分割和 OCR 环节的输出。
第四章 场景决策与运动控制
4.1 场景状态与任务决策
上位机需要将连续的视觉结果整理为车辆可理解的场景状态，例如正常行驶、接近行人或车辆、发现金币、识别到路牌、进入岔路口、检测到起始标注和结束标注等。状态判断应具有一定的时间连续性，避免单帧误识别直接引起车辆动作跳变。
在状态输出层面，系统不必把所有视觉细节直接传给下位机，而是将当前决策压缩为舵机 PWM、速度环目标速度和必要的状态/启动信号。这样可以保持串口协议简单，同时把复杂的场景理解留在 RK3588 上。
任务决策应按照比赛奖惩和行驶安全设置优先级：行人和车辆的避让优先于金币获取，终点和圈数状态优先于普通目标处理，路牌方向在进入岔路口前完成确认。对于同时出现多个目标的画面，决策模块可先确定最高优先级状态，再在该状态结束后恢复正常行驶逻辑。具体速度、转向和保持时间由实际控制程序和赛道标定结果确定。
4.2 路牌识别与岔路方向决策
路牌处理先由 YOLO11 取得检测框，再裁剪文字 ROI 交给 PP-OCR。识别文本经过字符清洗和方向集合约束后，与当前路口状态共同组成大模型 API 输入；接口返回结果只接受左转、右转和直行三类方向，随后映射为车辆控制状态。
同一路牌在连续画面中可能被多次检测，程序通过连续帧一致性判断复用稳定的文字结果，减少重复调用。API 返回值经过格式校验后写入当前路口状态；接口超时或结果不在方向集合内时，车辆保持当前状态并限制速度。
4.3 上下位机串口通信
RK3588 与 TC377 通过串口交换控制信息。上位机向下位机发送启动或状态信号、舵机 PWM 和电机速度环目标速度；下位机接收后完成数据校验、限幅和执行。通信数据采用字段含义固定的帧格式，使上位机算法调整不会改变底层控制接口。
上位机按固定周期发送启动状态、舵机 PWM 和目标速度，TC377 在接收完整数据后更新控制量。接收程序根据数据边界识别数据帧，并对舵机和速度指令进行限幅；通信中断时，下位机停止继续更新运动指令。
下位机程序将控制帧定义为 #Flag,DIR,speed_set_raw,get_pwm;，例如 #1,1,1200,2950;。其中 Flag 表示电机使能，DIR 表示方向，speed_set_raw 是速度目标，get_pwm 是舵机控制量。UART 接收中断只负责把字节放入 FIFO，HOST() 在主循环中恢复帧边界并完成字段解析；字段越界、帧头帧尾错误或数据过长时直接丢弃，避免异常字节改写运动控制量。

4.4 下位机运动控制
TC377 通过正交编码器获得驱动电机的速度反馈，并使用 PID 速度环使实际速度跟随 RK3588 下发的目标速度。速度环能够减小电池电压、负载变化和路面阻力对车速的影响，是保证三圈运行稳定性的底层基础。
舵机采用开环 PWM 控制。系统通过实车标定确定舵机中值、左右转向边界和可用 PWM 区间，并在前轮转向机构减小虚位后重新标定。控制程序对舵机指令进行限幅，使机械转向范围与上位机输出保持对应。
速度环调试从低速工况开始，逐步提高目标速度并观察编码器反馈，随后调整比例、积分和微分参数。调试重点是启动过程、负载变化和转弯时的速度波动。舵机采用开环 PWM 控制，中值和左右边界通过实车标定确定，转向一致性由 PWM 限幅和机械间隙控制共同保证。
实际控制链路以 5 ms 为一个电机控制周期：先读取并清零正交编码器计数，再进行一阶低通滤波和速度换算，随后计算速度误差并执行增量式 PID，得到的 PWM 增量在电机输出函数中累加、限幅并转换为方向和占空比。舵机没有使用角度反馈，程序只对上位机给出的 PWM 参数进行范围限制和频率映射；工程中保留的角度 PID 与 IMU 读取代码属于调试/扩展接口，当前比赛控制不依赖它们。

第五章 系统联调与比赛验证
5.1 软硬件联调流程
调试首先从电源和板卡单独测试开始，确认各路降压输出和缓启动功能正常；随后在 TC377 侧完成编码器采集、电机驱动和舵机 PWM 测试；在 RK3588 侧单独验证模型运行和摄像头输入；最后接通串口，逐步进行上位机指令、下位机执行和完整赛道测试。
联调按照由底层到上层、由单模块到整车的顺序进行，可以缩小故障定位范围。每次测试记录供电条件、软件版本、输入场景、观察现象、修改内容和修改后结果；当单模块通过后再引入下一模块，避免模型、通信和执行器问题同时出现而难以区分。完整赛道测试阶段重点观察三圈连续运行、目标处理和结束状态切换是否一致。
5.2 关键问题与解决方法
目前已经确认的关键问题包括 RK3588 供电压降和 Type-C 线材性能不足。前者通过调整 RK3588 降压输出和检查高负载下的实际电压进行处理，后者通过更换满足功率传输要求的线材解决。两类问题说明，视觉模型的运行帧率不仅取决于软件模型，也受到供电路径和连接器件的影响。
前轮转向虚位会使相同 PWM 指令对应的实际转角发生变化。机械结构改装后，重新标定舵机中值和左右边界，并通过连续转弯测试比较改装前后的响应。供电压降、线材载流能力和转向间隙均采用现象复现、原因测量和修改后复测的方式处理。
5.3 性能指标与比赛结果

5.4 系统局限性
当前系统仍存在一些可以继续改进的地方。舵机采用开环控制，车辆无法直接测量实际转角；系统没有使用 IMU，姿态和车身运动状态主要依靠视觉和底盘控制间接判断；摄像头是主要环境感知源，在遮挡或画面质量下降时可能出现识别不稳定；大模型 API 的响应时间和网络条件也可能影响岔路决策。
现阶段的限制主要体现在舵机缺少角度反馈、车辆没有使用 IMU，以及岔路决策依赖外部 API。系统通过机械间隙控制、视觉连续帧确认和接口异常处理降低这些因素对比赛运行的影响。

6.1 工作总结

static uint8 host_parse_and_apply(const char *frame)
{
    const char *p;
    uint32 values[4] = {0};
    if ((frame == NULL) || ('#' != frame[0])) return 0;
    p = frame + 1;
    for (uint8 i = 0; i < 4; i++) {
        uint32 value = 0; uint8 has_digit = 0;
        while ((*p >= '0') && (*p <= '9')) {
            has_digit = 1; value = value * 10u + (*p - '0'); p++;
        }
        if (!has_digit) return 0;
        values[i] = value;
        if (i < 3) { if (*p++ != ',') return 0; }
        else { if (*p++ != ';') return 0; }
    }
    if (values[0] > 1u || values[1] > 1u || values[2] > 4000u ||
        values[3] < 2300u || values[3] > 3700u) return 0;
    Flag = (uint8)values[0]; DIR = (uint8)values[1];
    speed_set_raw = (int32)values[2]; get_pwm = (int32)values[3];
    return 1;
}
代码 A.2  code/uart.c：连续字节流中的帧边界恢复
static void host_feed_byte(uint8 rx_byte)
{
    static uint8 in_frame = 0, frame_index = 0;
    static char frame_buffer[UART_FRAME_MAX_LEN];
    if ('#' == rx_byte) { in_frame = 1; frame_index = 0;
        frame_buffer[frame_index++] = (char)rx_byte; return; }
    if (!in_frame) return;
    if (frame_index >= UART_FRAME_MAX_LEN - 1) {
        in_frame = 0; frame_index = 0; return;
    }
    frame_buffer[frame_index++] = (char)rx_byte;
    if (';' == rx_byte) {
        frame_buffer[frame_index] = '\0';
        host_parse_and_apply(frame_buffer);
        in_frame = 0; frame_index = 0;
    }
}
代码 A.3  code/PID.c：编码器滤波与速度换算
void filter_encoder(float new_val)
{
    encoder_filt = (int16_t)((alpha * 100 * encoder_filt
        + (100 - alpha * 100) * new_val) / 100);
}

int16_t speed_read(void)
{
    filter_encoder(encoder_data_1);
    sd = (int16_t)(((int32_t)encoder_filt * 200 * 100) /
                    (1024 * (72 / 36)));
    return sd;
}
代码 A.4  code/PID.c：增量式电机速度 PID
void speed_pid1(void)
{
    speed_set = (DIR == 0) ? (-speed_set_raw) : speed_set_raw;
    speed_now = speed_read();
    speed_error = speed_set - speed_now;
    double e = (double)speed_error;
    double delta_u = speed_Kp * (e - speed_prev_error)
        + speed_Ki * e
        + speed_Kd * (e - 2 * speed_prev_error
                         + speed_prev_prev_error);
    speed_outpwm = (int16_t)delta_u;
    speed_prev_prev_error = speed_prev_error;
    speed_prev_error = e;
}
