摘    要
本文面向第二十一届全国大学生智能车竞赛人工智能模型组，介绍一套由上位机视觉驾驶程序与TC264下位机控制程序组成的智能汽车系统。系统以共享内存中的第一人称AR输入帧为感知入口，采用UNet完成可行驶赛道二分类分割，使用PP-YOLOE识别行人、金币和车辆等目标，再由结合双边缘一维高斯平滑滤波、扫描线和Bezier中心线拟合的巡线算法生成高鲁棒性舵机与速度指令。上位机主程序通过本地TCP Socket将控制包发送给独立桥接进程icar_socket_bridge，再由其通过串口与下位机进行异步通信，实现视觉高吞吐推理与底层串口阻塞I/O的解耦。针对复杂交互场景，报告给出了60帧历史环形队列加权判定的丢线反向回正算法、动态安全走廊约束的金币拾取策略、岔路状态机补线、目标区域停车、左右侧绕行以及结合PaddleOCR与ERNIE云端大模型的智能岔路决策。下位机部分采用TC264的10ms电机控制周期、编码器反馈和增量式PID速度闭环，并着重设计了包含动态斜坡软过渡、反向制动限幅与零速死区防抖的ABS防抱死算法，有效消除了连续启停对差速器齿轮的机械冲击磨损，同时保证了紧急刹车时不打滑抱死；此外，下位机设计了基于树状拓扑、带PD阻尼光标平滑动画与片上Flash掉电持久化的OLED多级交互菜单系统，支持脱机调参、状态监视与外设单体自检诊断。硬件方面，全车自制电路板（控制板、驱动板、电源板）总滤波电容容量为1939.30μF（约1.94mF，不含上位机），整车在12V供电下的典型运行功耗约为30～40W（静态待机11.5W，高动态峰值75～95W），配备2200mAh 22C电池可稳定续航35～45分钟。报告重点讨论软件实现中具有创造性的模块化、异步流水线、异构硬件加速、可配置参数以及失效保护机制。

第1章 引言
1.1 智能汽车制作背景与任务概述
智能车竞赛将机械结构、嵌入式控制、机器视觉、人工智能和系统工程整合到一个受约束的移动平台中。人工智能模型组的核心难点并不是单独提高某一个模型的识别精度，而是在有限的算力、存储、通信带宽和车体响应时间内，把感知结果稳定地转化为可执行的运动动作。赛道颜色、透视形变、遮挡、岔路和动态目标会同时影响视觉输入与车辆控制，因此系统必须具备从图像获取、语义理解、路径规划到低层执行的闭环能力。
本项目的制作思路是将计算量较大的视觉任务放在上位机，将确定性较强的电机、编码器、舵机和通信任务放在TC264下位机。上位机XSmart_Car_2.0以AR输入帧为统一数据源，输出车道中心、速度和舵机控制量；主程序通过本地TCP将控制帧发送至icar_socket_bridge，再由其通过串口下发给TC264下位机工程icar，负责把速度目标转换为编码器脉冲目标并执行结合ABS防抱死保护的PID调节，同时下位机配合OLED菜单系统实现脱机参数调节与状态监视。这样的分工降低了单个处理器的实时压力，也使视觉算法和底层驱动能够独立调试。
1.2 相关文献与技术路线综述
在语义分割方面，使用了Ronneberger等提出的U-Net通过编码器—解码器结构和跳跃连接实现了细粒度像素分割，适合把赛道转换为二值可行驶区域。PP-YOLOE是面向工程部署的单阶段目标检测器，在保持较高检测速度的同时提供了较好的精度，适合识别行人、车辆和金币等稀疏目标。传统智能车研究中常见的边缘跟踪、透视变换、拟合中心线和PID控制方法具有计算开销小、可解释性强的特点，因此本项目没有直接用神经网络回归舵机，而是将UNet的分割结果交给可解释的扫描线、高斯平滑滤波和几何控制模块。
综合已有研究可以得到三点启示：第一，模型输出必须经过尺寸、阈值和噪声处理后再进入控制器；第二，感知周期、推理周期和控制周期应解耦，不能用阻塞式推理拖慢车辆控制；第三，复杂场景应使用带滞回和超时的状态机，而不是根据单帧结果立即切换动作。本项目围绕这三点形成了“模型感知—几何跟踪—规则交互—闭环执行”的技术路线。
1.3 报告内容安排
第2章介绍系统目标、软硬件分工、机械改造及数据流；第3章说明共享内存取帧、UNet分割、边缘高斯平滑、PP-YOLOE检测及车道建模；第4章讨论巡线控制、丢线历史反向回正、岔路补线、行人停车、车辆避让、安全金币拾取和路口OCR与大模型决策；第5章说明TC264下位机的软件结构、ABS防抱死与差速器保护、速度闭环、双级通信协议、OLED菜单交互系统以及包含电容容量核算与功耗推算的硬件电路详细设计；第6章总结工程联调、配置和安全机制；第7章给出系统测试、模型车主要技术参数、电容统计与功耗推算表；第8章总结制作情况并提出改进方向。


第2章 系统总体方案设计
2.1 设计目标与约束
系统设计目标包括：在赛道图像存在局部噪声或单侧边界缺失时保持可控；在出现边缘毛刺或局部跳变时通过滤波消除抖动；在丢线瞬间能够依据历史偏差记忆智能反向回正脱困；在金币拾取时基于动态安全走廊约束避免冲出赛道；在岔路处能够识别结构变化并暂时修补边界；在行人或车辆进入危险区域时优先保证安全；在模型推理较慢或通信中断时使车辆进入可解释的安全状态；下位机在频繁启停和急刹时通过ABS算法消除机械冲击以保护差速器并防止打滑；提供脱机交互菜单便于现场无电脑标定；硬件电源树合理布局以确保大动态负载下纹波抑制良好且续航充足；通过配置文件调整阈值、速度和状态机参数，减少重新编译次数。约束条件包括上位机NPU/CPU资源有限、图像帧具有异步到达特性、下位机控制周期固定以及比赛规则对模型车尺寸、运行区域和动作安全性的要求。
2.2 系统总体架构
智能汽车系统采用分层架构设计，自上而下分为输入层、感知层、几何层、决策层和执行层，各层之间数据流向清晰、接口解耦。上位机主程序与下位机之间采用两级通信机制：主程序通过本地TCP连接将控制包发给独立的icar_socket_bridge进程，icar_socket_bridge再通过串口与TC264建立硬件通信。系统分层与数据接口如表2-1所示。

2.3 数据流与任务调度
上位机启动后加载xsmart_car.json，分别创建共享内存读取器、UNet分割器、PP-YOLOE检测器、金币收集器和控制桥。读取器检查16字节帧头中的frameId、宽度和高度，并采用“两次读取帧头一致性”判断生产者是否正在写入，从而避免读取到半帧。每个新帧同时提交给分割线程池和检测线程池，主循环通过frameId对结果进行配对。线程池默认各使用3个worker，主循环限制pending任务数量为最大worker数加1，防止输入速度过快导致队列无限增长。
完成分割与目标检测后，主循环先构建平滑车道线并计算历史偏置，再依次运行丢线回正、金币拾取、岔路状态机和目标交互策略，最后调用ControlBridgeClient发送速度与舵机PWM。控制包通过本地TCP (127.0.0.1:8899)发送至icar_socket_bridge，由该独立桥接进程通过Linux串口透明转发给TC264下位机。下位机主循环同时响应OLED多级菜单、按键与电量检测任务，在10ms中断中执行ABS与速度闭环控制。调试模式只在副本图像上绘制边界、检测框和文字，巡线仍使用未叠加调试信息的原始帧，避免可视化内容污染控制输入。

第3章 视觉感知与赛道建模
3.1 AR 输入帧与共享内存取帧
输入模块将setupUI产生的第一人称AR视频视为唯一感知源。共享内存头部包含frameId、width和height等字段，载荷为RGB三通道数据。读取器完成映射后复制图像载荷，利用OpenCV将RGB转成BGR，并根据配置选择水平或垂直翻转。frameId为零、尺寸为零、帧号未变化或载荷超出映射区域时，当前周期不提交任务。双次读取帧头不一致时丢弃本次结果，这一做法以极小的等待换取了跨进程数据一致性。
3.2 UNet 赛道分割
3.2.1 训练与模型设计
工程固定采用 512×384 作为输入尺寸，这一点在运行参数和模型说明中都很明确。这样的设计并不只是为了控制输入大小，更重要的是让训练和部署阶段保持一致的画面比例，减少推理时对原始视频画面的形变。对分割任务来说，输入比例和真实场景一致非常关键，因为语义分割依赖的是像素级空间关系，任意拉伸都会影响边界和细节的稳定性。当前代码在后处理时也始终保留原图尺寸与模型输入尺寸之间的比例关系，说明这一套流程是围绕固定画幅设计的，而不是临时拼接出来的推理路径。
这个 UNet 模型走的是二分类分割路线。后处理函数会直接检查 logits 的尺寸是否等于 2 × input_width × input_height，模型输出本质上是每个像素对应两个类别的得分图。相比多类别分割，二分类在模型输出和后处理开销上都更轻，特别适合车载、移动端或者板端这类对实时性敏感的场景。它的价值不是“功能复杂”，而是把问题收敛到道路前景和背景这类最核心的语义上，从而获得更稳定的端侧吞吐。
3.2.2 前处理优化
前处理部分默认由 RK3588 的 RGA 完成缩放和颜色空间转换，输入帧从 BGR 直接转成 RGB，并同步缩放到模型所需尺寸。这个设计很典型，也很有效，因为缩放和颜色转换是视频推理里每一帧都会重复执行的固定成本，放在 CPU 上会持续占用大量算力和带宽，而交给 RGA 之后，CPU 就可以把时间留给调度、后处理和视频写回。
源码里同时保留了 OpenCV 的回退路径，这意味着工程在硬件条件不完整时也能继续编译和运行，但从主路径看，RGA 仍然是默认优先级最高的方案。对技术报告来说，这一点可以表述为：工程通过硬件前处理把图像预处理从通用 CPU 路径转移到专用 2D 引擎上，减少了内存搬运和软件插值带来的额外损耗。
3.2.3 NPU 并行推理
推理阶段采用多 worker 方式组织，默认 worker 数为 3，并且每个 worker 都有独立的 RknnRunner 和独立的线程。代码在创建 worker 时会把前 3 个 worker 分别绑定到 RKNN_NPU_CORE_0、RKNN_NPU_CORE_1 和 RKNN_NPU_CORE_2，这和 RK3588 的三核 NPU 结构是直接对应的。换句话说，这里不是简单地把同一个模型串行执行多次，而是把任务拆分后交给三颗物理 NPU 核并行处理，从而把芯片的吞吐能力尽量吃满。
这种组织方式还有一个好处，就是天然适合视频流流水线。前一帧在推理时，后续帧可以继续进入队列等待处理，整个系统不容易因为某一环节阻塞而空转。主线程则按提交顺序回收结果，因此即使后台是并行执行，输出视频的帧序也不会乱。这一点对实际工程很重要，因为它说明并行化没有破坏时序一致性。
3.2.4 输入输出与后处理
推理输入侧保持得很干净，代码直接将 uint8 的 NHWC 图像数据送入 RKNN，没有额外引入手工归一化、转置或复杂的 CPU 预处理步骤。这样做的好处是路径短、稳定性高，也更符合端侧量化部署的使用习惯。输出侧则通过 RKNN 运行时直接拿到 float 结果，避免了自己再写一层反量化逻辑。
后处理是这套分割工程里很值得写进报告的部分。它先对每个像素做 argmax，得到二值掩膜，再通过 3×3 的形态学开运算去掉孤立噪点，最后用最近邻插值把预测图恢复到原始视频分辨率，并以半透明方式叠加回原图。这个流程的优点在于，既保留了分割边界的离散属性，又减少了细碎噪点对视觉效果的影响。最近邻插值尤其适合分割任务，因为它不会像双线性插值那样引入中间灰度，从而避免类别边界被“抹开”。
从性能角度看，这个后处理也足够轻。二分类意味着每个像素只需要比较两个通道，计算量本身就很小；再加上整套逻辑是顺序访问内存、按行处理掩膜，缓存友好性也比较好。它不是追求复杂的后处理花样，而是把分割结果以最直接、最省开销的方式还原出来。
3.2.5 调试与评估方式
工程提供了 --benchmark-only 模式，并把前处理、推理、后处理和视频写出分开统计。这样做的意义是，优化时不必只看一个总耗时，而是能很快定位到底是图像预处理、NPU 推理，还是视频编码在拖慢整条链路。对于边缘端工程来说，这种分段计时比单一总 FPS 更有价值，因为它能直接告诉你该优化哪一段。
代码还会在运行时读取 RKNN 的输出数量和输出维度，而不是把 shape 写死在源码中。这个设计让模型后续升级或者导出参数变化时更容易适配，减少了因为输出尺寸变化而反复改代码的成本，也让工程更接近可维护的部署模板，而不是一次性的演示程序。
3.3 赛道扫描与双边缘 1D 高斯平滑滤波
巡线模块先将Track Mask灰度化并以127为阈值二值化，然后从图像底部向上逐行扫描。起始阶段在候选白色连通块中选择最宽且满足透视宽度约束的区域，以获得左右边界初值；跟踪阶段依据上一行边界与当前白色块的重叠关系选择候选，若出现多个候选则综合中心距离和左右边界距离进行匹配。当赛道被切分为多个白色块时，算法设定单块和多块的最小宽度比例，避免把细小噪声误认为赛道；当候选突然消失时，允许在最大中心偏移范围内选择最近块。
在实际运行中，受镜头畸变、光照渐变以及模型降采样插值影响，UNet输出的二值掩码边缘往往存在局部像素阶梯锯齿和跳变噪点，若直接用于中心线拟合会导致控制量抖动。为此，工程设计并引入了1D高斯加权平滑滤波算法（smoothEdge）。滤波采用可配置高斯卷积核：
w(k) = exp( -k² / (2 · σ²) ), 其中 k ∈ [-r, r]
工程默认设置滤波半宽半径r=2（即5点平滑窗口），高斯标准差σ=1.2。提取边缘后，算法分别对完整的前瞻边界（previewLeft/Right）以及参与实际控制的底部三分之一边界（left/right）列坐标进行加权平滑卷积，并重新计算点列的导数斜率（slopeCal）。高斯平滑在保留赛道整体曲率走势的同时，有效滤除了单点孤立毛刺和局部跳变，为后续Bezier中心线拟合提供了高信噪比的连续几何输入。
3.4 PP-YOLOE 目标检测
3.4.1 训练与模型设计
工程采用 512×384 作为固定输入尺寸，这一点从模型说明和运行参数里都能直接看到。它的价值不只是“输入变小”，更重要的是让训练和部署阶段尽量保持一致的画面比例。这样做可以避免常见的强制拉伸，也能减少 letterbox 带来的无效区域，使目标几何关系在训练和推理之间保持一致。代码里的坐标映射逻辑也是按原始图像尺寸和模型输入尺寸分别处理的，说明这一套流程本身就是围绕非矩形输入来设计的，而不是把正方形输入硬套到视频画面上。
另一个明显的设计点是类别数被压缩到 3 类，分别是 man、coin 和 car。这类定制化模型对边缘端很有意义，因为类别越少，分类分支和后处理候选的压力就越小，模型输出也更集中。结合当前代码里的输出组织方式，可以看出这个工程不是追求通用检测，而是针对特定业务场景做了裁剪，目标是把精度、速度和部署复杂度控制在一个更实际的平衡点上。
从部署形态看，工程交付的是 *.rknn 模型，推理接口直接以 uint8 的 NHWC 数据送入 RKNN 运行时。虽然代码里没有展开模型转换流程，但这种输入输出路径本身就说明它是按 Rockchip NPU 的量化推理习惯来组织的。换句话说，模型并不是停留在通用训练框架里，而是已经面向端侧部署做了轻量化适配，这也正是 RK3588 上常见的高性价比方案。
还有一个容易被忽略但很实用的点，是模型输出并不是要求在 CPU 侧重新做复杂解码，而是已经以 decoded box 和 class score 的形式提供给后处理模块。这样一来，后处理就可以专注于阈值筛选、坐标映射和 NMS，而不必再承担 anchor 解码、分布回归还原之类的重计算工作。对边缘端来说，这种“把复杂度前移到模型侧”的设计非常重要，因为它直接决定了 CPU 侧负担是否会成为瓶颈。
3.4.2 前处理优化
前处理部分是这套工程里最明确的硬件加速点。在 src/rga_preprocess.cpp 里，输入帧会通过 RK3588 的 RGA 完成缩放和颜色空间转换，直接从 BGR888 变成 RGB888。如果不开 RGA，代码才会退回到 cv::resize 和 cv::cvtColor 的纯软件路径。这个设计的意义很直接，就是把最常见、最耗 CPU 的图像预处理操作交给专用图形硬件去做，从而把 CPU 资源留给调度、后处理和视频 I/O。
这类前处理方式对视频流尤其合适，因为视频帧是连续到来的，缩放和颜色转换是每帧都要做的固定成本。一旦这部分被 RGA 吃掉，主线程和工作线程就能把精力集中到更有价值的计算上。对于 RK3588 这类异构平台来说，真正高效的做法不是单纯追求某一段代码更快，而是尽量让每一类硬件都做最擅长的事情。
3.4.3 NPU 并行推理
推理部分采用了很典型的多 worker 设计。代码默认开启 3 个 worker，每个 worker 都持有独立的 RknnRunner，并分别绑定到 RKNN 的三个 NPU 核心。这不是同一个上下文顺序执行三次，而是把任务拆开以后交给三颗 NPU 核并行处理，因此更接近端侧视频推理需要的吞吐模型。
这种方式的价值不只是峰值 FPS 更高，还在于它天然适合流水线。前一帧在 NPU 上推理时，下一帧可以同时排队等待前处理或调度，整个链路不容易出现长时间空转。工程里还用了预提交队列，先把 workers + 1 帧压进去，再边消费边补充，这让吞吐更稳定，也更符合连续视频处理的节奏。
同时，结果回收是按提交顺序进行的，所以即使后台工作线程是并行完成的，输出视频的帧序仍然保持一致，不会出现画面重排的问题。这一点在技术报告里也值得提，因为它说明并行化不是以牺牲输出有序性为代价换来的。
3.4.4 输入输出与后处理
推理输入侧尽量保持简单，代码直接把 RGB 数据作为 uint8 的 NHWC 张量送入 RKNN，没有额外引入 CPU 侧归一化、转置或手工量化步骤。这样做的好处是路径短、实现稳，尤其适合已经完成端侧量化部署的模型。输出侧则直接要求 RKNN 返回 float 结果，避免了自己再处理反量化逻辑，工程实现上更直接，也更容易维护。
后处理部分也体现了“够用就好”的思路。代码会先按置信度阈值筛选，再按 topk 截断候选框，最后按类别做 NMS。对于一个输出已经是 8400 个 decoded boxes 的模型来说，这种裁剪很必要，因为它能明显压缩后处理的计算量。更重要的是，坐标映射方式是根据原图尺寸和输入尺寸做比例还原，这和前面说的非矩形输入策略是连在一起的，能保证检测框回到原图时仍然保持正确比例。
3.4.5 调试与评估方式
工程还提供了 --benchmark-only 模式，并且把前处理、推理、后处理和写出分别计时。这种分段统计的意义在于，优化时不需要靠猜测，而是可以直接看出时间到底消耗在哪一段。对于边缘端部署来说，这比单一总耗时更有价值，因为不同硬件平台的瓶颈往往不一样。
另外，代码会在运行时读取 RKNN 的输出数量和输出形状，没有把输出维度写死在源码里。这种做法让模型升级或导出参数变化时更容易适配，减少了因为 shape 变化而反复改代码的维护成本。
3.5 中心线拟合与车道表征
中心线拟合首先检查左右滤波后边界的有效点数、边界标准差、平均斜率和近远端位移。当两侧边界充分且曲率较小时，使用四个控制点构造Bezier中心线；当曲率较大或边界不稳定时，增加控制点并缩小采样步长，使曲线更贴近弯道。若只得到一侧边界，则以图像中线为镜像参考生成另一侧的虚拟中心线，并将车道样式标记为LEFT或RIGHT。中心点采用按行位置加权的方式计算，近处点权重更大，最终将中心点限制在图像范围内。

第4章 路径跟踪与场景交互策略
4.1 基于中心线的巡线控制
巡线控制误差定义为中心线加权中心与图像中心之差。为防止检测突变造成舵机瞬时大幅跳变，程序限制相邻帧误差变化幅度，再根据误差绝对值调整比例增益，叠加误差变化率的微分项得到舵机PWM修正量。当前配置的舵机中位为1500，输出范围为1100～1900，比例参数为run_p1=1.5、run_p2=0.012，微分参数turn_d=3.5。速度根据中心线起始行和曲率状态在vel_low与vel_high之间插值；当前基础速度配置为1.0m/s，优先保证高速与可重复性。
4.2 丢线偏置历史记录与反向回正算法
在高速过弯或突发强遮挡场景下，车道线可能短暂完全脱离摄像头视野（lane.valid == false）。传统策略若立即停车会破坏比赛节奏，若盲目直线前行则极易冲出赛道。为此，系统设计了基于历史偏置记忆的智能反向回正脱困算法。
LineFollower在主循环中维护一个容量为60帧的环形队列（history_），记录最近每一帧的中心偏差centerOffset、舵机量、弯道样式以及左右边界有效行数。当检测到丢线时，算法调用determineLostDirection函数对历史数据进行指数时间衰减加权评估：
avgOffset = ( Σ offset_i · w_i ) / ( Σ w_i ), 其中权重递减为 w_i = max(0.2, w_(i-1) · 0.90)
判定逻辑与动作响应如下：
1. 向左出界（OutLeft）：若丢线前加权中心偏差avgOffset > 10px或右转弯特征占优，表明赛道位于小车右侧、车辆向左偏离。控制器下发向右大转向角（servoMid + recoveryTurnPwm，默认+300 PWM），并以recoverySpeed = 0.30m/s低速爬行向右回正；
2. 向右出界（OutRight）：若丢线前加权中心偏差avgOffset < -10px或左转弯特征占优，表明赛道位于小车左侧、车辆向右偏离。控制器下发向左大转向角（servoMid - recoveryTurnPwm，默认-300 PWM），以一定速度爬行向左回正；
3. 平滑退出与超时熔断：回正过程中，一旦赛道重新进入视野且连续2帧（recoveryConfirmFrames = 2）有效检测，立即平滑退出回正状态恢复正常巡线；若尝试超过75帧（recoveryMaxFrames = 75，约2.5秒）仍未找回赛道，则自动熔断减速停车。
4.3 岔路检测与直行补线状态机
岔路模块不是简单寻找单个白色跳变，而是同时检查车道有效、左侧前瞻边界加权直线拟合误差、右侧边界的向左跳变量以及跳变后仍存在的点数。满足条件后，状态由Idle进入PatchToJump，固定右边界近端起点，并将当前跳变后的点作为目标，按行插值得到补线。跳变消失后进入PatchToFirstSeen，继续沿用上一次目标若当前帧暂时没有目标；当右侧近端缺失达到图像高度四分之一并连续确认两帧时，允许加入左侧镜像起点。右侧近端连续恢复并满足确认帧数后进入Cooldown，冷却结束才回到Idle。
当前配置的岔路冷却帧数为120，补线速度系数为0.85，左侧拟合至少需要8个点且加权RMS不超过12像素。状态机还提供补线超时参数和调试关闭超时开关，便于在模型调试阶段观察长期状态而不被强制退出。
4.4 行人停车策略
行人处理器将检测结果中的model类目标视为行人候选，先按距离筛选，再判断目标投影点是否位于视野范围和梯形阻挡区域内。梯形区域上边界为图像宽度的0.30～0.70，下边界为0.22～0.78，形成近处更宽的安全区。当最近候选距离小于等于0.30m且落入区域时输出stop，并保存目标ID；目标消失或离开区域后输出resume。停车状态具有记忆，避免目标在边界附近抖动时出现连续启停。
4.5 动态车辆避让策略
车辆避让器从类别为car的可见目标中选择最近者，要求距离不超过0.50m且边界框与当前画面有交集。触发后将目标框左侧作为绕行目标，并把中心点向左偏置28像素，同时将当前速度乘以0.80。车道边界缺失时，算法优先寻找底部右边界作为补线起点；若不存在，则把左边界关于图像中线镜像为右侧起点，再通过逐行线性插值生成局部补线。该策略只覆盖短时、轻量避让，不能替代完整的全局路径规划。
4.6 第一人称安全金币拾取策略
针对赛道上的金币目标，单纯对准目标转向极易导致车辆偏出赛道边界。为此，CoinCollector模块设计了“视场空间筛选 + 动态安全走廊约束 + 偏置引导降速”的拾取策略。
1. 视场空间有效性筛选：金币距离限制在0.25m～2.20m之间，纵向图像区域位于0.25H～0.95H之间，剔除过远噪点与车底盲区目标；
	2. 赛道动态安全走廊约束：算法查询金币所在行由LineFollower提取的赛道左右边界（leftCol, rightCol），按20%赛道宽度计算安全边距（trackSafetyMarginRatio = 0.20），构建动态安全走廊 [leftCol + margin, rightCol - margin]。若金币因误检或位于赛道外部，算法严格拒绝向外转向，确保巡线安全第一；
	3. 偏置引导与降速协同：在安全走廊范围内，根据金币偏离当前车道中心的横向距离计算引导偏置量（centerBiasGain = 0.65，硬限幅±65px），重构引导中心点；同时自动施加速度降速系数（speedScale = 0.88），通过轻微减速提升舵机吸附金币的响应精度；
	4. 丢目标平滑保持：当金币在帧间因遮挡短暂丢失时，启动4帧记忆保持（coinLostHoldFrames = 4），沿用上一次有效引导中心，彻底避免了检测闪烁引起的转向震颤。
4.7 路口决策
4.7.1 OCR 提取文字
主循环对岔路状态机产生的 fork 信号进行计数，当前配置在第 4 个岔路触发第一次 OCR 决策，在第 6 个岔路根据第一次决策选择互补方向，并在计数达到 9 时请求停车退出。第一次岔路出现时，程序异步调用 tools/ocr/junction_ocr_decision.py，使用云端的 PaddleOCR 对保存的路口路牌图像执行文字识别；OCR 未返回前，相关路口保持速度为零，避免在决策不完整时通过路口。OCR 和路口计数均使用独立状态字段记录请求次数、应用次数和当前决策，便于调试日志复盘。
4.7.2 AI 大模型选择岔路
在使用 OCR 获取到路牌文字信息后，程序会对云端的 ERNIE-4.5-Turbo-20260402 大语言模型发送精心构建的结构化提示词请求，模型具备强大的中文语义理解与反语、否定指令解析能力。具体系统提示词设计如下：
“你是一个精通汉语语义和驾驶动作逻辑的智能导航机器人。请阅读给定的【路牌文字】或【语音指令】，深刻理解其中的逻辑转折、反语、以及针对“驾驶动作”的禁止命令，严格执行【输出规则】。

【核心推理逻辑】
1. 动作禁止识别：密切注意“别往右”、“不让向右打方向盘”、“不能右转”等关于驾驶动作的否定命令。如果【禁止】向右操作，意味着你必须选择直行（straight）。
2. 反语与转折：识别类似“...才怪！”的反语，以及“但是”、“走不了”等转折，准确判断被否定的方向。
3. 安全优选：如果某条路被描述为危险、崎岖、封闭，果断选择相反的另一条路。

【少样本学习（Few-Shot Examples）】
- 输入：[右侧是一条不归路] -> 最终输出：straight
- 输入：[右道真的有点崎岖，但是直道真的走不了] -> 最终输出：right
- 输入：[右道比直道好走多了？才怪！] -> 最终输出：straight
- 输入：[他们来电话了说不让我方向盘往右打!] -> 最终输出：straight （原因：明确禁止往右打方向，故选择直行）
- 输入：[千万别直行，前面查车呢] -> 最终输出：right （原因：禁止直行，故选择右转）

【输出规则】
- 如果判定为直走，只输出：straight
- 如果判定为右转，只输出：right
- 绝对不能包含任何标点符号、空格或其他解释。

【路牌文字】：[{{input_text}}]
最终输出：”
在经过给定提示词处理后，云端大模型会返回“straight”或“right”等严格格式化的方向决策文本，主循环根据该决策结果控制车辆行驶路径，由此实现高鲁棒性、高智能化的未知复杂语义岔路自主决策。

第5章 TC264 下位机与硬件电路设计
5.1 下位机软件分层
icar工程按BSP、mid、app、user和libraries分层。BSP提供电机、编码器、舵机、GPIO、RGB、OLED、USB、SOC和定时器接口；mid层实现通用树状多级菜单框架与显示驱动；app层承载菜单任务、调参接口与发车主任务；user层完成CPU0/CPU1入口和中断注册；libraries提供TC264官方底层驱动与常用组件。CPU0启动后依次初始化电机、时钟、调试串口、综合车辆状态、编码器、GPIO、RGB、PID、舵机、USB、SOC、定时器和OLED菜单，再进入多任务调度的前后台主循环。
5.2 电机、编码器与速度闭环控制（含 ABS 防抱死与差速器保护）
电机驱动采用PWM与方向引脚控制，默认工作在闭环控制模式。工程设定编码器线数为512、减速比为2.7、驱动轮直径为0.064m，控制周期为10ms（100Hz），最高允许线速度为10.0m/s。在每个10ms控制周期内，TC264读取四倍频编码器采样脉冲并清零计数器，采用一阶低通滤波（滤波系数alpha = 0.35）消除齿轮侧隙及高频抖动，再结合轮周长与减速比精确折算为实时反馈速度。

图5-1 差速器公差示意图

在实际控制中，由于差速器本身存在一定的公差，以及行人停车、避障绕行及终点刹车等场景存在频繁启停，若直接下发阶跃速度或全速反转PWM，电机会瞬间产生极大的反向反电势与制动冲击扭矩，不仅导致车轮抱死（100%滑移率）在赛道上打滑失控，更会对后桥差速器（Differential Gear）伞齿轮与齿圈产生致命的机械冲击与剧烈磨损(实际上在加入ABS前我们差速器的寿命大概只有一个星期)。为此，系统在底层构建了完备的ABS（防抱死系统）与机械保护算法：
1. 速度动态斜坡软启停（Speed Ramp Protection）：下位机引入ProtectRampTime = 0.10s的动态过渡斜坡。当目标速度发生阶跃变化或急停归零时（ProtectZeroRampEnable = true），系统将目标值在10个控制周期（100ms）内线性插值平滑递变，从源头消除了阶跃力矩对差速器齿轮的机械敲击；
	2. 运行态反向制动限幅（Running Brake PWM Clamping / ABS 防抱死）：当车辆处于前进运动状态（vi_Ref > 2.0）而突发减速或反向制动时，PID算法将反向制动PWM严格限制在-120以内（PID_RUN_BRAKE_PWM_LIMIT = 120.0f），坚决禁止-1500满额反转制动。这一限幅确保轮胎始终处于最佳滑移率滚动摩擦区间，彻底杜绝了车轮抱死拖印打滑现象，并消除了大扭矩反拖对差速器的齿面剪切损伤；
	3. 零速静止死区保护（Zero-Speed Anti-Jitter Deadband）：当速度设定值处于零速死区（|vi_Ref| < 2.0）且实际反馈接近静止（|vi_FeedBack| < 8.0）时，算法自动清零积分与历史误差项并将输出置零，彻底消除了静止状态下高频微幅抖动对传动齿轮的磨损；
	4. 零速滑行驻车平稳刹车限幅（Zero Brake Limit）：当车辆在零速指令下减速滑行至完全停止过程中，反向刹车限幅放宽至500 PWM（PID_ZERO_PWM_LIMIT = 500.0f），既保证了快速平稳停车，又防止了过冲反向起步。
5.3 舵机及运动安全保护
舵机模块采用独立PWM输出并保存中位、左限位和右限位参数。上位机当前控制桥使用1500作为软件中位并将输入限制在1100～1900；下位机仍保留自身的角度和PWM限幅，形成双层保护。USB诊断接口还限制测试速度不超过1.0m/s、舵机范围为1300～1700，便于在悬空或低风险条件下执行通信测试。通信超时、程序退出和调试桥关闭时均应发送速度为零、中位舵机的停止帧。
5.4 上下位机两级通信架构与协议规范
为彻底隔离上位机复杂视觉模型（UNet/PP-YOLOE）的计算吞吐与底层串口的阻塞式I/O操作，系统设计了“上位机主程序 -> 本地TCP Socket -> icar_socket_bridge独立桥接进程 -> UART串口 -> TC264”的两级通信架构。
上位机主程序ControlBridgeClient通过本地回环TCP（127.0.0.1:8899）连接后台运行的icar_socket_bridge守护进程。通信采用高精简11字节定长二进制控制帧：
Frame = [ 0x42, 0x01, 0x0A, Speed_LE(4B), Servo_LE(2B), Checksum(1B), 0x00 ]
协议字段具体定义如下：
• 帧头（1 Byte）：固定为0x42，用于帧边界同步定位；
• 目标地址（1 Byte）：固定为0x01，表示主车模控制器；
• 数据长度（1 Byte）：固定为10（0x0A），标识后续载荷字节数；
• 目标速度（4 Bytes）：IEEE 754标准Little-Endian单精度浮点数（m/s）；
• 舵机PWM（2 Bytes）：Little-Endian无符号16位整型数（范围1100～1900）；
• 累加和校验（1 Byte）：前9个字节的无符号8位算术累加和（Checksum）；
• 帧尾保留（1 Byte）：填充0x00，用于对齐与未来扩展。
icar_socket_bridge进程接收到TCP数据后，校验帧头与校验和无误后，通过标准Linux串口接口（115200波特率、8N1）透明写入硬件串口。启动阶段默认发送50帧零速保持帧，程序异常或退出前主动下发全零停止帧，确保全链路通信安全。
5.5 下位机 OLED 动态多级交互菜单与参数持久化系统
在智能车调试与现场比赛中，频繁通过电脑重新编译烧录或连接上位机调参极为繁琐低效,为了实现快速调参和整车自检。为此，项目在mid层与app层设计并实现了一套基于128×64 OLED与五向按键的动态多级树状交互菜单系统（menu.c / app_menu_task.c）。
1. 树状拓扑节点架构：菜单采用多叉树拓扑结构，支持目录节点（FILE_TYPE）、多类型参数节点（FLOAT, INT8/16/32, UINT8/16/32, BOOL）以及动作执行节点（EXEC_TYPE）。每个节点通过父指针、子指针及同级兄弟双向链表灵活组织，支持任意深度的菜单层级嵌套；
	2. PD 阻尼平滑光标动画算法：为提升交互流畅度与视觉质感，菜单创新性地引入了基于二阶阻尼响应的光标位置插值算法。光标指针实时坐标通过比例-微分（PD，p=0.7, d=0.0）算法向目标行平滑逼近，并在8行OLED视口内实现窗口自适应滚动与参数编辑星号（*）标记；
	3. 片上 Flash 掉电持久化机制：每个核心参数（PID系数、ABS保护时间、舵机中位与左右限位、电量计校准值等）均绑定唯一的PARAM_ID。系统支持一键保存（save）与开机自动读取（load），使脱机调节的参数能够永久保存在TC264片上Flash中，断电重启不丢失；
 	4. 功能子菜单划分：
  • run 菜单：提供icar正式发车运行循环、休眠与紧急停机（kill/exit）；
  • pid / pid_uart 菜单：支持脱机及上位机VOFA+联动调节Kp/Ki/Kd，并实时显   示编码器速度与目标速度；
   • ABS 保护菜单：实时配置ABS总使能、零速软过渡开关与0.001s级斜坡过渡    时间；
   • device 设备诊断菜单：提供电机开环/闭环测试运转、编码器累计脉冲监视、    舵机三位（中/左/右）标定、WS2812B RGB灯效设置以及CW2015电池电压       与电量计校准。

第6章 上下位机联调与工程实现
6.1 控制桥与 icar_socket_bridge 独立转发进程
在实际工程部署中，Linux串口驱动在打开、配置波特率或极端异常情况下可能引发线程阻塞或上下文切换延迟，若直接嵌入到视觉主循环中极易造成画面掉帧或感知流水线卡顿。为此，项目将串口管理剥离为独立的守护进程icar_socket_bridge。
控制架构分为TCP客户端（ControlBridgeClient）与Socket桥服务端两部分。主程序通过TCP客户端向127.0.0.1:8899发送控制指令包，设置TCP_NODELAY禁用Nagle算法以消除发送缓冲延迟，并在发送端处理短写与EINTR中断。icar_socket_bridge进程负责建立非阻塞TCP监听，在接收到完整11字节数据后核对校验和，然后通过标准POSIX串口API（设置原始模式raw mode、115200波特率、8数据位、无校验、1停止位）写入硬件串口并调用tcdrain确保硬件FIFO刷新送出。当TCP链路断开或异常时，桥接程序自动向下位机发送零速停止帧并保持重连监听，实现了高可靠的解耦设计。
6.2 参数配置与可观测性
xsmart_car.json集中保存输入路径、模型路径、线程数、阈值、控制增益、高斯滤波半径、丢线回正参数、金币拾取走廊、岔路状态机、目标交互和通信端口等参数。主程序在启动时依次尝试工作目录、可执行文件目录和上级目录中的配置文件，并在调试画面与日志中输出FPS、分割预处理/推理/后处理时间、检测框数量、检测推理时间、车道样式、中心点、舵机、速度和交互状态。下位机通过OLED菜单、USB浮点数据和PID调参命令提供另一套观测通道，形成从图像到执行器的端到端调试闭环。
6.3 异常处理与失效保护
输入帧无效时不提交任务；共享内存尺寸不合法或mmap失败时关闭映射并按轮询周期重试；模型推理异常通过future传递到主循环；控制桥发送失败时释放套接字；丢线超时未能找回赛道时速度为零；行人阻挡和OCR等待时速度为零；程序退出时发送停止帧。下位机侧还具有速度限幅、PWM限幅、零速死区、ABS反向制动限幅和目标速度动态斜坡。上述机制不能消除全部风险，但可以将多数软件异常收敛为“减速或停车”而不是不可控加速。
6.4 联调流程
联调按“单模块—虚拟输入—通信闭环—低速实车—完整赛道”的顺序进行。首先使用固定图像检查Track Mask、高斯平滑滤波、边界点和中心线；随后用回放帧验证丢线回正、金币拾取、岔路状态机和目标交互；再启动icar_socket_bridge，用模拟速度与PWM检查11字节协议、校验和及停止帧；接着在车轮架空状态下通过OLED菜单验证编码器反馈、PID与ABS制动限幅；最后从低速开始逐步放开速度上限，并在每次参数改动后记录帧率、丢线次数、停车触发次数和跑圈时间。
6.5 开发工具、制作、安装与调试
上位机采用C++、CMake、OpenCV、JsonCpp和RKNN/RGA相关运行库，使用xsmart_car.json管理模型、线程、检测阈值和控制参数；下位机采用AURIX/TC264工程环境、C语言和厂商底层驱动库，使用调试串口、OLED动态多级菜单、USB数据和VOFA/PID调参接口观察运行状态。
6.6 ArUco 辅助定位系统
为构建虚拟场景与显示融合，我们设计了一套基于视觉的定位工具。该工具部署在一台Linux主机中作为定位器，通过特定的UDP包为setupUI提供场地坐标、车辆位置和偏航角。
定位流程分为四步。第一步读取1920×1080鱼眼相机标定文件，对输入图像进行去畸变；当前标定文件记录了相机内参、畸变系数、77张有效标定图像和约0.3285像素的RMS误差。第二步使用DICT_4X4_50字典检测场地四角ArUco标记，要求至少检测到4个有效角点。配置中的ID 4、3、1、2分别对应场地坐标(0,0)、(5000,0)、(0,4000)、(5000,4000)，单位为毫米。
第三步使用检测到的像素角点和已知场地坐标，通过RANSAC计算单应性矩阵H，并用透视变换将像素坐标映射到场地坐标。车辆标记ID默认为0，标记四角中心作为车辆位置；由标记第2、3个角点映射后的方向向量计算yaw = atan2(vy, vx)，得到车辆在场地坐标系中的位置和偏航角。若角点不足或单应性计算失败，定位状态被重置为未标定，不输出伪造姿态。
第四步对位置和方向向量进行可选的Kalman或One Euro滤波。当前配置启用Kalman，过程噪声参数kalman_q = 80.0、测量噪声参数kalman_r = 1.5，prediction_ms = 0表示只平滑、不进行前向预测。工具可将姿态以JSONL记录，也可按30Hz通过UDP发送robot_position遥测；该数据用于对照跑车轨迹、检查摄像头视场和评估延迟，不直接写入下位机速度闭环。ArUco辅助定位调试项目如表6-1所示。

从当前工程结构看，最需要关注的问题有四类。第一，视觉模型的实时延迟和线程队列长度会直接影响控制滞后，必须通过日志确认实际帧率而不能只看配置中的max_fps=30。第二，Track Mask的形态学处理和高斯滤波参数依赖赛道材质、照明和摄像头姿态，跨场地泛化能力需要实车数据验证。第三，金币拾取的安全走廊边距与行人和车辆的距离阈值依赖上游投影几何，若标定存在偏差需实车微调。第四，下位机ABS参数（斜坡时间与反向制动限幅）及Flash存储参数需根据电机扭矩和轮胎附着力实地标定，以达到最佳制动距离与差速器保护效果。

第8章 结论与展望
8.1 制作工作总结
本项目完成了人工智能模型组智能汽车的软件与硬件系统主体：上位机能够读取共享内存AR输入帧，使用UNet生成Track Mask，使用PP-YOLOE输出目标检测结果，并通过双边缘1D高斯平滑滤波、扫描线、Bezier中心线拟合实现平滑高精度的视觉巡线；上位机通过本地TCP Socket与icar_socket_bridge桥接程序通信并转发至串口，实现计算与硬件通信解耦；针对复杂交互场景，形成了丢线偏置历史记录与反向回正算法、第一人称动态安全走廊金币拾取策略、岔路状态机补线、梯形区域停车、左右侧绕行以及结合PaddleOCR与ERNIE大模型的路口决策等全套策略。下位机完成TC264的初始化框架、10ms电机控制、编码器滤波、增量式PID速度闭环、动态斜坡过渡与ABS防抱死制动保护，有效保护了机械传动差速器，并构建了完备的OLED多级菜单与参数持久化系统，极大提升了调试与比赛现场的维护效率。整车典型运行功耗约30～40W，具备优良的电源稳态特性与长续航表现。
系统当前已经具备从视觉感知到执行器控制的完整软硬件闭环链路，代码中也加入了模型输入一致性检查、线程队列限制、丢线脱困与超时停车、ABS制动限幅、PWM限幅、启动保持帧和退出停止帧等安全措施。需要强调的是，报告中的参数表主要来自工程配置和源代码，不能替代最终实车测试；完整跑圈时间、最高速度、成功率和误触发次数仍需在硬件装配完成后补测。
8.2 主要问题与改进方向
后续工作首先应完成第5.6节的下位机硬件描述，并建立与软件端口、供电和机械尺寸一致的系统图。其次应建立带时间戳的端到端延迟测量，分别统计取帧、分割、检测、决策、网络发送和下位机执行的耗时，以便判断速度上限应受模型延迟还是车体响应限制。再次，应通过多光照、多曲率和多遮挡数据扩充分割与检测测试，必要时引入置信度自适应、边界历史滤波或轻量级时序模型。
在控制策略方面，可以将当前固定速度参数改为基于曲率、边界标准差和目标距离的连续速度规划；对岔路补线可加入更稳定的几何拟合和退出滞回；对行人和车辆应使用摄像头标定后的距离估计而非单一经验阈值；对OCR与大模型应增加本地离线轻量模型作为网络断连时的兜底方案。系统最终应以“可解释、可观测、可停车”为优先，在确认稳定性后再逐步提高速度。
8.3 结语
智能汽车的性能来自感知、决策、控制和机械执行的共同约束。本文给出的方案没有把问题简化为单一模型精度，而是把模型输出转换为可检查的Track Mask、Detection Result、Smoothed Lane Point Set和Interaction Plan，再通过通信协议交给有闭环反馈的下位机。这种分层设计为后续硬件补充、实车标定和竞赛规则适配留下了清晰接口，也为进一步提高系统可靠性和运行速度奠定了基础。

附录B.1 赛道双边缘 1D 高斯平滑滤波算法（LineFollower::smoothEdge）
// LineFollower.cpp：1D 高斯平滑滤波，消除语义分割边缘噪点与阶梯锯齿
std::vector<LanePoint> LineFollower::smoothEdge(const std::vector<LanePoint>& edge,
                                                int radius, float sigma, int imageWidth) {
    if (edge.size() < 3 || radius <= 0 || imageWidth <= 0) return edge;
    const int r = std::min(radius, static_cast<int>(edge.size()) / 2);
    if (r <= 0) return edge;
    const float s = std::max(0.1f, sigma);
    std::vector<float> kernel(2 * r + 1);
    for (int k = -r; k <= r; ++k) {
        kernel[k + r] = std::exp(-0.5f * static_cast<float>(k * k) / (s * s));
    }
    std::vector<LanePoint> smoothed = edge;
    const int n = static_cast<int>(edge.size());
    for (int i = 0; i < n; ++i) {
        float weightSum = 0.0f, colSum = 0.0f;
        for (int k = -r; k <= r; ++k) {
            const int idx = std::clamp(i + k, 0, n - 1);
            const float w = kernel[k + r];
            weightSum += w; colSum += w * static_cast<float>(edge[idx].col);
        }
        if (weightSum > 1e-6f) {
            const int smoothedCol = static_cast<int>(std::lround(colSum / weightSum));
            smoothed[i].col = std::clamp(smoothedCol, 0, imageWidth - 1);
        }
    }
    return smoothed;
}
附录B.2 丢线历史偏置判定与反向回正算法（LineFollower::determineLostDirection）
// LineFollower.cpp：基于 60 帧历史偏差记忆的丢线反向脱困算法
LostDirection LineFollower::determineLostDirection() const {
    if (history_.empty()) return LostDirection::None;
    int validCount = 0; double weightedOffsetSum = 0.0, weightTotal = 0.0;
    int leftStyleCount = 0, rightStyleCount = 0;
    double currentWeight = 1.0;
    for (auto it = history_.rbegin(); it != history_.rend(); ++it) {
        if (!it->valid) continue;
        weightedOffsetSum += static_cast<double>(it->centerOffset) * currentWeight;
        weightTotal += currentWeight;
        currentWeight = std::max(0.2, currentWeight * 0.90);
        if (++validCount >= 20) break;
    }
    if (validCount == 0 || weightTotal <= 0.0) return LostDirection::None;
    const double avgOffset = weightedOffsetSum / weightTotal;
    if (avgOffset > 10.0) return LostDirection::OutLeft;   // 赛道在右，向右大打角回正
    if (avgOffset < -10.0) return LostDirection::OutRight; // 赛道在左，向左大打角回正
    return (avgOffset >= 0.0) ? LostDirection::OutLeft : LostDirection::OutRight;
}
附录B.3 第一人称动态安全走廊金币拾取算法（CoinCollector::plan）
// CoinCollector.cpp：基于赛道边界安全走廊约束的金币引导与降速协同
InteractionPlan CoinCollector::plan(const cv::Mat&, const LineFollowerResult& lane,
                                    const std::vector<ProjectedTrackObject>& objects) {
    InteractionPlan plan;
    if (!config_.enabled || !lane.valid) return plan;
    const ProjectedTrackObject* coin = findTargetCoin(lane, objects);
    if (coin != nullptr) {
        int leftCol = 0, rightCol = lane.imageWidth - 1;
        if (queryTrackBoundaries(lane, coin->center.y, leftCol, rightCol)) {
            const int trackWidth = std::max(20, rightCol - leftCol);
            const int safetyMargin = static_cast<int>(std::lround(trackWidth * config_.trackSafetyMarginRatio));
            const int safeMinX = leftCol + safetyMargin, safeMaxX = rightCol - safetyMargin;
            if (coin->center.x < leftCol - 30 || coin->center.x > rightCol + 30) return plan; // 出界拒转向
            const int clampedCoinX = std::clamp(coin->center.x, safeMinX, safeMaxX);
            const int bias = std::clamp(static_cast<int>((clampedCoinX - lane.center) * config_.centerBiasGain),
                                        -config_.maxCenterOffsetPx, config_.maxCenterOffsetPx);
            plan.center = std::clamp(lane.center + bias, safeMinX, safeMaxX);
            plan.speed = std::max(0.0f, lane.speed * config_.speedScale); // 降速稳定吸附
            plan.overrideCenter = true; plan.overrideSpeed = true; plan.state = "COIN_COLLECT";
        }
    }
    return plan;
}
