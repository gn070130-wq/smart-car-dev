# KM13 问题及解决方案

更新时间：2026-08-19
适用工程：`km13/km1/km13_tc387`
当前分支：`encoder`
整理时基线提交：`62d9538`（该提交之后仍有大量未提交源码修改）

> 本文按当前源码和实车反馈整理。`KM13_TC387_README.md`、`视觉联调.md` 中仍有旧的 CPU 分工、WiFi、显示和操作说明，不能作为当前调车依据。当前操作以本文和 `下午调试记录.md` 为准。

## 1. 比赛目标与当前结论

整车只完成一个流程：

1. 上电静止，完成 IMU963RA 零偏标定，进入 `READY`。
2. 按 KEY1 进入 `REC`，视觉跟随人背后的标志，同时记录后轮里程、IMU 航向和实际前轮角。
3. 再按 KEY1 停止录制，轨迹有效则回到 `READY`。
4. 按 KEY2 进入 `BACK`，车辆倒车沿本次路线返回。
5. 剩余里程小于停车阈值后进入 `DONE` 并停车。

比赛路线随机，当前只保留本次上电后记录的路线：

- `CAR_PATH_SAVE_TO_FLASH=0`，不保存旧路线到 Flash。
- WiFi 已完全禁用：`CAR_REMOTE_ENABLE=0`、`CAR_REMOTE_LINK_WIFI_SPI=0`。
- 视觉跟随已经能够工作。
- 两个后轮编码器已经都有数据，前进为正、后退为负。
- 前轮绝对角度传感器能够稳定输出原始位置。
- IMU 基本稳定，已经做零偏、死区和低通。
- 倒车直线回放的框架已经具备。
- 大半径弯道已改为“录制前轮角主前馈 + 双窗口曲率兜底 + IMU 航向反馈”，算法链路已完成，尚需完成实车闭环验证和参数微调。

## 2. 当前多核架构

当前不是旧文档所写的单核方案，实际分工如下：

| 核心 | 当前职责 | 关键文件 |
| --- | --- | --- |
| CPU0 | 初始化 MT9V03X、相机 DMA、曝光请求和视觉校准协议 | `user/cpu0_main.c` |
| CPU1 | 获取稳定帧、AprilTag/标志识别、发布结果、IPS200 参数显示 | `user/cpu1_main.c` |
| CPU2 | 语音 UART、蜂鸣器和 LED 非阻塞任务 | `user/cpu2_main.c` |
| CPU3 | 读取视觉结果、10 ms 底盘控制、编码器、IMU、状态机、记录和回放 | `user/cpu3_main.c`、`user/car_nav.c` |

跨核视觉数据通过 `code/vision_shared.c/.h` 发布和读取。相机帧只由视觉链路按 `acquire -> process -> publish -> release` 使用，控制核不直接争抢相机缓冲区。

### 多核问题的历史结论

曾出现画面只有第一帧、控制数据全部为零、核心像卡死等现象。根因不是“TC387 性能不够”，而是相机 DMA 所属核、帧缓冲生命周期、跨核共享和显示刷屏互相干扰。最终按参考视觉工程恢复相机架构后帧率和识别恢复。

注意事项：

- 不要把相机初始化和帧获取随意搬到不同核心。
- 不要让两个核心同时初始化或写 IPS200。
- 不要在相机帧释放后继续读取该帧。
- 跨核共享结构必须使用现有发布/快照接口，不能直接读写一半更新的数据。
- `car_nav.c` 当前用 `#pragma section all "cpu0_dsram"`，但控制实际运行在 CPU3。这是需要后续审计的技术债；现阶段实车稳定时不要临赛改内存区。

## 3. 状态机与按键

按键低电平有效：按下为 0，松开为 1。软件使用下降沿并带 300 ms 冷却。

| 操作 | 有效前置状态 | 结果 |
| --- | --- | --- |
| KEY1 第一次 | `READY`/`DONE`/`ERR`/`FULL` | 清空旧轨迹，进入 `REC` |
| KEY1 第二次 | `REC` | 结束记录；轨迹有效则进入 `READY` |
| KEY2 | `READY`/`DONE`/`ERR` | 检查轨迹并进入 `BACK` |

不能回放时先看：

- `REC` 是否至少 800 mm。
- `PT` 是否至少 3。
- `ERR` 是否为 2（路线太短）或 4（记录已满）。
- KEY2 是否确实产生一次 1 到 0 的下降沿。

当前错误码：

| ERR | 含义 | 处理 |
| ---: | --- | --- |
| 0 | 正常 | 继续测试 |
| 1 | 自检失败 | 检查初始化流程 |
| 2 | 路线太短 | 录制超过 0.8 m 且至少 3 点 |
| 3 | IMU 丢失 | 检查 I2C、供电和 IMU 初始化 |
| 4 | 路径点满 | 降低记录密度或缩短路线 |
| 5 | 编码器/转向传感器错误 | 检查 SPI、引脚和传感器供电 |
| 6 | 回放航向误差过大 | 立即停车，检查初始姿态和回放符号 |
| 7 | Flash 错误 | 当前 Flash 路线保存关闭，正常不应出现 |

## 4. 后轮编码器与里程

### 接线和方向

| 轮 | 定时器 | 脉冲 | DIR | 软件符号 |
| --- | --- | --- | --- | ---: |
| 左后轮 | TIM3 | P02.6 | P02.7 | +1 |
| 右后轮 | TIM6 | P20.3 | P20.0 | -1 |

两路都使用硬件 TIM 的 DIR 模式。之前 TIM3 只有个位数跳变，是因为曾把四倍频结果再除以 4，并且每 1 ms 读取后清零，低速边沿被持续丢失。当前应直接读取硬件计数增量，不再额外除 4。

### 里程换算

- 每个后轮约 1024 count/rev。
- 后轮直径约 0.25 m。
- 理论周长：`pi * 0.25 = 0.7854 m`。
- 单计数理论距离：`0.7854 / 1024 = 0.000767 m`，约 0.767 mm。
- 里程使用左右轮增量平均值，减小单轮打滑和转弯内外轮差影响。
- 16 位硬件计数到 65536 回绕不是问题，前提是周期性读取“增量”并累加到 32 位软件总计数。

### 现实风险和方案

| 问题 | 物理原因 | 代码方案 |
| --- | --- | --- |
| 两轮同向但一正一负 | 安装朝向/方向线相反 | 保留左右独立 `SIGN`，最终前进必须都为正 |
| 转弯里程偏差 | 内外轮路程不同 | 使用左右平均；不要只用单轮 |
| 原地打滑仍产生里程 | 编码器只能测轮转，不能测地面位移 | 降低 PWM 和加速度，实车标定每米计数 |
| 倒车 `REM` 不下降 | 倒车符号或绝对里程处理错误 | 架空确认倒车时两轮 delta 都为负，回放模块按倒车绝对位移累计 |

## 5. 前轮绝对角度传感器与转向闭环

### 接线

当前使用 0~4095、0~360 度的 SPI 绝对角度传感器，软件 SPI 模式 0：CPOL=0、CPHA=0。

| 传感器 | TC387 |
| --- | --- |
| VCC | 3.3 V |
| GND | GND |
| SCLK | P10.3 |
| MOSI | P10.1 |
| MISO | P10.2 |
| CS | P10.5 |

传感器虽然主要向主控返回角度，仍按六线全部连接。当前逐飞绝对编码器驱动使用软件 SPI。

### 实测标定

| 位置 | 原始 SA |
| --- | ---: |
| 右机械极限 | 925 |
| 中位 | 2006 |
| 左机械极限 | 2960 |
| 右软件限位 | 925 |
| 左软件限位 | 2960 |

抽象目标角度不是传感器直接输出，而是按左右不同量程分段映射到原始值。屏幕 `SA` 直接显示原始值，便于判断闭环。

### 已解决的转向问题

1. **一给目标就打死**：位置环极性错误。实车反接转向电机线后反馈变为负反馈，闭环才稳定。
2. **视觉左右反了**：电机线不能再反回去，否则位置环重新变正反馈。现用 `CAR_VISION_STEER_SIGN=-1` 只修正视觉外环方向。
3. **到软限位后不能反向**：软限位曾被理解为锁死。现在只禁止继续向当前极限外推，反方向命令始终放行。
4. **二维码丢失后自动回正**：旧逻辑在 `valid=0` 时给目标 0。现在丢标后后轮停车、转向 PWM 归零并停在当前位置，重获目标后继续跟随。
5. **小误差一直嗡响**：原始位置容差设为 6 count，进入容差后停止 PWM。

### 当前闭环方向判据

- 左转目标应使目标原始值大于 2006，电机运动后 `SA` 增大。
- 右转目标应使目标原始值小于 2006，电机运动后 `SA` 减小。
- 如果输出 PWM 后误差反而持续增大，必须立即断电，不能靠调 Kp 修复极性。
- 软限位只负责拒绝向外命令，不负责自动回正。

## 6. 视觉跟随

视觉识别链路能够输出：

- `valid`：目标是否可信。
- `DX`：目标中心相对画面中心的横向偏差。
- `DIST`：根据标志尺寸估计的距离，单位 mm。
- 置信度、目标框和处理耗时等内部信息。

实测坐标约定：目标在画面左边时 `DX` 为正，右边时 `DX` 为负。

当前跟随策略：

- 不使用步进脉冲转向。
- `DX=-60..+60` 连续映射到约 `-55..+55 deg` 抽象目标，再映射成原始 `SA` 目标。
- 转向目标低通系数 0.35，目标每 10 ms 最大变化 0.8 deg。
- `DIST <= 400 mm` 停止。
- 400~500 mm 区间平滑减速。
- `DIST >= 550 mm` 恢复正常跟随，形成迟滞，避免在阈值附近启停抖动。
- 正常目标速度约 0.23 m/s，远距离约 0.28 m/s。
- 丢标短时间保留视觉结果；超时后后轮停车，转向不自动回正。

现实注意事项：

- 距离来自标志像素尺寸，不是真正测距；人的俯仰、标志倾斜、光照和部分遮挡都会改变 `DIST`。
- 跟人绕桩时不要让人突然横穿画面；车辆有转向机构响应时间和最小转弯半径。
- 跟随参数和回放参数分文件保存，不要为修回放去改 `car_follow_config.h`。

## 7. IMU 航向

当前使用逐飞 IMU963RA，只积分 Z 轴角速度得到连续航向。没有 GPS、磁力计和 EKF，因此短时间比赛可用，但绝对航向必然随时间漂移。

当前处理：

- 上电等待 300 ms。
- 采 1000 次零偏样本，每次间隔 2 ms，有效样本至少 850。
- 角速度死区 0.6 deg/s。
- 两级一阶低通，系数 0.18。
- 只在首次录制前的 `READY`、路线尚为空、后轮和电机静止，并且原始角速度与当前零偏之差不超过 0.30 deg/s 时，持续 1 s 后才以 0.003 的系数缓慢跟踪零偏。
- 进入 `REC` 后整场任务冻结零偏，防止手动转动车身或停车后的真实角速度被误学成零偏。
- 10 ms 积分一次航向。

### IMU 自己增减的原因

物理上，陀螺仪存在温漂、机械振动和供电噪声；代码上，任何剩余零偏积分后都会变成持续航向漂移。旧代码只看后轮静止，会把架空手动旋转误学成零偏，停手后产生反向角速度并让 `YAW` 慢慢退回；现已加入状态和角速度残差门限。滤波只能降低漂移，不能像磁航向那样长期锁定绝对方向。

正确测试方法：

1. 上电后至少 2.5 s 不碰车、不转轮、不震动桌面。
2. 观察静止 30 s 的 `YAW` 漂移。
3. 静止漂移小于约 2~3 deg/30 s 可进入短路线测试。
4. 若持续单向快速漂移，先查固定、供电和上电标定，不要先调回放增益。

## 8. 路径记录

路线不是二维坐标，也不是 GPS 拟合曲线，而是按里程保存的关键点：

```text
path point = {累计前进里程 s, 过滤后的连续航向 yaw, 实测前轮角 steer, 时间}
```

记录规则：

- 只累计前进里程，负增量不会增加录制路线。
- 车辆前进时才更新航向，直线每约 0.08 m 保存一个点。
- 航向累计变化达到约 5 deg 且至少移动 0.025 m 时提前保存转弯点。
- 录制航向有 0.5 deg 死区和 0.35 低通。
- 前轮角相对固定标定中位 `SA=2006` 解算，使用 0.35 deg 死区和 0.50 低通；停车时不更新，避免转向静态抖动污染路线。
- 最多 900 点。
- 路线至少 0.8 m 且至少 3 点才有效。

这种 `s-yaw-steer` 路线不会在八字交叉处搜索错支路，因为它按记录顺序和剩余里程读取；但它不能直接测量车体横向位置，严重轮胎打滑仍会造成二维位置偏差。

## 9. 倒车回放

回放每 10 ms 执行：

1. 根据后轮倒车增量更新已回放里程。
2. `remaining = total - replayed`。
3. 用编码器剩余里程和 IMU 局部相位校正得到参考位置，在倒车方向前视 0.15 m 查询目标航向和录制前轮角。
4. 录制前轮角作为主前馈，直接复现跟随时的机械转角；仅当前轮角接近中位时才用航向曲率作为前馈兜底。
5. IMU 航向误差和角速度产生反馈修正；低曲率直线额外使用限幅很小的航向积分，抵消机械中位误差造成的持续跑偏。
6. 目标转角经过 0.30 低通后送入与跟随相同的原始 `SA` 位置环。
7. 剩余 0.65 m 开始减速，剩余 0.06 m 停车。

内层电机位置环极性始终不变。实车验证表明，回放公式本身已经包含倒车运动方向，外环不得再额外反号；当前使用 `CAR_REPLAY_STEER_SIGN=+1`。正向右弯倒车原路返回时前轮仍应向物理右侧打，正向左弯同理仍向左打。

### 直线保持

当以下条件同时成立时，目标保持物理中位 `SA=2006`：

- 录制前轮角绝对值小于 1 deg。
- 局部曲率绝对值不超过 0.10 1/m。
- 航向误差不超过 1.2 deg。
- 当前角速度不超过 3 deg/s。

这样可以抑制 IMU 微小抖动被重复回放；一旦累计偏航超过 1.2 deg，航向 P/I 反馈就会离开中位并修正直线跑偏。

### 大半径弯、S 弯和整圈绕桶（已实现）

`car_path_sample()` 不再只看相邻两个点，而是对 `yaw(s)` 做两组最小二乘拟合：

- 0.12 m 半窗口：保留紧弯以及 S 弯换向处的局部方向。
- 0.30 m 半窗口：累计大半径缓弯的航向变化，避免逐点变化太小而误判直线。
- 短、长窗口符号相反时使用短窗口，防止 S 弯两侧互相抵消。
- 弯道内用未折叠 IMU 航向在编码器位置前后 0.40 m 搜索相符的路线相位，参考索引只能向起点移动。
- 整圈的正负 360 deg 航向不会被折叠成 0 deg，因此绕桶入口和出口可区分。

该改动完成后仍必须依次测试：直线、单个宽左弯、单个宽右弯、90 度宽弯、单桶整圈，最后才测试随机组合或八字。

## 10. IPS200 显示

当前只显示参数，不显示摄像头图像，避免图像刷屏造成黑屏、雪花、叠帧和抢占视觉处理时间。显示由 CPU1 单点管理，黑底红字。

| 项目 | 含义 |
| --- | --- |
| ST | `READY`、`REC`、`BACK`、`DONE`、`ERR`、`FULL` |
| ERR | 错误码 |
| DX | 视觉横向偏差；无目标显示 `-----` |
| DIST | 视觉距离 mm；无目标显示 `-----` |
| REC | 当前记录总里程 mm |
| REM | `BACK` 时剩余里程 mm，其他状态显示记录里程 |
| PT | 路径点数量 |
| SA | 前轮传感器原始值 |
| YAW | 连续航向整数度 |
| SPWM | 转向电机 PWM，正负表示方向 |

历史雪花屏和字符串残影主要来自：多个核心写屏、图像和文字区域交叠、未清理定宽字段、刷新过快或 SPI 写屏与其他流程并发。当前原则是：只由一个核写屏、固定刷新周期、固定字段宽度、先清值区再写值。

## 11. 语音、蜂鸣器和 LED

### 串口和接线

- UART3，115200 baud。
- 主板 TX：P15.6，接语音模块 RX。
- 主板 RX：P15.7，接语音模块 TX。
- 必须共地。
- 握手帧：`A5 FA 00 82 0D 00 4A FB`。
- 控制帧：`A5 5A CMD FB`。

模块空闲时出现大量看似随机数据，实际包含重复握手帧和语音芯片协议帧，不能把所有收到的四字节都当控制命令。当前解析器用滑动窗口只识别完整握手和 `A5 5A xx FB`。

### 输出

- 无源蜂鸣器使用 3 kHz 硬件 PWM。
- 上电自检鸣响约 160 ms，证明蜂鸣器和 PWM 输出链路正常。
- LED 命令 0x21~0x28 已实现 1 s 动作，包括常亮、半亮和双闪。
- LED 上电微亮通常是默认电平、漏电或有效电平定义不符。当前初始化为推挽输出并明确写 OFF；若仍亮，需用万用表确认板上 LED 是高电平亮还是低电平亮。

语音由 CPU2 独立执行，不应阻塞视觉和底盘。比赛前若语音仍不可靠，可以只关闭 `CAR_VOICE_ENABLE`，不要改视觉或回放链路。

## 12. WiFi

WiFi 已按用户决定彻底停用，不参与比赛流程。历史上出现 `WF30/31/40/41`、模块蓝灯不亮和连不上热点，涉及模块上电、SPI握手、热点 WiFi 6 兼容和旧工程初始化流程。

当前结论：

- 不再继续调 WiFi。
- 不依赖网页遥控。
- 不要因为旧 README 仍有 WiFi 命令就重新打开宏。
- 若赛后恢复，必须从验证过的旧 `km3` 工程整体移植初始化和连接流程，不能只照搬引脚宏。

## 13. 编译和链接历史问题

### `unresolved external: dma_retarget_destination`

原因：视觉相机对象引用 DMA 重定向函数，但对应 DMA 驱动源文件没有进入链接或工程配置不一致。解决方向是确保逐飞 DMA 驱动实现参与编译，不能用空函数掩盖。

### CPU2 DSRAM 无法放置约 91 KB

原因：视觉大数组/帧缓冲被放入 CPU2 本地 DSRAM，超过该内存区容量。解决方案是让大视觉缓存留在参考工程指定内存区，CPU2 只保留小型语音状态。

### 当前生成物大量变更

`Debug/` 下 `.o/.src/.elf/.hex/.map` 都是构建产物，不应当用它们判断源码差异，也不应在每次源码提交中全部上传。提交前应重点检查 `user/`、`code/`、必要的 `libraries/` 修改和文档。

## 14. 比赛前分级测试流程

任何一级失败都不要进入下一级。

### A. 断开电机或架空测试

1. 上电保持整车静止至少 2.5 s。
2. `ERR=0`，`ST=READY`。
3. `SA` 中位约 2006，手动左右移动连续到约 925~2960，无跳变。
4. 两个后轮向前转均为正，向后均为负。
5. 后轮一圈约 1024 count。
6. 静止 30 s 观察 `YAW` 漂移。
7. 移动标志：左侧 `DX>0`、右侧 `DX<0`，`DIST` 随距离合理变化。

### B. 架空闭环测试

1. 进入 `REC`。
2. 标志缓慢左右移动，`SA` 应平滑追目标，不能持续顶软限位。
3. 遮挡标志，后轮输出降为 0，转向停止在当前位置。
4. 手转后轮模拟超过 0.8 m，结束录制后显示 `READY`。
5. 按 KEY2 显示 `BACK`，后轮方向为倒车，`REM` 单调减小。
6. 直线记录的回放目标应保持 `SA` 接近 2006。

### C. 低速落地直线

1. 只录制 2~3 m 直线。
2. 标记起点和终点，测量实际回放停车误差。
3. 若 `REM` 正常归零但物理位置不对，标定每米计数，不要改停车状态机。
4. 若车体偏航但 `YAW` 不变，检查 IMU 安装方向和 Z 轴符号。

### D. 单弯测试

1. 单个宽左弯。
2. 单个宽右弯。
3. 查看录制后 `PT` 是否在弯道增加。
4. 回放中观察转弯前 `SA`、`SPWM` 和 `YAW` 是否开始变化。
5. 当前宽弯问题修复前，不直接测试复杂绕桩。

### E. 完整流程

1. 人按比赛速度走完整路线。
2. 中途至少测试一次短暂遮挡和停止。
3. 停车区 KEY1 结束录制，确认 `READY`、`ERR=0`。
4. 所有人离开车辆倒车范围后按 KEY2。
5. 记录最终位置误差、最大横向误差、是否漏弯和是否提前停车。

## 15. 参数调整顺序

每次只改一类参数，并记录修改前后结果。

1. **先确认极性**：后轮正负、`DX` 左右、`SA` 增减、倒车转向方向。
2. **再标定传感器**：轮周/每圈计数、转向中位和软限位、IMU 静止漂移。
3. **再调跟随速度**：先低 PWM，保证人停车停，再提高跟随能力。
4. **再调前轮位置环**：目标能到、不过冲、不顶死后才能继续。
5. **再调回放里程**：先只做直线停车。
6. **再修宽弯曲率窗口**：确认左右单弯都正确。
7. **最后调航向 Kp、角速度 Kd、前视距离和速度**。

禁止用以下方式掩盖根因：

- 极性错时调 PID。
- 里程标定错时改停车余量。
- 宽弯曲率为 0 时盲目增大航向 Kp。
- IMU 上电被碰动时调滤波参数。
- 显示异常时让多个核心重新初始化屏幕。

## 18. 最终原则

这辆车的回放精度上限由四件事共同决定：轮胎不打滑、后轮里程标定正确、IMU 短时航向稳定、前轮位置环确实到达目标。代码滤波不能补偿严重打滑，单纯编码器也不能感知车身横向侧滑。

当前最稳妥路线是：保持已经验证的视觉架构和转向内环不动，先补上宽弯累计航向检测，再从直线到单弯逐级验证。复杂绕桩和八字必须建立在左右单弯都能稳定倒车回放之后。

## 19. 随机路线与完整绕桶方案（2026-08-19）

比赛随机抽取路线，因此代码不识别“锥桶编号”，也不预存某条地图。它只回放本次 `REC` 得到的连续 `yaw(s)`：

1. 路线直线每 0.08 m 保存一次；转弯累计约 5 deg 时可提前保存。
2. 短窗口曲率负责紧弯和 S 弯的左右切换，长窗口曲率负责图中半径较大的绕行弧线。
3. 若短、长窗口曲率符号相反，优先短窗口，防止 S 弯两侧在长窗口内互相抵消。
4. 弯道内用连续 IMU 航向在编码器位置前后 0.40 m 搜索最佳相位；修正量低通且单周期限幅，不能瞬间跳路线。
5. 完整绕桶累计航向约为正负 360 deg。相位匹配使用未折叠航向，所以入口和出口即使物理朝向相同也不是同一点。
6. 路径索引只能向起点单调移动；回放停止只看后轮剩余里程小于 0.06 m，避免 IMU 漂移导致提前停车。

该方案能覆盖图中的随机特殊路径，但仍受物理条件限制：轮胎严重打滑、倒车偏出原弧线超过约 0.40 m、IMU 在一圈内漂移过大，都会超过局部校正能力。实车必须按“直线 -> 单宽弯 -> 90 度弯 -> 整圈 -> 随机组合”的顺序验证。

## 20. 本轮整工程静态审查

- 相机 ERU/DMA 属于 CPU0，视觉识别和 IPS200 属于 CPU1，语音 UART3 属于 CPU2，10 ms PIT 与底盘属于 CPU3；中断服务核与主循环一致。
- UART3 接收解析只允许中断调用，CPU2 主循环不再重复调用同一个滑动窗口解析器。
- IPS200 只有 CPU1 初始化和刷新，当前不显示图像，降低 SPI 并发和雪花屏风险。
- 路径 RAM 上限 900 点；逐飞 DFlash 每页 512 个 `uint32`，预留 8 页可容纳 4096 字，900 点加头部需要 2708 字，容量充足。比赛配置 `CAR_PATH_SAVE_TO_FLASH=0`，只使用本次路线。
- WiFi 宏均为 0，不进入初始化、轮询或遥控分支；旧实现仍是编译期关闭的历史代码，不消耗运行进程。
- IMU963RA 库的周期读取接口没有返回通信状态，因此初始化失败能报错，但运行中断线无法仅靠当前驱动可靠识别；比赛前必须做插头拉扯和静止漂移测试。
- `car_nav/car_path/car_replay` 数据目前位于 `cpu0_dsram`，控制在 CPU3 执行。TC387 可访问该内存，但这是跨核访问，后续若迁移到 CPU3 本地 DSRAM，必须整体迁移并重新检查链接容量，不能零散改段名。
- PIT 待处理计数允许积压到 20；若 CPU3 被长任务阻塞，会连续补跑多个名义 10 ms 控制周期。当前回放搜索量小，但实测仍需观察控制周期是否稳定。
