第一章  引  言
1.1 竞赛背景
全国大学生智能汽车竞赛是一项融合机械设计、嵌入式系统、传感器技术、自动控制和计算机视觉的综合性工程实践活动。轮腿穿越组不仅要求车模能够自主识别赛道并稳定行驶，还要求车辆利用轮腿机构完成复杂路面与障碍的穿越，因此对机械刚度、重心布置、感知可靠性、姿态稳定和多执行机构协同提出了更高要求。[1]
1.2 设计任务与目标
本项目的设计目标是在竞赛规则允许范围内，完成轮腿式智能车的机械改造、电路设计和控制程序开发，使车模能够完成常规赛道循迹、障碍距离判断、车身姿态估计以及轮腿协调穿越。系统设计遵循可靠、便于维护和便于调试的原则，并为后续元素识别预留硬件与软件接口。
1.3 技术路线与报告结构
技术路线依次包括规则约束解析、机械结构改造、传感器与电路设计、双核软件分工、路径记录与复现、科目状态机、多闭环控制和整车调试。本文第二章说明三个比赛科目及总体方案；第三章介绍机械结构与轮腿机构；第四章介绍CYT4BB7双核平台、三块PCB与传感器接口；第五章说明路径导航、科目逻辑、障碍处理和PID；第六章介绍开发、制作与调试。

第二章  系统总体方案设计
2.1 功能需求分析
轮腿穿越智能车需要具备环境感知、运动控制、姿态稳定、穿越动作执行和安全保护五类功能。环境感知由摄像头、测距模块和惯性传感器完成；运动控制包含轮端速度和行驶方向控制；姿态稳定根据IMU数据调节轮腿或舵机；穿越动作由状态机协调各执行机构完成。
2.2 系统组成与信息流

图2.1 轮腿穿越智能车系统总体框图
主控接收MT9V034输出的赛道图像、DL1B输出的距离数据以及IMU660RC输出的角速度和加速度信息，经图像处理、状态判断与控制运算后，向驱动板输出电机控制信号，向舵机或轮腿执行机构输出姿态调整信号。TPS54821RHL电源模块为主控、传感器和执行机构提供稳定电源。
2.3 工作模式与状态转换
软件将车辆运行过程划分为初始化、自检、常规循迹、障碍预判、减速准备、轮腿穿越、落地稳定和恢复循迹等状态。状态转换依据图像特征、测距结果、IMU姿态和持续时间共同判断，避免仅依赖单一传感器造成误触发。
2.4 元素识别与通过方案
2.4.1 锥桶：纯惯性导航
锥桶通过采用纯惯性导航方案，不使用GPS，也不依赖视觉矫正。车辆以IMU航向为主要方向基准，结合编码器里程推算建立局部坐标；示教阶段记录锥桶间通过路径，运行阶段通过Flash路径复现、前视点航向计算和Yaw闭环完成直行、绕桩及返回。每次启动时统一发车位置和初始车头方向，以减小惯性与里程积分的累计偏差。
2.4.2 雷区：纯惯性导航与视觉矫正扩展
雷区当前同样采用纯惯性导航方案。系统把普通路线与雷区段分开记录，依靠IMU航向、编码器里程坐标和分段路径复现进入雷区；到达目标段后暂停常规路径跟随，执行原地旋转。为降低惯性导航误差对雷区边界位置的影响，正在增加基于白色边框的视觉矫正功能。
2.4.3 单边桥：视觉矫正通过
单边桥通过采用视觉矫正方案。摄像头提取桥面或边缘特征，计算车辆相对单边桥中心方向的横向与航向偏差，并将偏差送入转向控制，使车辆在进入障碍前完成对正。进入单边桥状态后，程序降低目标速度并配合姿态闭环和轮腿控制保持车身稳定；通过结束后退出元素状态，恢复对应分段的路径复现。
2.4.4 三级台阶：视觉矫正与ToF跳跃判断
三级台阶采用视觉矫正与ToF跳跃判断相结合的方案。摄像头识别台阶边缘及其相对位置，用于进入台阶前的横向和航向矫正；DL1B ToF测距数据用于判断台阶接近状态和各次跳跃触发时机。并在三次跳跃完成后进入稳定检测，再恢复路径复现。

第三章  机械结构设计与调整
3.1 整车结构与尺寸
车模外形尺寸为长18.5 cm、宽27.3 cm、高35.9 cm。整车由底板、轮腿机构、轮端驱动、舵机安装座、摄像头支架、传感器支架、电路板和线束组成。

图3.1 整车结构
3.2 腿部结构加强
原车模腿部部件较软，快速行驶及落地冲击时容易发生变形。项目仿照逐飞六无刷车模的结构，修改并替换腿部部件，以减小快速行驶时的腿部变形，提高承载能力和左右一致性。

图3.2 腿部结构改造前后对比图
3.3 底板加宽与舵机维护设计
原车模整体结构较为紧凑，更换舵机需要较长时间。为缩短维护时间，项目将车底板加宽，并调整舵机固定孔位与线束走向，使舵机能够从指定方向快速拆装。
3.4 轮胎选择与通过性
原车模轮胎外径较小。为便于通过颠簸路段，项目将轮胎更换为外径10 cm的型号。效果较原装轮胎更好。

图3.3 10 cm轮胎及轮端安装结构
3.5 重心与线束布置
轮腿车辆在抬腿、跨越和落地过程中重心位置变化明显。主控板、电源板和电池应尽量靠近车体几何中心并降低安装高度；左右驱动板和线束应对称布置。运动关节附近的线束需预留弯折长度并进行应力释放，防止轮腿动作造成连接器松脱或导线疲劳断裂。

第四章  硬件系统设计
4.1 硬件总体设计原则
硬件设计以供电稳定、接口明确、抗干扰和便于检修为原则。将pcb板分为了磁编板、CYT4BB7主控板、无刷电机驱动板和舵机驱动板。
4.2 CYT4BB7主控板
工程采用CYT4BB7双Cortex-M7平台，两核均配置为250 MHz，开发环境为IAR Embedded Workbench 9.40.1，逐飞CYT4BB开源库版本为V3.9.3，主控工程版本标识为2.0.17。M7_0负责菜单、SBUS、路径记录/复现、PID、IMU与电机/舵机协调；M7_1负责摄像头、图像二值化、DL1B测距和视觉障碍识别。两核通过位于0x28001000附近的共享区域交换曝光、阈值、测距、跳跃事件，并进行DCache一致性维护。

4.5 传感器接口
4.5.1 MT9V034视觉接口
MT9V034总钻风摄像头配置为188×120像素，默认帧率100 fps、曝光时间250、增益32，8位并行数据由P18_0～P18_7输入，PCLK和VSYNC分别接P06_5、P06_6。实际程序使用固定阈值150加可调偏移完成二值化，曝光时间和阈值偏移由M7_0从Flash恢复后通过跨核共享下发；菜单允许曝光在1～400范围内调整。[2]
4.5.2 DL1B测距接口
DL1B采用软件I²C进行通信，测量结果以毫米为单位。M7_1周期读取距离并通过共享区发布；该数据用于三级台阶识别和坡道速度保护。[3]
4.5.3 IMU660RC姿态接口
IMU660RC采用SPI2硬件接口，通信速率10 MHz，默认加速度量程±8 g、角速度量程±2000°/s。程序在M7_0初始化阶段完成陀螺仪零偏校准，并在1 ms节拍中读取加速度和角速度，计算pitch、roll和yaw，用于平衡、横滚补偿、台阶结束检测、坡道结束检测与失控保护。

第五章  软件与控制算法设计
5.1 软件架构与主流程
软件采用双核分层结构。M7_0主循环负责菜单显示、路径Flash读写、SBUS、串口命令、科目调度和共享数据发布；其1 ms中断执行IMU采样、姿态解算和各PID节拍。M7_1主循环负责MT9V034帧处理、固定阈值二值化、DL1B采样和障碍目标提取，并将测距数据写入共享区域。跨核事件通过序号和应答机制防止跳跃触发丢失。

图5.1 软件主流程图
5.2 图像处理与路径提取
摄像头图像首先进行灰度预处理和阈值分割，再从近端可靠区域向远端搜索左右边界，根据有效边界计算中心线和横向偏差。该视觉偏差当前用于单边桥及三级台阶进入前的方向矫正；雷区白色边框视觉矫正正在增加。三级台阶的视觉结果负责车辆对正，实际跳跃时机由DL1B ToF测距判断。对于边界缺失、强反光和车身颠簸造成的图像抖动，程序采用连续帧确认、有效性判断和异常帧保护。
5.3 三个科目的控制逻辑
5.3.1 行进绕桩：路径记录与复现
锥桶科目采用纯惯性导航。路径记录使用双缓冲与Flash分页写入：中断按距离或手动触发把里程坐标写入当前缓冲区并置位，主循环中的Route_Write()完成Flash操作。复现阶段依据IMU航向和编码器里程坐标，在有限搜索范围内寻找邻近点，并使用前视点计算目标航向和偏差。
5.3.2 定点排雷：分段导航与原地旋转
雷区当前采用纯惯性导航，将普通路线与雷区段分开存储。车辆依据IMU航向和里程坐标到达雷区后，暂停路径复现并启动Spin()；旋转过程中由Yaw闭环累计转角，并临时调整输出限制和相关控制状态，完成规定旋转后切换至下一雷区或返回路线。基于雷区白色边框的视觉位置矫正正在增加，当前版本仍以惯性与里程信息作为主要导航依据。
5.3.3 颠簸路段：障碍独立状态机
科目3最多支持10段路径，每段可关联一种障碍类型。单边桥和三级台阶在进入元素前均使用摄像头输出的偏差进行视觉矫正，使车辆对准障碍中心方向。三级台阶对正后，由DL1B ToF测距判断台阶接近状态和跳跃触发时机，控制核按ToF事件执行三次跳跃序列，并在结束后进入稳定检测。程序同时为交错单边桥、草地、颠簸路面和坡道设置独立的进入、周期处理、退出和复位逻辑，元素结束后恢复对应分段的路径复现。
5.3.4 里程坐标构建
当前方案不使用GPS。开始记录时，系统把发车点设为坐标原点，并以此时的IMU航向建立零向；在5 ms周期内，根据编码器平均速度与IMU航向积分更新车辆的x、y里程坐标。距离触发模式下，车辆每行驶约2 cm记录一个坐标点。复现时再次从相同发车位置和朝向建立坐标系，在已存路径中寻找邻近点并选取前视点，计算目标航向和偏差。该方案无需GPS原点或ENU坐标对齐，但要求起点、初始朝向及轮径换算保持一致。

图5.2 科目1/2/3路径记录、复现与障碍状态机关系图
5.4 PID闭环控制
5.4.1 方向控制[5]
方向控制以图像中心与赛道中心的偏差为输入，采用PID或PD算法生成左右轮差速或转向执行量。比例项提高纠偏速度，微分项抑制快速变化引起的振荡，积分项仅在确有稳态偏差且不会引起饱和时启用。
5.4.2 速度控制
速度环根据目标速度与反馈速度的误差调节驱动输出。常规直道可提高目标速度，弯道、障碍预判和穿越状态应降低目标速度。更换10 cm轮胎后需重新计算单位脉冲对应的行驶距离并重新整定参数。
5.4.3 姿态与轮腿控制
姿态控制以IMU输出的俯仰角、横滚角或角速度为反馈，对轮腿或舵机目标量进行修正。为避免执行机构频繁抖动，可设置死区、输出限幅、变化率限制和状态相关增益。

5.5 核心程序设计

5.5.1 双核任务分工与中断节拍

代码工程采用CYT4BB7双Cortex-M7结构。main_cm7_0.c负责整车控制入口、菜单、SBUS、串口命令、电池电压、路径记录与复现以及电机和舵机协调；main_cm7_1.c负责MT9V034图像采集、二值化、DL1B测距、视觉处理和跨核数据发布。cm7_0_isr.c承担周期控制、IMU姿态解算、PID计算及路径触发，cm7_1_isr.c承担视觉侧触发和共享数据时间戳。中断中仅完成采样、状态更新和缓冲标记，Flash写入与较重计算放在主循环执行。

5.5.2 业务模块与接口关系

project/code/move.c/.h提供轮腿、舵机、电机和车辆状态接口；navigation.c/.h提供坐标、路径记录、路径复现和坐标校正；subject.c/.h将三个科目组织为独立状态处理函数；imu.c/.h和pid.c/.h分别完成姿态解算与闭环控制；uart_command.c/.h和small_driver_uart_control.c/.h负责无线串口命令及驱动通信；Share.c/.h维护跨核共享数据。各模块通过move_data、work_state、move_state等结构传递状态，减少科目逻辑对底层驱动的直接耦合。

5.5.3 路径记录、复现与里程坐标

路径服务采用双缓冲与Flash分页写入机制。编码器平均速度与IMU航向在5 ms周期内积分形成x、y里程坐标；记录时，中断按约2 cm的行驶间隔把坐标写入当前缓冲区，缓冲区切换后仅置位存储标志，由主循环调用Route_Write完成Flash写入。复现时先分页读取路径点，再依据当前里程坐标在有限范围内寻找邻近点，并利用前视点计算目标航向和横向偏差。记录与复现均以发车点和初始车头方向为统一坐标基准。

5.5.4 配置、调试与安全机制
公共配置集中在project/code/myconfig.h和MyDefine.h，外设引脚及设备驱动分别由move.h、设备驱动头文件和IAR工程配置管理。当前提交配置中GPS_ENABLE=0，路径记录与复现不接入GPS；工程内保留的GPS条件编译兼容代码不参与当前版本运行。调试过程中重点检查编码器轮径换算、IMU航向零偏、发车点与初始朝向一致性、路径页号与缓冲区切换、SBUS通道语义、测距功能开关以及执行机构的限幅和故障保护。

void Yaw_PID(Yaw_PID_t *PID)
{
    PID->last_error = PID->error;
    PID->error = PID->target - PID->actual;
    if (PID->mode == 0)
    {
        while (PID->error > 180) {PID->error -= 360;}
        while (PID->error < -180) {PID->error += 360;}
    }

    if (fabsf(PID->error) < 1.5)
        PID->integral += PID->Ki * PID->error;

    if (PID->integral > PID->integral_max)
    {
        PID->integral = PID->integral_max;
    }
    else if (PID->integral < PID->integral_min)
    {
        PID->integral = PID->integral_min;
    }

    PID->output = PID->Kp * PID->error + PID->integral + PID->Kd * (PID->error - PID->last_error);
    if (PID->output > PID->output_max)
    {
        PID->output = PID->output_max;
    }
    else if (PID->output < PID->output_min)
    {
        PID->output = PID->output_min;
    }
}

void Coordinate_Get(float speed, float dt)
{
    float yaw_rad = move_data.yaw * PIf / 180;

    move_data.delta_distance = speed * dt;      
    move_data.run_distance += move_data.delta_distance;
    move_data.x_pos += move_data.delta_distance * sinf(yaw_rad);
    move_data.y_pos += move_data.delta_distance * cosf(yaw_rad);
    move_data.odom_x_pos += move_data.delta_distance * sinf(yaw_rad);
    move_data.odom_y_pos += move_data.delta_distance * cosf(yaw_rad);

    #if GPS_ENABLE
        // KF预测步：行驶距离越长，死推算累积误差越大，协方差随之增大
        float abs_dist = fabsf(move_data.delta_distance);
        float q_scale = (work_state.obstacle == bumpy_road) ? KF_BUMPY_ROAD_Q_SCALE : 1.0f;
        kf_P_x += KF_Q_PER_CM * q_scale * abs_dist;
        kf_P_y += KF_Q_PER_CM * q_scale * abs_dist;
    #endif
}
