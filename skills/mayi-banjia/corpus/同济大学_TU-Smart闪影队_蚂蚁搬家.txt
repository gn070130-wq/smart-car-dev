摘要
本文以全国大学生智能汽车竞赛“蚂蚁搬家”组别为背景，介绍了两辆搬运车模的设计与制作。车模采用麦克纳姆轮全向底盘与3D打印轻量化结构，配合自制的主驱一体板实现机械结构与硬件电路的紧凑集成；以RT1021微控制器为核心，采用“底层运行时—任务状态机—视觉感知”的分层软件架构，实现目标的识别、双车协同编队、同步推送与恢复返航的完整闭环。本文依次介绍了车模的机械结构、硬件电路、软件系统设计与开发调试工具，并对车模整体性能进行了总结。经过反复调试与优化，两车能够在规定场地内稳定、快速地完成目标物体搬运任务。
关键词： 双车协同；任务状态机；四元数互补滤波；麦轮运动控制；目标检测；模型量化
第一章 引言
全国大学生智能汽车竞赛是以智能汽车为研究对象的创意性科技竞赛，是面向全国大学生的一种具有探索性工程实践活动，是教育部倡导的大学生科技竞赛之一。该竞赛以“立足培养，重在参与，鼓励探索，追求卓越”为指导思想，旨在促进高等学校素质教育，培养大学生的综合知识运用能力、基本工程实践能力和创新意识，激发大学生从事科学研究与探索的兴趣和潜能，倡导理论联系实际、求真务实的学风和团队协作的人文精神，为优秀人才的脱颖而出创造条件。
本届智能车竞赛蚂蚁搬家组别规定需要自制两辆搬运车模，根据搬运的目标种类，将目标从室内长3.2米、宽2.4米的场地，搬运到场地四周。除了搬运车模，还允许自行设置数量不超过2台的辅助车模或者导引信标。本届赛题在要求车模具有一定搬运速度水平的同时，对两辆车模的目标识别、协同搬运能力的要求更高，车模间的通信也需要做到高实时、低延迟。
根据组别比赛规定，我们使用恩智浦公司基于NXP控制器的MicroPython控制开发板RT1021DAG5x作为主控，接收各个传感器采集到的信息；使用IMU660RA六轴惯性传感器提高更新频率，保证车模高速时稳定运行；搭配开关、IPS屏幕实现人机交互，完成车模调试、发车等功能；使用了自带编码器的直流有刷电机。在软件方面，车模采用“底层运行时—任务状态机—视觉感知”的分层架构，两车通过半双工无线链路协同完成目标的搜索、接近、同步推送与恢复返航，视觉部分依托OpenART协处理器实现黄色边线定位、目标检测与标记球跟踪。
本篇报告分为六个章节：第一章阐述车模制作的整体思路；第二章介绍车模机械结构的调整与整体布局设计；第三章介绍主控板与驱动板的硬件方案与电路设计；第四章介绍车模运行的软件系统设计，涵盖系统总体架构、底层运动控制、双车协同任务状态机与视觉模型；第五章介绍调试过程中使用到的软硬件工具；第六章对车模的整体工作进行总结。


第二章 机械结构
蚂蚁搬家组别对车模的灵活性和轻量化有较高要求，对于两辆搬运车平均重量超过100g的部分进行罚时。为保证车模在搬运物体时有良好的稳定性和平顺性，需要车模具备合理的机械结构，否则在搬运过程中，容易出现物体丢失、车模频繁抖动等不良运行状态。
2.1 整车布局
根据车模设计要求，我们需要自制两辆搬运车模的底盘、推杆、主控板、驱动板，并给车模搭配必要的轮子、有刷电机、摄像头、摄像头杆、无线串口等部件。为了实现车模的轻量化，我们通过3D打印制作了底盘和推杆。车模的底盘除了预留的电机、主板安装孔位外，我们还进行了合理的镂空设计，尽可能减少车模的重量。同时，我们把主控板和两块驱动板合为一体，制成主驱一体板，极大地减小了PCB板的重量，增加了搬运车模整体的灵活性。车模在搬运物体的过程中，需要实现平面内任意方向平移及零半径旋转‌。因此，我们选用麦克纳姆轮作为搬运车模的轮子。此外，我们采用了自带编码器的有刷直流电机，以及逐飞OpenART Plus摄像头传感器电路板。
对于车模整体的安装，我们将麦轮与无刷电机通过刚性连接固定在一起，再使用尼龙螺栓和螺母，将四个电机固定在车模底盘上。使用尼龙和金属螺柱将主驱一体板、摄像头安装杆固定在底盘上，并将摄像头模块安装在推杆合适的高度，在保证车模灵活性的同时，减轻整车重量。
最终我们车模的整体尺寸为：主车（推杆上带有两个小球）车长为158mm（±5mm），车宽为104mm（±5mm），车高为183mm（±5mm）（连摄像头杆），推杆长度为95mm（±4mm）（水平横向长度），推杆高度为14mm（±5mm）（竖直高度）摄像头距离地面高度为142mm（±5mm）；从车（推杆上无小球）车长为157mm（±5mm），车宽为102mm（±5mm）车高为182mm（±5mm）（连摄像头杆）推杆长度为95mm（±4mm）（水平横向长度）推杆高度为14mm（±5mm）（竖直高度）摄像头距离地面高度为142mm（±5mm）。规则对于车模尺寸的限制为车长不超过300mm，车宽不超过300mm，车高不超过500mm，推杆长度不超过100mm，推杆高度不超过50mm。两辆搬运车的尺寸均符合规则要求。

2.2 电池固定
为追求整车的极致轻量化，我们未为电池设计独立的容纳仓体，而是充分利用车架现有结构进行紧凑固定。电池选用300mAh容量3s锂电池，通过安装在主驱一体板上的M3尼龙螺柱与摄像头安装杆之间的自然间隙实现定位。具体固定方式为：将电池自然倾斜放置，使其一侧紧贴尼龙螺柱，另一侧卡入摄像头杆与尼龙螺柱之间的空隙，借助尼龙螺柱的限位作用和摄像头杆的夹持力，确保电池在车模急加速、急停及转向时不会发生窜动或旋转。该方案既省去了额外的电池仓结构，又保证了电池在动态工况下的位置稳定性。此外，电池与主驱一体板之间单线接触，兼顾了散热与安全。图2.2清晰展示了电池的固定位置与约束关系。

图2.2 电池固定示意图
2.3 摄像固定
在双车协同搬运任务中，车模频繁经历急加速、急停及大角度转向等剧烈动运动，由此产生的机械振动极易传递至摄像头安装结构，导致摄像头的位置发生偏移。而摄像头的俯仰角、偏航角及滚转角的微小变化，都会影响逆透视变换的几何映射精度，进而造成物体识别置信度下降、位姿解算偏差累积以及从车跟随控制的精度下降等问题。为解决上述隐患，我们在完成摄像头逆透视变换矩阵标定后，使用高粘接强度的光固化胶，将摄像头模块与安装杆之间的接触面进行全覆盖涂覆并固化，保证在不损伤摄像头外壳的前提下，形成稳固的连接，消除相对运动间隙。

图2.3 摄像头固定示意图



第三章 硬件电路
车模安装有主驱一体板一块电路板，搭载一块RT1021DAG5x LQPF122 BTB最小系统核心板。硬件电路采用模块化设计，用以完成必要的电源输入、电源降压、设备通信、电机驱动、姿态结算、人机交互等各种功能。
3.1 最小系统核心板
主驱一体板使用一块逐飞科技RT1021DAG5x LQPF122 BTB最小系统核心板，主控芯片为MIMXRT1021DAG5X，为32位单核，主频最高可达500MHz。

图3.1 RT1021DAG5x最小系统核心板
3.2 电源模块
车模使用300mAh容量3s锂电池供电，该电池输出电压为12V，为了使电路板各个模块供电正常，需要对电池电压进行5V、3.3V两级降压。同时，为了保证5V上电时序，让核心板先上电，增加了一个功率电子开关。
3.2.1 5V稳压
使用降压芯片TPS82130SILR将电池12V电压降为5V，且在主板上布置有一个5V稳压模块。一方面为核心板模块供电，另一方面输入后级3V3降压模块，以及5V功率电子开关。
在方案选型上，我们优先采用DC-DC降压转换器而不是LDO：因为LDO在12V-5V的大压差下，功耗极高（），当负载电流达1A时功耗达到7W，不仅严重浪费电能，而且在工作过程中会产生大量的热量，在紧凑的PCB布局中，容易造成过热风险；而DC-DC转换效率可达90%以上，具有低发热、长续航的优势，更加契合车模对电源系统高效、稳定的严格要求。
在众多DC-DC方案中，我们选定TPS82130SILR集成电源模块。因为该芯片将功率电感与同步降压转换器封装在3mm × 2.8mm × 1.5mm 的超小型MicroSiP内，极大地减少了外围分立元件数量，简化PCB布局，节约大量主驱一体板的空间，契合车模轻量化的设计要求。该模块输出5V后，为高精度的核心板直接供电，并供给后级3.3V LDO及5V功率电子开关，构成简洁可靠的多级电源分配网络。

图3.2 5V稳压电路
3.2.2 3V3稳压
5V电源需进一步降压至3.3V，为IMU惯性传感器、IPS显示屏、电机编码器等外设供电。在3.3V稳压方案选型上，我们选用低压差线性稳压器LDO，因为5V至3.3V的压差仅为1.7V，LDO在此工况下的功耗（）远小于12V至5V的大压差场景，效率损失在可接受的范围内。并且IMU等传感器对电源噪声高度敏感，DC-DC开关噪声极高，容易耦合到传感器输出，影响位姿解算精度，而LDO具备极高的电源纹波抑制比，为敏感负载提供纯净的供电。此外，LDO外围电路极为简洁——仅需输入输出各一颗小容量陶瓷电容即可稳定工作，无需电感等磁性元件，既节省PCB面积，又避免额外的高度空间。
图3.3 3V3稳压电路

3.2.3 5V上电时序开关
此外，我们采用SY6280AAC 5V功率电子开关，由MCU EN使能控制，保证了核心板先上电、外设后上电的时序要求，确保核心板安全启动。

3.3外设
外设部分，我们使用了按键、拨码开关、轻触开关、蜂鸣器、ips屏幕实现人机交互；使用openart接口、无线串口实现上下位机、搬运车之间的通信；以及使用LSM6DSRTR姿态传感器解算三轴加速度以及车模位姿。
3.3.1 人机交互
为了实现便捷的调试与现场发车控制，车模配备了一套完整的人机交互接口。主驱一体板上集成了独立按键、拨码开关、轻触开关以及无源蜂鸣器，配合IPS屏幕，可以实现状态提示、故障报警，并实时显示车模运行状态、关键控制参数、调试数据，实现脱机状态下的调试，避免调车过程中频繁连接电脑。
图3.5 人机交互部分
3.3.2 通信部分
车模的通信部分通过OpenART Plus 视觉模块与无线串口模块构建。OpenART Plus 作为独立的视觉协处理器，负责目标物识别等视觉任务，识别结果通过串口通信实时发送至主控，有效分担了主控的算力压力，实现高效的上下位机协同。同时，两辆搬运车各配备一个逐飞科技无线串口V2.4模块，实现双车之间的实时状态数据交互与指令下发，确保协同搬运过程中的动作同步与精准配合。
图3.6 通信部分
3.3.3 传感器部分
车模的运动控制与位姿估计依赖于高精度、高更新率的传感数据，主要包括姿态传感器与轮速编码器两部分。
姿态传感器选用LSM6DSRTR六轴惯性传感器用于实时解算车模的俯仰、横滚、偏航角以及三轴加速度信息，为闭环控制提供可靠的位姿反馈与运动状态参考。轮速感知方面，车模搭载的四个直流有刷电机均自带霍尔编码器，输出正交编码信号，主控实时解算各轮转速与转向，为车速闭环控制提供精准的转速反馈数据。姿态数据与轮速数据经主控融合处理后，共同构成车模运动控制的全状态反馈闭环。
图3.7 传感器部分

3.4有刷驱动
我们的搬运车使用四个自带霍尔编码器的直流有刷电机作为动力来源。为了满足在搬运过程中急加速、急停及频繁换向时对瞬态大电流的需求，我们舍弃了集成度高但输出电流受限的一体式驱动芯片DRV8848，选用了基于DRV8701E栅极驱动器配合分立式N沟道MOSFET的全桥驱动方案。该方案由预驱电路、H桥功率电路两部分组成。
3.4.1 预驱电路
驱动核心选用德州仪器DRV8701E栅极驱动芯片，主控输出的PWM信号连接至EN引脚，通过调节占空比实现电机转速的精准控制；通过电平控制PH引脚，切换H桥输出极性改变电机旋转方向；nSLEEP引脚由使能开关控制。在EN与PH控制线上各并联了10kΩ下拉电阻，确保核心板刚上电时，电机不会因干扰信号误动作，提高了系统安全性。
3.4.2 H桥功率输出电路
功率输出级采用四颗AO3400A N沟道MOSFET搭建全桥电路。电机两极直接连接L_F_A与L_F_B两端，通过预驱芯片控制对角线上的MOSFET交替导通，完成大电流功率输出。

第四章 软件系统设计
4.1 软件系统设计概述
4.1.1 竞赛背景与任务概述
全国大学生智能汽车竞赛是以智能汽车为载体的综合科技竞赛，参赛队伍需要在统一规则下自行设计车模的感知、决策与控制软件，并在规定场地内完成既定任务。本报告对应第二十一届竞赛中的双车协同类组别：系统由两辆全向移动平台组成，分别称为主车与从车，两车通过无线链路交换状态并协同完成同一项搬运任务。
按照任务要求，场地中央散布若干待搬运货物，货物类别包括网球、沙包与玩偶，其中沙包又分为蓝、红两种颜色，玩偶又分为白、棕两种颜色；场地四条边线之外是合法的推出区域。两车需要在不互相碰撞、不破坏货物的前提下，先搜索并识别目标货物，再以“V 字夹持”的编队姿态贴住货物两侧，最后同步将货物推出指定边线。每完成一件货物后，两车需要撤离边线、恢复队形并开始下一轮搜索，直到全部货物搬运完成并返回结束区域。
这一任务对软件提出了三方面要求。其一是实时控制：全向底盘、航向闭环与货物贴合控制都运行在毫秒级周期上，任何抖动或迟滞都会直接表现为货物被顶跑或队形被破坏。其二是多源信息融合：系统同时使用摄像头、惯性测量单元、四轮编码器与无线镜像四类信息，必须明确每一类信息的可信范围与失效时的降级路径。其三是双车协同：两车没有全局集中式调度，只能通过带宽有限的半双工无线链路同步目标、站位与命令，因此任务层需要一套“主车决策、从车跟随、双向确认”的协同协议。
4.1.2 系统技术路线概述
本系统的软件主体运行在两台以 RT1021 为核心的主控板上，采用 MicroPython 编写并以字节码编译后烧录；两车各配一块 OpenART 摄像头模块，负责黄色边线定位、目标检测与标记球跟踪。软件按照“底层运行时—任务状态机—视觉感知”三层组织：底层运行时封装传感器、执行器、姿态解算、里程计与通信协议，对上提供统一的运动请求接口；任务状态机在每辆车上维护一份主从共用的大状态机，主车负责搜索、选目标、规划站位与推送决策，从车负责编队跟随、V 字贴靠与协同推送；视觉层独立运行在 OpenART 上，通过串口帧向下位机发布边线位姿与目标列表。
在定位方面，系统以四轮编码器里程计提供连续位置，以惯性测量单元的四元数互补滤波提供连续航向，并在特定状态下用黄色边线给出的绝对位置与绝对航向对里程计进行门控修正。在感知方面，OpenART 使用量化后的轻量目标检测模型识别货物、对方车辆与障碍物，再结合框内颜色统计把沙包与玩偶细分为具体类别，同时用色块加 α-β 跟踪的方式稳定跟踪主车推杆上的标记球。在协同方面，双车之间以固定帧格式、带 CRC 校验的主从问答方式同步位姿、目标、模式与命令，所有跨车命令都设置新鲜度超时，链路短时中断时系统优先停车或回退而不是沿旧命令继续运动。

4.2 系统总体设计
4.2.1 总体架构与软件分层
系统按功能划分为三个层次，如图4.1所示。最上层是运行在 OpenART 上的视觉感知层，它通过 UART 串口与主控交换数据；中间是运行在 RT1021 上的任务决策层，对应主车与从车两个角色文件；最下层是底层运行时，所有任务层代码都通过它访问硬件。

图4.1 系统总体分层架构
三个层次之间只通过少量明确接口交互，这是整个工程最重要的结构约束。任务层从不直接写电机，而是调用 request_world、request_pos、request_hold、request_push、request_yaw_rate 等请求，把“想做什么”交给底层；底层也不替任务层做决策，无线接收到的对方状态只镜像到 _Other_* 变量，由任务层决定是否采用。视觉层同样只负责“看见什么”，目标选择、站位规划与推送判断全部留在任务层。这种边界让三个层次可以分别调试：底层可以在台架上单独验证运动学与控制闭环，任务层可以用回放数据验证状态切换，视觉层可以单机验证检测与定位。
4.2.2 平台资源与软件视角
从软件角度，系统可用的资源可以归纳为四类。第一类是运动执行与反馈：四个带编码器的驱动轮以 13 kHz 的 PWM 驱动，四路编码器以硬件捕获方式提供增量读数。第二类是姿态与位置感知：六轴惯性测量单元提供角速度与加速度，配合四轮里程计构成连续定位；摄像头提供绝对位置与绝对航向的间歇修正。第三类是通信：一条串口连接本车 OpenART，一条半双工无线串口连接对车。第四类是调试资源：LCD、蜂鸣器与串口打印，用于显示状态、提示事件与诊断异常。
主从两车烧录的是同一份 base.py，差异只由编译期的角色配置决定；task_leader.py 与 task_follow.py 则分别实现两车的任务逻辑。构建脚本用附带的交叉编译工具把根目录源码编译为主从两套烧录目录，并把任务文件统一命名为 task.mpy，因此底层固定以 import task 的方式装载任务层。这一构建方式保证了主从代码共享底层时不会出现接口漂移，代价是任何对共享协议的修改都必须同时检查两端。

4.2.4 任务状态机总览
主从车使用同一套大状态编号，状态切换由各自任务文件中的 update() 分发、enter_mode() 清理。主流程为：开机同步、搜索、接近、就位确认、同步推送、撤离恢复，若还有剩余目标则回到搜索；全部完成后进入全局重定位并返回结束点，如图4.2所示。

图4.2 双车任务主状态机
状态机并不是严格的单向链表。目标长时间丢失、对方回到搜索状态、站位不合格或路径被挡时，系统会从接近、就位确认或推送状态回退到重新靠近甚至重新搜索。因此每个状态的入口都要求“完整重置”，出口都要求“清理目标与命令”，这是阅读与维护这套状态机时的基本准则。

4.2.6 构建、烧录与验证流程
可复现性是本工程的重要目标。源码修改后运行构建脚本，脚本先把 config.py 的角色标志改为从车、临时把 task_follow.py 改名为 task.py 并编译出从车目录，再以同样方式生成主车目录，最后恢复根目录文件。OpenART 脚本不属于该构建范围，需要单独烧录，并与其 SD 卡中的模型文件配套。
由于桌面环境无法完整运行硬件代码，工程约定了一套分层验证清单：先做语法与常量定义顺序检查，再验证构建产物与角色配置，随后在台架上依次验证通信时间戳、轮向与坐标方向、异常停车、主从静态握手，最后分状态低速测试再到完整任务测试。此外，工程内部文档明确警告“参数漂移”风险：注释与旧说明中的数值可能已过时，调参与排错必须追到实际调用点。本报告所有行为描述均以当前源码为准。
4.2.7 调试与诊断手段
软件在运行期提供三类自检信息：LCD 状态页显示本车与对方模式、位置、融合航向与最近视觉航向、链路字节数与帧间隔，从车还显示左右标记球的实测与参考坐标，供手动摆 V 形时读数回填标定；蜂鸣提示用不同响数区分视觉修正、斜推、路线重就位、锥桶绕行与异常停车，现场无需看屏即可判断所处流程；串口与异常记录在任务层抛错时停车、报警并在 LCD 显示错误类型、限频打印详情。此外，工程内置里程计标定模式，与球坐标读数、就位位置自学习共同构成不依赖桌面仿真的现场标定工具链。调试开关集中在独立配置文件中，比赛前应逐项确认关闭。
4.3 底层运行时与运动控制
4.3.1 启动链与实时调度
板端入口 main.py 只有两行：调用 base.main_init() 完成初始化，随后进入 base.loop() 主循环。初始化依次完成硬件初始化、全局状态初始化、基础控制参数应用与定时器启动；主循环每周期依次执行蜂鸣器更新、通信发送、任务状态机更新、LCD 刷新与垃圾回收，并捕获任务层抛出的任何异常，异常时先停车、报警并在 LCD 显示错误类型，保证主循环永不退出。
实时任务由三个周期中断承担，如图4.4所示。PIT1 以 1 ms 为基准，通过分频调度角度环、运动状态机、角速度环、位置环与电机环；PIT2 以 10 ms 周期完成惯性测量单元姿态更新、编码器读取、视觉修正融合与里程计积分；PIT3 以 3 ms 周期处理无线收发的完整时序，并把摄像头串口解析分频到约 9 ms 一次。控制环频率沿“位置环—角度环—角速度环—电机环”逐级提高，越靠近执行器的环越快，避免外环指令在低速内环中产生相位滞后。

图4.4 实时调度与分频
定时器回调被严格限制为轻量操作：打印、大对象分配与视觉类计算都留在主循环。通信中断内直接完成无线“接收—调度—发送”闭环，把半双工链路的转向时间压缩到中断周期量级，这是双车同步延迟控制的关键设计。

4.4 双车协同任务状态机
4.4.1 大状态机与模式切换
主从车的任务层以“模块级状态加每周期更新函数”的方式实现。每辆车的 update() 按当前大状态编号分发到对应的更新函数，更新函数可以置位 _next_task_mode，主循环在本次分发结束后统一执行 enter_mode 完成模式切换。模式切换统一负责三件事：调用目标状态的重置函数、按新模式改写 OpenART 的识别开关、清理可能残留的旧目标与协同命令。把“请求切换”与“执行切换”分开，可以保证一个周期内只发生一次状态跃迁，避免状态清理与状态运行互相穿插。
主从车共享同一套大状态编号，但同一编号下两车的职责并不相同：主车负责决策，从车负责跟随与配合。以搜索为例，主车执行蛇形扫描并锁定目标，从车则把主车当作圆心编队跟随，自己不读取任何场上目标；主车锁定目标并通过无线帧发布后，从车只复制该目标并进入接近流程。这种“一个决策者、一个执行者”的划分贯穿全部状态，后面各节将逐状态展开。

4.4.2 BOOT_SYNC 开机同步
开机同步要解决的第一个问题是链路就绪：两车先确认摄像头帧与无线帧都已到达，分别用不同时长的蜂鸣提示。主车确认从车在线后，持续下发启动命令；两车随后都以固定航向 90°、固定世界速度沿 +Y 方向做纯横移，各自以本车里程计的 Y 向增量判断完成，主车与从车的横移距离分开配置以拉开横向站位。这段横移完全开环、不依赖视觉，因此里程计标定的精度会直接体现为两车起始间距的偏差。
主车完成横移后立即进入搜索；从车完成自己的横移后才进入搜索。从车若漏收最初的启动命令，允许由主车的搜索模式或补发的搜索信号兜底触发横移，但本车距离条件不可跳过。主车在首次搜索入口还会执行一次固定方向的斜移，斜移期间允许识别并锁定目标，看到有效目标即可不停车切入接近流程。同步期间主车暂不锁定目标、也不做黄线补坐标，防止边线流程打断两车建立握手。
4.4.3 SEARCH 搜索与编队
主车蛇形扫描
主车搜索采用“正交车头下的蛇形轨迹”：车头锁定为 0°、90°、180°、270° 之一，先以恒定速度做无前向偏置的纯横移，到搜索区边界后立即沿车头方向前进固定步长，再反向横移，两个动作之间不停车。前进轴剩余距离不足时只走到搜索区尽头，之后在最后一行反复横扫，直到锁定目标或搜索超时。首轮搜索点与初始航向由配置给出，后续搜索的航向取上一次推送方向的反方向，并按刚推出的边线确定下一条搜索线的起点坐标，从而让每一轮搜索都从刚离开的边界附近开始、朝场内推进，如图4.8所示。

蛇形扫描期间还运行两项辅助逻辑。第一项是黄线补坐标：当画面中出现靠近中心、且与当前横扫方向同侧的黄色边线框时，主车停车、转向边线方向、打开对应轴的视觉位置修正，取到可信修正后转回原航向并继续搜索；该流程每次进入搜索最多触发一次，修正后强制下一段横扫方向朝场内，防止车体继续向场外行驶。第二项是障碍斥力：主车维护最近看到的锥桶与砖块坐标，距离小于触发阈值时，按与距离成线性反比的关系向“下一段蛇形运动方向”叠加附加速度，横扫时推向下一换行方向，换行时推向下一反向横扫方向。斥力只使用本车视觉，不进入绕行子状态，保证扫描节奏不被单次避障打断。
黄线补坐标是一个由六个子状态组成的短流程：停车、转向边线、位置修正、转回。触发条件采用带迟滞的锁存——黄线框中心的像素位置越过触发门限且与横扫方向同侧时锁存方向，越过更大的释放门限才解除，避免边线在画面边缘反复进出导致流程抖动；触发条件还要求边线连续出现多帧。转向边线后只打开横扫轴对应的视觉修正，取到的修正值必须落在“预期边界附近”的窗口内才计为有效；若修正超时仍未取得有效值，仍可按“看到的边线即一条确定边界坐标”强制提交一次单轴修正，保证流程不因视觉偶尔丢帧而卡死。整个流程每次进入搜索最多执行一次，物体确认的优先级高于黄线流程，正在确认目标时不允许边线流程抢占。

站位规划按“两候选角相对主车当前朝向的位置关系”分情形处理。若两个候选角落在主车当前朝向的两侧，主车取角差绝对值较大的一侧、从车取另一侧，绕行方向相反；若两个候选角落在同一侧，两车绕行方向相同以避免对穿，并比较两条路径的带符号角距分配左右槽位；若某个候选角恰好与当前朝向重合，按角差大小分配。无论哪种情形，主车始终选离自己更近的槽位，从车通过无线收到互补槽位与绕行方向，命令序号作为本轮规划版本号，从车只在规划版本变化时重建自己的规划，旧版本残留的槽位与方向不会混入新规划。
面向与预绕行
面向子状态用视觉方位误差驱动车头，同时用横向比例控制把货物拉回画面中线、用径向比例控制把前后距离收敛到环绕半径附近，两个门限同时满足后进入绕行，不再停车保持。预绕行用于绕障重靠近等特殊入口，它先建立环绕锚点，再沿“车指向货物”的单位向量反方向以径向比例控制贴到环绕半径，同时保持朝向误差，进入捕获范围后立即交给绕行。目标短暂丢失时，任务层优先按最近一次可信的世界坐标转回朝向；绕行期间则使用锚点坐标继续闭环，锚点以缓慢的融合比例跟随视觉坐标、并限制每帧移动量，防止视觉抖动让环绕圆心跳变。

主车贴近与从车 V 字贴靠

4.4.5 WAIT_READY 就位确认与路线避障
两车完成各自贴靠后进入就位确认，互报 ready 并保持当前航向。该阶段逐周期校验三类条件：本车是否仍看到目标且相对位置仍在可开始推送的范围内；对方模式与 ready 是否匹配且无线时间戳足够新鲜；推送走廊是否需要绕障处理。目标姿态长时间变差时触发一次只重做最后贴靠的重新接近，而不是重跑整个环绕，避免无谓的耗时。
主车在确认可推送前先检查目标正前方的推送走廊：把其他未完成货物的世界坐标投影到“沿推送方向”与“垂直推送方向”两个轴上，落入前方规定距离且横向在规定半宽内的货物视为挡路。存在挡路时，主车计算一个清障轴坐标——绕到挡路货物所在横向位置再向外留出安全余量——并生成“先横向带离、再恢复阵列”的路线命令。两车先退回接近状态沿清障方向重新形成侧向站位，把目标侧向带出障碍区，到达后再恢复为正常推送方向的站位。这一流程把“发现挡路”与“执行绕障”拆在就位确认与接近两个状态之间，通过路线阶段号与无线命令协调。
4.4.6 PUSH_SYNC 同步推送
起步同步与推送闭环
就位确认通过后进入同步推送。起步采用“命令先发、本体后动”的对齐方式：主车把 ready 置为推送准备状态并即时触发一次无线发送，从车收到后立即进入推送，主车再延迟一个补偿时间起步，用提前量抵消无线传播与循环调度延迟，使两车起步尽量对齐。推送过程中主车以固定标称速度为基础，从车使用相同标称速度，两车各自用货物环贴住货物，而不是让从车开环复制主车速度——复制会把主车的抖动延迟一个无线周期再复现到从车上，双固定标称加各自闭环反而更稳。
推送控制即4.3.6节介绍的专用控制器：货物横向误差走车体横移轴、前后误差走推送轴，从车再叠加标记球开合通道。主车在推送中还维护世界系横向保持，以起推时刻的横向坐标为参考，抑制长距离推送时的横向漂移；该保持只作用于垂直于推送方向的世界轴。
丢目标恢复
目标视觉在推送中连续丢失超过确认时间后，两车进入原地旋转搜索：以固定角速度绕一整圈扫视，任一车重新看到目标即互报“已找到”并停车保持，双方都找到后回到接近流程重新组织队形；超时仍无法恢复则清目标回搜索，流程如图4.13所示。从车不根据自己的视觉丢失独立决定旋转，而是跟随主车的旋转子状态同步进入，避免两车在丢目标判断上不同步。对方在推送中掉线超过确认时间同样触发中止并回接近，链路异常时绝不允许单边继续推送。

图4.13 推送丢目标恢复流程
旋转搜索的目标航向按经过时间线性推进一整圈，接近目标角时保持一个最小角差避免原地抖动；恢复判定要求双方都确认“已找到”才离开旋转，一方找到而另一方未找到时先停车等待，超过等待时间仍无法同步则回搜索。网球类货物在普通推送中放宽了丢失判定，因为其高亮度外形使其在贴近时容易出现短暂的目标框丢失，若按普通门限处理会频繁触发无谓的旋转。
斜推避障与完成判定
推送中若检测到目标两侧走廊被锥桶、砖块或未完成货物单侧占用，主车生成一个带侧向偏置的斜推方向：以基础推送方向为基准向障碍反侧偏转一个固定角度，先广播斜推命令再延迟补偿时间执行，横向位移达到清空间距或超时后，先广播退出命令再恢复普通推送。障碍侧向判定必须来自两个不同时间戳的新观测，用时间戳去重防止同一相机帧被主循环重复处理时被误当成连续两帧。完成判定不只看里程计：先要求对应轴收到过新的视觉修正，再要求本车越过对应场地边界加安全余量，双重条件防止编码器漂移导致提前误判推出。
4.4.7 RECOVER 撤离恢复
推出完成后两车进入撤离恢复。主车先沿车体后方退出目标区域，再根据刚推出的边线选择修正轴：沿 +Y 推出的边用 Y 轴修正、沿 X 推出的边用 X 轴修正。修正时锁住正交航向、沿目标轴前进并打开对应轴的视觉修正，取到落在预期边界附近的修正值后停止；随后离边足够远时进入视觉航向精调：以固定角速度向正交航向旋转，视觉航向误差进入死区并稳定后一次性调用航向校准，再静止等待从车进入实际跟随阶段。视觉航向在这里只用于判断旋转方向，旋转速度始终固定，避免视觉抖动直接放大成角速度抖动。
从车恢复更简单：后退后转到下一搜索过渡航向，同时挂起一次“看到主车后反算自身坐标”的强制修正。恢复结束若还有剩余目标则回搜索，否则进入全局重定位。主车在等待从车跟随时用对方上报的子状态判断其是否已进入平移编队，避免主车抢先开跑而把从车甩下。
4.4.8 RELOCALIZE 全局重定位与 DONE
全部货物完成后，两车做收尾定位。主车先转到 270° 航向、移动到重定位起点，随后不停车地沿低 X 方向前进并打开 X 轴视觉修正，取到可信的低 X 修正后转到 180° 沿低 Y 方向前进并做 Y 轴修正，最后进入结束状态。两条修正轴的驱动都保持恒定速度，视觉值只做“是否落在预期边界附近”的判定，不做位置闭环，这与恢复阶段的设计一致。从车先按无线跟随主车避免碰撞，再完成自己的定位。
结束状态中两车各自回到配置的结束点，主车到点停稳后原地自转一圈作为任务完成的标志，随后保持不动。至此一轮完整任务结束：从开机同步、搜索、接近、推送、恢复，到重定位与返航，状态机在所有异常分支上都提供了回退路径，任何环节的失效都不会让车辆沿陈旧命令继续运动。
4.4.9 协同规划与安全性小结
回顾整条状态链，安全性由三层机制共同保证。第一层是新鲜度：所有跨车数据都带时间戳，命令类字段超过 1 s 未更新即被清除，对方状态过期就停车或回退。第二层是确认与防抖：目标锁定、障碍侧向、贴靠完成、推送完成都要求连续多帧或多个新观测，单帧抖动不触发状态切换。第三层是几何安全：绕行时检查两车间隔角，编队时检查主车是否在前方，推送时两侧障碍才退出、单侧障碍才斜推。这三层机制彼此独立，任何一层单独失效都不会直接导致危险动作。

4.4.10 状态机实现的工程模式
两车任务文件各数千行，其可维护性依赖若干条被严格遵循的工程模式，这些模式虽然不是算法，却决定了整套状态机在长时间运行中的行为边界。第一是入口重置、出口清理：每个状态的重置函数把计时器、计数器、历史误差与子状态全部归位，每次退出都清空目标与协同命令，避免上一轮状态的残留污染下一轮。第二是时间统一走环形差分：所有时长判断使用环形时钟差函数而不是直接相减，时钟回绕不会造成计时异常。第三是哨兵值显式恢复：无效坐标、无效角度、无命令统一用 999 附近的数值表示，有效性判断以 900 为界，状态重置时必须把相关字段写回哨兵。第四是对方数据只读镜像：底层只把无线帧写入 _Other_* 变量，任务层决定是否采用，跨车命令一律带新鲜度检查。第五是常量定义顺序：MicroPython 的下划线常量是编译期常量，必须先于首次引用定义，否则在交叉编译后变成运行期未定义变量，这是工程内反复踩过的一类坑。
主从任务文件存在大量结构相似但参数不同的镜像逻辑，修改共同行为时必须同步检查另一角色。这一成本换来的是两车行为的高度对称：任何协同流程在主从两侧都有明确对称的入口、退出与超时路径，调试时只需要对照两侧同一状态即可定位差异。

4.5.5 目标跟踪、选择与观察窗

4.5.8 双车协同的时序预算
汇总前几节的延迟项：下位机以约 9 ms 节拍解析摄像头帧；无线主车发起、从车延迟 5 ms 应答、主车 60 ms 超时；通信中断把半双工的“接收—调度—发送”压缩在 3 ms 节拍内；时序敏感事件经“即时发送”通道把跨车传播延迟压到“最多一个中断周期”，并以“命令先发、本体延迟补偿再动”对齐两车动作。这些预算决定了上层状态机的设计：任何跨车确认都不假设对方本周期响应，而是用新鲜度门限加等待时间的异步模式；本车动作不依赖对方动作的精确时刻，只依赖双方共享的命令版本号与 ready 状态。状态机中大量“连续多帧确认”与“超时回退”，正是异步链路下保证安全性的必要代价。

4.6.3 标签编码与样本分配
训练标签来自“图像路径加框列表”的文本索引，每行以分隔符连接图像路径与若干“左上右下坐标加类别号”的框。数据管线先把框坐标转换为中心点与宽高，再除以输入尺寸归一化。编码阶段为每个真实框选择一个负责的先验框：计算真实框与所有先验框的交并比，取交并比最大的那个；该真实框随后被写入其中心点所在网格的对应先验通道，目标置信度置 1、对应类别置 1，其余通道保持为零。这样每个目标只有一个先验框负责，正样本数量被严格控制，而所有其他位置默认是负样本候选。
负样本并非全部参与置信度损失，而是引入忽略掩码：每个预测框与同批次所有真实框计算最大交并比，低于忽略阈值的预测框才计入“无目标”损失，高于阈值但不负责该目标的框被忽略。忽略掩码的作用是避免把“与真实框高度重叠但未获分配的预测”当作硬负样本惩罚，从而抑制同一个目标被重复检出。

其中  为量化步长、 为零点。量化器开启默认优化并限制为 TFLite 内置算子，输入输出也量化为 8 位。代表性数据从训练管线中采样，与训练同分布，保证激活范围统计具有代表性。定点量化在边缘设备上同时降低存储、内存带宽与推理时间，代价是引入少量量化误差，需要靠代表性的校准数据控制。
导出后还有一个关键步骤：把“解码、分数阈值、非极大值抑制”整段后处理追加为模型图内节点。普通导出的输出是原始回归张量，下位机自行实现解码与 NMS 需要跨端重复维护参数化逻辑；并入模型后，输出直接就是按类别非极大值抑制过的“框、分数、类别”列表。非极大值抑制以分数降序贪心保留与已选框交并比低于阈值的框并限制最大框数；并入的节点还包含解码，原始输出按4.6.1节的 sigmoid 与指数公式换算成绝对坐标，部署端无需再做网格算术。两个模型文件由此区分：一个保留原始输出用于调试，一个带后处理用于部署。后处理节点由平台相关的动态库在导出时注入，参数来自与训练同一份配置，保证训练与部署的类别、阈值、最大框数一致。
导出后还有一个关键步骤：把“解码、分数阈值、非极大值抑制”这一整段后处理追加为模型图内节点。普通导出模型的输出是原始回归张量，下位机若自行实现解码与 NMS，需要跨端重复维护参数化逻辑；把后处理并入模型后，模型输出直接就是按类别非极大值抑制过的“框、分数、类别”列表，OpenART 端调用一次推理即可得到可用结果。非极大值抑制以类别分数排序，贪心保留与已选框交并比低于阈值的框，并限制最大输出框数。两个模型文件由此形成区分：一个保留原始输出用于中间调试，一个带后处理用于实际部署。
4.6.8 部署接口与一致性检查
部署端在推理前对图像做等比缩放加填充的 letterbox，再按同样的比例与偏移把输出框反算回原始像素，其处理必须与训练管线的坐标映射一一对应，否则框会整体错位。训练配置的输入尺寸与部署端 letterbox 尺寸必须一致：当前仓库中的导出模型输入为 128×128，而 OpenART 部署脚本中的模型输入常量仍为 96×96，两者存在配置漂移，重新部署前必须先对齐输入尺寸与对应先验框，这是“训练结果可复现到车上”的第一道检查。模型类别顺序、颜色细分阈值、单应矩阵角色与输出阈值同属跨端约定，任一改动都要在训练、导出与 OpenART 三处同步。
letterbox 的反算与训练端同构：模型框坐标先乘以模型输入尺寸、减去填充偏移、除以缩放系数，得到原图像素坐标，再做边界钳位：

4.6.9 训练过程的监控与收敛判据
训练过程的控制依据全部来自验证集损失这一单一观测量，检查点、学习率衰减与提前停止三个回调都围绕它展开：验证损失改善才保存权重，连续多轮不降时学习率降为原来的十分之一，长时间无改善则提前停止。张量板日志记录训练与验证损失曲线、学习率变化与各损失分量，用于判断当前主导误差来自定位、置信度还是分类。监控中要区分两类“不收敛”：损失振荡但总体下降通常意味着学习率偏大或增强过强，应依靠衰减回调而非人工干预；损失走平而验证损失回升是过拟合信号，此时保存的最佳权重才是有价值的产物。由于任务是稳定的小类别检测，最终模型不以绝对精度数字为唯一验收标准，而以“在车上给定阈值下目标稳定、误检可控”为验收口径。
4.7 软件设计总结与展望
4.7.1 工作总结
本报告完整梳理了双车协同搬运系统的软件实现。系统的核心可以概括为“一个分层边界、一套状态机、三条通信链路、四级控制级联”。分层边界让视觉、决策与执行各自独立演进；主从共用的大状态机把开机、搜索、接近、推送、恢复与重定位组织成一条带完整回退路径的闭环；三条通信链路以统一帧格式与 CRC 校验承载视觉与协同数据；四级控制级联把任务层的运动意图最终落实到四个轮子上。
从实现细节看，系统的稳健性主要来自几个反复出现的设计原则。其一是数据源与信任边界显式分离：视觉位置是否生效由阶段开关决定，视觉航向加门限，无线镜像只读不代决策，每条失效路径都有明确降级顺序。其二是确认与防抖前置：目标、障碍、就位与完成判定都要求连续多帧，单帧抖动不产生状态跃迁。其三是双通道解耦：V 字贴靠把推送轴与张开轴分开控制，推送控制把货物横向与前后分开控制，从车编队把切向绕行与径向修正分开控制，每个物理自由度都有且仅有一个主导约束，从根本上避免了多约束争抢同一自由度导致的极限环。
在视觉模型方面，系统用精简的 MobileNetV2 主干加单检测头在边缘设备上实现了六类目标的实时检测，配合先验框聚类、交并比损失、在线增强与训练后定点量化，把完整的训练、导出与部署链闭合起来，并将解码与非极大值抑制并入模型图以简化部署端。
4.7.2 存在的问题与改进方向
当前实现仍有一些可以改进的地方。第一，训练配置与部署配置之间存在漂移，例如模型输入尺寸与先验框需要随训练结果重新对齐，这类跨端约定应当纳入构建脚本做自动校验，而不是依赖人工核对。第二，两车航向依靠各自惯性测量单元独立积分，差分漂移会缓慢改变 V 字几何，目前依靠每个货物周期在就位时用物体与球的实测值重新校准来抑制，若进一步利用标记球之间的固定间距做实时观测，可以把漂移修正做得更连续。第三，搜索与推送中的锥桶避障目前主要依赖几何预测与斥力，缺乏对障碍未来位置的显式推理，在面对移动障碍时仍有优化空间。第四，大量控制参数分散在两个任务文件的常量区，主从镜像逻辑存在重复，后续可以引入统一的参数校验与跨角色差异审计，降低误改风险。第五，视觉模型仍以单尺度和固定输入处理所有目标，小目标与远距离目标的分辨率受限，后续可评估多尺度特征或更高分辨率的轻量结构在边缘设备上的收益。
总体而言，本系统已经具备从搜索、协同接近、同步推送到恢复返航的完整闭环能力，其设计经验——尤其是多源信息信任管理、双车同步时序与多自由度解耦控制——对同类双车协同任务具有直接的借鉴意义。
4.7.3 可复现流程
为使本报告描述的实现能够被完整复现，软件侧的流程可以归纳为两条独立又相互衔接的链。车上软件链：在源码根目录运行构建脚本，脚本按“从车后主车”的顺序生成两套烧录目录，任务文件被统一编译为 task.mpy，根目录角色配置与两个输出目录需要逐项核对；OpenART 脚本单独烧录，并确认其角色编号、单应矩阵、模型路径与 SD 卡中的模型文件配套。上电后按工程约定的验证清单依次确认：主从链接时间戳持续更新、轮向与坐标方向正确、异常停车有效、主从模式与 ready 状态互镜像，再分状态低速测试到完整任务。
视觉模型链：准备索引格式的训练与验证文本，运行锚点聚类得到先验框，核对配置中先验框数量与检测头数量的校验，随后启动训练；训练输出最佳权重后重新加载到推理模型，经代表性数据集量化导出原始 tflite，再调用后处理注入工具得到部署模型。部署前必须把训练配置的输入尺寸与部署脚本的 letterbox 尺寸对齐，并核对类别顺序与阈值。两条链的交汇点是 Frame1 与 Frame2 协议：任何类别、槽位、精度的改动都要在训练脚本、导出脚本与 OpenART 脚本三处同步。
本报告正文给出的全部公式都对应源码中的实际计算路径，读者可以按章节编号在 base.py、task_leader.py、task_follow.py、openart.py 与训练目录的对应函数中定位。需要强调的是，工程内部的历史说明文档与源码之间存在已知的参数漂移，复现与排错时应始终以当前源码为最终依据。

第六章 总结
本文针对“蚂蚁搬家”组别，完成了两辆搬运车模的设计与制作。机械方面，采用3D打印轻量化底盘与麦克纳姆轮全向布局，并将主控与驱动集成为主驱一体板，在减轻重量的同时保证了车模的灵活性与稳定性；硬件方面，以RT1021DAG5x微控制器为核心，设计了12V至5V、3.3V两级降压电源与基于DRV8701E的分立MOSFET全桥驱动电路，配合LSM6DSRTR姿态传感器、OpenART视觉模块与无线串口，构成完整的人机交互与双车通信链路。
软件方面，系统采用“底层运行时—任务状态机—视觉感知”的分层架构，底层实现了四元数互补滤波姿态解算、编码器里程计融合、四级控制级联与麦轮逆运动学控制；任务层由主从两车共享的大状态机驱动，通过半双工无线链路协同完成开机同步、搜索编队、接近站位、同步推送与恢复返航的完整闭环；视觉层依托OpenART完成黄色边线定位、目标检测与标记球跟踪，检测模型采用轻量MobileNetV2主干并经INT8量化后部署。
在制作与调试过程中，我们经历了主驱一体板焊接失败、机械结构出问题的反复挫折，也经历了在非常炎热的场地中调试的痛苦，通过不断学习与迭代，最终使车模能够在规定场地内稳定、快速地完成搬运任务。这一过程既锻炼了我们的工程实践能力，也让我们深刻体会到团队协作与求真务实的重要性。

        base._vis_yaw_fix_en = False
        base._vis_x_fix_en = False
        base._vis_y_fix_en = False
        base.request_world(0.0, 0.0, 180.0)
        err = _angle_diff(base._car.current_angle, 180.0)
        if abs(err) < _TASK_RELOCALIZE_DEPLOY_TURN_EPS_DEG:
            _relocalize_sub_t0 = now
            _reloc_y_snap = base._vis_y_fix_cnt
            _y_ok_cnt = 0
            base._vis_x_fix_en = False
            base._vis_y_fix_en = True
            _mode_sub = _RELOC_Y_DRIVE
            _self_sub = _mode_sub
            # 转向进入 6 度范围后不停车，当周期直接向低 Y 前进。
            _relocalize_request_with_repulse(0.0, -_RELOC_SPEED, 180.0, now)
    elif _mode_sub == _RELOC_Y_DRIVE:
        base._vis_yaw_fix_en = False
        base._vis_x_fix_en = False
        base._vis_y_fix_en = True
        _relocalize_request_with_repulse(0.0, -_RELOC_SPEED, 180.0, now)
        if _relocalize_sub_t0 == 0:
            _relocalize_sub_t0 = now
        elapsed = ticks_diff(now, _relocalize_sub_t0)
        if elapsed >= _RELOC_DRIVE_TIMEOUT_MS:
            _relocalize_sub_t0 = 0
            _y_ok_cnt = 0
            # 去掉刹停：无缝切 DONE 起步回库。
            _finish_relocalize()
            return
        if elapsed < _RELOC_DRIVE_SETTLE_MS:
            return
        if base._vis_y_fix_cnt != _reloc_y_snap:
            _reloc_y_snap = base._vis_y_fix_cnt
            if base._Position_Y_fix < _RELOC_FIX_THRESH:
                _y_ok_cnt += 1
            else:
                _y_ok_cnt = 0
        if _y_ok_cnt < _RELOC_FIX_REQUIRE:
            return
        _relocalize_sub_t0 = 0
        _y_ok_cnt = 0
        # 去掉刹停：不再 request_hold，保留本拍平移命令，无缝切 DONE 起步回库。
        _finish_relocalize()
