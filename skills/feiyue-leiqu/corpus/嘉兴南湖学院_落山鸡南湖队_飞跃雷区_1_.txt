 摘要
  第二十一届全国大学生智能汽车竞赛“飞跃雷区”组别要求参赛队伍设计并制作一套由地面车模与悬停无人机组成的空地协同系统，无人机通过线缆与车模连接，在有线通信的条件下完成信标检测、目标识别与自主压灯任务。本文围绕该赛题要求，系统阐述了“落山鸡南湖队”参赛作品的整体设计方案与工程实现。
  在硬件架构方面，系统采用三控制器分布式架构：车模与无人机各搭载一枚逐飞CYT4BB7核心板作为主控，四个无刷电机各配一枚STC32G12K128电调主控。车模基于M车底盘，四轮独立驱动，采用麦轮实现全向移动，搭载IMU660RC惯性传感器与四路1024线正交编码器，实现高精度速度闭环。无人机采用四旋翼构型，搭载IMU660RC、VL53L8CX多像素TOF、UP-FLOW-302-3C光流传感器以及双摄像头视觉系统，实现稳定悬停与目标识别。
在软件算法方面，无人机采用分层串级控制架构，利用IMU660RC、VL53L8CX与LC-302光流分别完成姿态、高度和水平速度闭环；主摄与副摄均独立识别车板和信标，CYT4BB7依据同摄当前帧观测完成目标锁定、来源选择与任务决策，并通过有线串口向车模发送车体坐标系下的引导方向。系统在分视野时采用定向迁移，在双摄确认丢灯后请求车模惯导回中心，并保留最终360度搜索作为兜底。
  关键词：智能汽车竞赛；飞跃雷区；空地协同；四旋翼；麦轮全向车；双摄像头；串级PID





一、引言
第二十一届全国大学生智能汽车竞赛“飞跃雷区”组别是一道典型的“空地协同”赛题，要求参赛队自制一辆运行车模和一台可悬停的飞行器，在室内信标赛道上完成信标位置检测并越过信标。本组别的核心约束包括：环境感知传感器必须安装在悬停飞机上，地面执行平台不能直接依靠自身传感器去搜索信标；飞机与车模之间通过不超过1.5米的线缆连接，既可以供电也可以传输数据，但不能使用无线通信。
本报告基于“落山鸡南湖队”在“飞跃雷区”组别中的设计实践，从总体方案设计、机械结构改造、电路系统设计、控制算法实现等方面，系统阐述参赛车模与飞行器的设计制作过程。本方案采用车模与无人机协同的工作模式，无人机负责信标检测与车模识别，车模根据无人机给出的信息完成接近和压灯动作。车模采用M车底盘，四轮全向驱动；无人机采用四旋翼构型，搭载双摄像头视觉系统，实现信标与车模的双目标识别。
二、模型车设计制作的主要思路及技术方案概要
2.1 总体设计思路
本系统的设计遵循“分而治之、协同联动”的思路，将整个系统分解为三个相互关联的子系统：无人机飞控子系统、视觉感知子系统、车模执行子系统。无人机首先实现稳定悬停，为视觉系统提供稳定的观测平台；视觉系统完成信标与车模的双目标识别；车模根据视觉系统输出的误差信息完成全向运动控制与压灯动作。
2.2 系统架构
系统采用三控制器协同架构：
无人机主控：逐飞CYT4BB7核心板，负责飞控姿态解算、视觉数据处理、与车模通信。
车主控：逐飞CYT4BB7核心板，负责全向运动控制、电机驱动、接收无人机指令。
电调主控：STC32G12K128（4个），分别驱动四个无刷电机。
2.3 技术方案要点
（1）双摄像头宽视野方案：无人机搭载两颗MT9V034摄像头并采用前后对称倾斜安装，两路均能独立识别车模红外车板和场地信标。主摄图像由CYT4BB7的CM7_1核直接处理，副摄图像由独立CYT2BL3完成本地车板测量和最多5个信标候选提取，再通过UART3发送原子观测。系统不传输整幅副摄图像，也不进行运行时图像拼接；CYT4BB7为两路分别维护跟踪状态，仅用同一摄像头、同一捕获帧中的车板与信标建立精确闭环。当车板和信标分处两路视野时，系统不直接相减两路像素，而是驱动车模沿固定机体系方向进入目标摄像头视野，随后切换到该路同摄闭环。
（2）全向麦轮车模控制：车模采用M车底盘，四轮独立驱动，通过麦轮实现全向移动，可完成前后、左右、旋转等任意方向运动。
（3）有线协同通信：无人机与车模之间通过不超过1.5米的线缆连接，提供数据通信，不使用无线通信。
（4）车模红外标识：在车顶将4个红外灯板布置成V字形箭头，作为无人机判断小车方向的标志位。
三、机械部分安装及改造
3.1 车模机械改造
3.1.1 底盘与结构
车模采用M车底盘，轴距、轮距保持原厂参数未作改动。原车部分机械件更换为CNC铝合金件，在保证结构强度的同时适当减轻重量。车模整体尺寸（含传感器）为：长2930mm×宽2980mm×高2750mm。

3.1.2 轮胎与驱动
轮胎采用原车同款轮胎，尺寸符合原车规格要求。后轮驱动电机为原车模电机，防伪易损标签完整。传动机构保持原厂设计，未作改装。
3.1.3 传感器安装
IMU660RC惯性传感器：固定于车模侧边位置，采用尼龙铜柱安装，减少振动对姿态测量的影响。
正交编码器（1024线，4个） ：分别安装于四个车轮轴端，用于测量各轮转速，实现速度闭环控制。

3.1.4 红外灯板安装
四个红外灯板呈V字形摆放。无人机通过识别这个红外标志点的相对位置，可计算出车模的中心位置与朝向角度。
3.2 无人机机械结构
3.2.1 机架
采用逐飞机架，四旋翼构型。整机（含桨叶和保护罩）能够放置在50cm×50cm范围内。保护网罩孔眼尺寸满足乒乓球无法穿越的安全测试要求
3.2.2 传感器安装
IMU660RC惯性传感器：固定于飞控中心位置，用于姿态解算。
总钻风MT9V034摄像头（2个）：安装于机身下方，按一定倾角安装，用于赛道信标识别。 
VL53L8CX TOF传感器（1个）：朝下安装，用于定高测量。
UP-FLOW-302-3C光流传感器（1个）：朝下安装，用于水平位置估算。
IPS全彩2.0寸屏幕：安装于机身上方，用于调试信息显示。
3.2.3 减震设计
摄像头安装用热熔胶固定好，保证飞行振动不影响图像质量。摄像头采用轴承类机构实现始终对地，无需电机参与。
四、电路设计说明
4.1 主控核心板
车模与无人机的主控均采用逐飞科技提供的CYT4BB7核心板（组委会推荐MCU），该芯片基于Arm Cortex-M4F内核，具备丰富的外设接口与强大的运算能力。根据竞赛规则要求，图像处理和车模控制必须使用TRAVEO系列MCU，本方案完全符合要求。因此，本报告不对核心板本身进行详细说明。
4.2 自制电路板
本队自制电路板均已标记学校名称（嘉兴南湖学院）、队伍名称（落山鸡南湖队）及制作日期（2026年xx月xx年），标记位于PCB顶层。
4.2.1 车底板 
车底板作为车模硬件平台的核心连接板，承担着各功能模块的电气与机械互联重任。底板通过专用接口连接IMU660RC惯性传感器，用于实时采集车模的三轴角速度和加速度，为姿态估计与运动控制提供基础数据；同时接入4个1024线正交编码器，分别安装于四个驱动轮轴端，精确测量轮速与里程，实现闭环速度调节。底板还为车顶呈V字形排列的4个红外灯板提供供电与控制信号，作为无人机视觉定位的特征标志；此外，连接2块DRV驱动板，分别驱动左右两侧电机，确保大电流输出稳定。所有部件经由车底板统一整合，形成了高度集成的感知、驱动与供电子系统
4.2.2 DRV驱动板（2块）
驱动板选用两块基于DRV系列有刷驱动芯片的独立模块，每块驱动板分别控制两个有刷电机，共同驱动车模的四个车轮电机，实现四轮独立驱动。该驱动芯片具备良好的电流输出能力和热管理特性，支持宽电压输入，满足车模动力需求。每块驱动板均支持PWM脉宽调制调速功能，通过接收来自主控单元的不同占空比信号，可精确控制电机转速与转向，实现差速转向和速度闭环调节。此外，板载220μF大容量电解电容，有效滤除电机换向时产生的反向电动势和高频纹波，抑制供电电压突变，保证驱动芯片工作稳定并延长使用寿命。两块驱动板通过车底板统一供电，并接收主控发出的控制指令，构成车模动力执行子系统的核心部件。
4.2.3 红外灯板（4个）
车顶布置4个红外LED灯板，呈V字形排列，作为无人机识别车模位置与方向的标志。每个灯板的恒流驱动电路采用三极管加MOS管的组合方案，三极管负责恒流控制，MOS管驱动大电流LED阵列，确保发光强度稳定一致；灯板调制频率与摄像头曝光同步，有效滤除环境光干扰，提升复杂光照下的检测可靠性。4个灯板由车底板统一供电，协同工作。
4.2.4 分电板
 分电板将3S电池输入电压分流至底板、两块DRV驱动板及TLD7002，实现集中供电。板内集成470μF大容量滤波电容以抑制母线电压纹波与瞬态跌落，并联TVS管提供过压钳位保护，有效抵御电机换向反电动势及外部浪涌干扰，确保各模块在动态负载条件下获得干净、稳定的电源供给。
4.2.5 电源板（车模）
专门为红外灯板提供稳压电源（5V），确保红外灯板发光强度稳定。
4.2.6 无人机底板
  无人机底板作为飞控系统的核心连接板，承担着各传感器与执行部件之间的电气与数据互联功能。底板通过专用接口连接IMU660RC惯性传感器，实时采集飞行器的三轴角速度与加速度数据，为姿态解算、滤波融合与飞控闭环控制提供基础运动信息；连接双摄像头模组（型号MT9V034），实现信标灯与车模红外灯板的并行视觉识别，为无人机提供目标定位与跟踪的视觉依据；连接VL53L8CX TOF传感器，通过发射激光脉冲测量飞行器对地距离及下方障碍物间距，支持定高悬停、自动降落及避障功能；连接UP-FLOW-302-3C光流传感器，利用下视摄像头采集地面纹理变化计算水平运动速度，在GPS信号受限的室内或近地环境中辅助实现精准悬停与位置保持；同时连接4个电调，分别驱动四个无刷电机，接收飞控输出的PWM控制信号以实现电机转速的独立调节，完成飞行姿态与运动控制指令的最终执行；底板设有Type-B USB接口，用于无人机与车模之间的有线物理连接，支持板间数据传输，通过该链路进行车机通讯，将无人机视觉识别的红外信标位置信息发送至车模，指引车往红外信标走。底板统一汇聚各传感器数据流，并将飞控处理后的控制指令分发至执行端，配合板载电源管理电路对各模块提供稳定供电，构成了无人机感知、计算与动力执行一体化的核心硬件平台。
4.2.7 电调（4个）
无人机采用4个电子调速器，每个驱动一个无刷电机，实现四旋翼动力控制。电调主控芯片为STC32G12K128，通过PWM信号接收飞控转速指令，内置电压检测功能用于实时监测电池状态，保障飞行安全。四路电调协同工作，通过独立调节各电机转速实现飞行器的姿态控制与运动。 
4.2.8 电源板（无人机）
为无人机底板和各传感器提供稳定供电。
4.2.9 TLD7002LED灯带驱动板
TLD7002 LED灯带驱动板用于驱动无人机下视LED灯带，为光流传感器提供主动补光，改善光流数据质量。在室内或低照度环境下，环境光线不足会导致光流传感器采集的地面图像对比度下降、纹理信息模糊，影响特征点提取与速度估计精度。TLD7002驱动板通过恒流驱动高亮度LED灯带，为光流传感器视场区域提供均匀、稳定的主动照明，增强图像亮度与纹理清晰度，使光流传感器在暗光条件下仍能获取有效的地面特征信息
4.2.10 cyt2bl3板（提供另一个摄像头）
CYT2BL3处理板通过串口（UART）与无人机主控CYT4BB7通信。CYT2BL3完成第二摄像头的图像采集与车模红外灯板特征识别后，将识别结果通过串口发送至CYT4BB7。该串口通信方案简洁可靠，满足了双摄像头协同识别的实时性要求。
五、微处理器控制软件算法说明
5.1 软件总体架构
系统软件采用分布式、分层实时架构。无人机CYT4BB7的CM7_0核负责传感器采集、飞行控制和电机输出，CM7_1核负责主摄图像处理、副摄通信、双摄来源选择以及车机引导；CYT2BL3作为副摄视觉节点，只上传当前帧车板测量和信标候选；车模控制器执行全向运动、轮速闭环与任务状态机。该划分使高频飞控与计算量较大的视觉处理相互隔离，同时保留有线反馈形成空地协同闭环。

图5-1 空地协同软件总体架构
5.1.1 双核任务划分与数据流
CM7_0以1 ms定时中断为控制时基，按不同分频运行角速度环、姿态角环、光流速度环、视觉位置环和高度环，并最终完成四电机混控。CM7_1在相机帧交接完成后，严格按照“车板识别、信标识别、同摄关系更新、来源选择、共享发布”的顺序处理主摄帧；主循环同时解析副摄UART接收环，保证串口中断只搬运字节，不在中断中执行图像或状态机逻辑。
两个M7内核之间通过固定地址共享帧交换视觉目标、信标状态、车板状态、搜索状态和调试遥测。每个共享帧都采用首尾序列号保护，写入端完成数据后清理缓存，读取端先失效缓存并重复核对序列号，从而避免读取到更新一半的数据。副摄与主控之间则采用带版本号和CRC16的显式字节协议，不直接发送C结构体内存布局。

5.2 无人机飞控算法
飞控采用“任务状态机给出目标、外环生成运动期望、内环完成快速稳定”的分层控制方式。正常跟车、双摄迁移、回中心等待和最终搜索共用同一套姿态、高度与光流底层控制，任务切换只改变视觉目标、航向指令和车机状态位，避免在模式切换时重复维护多套飞控参数。
5.2.1 姿态解算
IMU660RC工作在四元数输出模式，驱动层提供Pitch、Roll和Yaw姿态角以及三轴角速度。控制侧对角速度进行零偏修正和一阶低通，再将Pitch、Roll姿态角外环与陀螺仪角速度内环串联。Yaw误差通过角度环绕处理限制在[-180°,180°]，避免跨越±180°时产生反向大误差。
姿态角环每5 ms更新一次，角速度环每1 ms更新一次。Pitch与Roll由水平速度环给出期望角，Yaw在正常状态下保持给定航向，在最终搜索状态下改由受限角速度命令驱动。三个轴的控制量与高度控制量经过四旋翼混控后转换为四路PWM，并在停机、正常飞行和缓降落三种电机模式之间进行限幅与状态清零。
5.2.2 高度控制
高度测量采用VL53L8CX多区TOF。程序从有效测距区域中提取对地距离，并结合机体Pitch、Roll计算垂直投影，同时补偿TOF相对机体中心的安装偏移。无效距离不会被当作0 mm直接送入控制器，防止上电或弱反射时出现突发升力指令。
h = d · cos(Pitch) · cos(Roll) + yₛ · sin(Roll)
高度位置环根据目标高度与补偿高度生成垂直速度期望，垂直速度环再生成总升力修正。当前自动任务默认目标高度为1200 mm；起飞与降落均使用120 mm/s的高度斜坡，降落过程中持续检测低高度保持时间，满足条件后自动停桨。该过程避免目标高度阶跃直接冲击电机输出。
5.2.3 水平位置控制
水平控制由视觉位置外环、光流速度环和姿态串级组成。视觉外环把车板或车板—信标视点的归一化误差转换为期望水平速度；LC-302光流根据当前TOF高度把角位移换算为实际速度，并使用陀螺仪补偿机体转动造成的伪光流。速度环比较期望速度与实际速度，输出期望Pitch和Roll，再交给姿态内外环执行。
为了降低线缆拉扯和目标快速运动造成的滞后，无人机同时接收车模实测速度作为前馈，并按当前累计航向将其旋转到无人机控制坐标系后叠加到速度期望。当前目标视点模式在只识别到车板时跟踪车板；同一摄像头连续确认车板和信标后，将观察点以0.6比例平滑移动到两者之间，使无人机既能保持车板可见，又能为车模靠近信标提供更稳定的俯视几何关系。
主副摄来源切换后，视觉位置PID状态会清零，并在300 ms内把新来源误差渐入，首帧输出同时限幅，避免安装零点差异造成姿态冲击。该渐入只作用于无人机X/Y跟车误差，不改变发送给车模的方向模式EF/EL。
5.2.4 视觉处理
两路摄像头分辨率均为188×120。主摄每次取得稳定图像后先执行车板识别，再执行信标识别；副摄也采用相同顺序，并把同一捕获帧的结果一次性封装。车板算法根据图像最大亮度生成自适应阈值，经过二值化、连通域提取、相邻分量合并和形状筛选得到车板中心；V形灯板的开口方向与累计旋转角共同确定车头方向。程序分别保存“本帧真实测量”和“短时跟踪保持”，只有真实测量可以参与同摄精确闭环。
信标算法采用背景差分和自适应阈值提取亮斑，经连通域计算面积、质心、峰值、均值、宽高比和填充率，最多保留5个候选。为适应斜视造成的椭圆投影，候选最大宽高比放宽至2.2，填充率要求不低于0.60，同时仍通过外观评分降低过度拉长目标的优先级。车板当前帧包围区域会作为信标排除区，减少红外车板被误识别为场地信标。
每个摄像头拥有独立的sticky tracker。未锁定时优先选择靠近本路车板的合格候选，候选需连续3帧位于20像素确认门内才建立锁定；锁定后只接受预测位置42像素范围内的匹配，不会因为另一盏灯外观分更高而立即换灯；连续12帧失配后才释放旧目标。该策略既允许多信标同时存在，又避免主副摄来源或候选排序变化造成频繁跳锁。
原始像素只用于检测和显示，控制误差优先通过标定LUT转换为视线角度。主摄直接查询LUT；副摄先按本路原始像素查询同一型号摄像头的LUT，再对两个控制分量同时取反完成180°对称安装校正，减去实测安装零点，最后叠加实时Pitch/Roll补偿。两路都遵循机体系X向右为正、Y向后为正的统一约定。
5.2.5 双摄来源选择与定向迁移
双摄方案不把两路原始像素拼成一幅图，也不使用不同时刻的车板和信标直接计算相对误差。精确车机引导必须来自同一摄像头、同一捕获帧中的真实车板测量和真实信标测量。两路同时形成有效pair时，初次选择会比较各自LUT坐标下的车灯距离；只有一路线性距离至少近20%才判为明显更近，否则优先主摄。选定后，只要该路sticky目标仍保持，就不因另一摄像头出现更高分候选而提前切换。
当车板位于一侧视野而信标只在另一侧视野时，系统进入定向迁移。迁移方向只取主摄到副摄或副摄到主摄的固定机体系方向，再依据当前车头投影为车体前向EF和左向EL；不做跨摄像头像素相减。迁移期间无人机继续以纯车板视点和车速前馈跟随车模，水平追车贡献乘可调系数，防止车模运动过快时线缆突然绷紧。目的摄像头连续3帧形成同摄pair后，车模先停车确认，再直接使用目的来源的精确方向。

5.2.6 丢灯恢复与安全状态
双摄联合视野接近完整场地区域后，常规丢灯不再优先驱动无人机原地旋转。只有主副摄都在健康的新图像中连续确认无合格候选、后摄链路有效、当前不处于迁移并且本任务已经稳定识别过至少一个信标时，才向车模发送回中心请求。这样车模上电后前往第一个惯导点的既有流程不会被误触发，通信断线或相机处理异常也不会被当作场地无灯。
回中心请求采用电平握手，车模返回执行中、已到达或失败三种互斥状态。执行过程中两路视觉仍持续工作，任一路重新确认信标即撤销回中心。车模到达中心后，无人机需连续满足姿态、角速度、光流、垂直速度和高度误差稳定门槛，才执行一次不依赖图像方向提示的360°最终搜索。完整搜索仍未找到信标时，由宏配置选择原地保持或进入现有缓降落流程。
5.3 车模运动控制算法
车模控制器接收无人机给出的车体坐标系方向、车头误差和任务状态，同时向无人机回传实测平移速度、通信序号以及惯导状态。控制周期约为5 ms，完成编码器采样、全向运动解算、轮速闭环和Yaw保持。
5.3.1 全向运动解算
四麦克纳姆轮底盘把车体前向速度v_f、左向速度v_l和旋转量ω映射为四轮期望速度。忽略统一比例系数时，混控关系可写为：
v₁ = v_f + v_l + kω，v₂ = v_f - v_l + kω
v₃ = v_f - v_l - kω，v₄ = v_f + v_l - kω
当前车机引导使用方向模式，EF和EL组成单位方向向量，车模以任务设定的固定速度沿该方向移动；航向量HA单独用于车头保持或纠偏。因此视觉误差幅值变化不会直接造成车速突变，车模运动方向与速度设定相互解耦。
5.3.2 速度闭环控制
四路1024线正交编码器在每个控制周期读取并清零计数。程序按对角轮组合形成两组平移速度反馈，增量式PID输出电机PWM；速度期望先经过每周期最大变化量为20的斜率限制，以抑制方向切换和起步时的电流冲击。Yaw采用角度外环和角速度内环，并按正负号叠加到四轮PWM，保证全向平移时车头方向基本不变。
5.3.3 任务执行控制
按键启动后，车模首先按自身惯导前往第一个预设点；无人机只有在任一路摄像头首次稳定识别到信标后，才允许后续双摄丢灯触发回中心请求。视觉跟踪阶段，车模依据有效位、EF/EL和迁移状态执行定向运动；无效帧、到达确认或迁移中止时立即使用零方向停车。回中心阶段持续返回ACTIVE、REACHED或FAILED状态，避免无人机重复启动同一惯导任务。
5.4 通信协议
5.4.1 副摄观测协议
CYT2BL3与CYT4BB7使用UART3、460800 bit/s、8N1通信。通用帧头为0xA5、0x5A，随后为版本、类型、负载长度和序号，末尾使用CRC16-CCITT-FALSE。OBS_V1整帧92字节，包含相机状态、相机帧号、捕获时刻、处理延迟、车板测量与车头方向以及最多5个信标候选；CTRL_V1整帧22字节，由CYT4以20 Hz下发电机状态、搜索/迁移状态、累计航向、曝光值和一次性复位命令。
CYT4只接纳捕获到发送延迟不超过60 ms的OBS，CRC、版本、长度、字段语义或候选数组任一异常都会拒绝整帧。合格后摄观测最长保持300 ms，精确同摄引导只在新OBS到达时更新，不把旧误差周期重发。接收中断只把硬件FIFO中的字节写入512字节环形缓冲区，流式解析、重同步和统计均在CM7_1主循环完成。
5.4.2 无人机与车模协议
无人机与车模使用UART2、57600 bit/s双向通信。下行帧固定15字节，以0xFE开头、0x0A结尾，中间携带状态字节、前向EF、左向EL和车头角误差HA；无效命令会把EF/EL清零。状态位分别表示搜索、车头有效、双摄迁移和回中心请求。上行帧同样为15字节，回传两轴实测速度、序号以及自动起飞、超时和回中心状态；连续120 ms未收到有效运动帧时，无人机清除速度前馈并按超时处理。
5.4.3 共享帧与曝光同步
双核共享内存中的视觉帧保持6个浮点字段，目标来源编码为0无效、1主摄、2副摄，兼容原有有效性判断。双摄状态、实际车机引导和诊断数据分别使用独立32字节或64字节共享帧，避免控制数据与显示数据互相覆盖。主摄曝光可由机载菜单调整并保存到Flash；双摄模式下同一曝光值通过CTRL_V1同步到副摄，一次性保存命令使用命令序号去重，防止20 Hz重复控制帧连续擦写Flash。

六、开发工具与调试过程
6.1 开发工具
主工程基于逐飞CYT4BB开源库和Infineon TRAVEO T2G SDK开发，使用IAR Embedded Workbench 9.40.1分别构建CM7_0与CM7_1目标；副摄工程独立构建CYT2BL3目标。图像阈值、坐标LUT和协议回归通过Python或主机C测试辅助验证，Git用于保存可回退的工程节点。机载IPS200菜单用于观察姿态、高度、光流、车板、信标、来源和车机引导量，无线示波器仅作为台架调试通道，不参与正式车机控制。
6.2 制作与安装过程
主摄与副摄采用前后对称倾斜安装，光心尽量靠近机体中心，固定后不再改变机械角度。实物方向验收以机体系为准：目标移向机体右侧时最终UAV X误差为正，移向机体后方时最终UAV Y误差为正；副摄原始图像方向与主摄相反，因此在控制坐标中执行双轴取反。副摄在约1200 mm高度、机体水平且车板位于机体正下方时测得安装零点，并只将该零点用于副摄无人机跟车误差。
主摄由CYT4BB7直接采集，副摄由CYT2BL3采集并通过CYT4 UART3连接，双方共地且TX/RX交叉。安装完成后先在停桨状态使用主摄View:P和副摄View:R检查车板、信标、车头方向和曝光，再验证OBS帧序号、延迟、CRC与断连恢复。标定阶段在常用1200 mm高度采集像素与地面位置数据；当前两颗相机型号和焦距相同，副摄暂复用主摄LUT，后续更换独立副摄LUT时仍保持“副摄raw像素、查询副摄LUT、双轴取反、安装零点、姿态补偿”的处理顺序。
6.3 调试过程
调试遵循由底层稳定到任务闭环、由停桨到低推力再到正常飞行的顺序。每次只改变一个环节或参数，并通过屏幕与八通道遥测核对输入、期望、输出和限幅，避免把视觉错误、坐标错误和控制器响应不足混为同一问题。
6.3.1 分模块调试
飞控部分先在拆桨状态检查IMU三轴符号、陀螺仪零偏、四电机混控和停机保护，再依次验证TOF无效值处理、倾角补偿、起飞/降落高度斜坡以及光流速度方向。姿态角环、角速度环、高度环和光流速度环分别闭合，确认底层稳定后才接入视觉位置外环与车速前馈。
视觉部分先以静态画面检查车板连通域、V形车头方向、信标背景差分、椭圆候选和车板排除区，再验证3帧确认、12帧释放和多灯不跳锁。主副摄分别验收原始图像方向、LUT符号、180°安装校正和Pitch/Roll补偿；通信部分使用主机测试覆盖CRC错误、分段收包、噪声重同步、版本不匹配、序号回绕、延迟帧和断连重启。
6.3.2 单机调试
无人机单机首先验证定高、定点、航向保持和自动起降，再用手持车板测试纯车板跟踪、车灯中点视点和主副摄来源切换。车模单机验证四轮方向、麦轮平移、Yaw保持、固定方向模式以及第一惯导点和中心惯导点，确认无效引导帧能够立即停车。
6.3.3 空地协同联调
整机联调按“主摄同摄pair、副摄同摄pair、主车副灯、后车主灯、双路丢灯”五类场景进行。重点核对EF前正、EL左正，检查活动pair在sticky保持期间不提前切换；分视野时验证车模沿固定方向进入目标摄、到达确认期间停车以及无人机继续纯车板跟随。随后测试双摄均无灯时的回中心请求/反馈握手、任一路重获信标立即退出惯导、到中心后的单次360°搜索以及最终失败保持或缓降配置。
飞行调参时发现，仅提高车速前馈增益对响应改善有限，因此需要同时观察前馈量、光流实际速度、速度环输出和Pitch/Roll实际响应，判断瓶颈位于通信滤波、速度环还是飞行器水平加速度。所有高增益、来源切换和线缆牵引测试均应先限制推力与活动范围，并保留单摄编译回退路径。

八、结论
本报告围绕“飞跃雷区”赛题完成了空地协同系统的硬件与软件设计。当前软件把无人机飞控、双摄视觉、车模全向运动和有线协议划分为相互独立又可闭环协作的模块，高频姿态控制与图像处理分核运行，副摄由CYT2BL3独立完成本地图像测量，从而在不传输整幅图像的条件下扩展了有效观察范围。
无人机采用视觉位置、光流速度、姿态角和角速度多级串级控制，并结合TOF倾角补偿高度、起降斜坡和车速前馈。视觉系统已实现主副摄独立车板与信标识别、来源本地sticky锁定、同摄当前帧精确闭环、车灯中点视点、后摄180°方向校正以及实时姿态补偿。多信标场景中，活动目标在释放门槛到达前不会因另一候选分数更高而切换。
针对双摄视野下的任务特点，系统取消了常规丢灯后的优先旋转策略：车板和信标分处两路视野时先执行定向迁移，双摄健康且确认无灯时请求车模惯导回中心，到达后仅保留一次360°最终搜索。通信断线、过期帧、相机异常、车头无效或迁移超时均会进入明确的停车、保持或缓降分支，不会把故障误判为正常无灯。
后续工作将集中在实机性能量化和参数收敛，包括用当前最终源码重新记录双核与副摄Map、统计长时间通信丢帧和最坏延迟、测量飞行状态下的光流速度环带宽，并在完整允许倾角范围内复核副摄独立LUT。上述项目属于性能与验收完善，不改变当前同摄闭环和失效恢复的总体架构。

姿态解算函数（四元数解算）
static void quarternion_to_euler(float q[4],
                                  float *roll, float *pitch, float *yaw)
{
    float sqx = q[0] * q[0];
    float sqy = q[1] * q[1];
    float sqz = q[2] * q[2];

    *roll = atan2f(2.0f * (q[1] * q[3] + q[0] * q[2]),
                   1.0f - 2.0f * (sqy + sqx)) * 180.0f / M_PI;
    *pitch = -asinf(2.0f * (q[0] * q[3] - q[1] * q[2]))
             * 180.0f / M_PI;
    *yaw = atan2f(2.0f * (q[0] * q[1] + q[2] * q[3]),
                  1.0f - 2.0f * (sqx + sqz)) * 180.0f / M_PI;
    if (*yaw < 0.0f) *yaw += 360.0f;
}
PID控制函数（位置环、速度环）
float PID_Control(PID *p, PIDOut *s,
                  float expect, float feedback, uint8_t i_enable)
{
    float integral_next, i_raw, i_limited, i_step;

    s->error = expect - feedback;
    s->differential = s->error - s->lasterror;
    s->lasterror = s->error;
    s->pOut = p->kp * s->error;

    if (i_enable) {
        integral_next = s->integral + s->error;
        i_raw = p->ki * integral_next;
        i_limited = func_limit(i_raw, s->max_iOut);
        i_step = p->ki * s->error;
        if (!((i_raw > i_limited && i_step > 0.0f) ||
              (i_raw < i_limited && i_step < 0.0f)))
            s->integral = integral_next;
        s->iOut = func_limit(p->ki * s->integral, s->max_iOut);
    } else { s->integral = 0.0f; s->iOut = 0.0f; }

    s->dOut = p->kd * s->differential;
    s->value = pid_out_limit_value(s->pOut + s->iOut + s->dOut, s);
    return s->value;
}

串口通信协议解析函数
dual_cam_parse_result_t dual_cam_decode_frame(
    const uint8_t *frame, size_t size, dual_cam_message_t *message)
{
    dual_cam_message_t decoded;
    dual_cam_parse_result_t result;
    uint16_t payload_size, expected_crc, actual_crc;

    if (frame[0] != DUAL_CAM_SYNC_0 || frame[1] != DUAL_CAM_SYNC_1)
        return DUAL_CAM_PARSE_PAYLOAD_ERROR;
    payload_size = dual_cam_get_u16(&frame[4]);
    if (size != DUAL_CAM_COMMON_HEADER_SIZE
                + payload_size + DUAL_CAM_CRC_SIZE)
        return DUAL_CAM_PARSE_LENGTH_ERROR;

    expected_crc = dual_cam_get_u16(&frame[size - DUAL_CAM_CRC_SIZE]);
    actual_crc = dual_cam_crc16_ccitt_false(&frame[2], size - 4U);
    if (actual_crc != expected_crc) return DUAL_CAM_PARSE_CRC_ERROR;
    if (frame[2] != DUAL_CAM_PROTOCOL_VERSION)
        return DUAL_CAM_PARSE_VERSION_ERROR;

    memset(&decoded, 0, sizeof(decoded));
    decoded.type = frame[3];
    decoded.frame_seq = dual_cam_get_u16(&frame[6]);
    if (decoded.type == DUAL_CAM_TYPE_OBS_V1)
        result = dual_cam_decode_obs(&frame[DUAL_CAM_COMMON_HEADER_SIZE],
                                     &decoded.payload.obs_v1);
    else if (decoded.type == DUAL_CAM_TYPE_CTRL_V1)
        result = dual_cam_decode_ctrl(&frame[DUAL_CAM_COMMON_HEADER_SIZE],
                                      &decoded.payload.ctrl_v1);
    else
        return DUAL_CAM_PARSE_TYPE_ERROR;
    if (result == DUAL_CAM_PARSE_MESSAGE) *message = decoded;
    return result;
}
