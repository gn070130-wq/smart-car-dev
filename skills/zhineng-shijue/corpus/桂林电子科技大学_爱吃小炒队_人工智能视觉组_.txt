摘 要
本文详细介绍了桂林电子科技大学在第二十一届全国大学生智能汽车竞赛缩微光电组的系统设计方案及其迭代调试过程。我队选用恩智浦半导体公司生产的单片机RT1064为主控，使用M车模，使用OpenARTPlus摄像头作为赛道信息感知模块，使用经典PID闭环控制算法对车模自由行进控制，配合路径规划、视觉识别等技术实现车模在赛道上的平稳丝滑运行。为了提供车模速度上限及运行稳定性，同时使用vofa等调试软件不断完善与改进软硬件方案。
关键词：RT1064，OpenARTPlus，PID闭环控制，路径规划，视觉识别
引 言
全国大学生智能汽车竞赛是以“立足培养、重在参与、鼓励探索、追求卓越”为指导思想，鼓励创新的一项科技竞赛活动[1]。竞赛要求在规定的汽车模型平台上，使用STC, Infineon, NXP系列单片机作为核心控制模块，通过增加道路传感器、电机驱动模块以及编写相应控制程序，制作完成一个能够自主识别道路的模型汽车。参赛队员的目标是模型汽车需要按照规则以最短时间完成单圈赛道。
以智能汽车为研究背景的科技创意性制作，是一种具有探索性的工程实践活动，其本质也是人类创造有用人工物的一种训练性实践[2]，其过程属性是综合，而结果属性很可能是创造。通过竞赛，参赛的同学们培养了对已学过的基础与专业理论知识与实验的综合运用的能力[3]；带着背景对象中的各种新问题，学习控制、模式识别、传感技术、电子、电气、计算机、机械等多个学科新知识，包括来自不同学科背景大学生的相互学习，逐渐学会了在学科交叉、集成基础上的综合运用[4][5]；若是以实用为目的，还必须考虑考虑可靠性、寿命、外观工业设计、集成科学与非科学，在具体约束条件下融合形成整体的综合运用[6]。
本竞赛被教育部批准列入国家教学质量与教学改革工程资助项目中科技人文竞赛之一。在全国数百所高校的支持下，全国大学生智能汽车竞赛至今已成功举办了二十届，参赛学生超过33万人次，学生收获和竞赛声誉保持高位[7][8]。
第二十一届全国大学生智能汽车竞赛人工智能视觉组别中，要求参赛队伍制作一辆可以在平面比赛场地内自由运动的车模。车模在场地内的位置、方向是由比赛系统根据车模上的标记目标板来确定。车模上放置有普通的手机或无线投屏器，屏幕上显示比赛虚拟现实仿真系统投影的实时动态图像。其中包括有比赛场地的全局图像和车模第一视角的图像。车模通过完成虚拟游戏任务来完成比赛。
在准备比赛的过程中，我们小组成员涉猎控制，硬件迭代验证，路径算法验证，视觉识别方案、 SW建模，机械设计，传感器，负压方案等多个方面。几个月来的经历，培养了我们电路设计、软件编程、系统调试、工程设计等多方面的能力，锻炼了我们知识融合、实践动手的能力，最重要的是锻炼了我们的心志[9]。

第一章  系统总体设计
本章主要简要地介绍智能车系统总体设计思路，在后面的章节中将整个系统分为机械结构、控制模块、控制算法等三部分对智能车控制系统进行深入的介绍分析。
1.1系统总体方案的设计
根据竞赛规则相关规定，人工智能视觉组组别车模限制使用指定车模，限制车模微控制器使用NXP系列的MCU作为主控，在Keil开发环境中进行软件开发。我们使用VSCODE进行代码的编写，使用Keil进行编译烧录，本设计以i.MXRT1064单片机作为系统控制处理器，含MCU的图像处理平台限定使用基于NXP公司微控制器的OpenART、OpenARTPlus等，我队选择使用OpenARTPlus作为图像处理模块[10]。系统主要由电源模块、主控模块、按键模块、显示模块、电机驱动模块、传感器模块组成。在传感器模块中，全局摄像头彩钻风PRO用于获取赛场图像信息，采用编码器传感器对电机速度进行检测，采用ICM42688姿态传感器辅助车模运行；在电机驱动模块中，使用DRV8701E作为直流电机驱动芯片，用于驱动H桥电路。控制总体采用PID闭环控制算法完成对车速的控制，通过PWM控制驱动电路调整电机功率。

第二章  硬件方案系统设计
2.1 方案选择
主控芯片选择：考虑到限制要求和性能需求，我们选择使用i.MXRT1064作为主控。
电源芯片选择：持续稳定的电压与电流是整个电路系统稳定工作的基础，输出5V的电源芯片我们选择了LMR14030SDDAR，它的最大持续输出电流为3.5A，更好的是其可以依靠SS外部引脚所接的电容实现硬件软启动。经过测试，其纹波噪声较小，足以持续稳定为整个系统供电。为保证整个系统的供电稳定性，选择使用双电源供电，一路LMR14030SDDAR降压5V单独用于单片机，另一路同样降压至5V用于其余外设包括摄像头、各种传感器等。3.3V的电源芯片我们选择了TP5108E23-3.3，它的最大持续输出电流为550mA，且纹波非常小，对于ICM42688这种对电源敏感的IMU非常友好。
电机驱动方案：对于有刷驱动的方案设计，我们选择了经典的DRV8701E驱动芯片，其内置栅极电阻与两个LDO，且控制简便，稳定性好；为控制四个直流电机，选择制成两块双路有刷驱动板进行电机控制，从硬件上实现分立控制，避免“一损俱损”的情况发生。
陀螺仪方案：在整个调试过程中我们尝试过多种陀螺仪，为了让我们的编码器控制方案更为稳定和精准，一款性能优越的陀螺仪是不可或缺的。最初使用了LSM6DSR陀螺仪，发现经过一两次自旋转后数据开始漂移严重，随后选择使用IMU963RA，经过使用和考虑，最终选择使用ICM42688并且自制硬件电路。
电路保护方案：考虑到电路的安全与稳定性，我们使用了VN5025AJTR-E车规级功率电子开关作为整个电路的开关控制与保护，该电子开关自带过流保护、过压保护、防瞬态尖峰等效果，最高能承受电源电压41V，最大过流能力40A，该芯片较好的保护了我们的硬件电路。同时使用TVS加稳压管对核心板供电进行保护，避免静电、过压将核心板毁坏。考虑到RT1064在上电内核启动期间，其GPIO不能有任何的电压波动，我选择使用SY6280电子开关作为整个外设5V、3.3V的电源控制，配合主控的Core Ready引脚（官方引出的专门用于控制外设上电时序的控制引脚）该引脚将在MCU内核启动后变为高电平。我们使用该引脚使能SY6280从而对外设供电，避免上电时序错误导致内核无法启动。
2.2 版本迭代
第一版主板制作时很多东西都处于验证阶段，第一代主板上只有一个OpenARTPlus接口，既有无线串口接口又有WIFI图传接口，甚至没有蜂鸣器，没有用户指示灯。我们还没有考虑电源保护，没使用功率电子开关保护，并且单电源降压给所有的外设以及核心板使用。当时使用的陀螺仪还是LSM6DSR，并且专门放置在中轴线上，减小数据误差，丝印也还不符合要求，虽然问题较多但是大体定下了主控板的整体样式。
第二代主板在第一代主板的基础上优化了布局，添加了双摄接口，蜂鸣器电路，使用了电子开关控制电源，添加了TVS和稳压管进行保护，使用两路LMR14030SDDAR降压用于核心板供电和外设供电，删去了WIFI图传接口，添加了符合要求的铜层丝印。
第三代主板在第二代主板的基础上优化布局和布线，陀螺仪接口改为自制的ICM42688，成为了我们最终的主控板，尺寸为长100mm宽85.5mm。
第一代双路有刷驱动使用DRV8701E作为电机驱动芯片，设计符合我们自己需求的接口和尺寸，使用LDO给驱动芯片和四路缓冲芯片供电。
第二代有刷驱动与第一代没有什么区别，第三代有刷驱动在第一代的基础上，删去了一些不必要的下拉电阻，更改了丝印，优化了布局布线，优化了焊盘尺寸和大小，以便能够插入接线端子便于更换，尺寸为长60mm宽30mm。此版本为我们最终使用的版本。
自制陀螺仪使用ICM42688，尺寸样式与IMU963一致，方便使用。


第三章 结构设计
3.1 摄像头与屏幕固定支架
我们在最初设计第一代结构的时候是将主控和摄像头放在整车的中间，参考以往总钻风摄像头的放置方式如图3.1所示，并且打印“手机支架”放置屏幕，但是后来发现由于摄像头比较重，每次位置都会有变化，这会让我们的参数变动非常大，调试也非常苦不堪言。
后来参考了逐飞科技的演示车模，摄像头和屏幕都立着放置在整车的中间，我们将这个结构做出来后，发现有较大的弊端。其一是当麦轮车行进的时候，车子自然会抖动，导致摄像头图像非常的不稳定，并且屏幕和摄像头的位置也非常容易改变，这非常影响调试和比赛；其二是容易被光线影响，尤其使用的是屏幕，反光严重会影响视觉识别，如果想要取得好的成绩，我们觉得这两个问题必须得到解决，于是想出了第三代结构如图3.2所示。
该结构上端用于固定两个摄像头模块，下端用于固定无线屏幕，使用螺丝固定摄像头，摄像头镜头与无线屏幕的距离为5CM。这个结构解决了上述两个问题的同时，能够做到摄像头与屏幕的完全相对静止，不论麦轮车多抖动行进多快，整体结构都能保持相对静止，这样就解决了系统的不确定性对视觉的影响，为后续的提速和便携调试，提高效率有显著效果。
华南赛区结束后，我们发现摄像头与屏幕固定支架整体非常重，测重483克，能够将车模底板压得微微形变，较重的车使得惯性变大，考虑到赛题要求不能够更换车底板也不能更换材料，选择将结构减重，在保证原有效果不变的情况下修改了这个结构，更换了打印材料，如图3.3所示，减重后整体结构重量仅有两百克。
为了符合赛题要求，打印了合适长度的固定杆和磁石固定件用于固定标识牌，如图3.4所示。

3.2 负压方案的探索
在华南赛区之前我们曾探索过负压方案，使用单涵道负压风机方案，自制AI8051无刷驱动，配合RS2205无刷电机、直径8CM的抽气风机、薄膜、可塑性海绵构建抽气空间。大致结构如图3.6所示，受限于数字电源仪器，实测在8.3%占空比，3A电流的情况下能够达到五百多克的下压力。选取电机在保证无刷电机的较高KV值前提下，提升无刷电机的扭矩，因为风机较大，而RS2205用于桨叶效果最佳，驱动大型抽气风机效果不佳。保证抽气空间不变情况下，对抽气风机进行减重、减小体积以换取更快的转速，可以找到最佳性能的效果。
后续考虑到大型单涵道抽气会对麦轮车产生一个较大的自旋转扭矩，对车身的自旋转与行进效果有较大的影响，且赛题要求不允许更换车模底板，再三斟酌下放弃了负压方案。

第四章  软件系统设计及实现
本系统的软件设计以 RT1064 微控制器为核心，采用模块化、分层化的软件架构，实现地图获取、视觉识别、路径规划、运动控制和任务调度等功能。系统软件主要使用 C 语言编写，结合视觉处理端的分类程序完成车模与外部设备之间的信息交互。各功能模块通过统一的数据结构和接口进行连接，使系统能够根据不同关卡的任务要求，自动完成地图解析、目标识别、路径搜索及运动执行。
在底层驱动方面，系统完成了电机 PWM 控制、编码器速度采集、IMU 姿态获取、摄像头串口通信、显示屏显示、定时器和按键等基础功能的初始化。运动控制层以麦克纳姆轮底盘为执行对象，通过速度环 PID 控制和底盘运动学解算，将路径规划模块输出的移动指令转换为四个电机的目标速度。同时，系统结合编码器反馈和 ICM42688 惯性测量单元获取车模的实际运动状态，并通过位置误差和角度误差对运动过程进行闭环调节。
视觉识别与通信模块负责完成地图数据接收、目标类别识别和车模位姿校正。主控通过串口向视觉处理端发送识别请求，视觉处理端利用分类模型对箱子、目标点及其类别进行识别，并将结果返回主控。主控程序对接收到的数据进行解析和缓存，同时利用视觉反馈对车模位置进行修正，以减小编码器累积误差和底盘运动误差对路径执行精度的影响。
在算法层，系统针对不同关卡设计了相应的路径规划方法。第一关主要采用基于搜索和启发式评价的推箱规划方法，并结合死锁检测、反向推箱距离和有限宽度搜索降低计算量。第二关将地图探索、目标识别和推箱求解分为两个阶段，通过 BFS 搜索、箱子与目标匹配以及分阶段搜索完成路径规划。第三关进一步引入未知目标识别、炸弹推动和墙体破坏机制，先完成地图探索与信息识别，再根据箱子与目标的配对关系进行推箱求解，从而适应更加复杂的动态地图环境。
系统通过 game.stage 状态变量实现不同任务阶段之间的切换。主循环负责检测当前阶段并调用对应的地图读取、识别或路径规划函数，定时控制任务则负责更新传感器数据、执行视觉校正、解析路径指令和完成电机闭环控制。当路径执行完成或当前关卡求解失败时，系统根据预设逻辑进入下一阶段、返回初始位置或停止车模。后续内容将分别对软件系统总体架构、运动控制与底盘执行、视觉识别与通信、路径规划算法以及系统状态机与任务调度进行详细介绍。
4.1软件系统总体架构设计
本系统以 RT1064 微控制器为核心，采用模块化、分层化的软件架构，结合视觉处理端和车载底盘控制程序，实现地图获取、目标识别、路径规划、运动控制和任务调度等功能。系统软件主要使用 C 语言开发，各功能模块通过头文件和接口函数进行调用，降低模块之间的耦合程度，便于程序调试、功能扩展和算法移植。
根据系统功能和代码实现，软件系统总体上可以划分为底层驱动层、运动控制层、视觉通信层、路径规划层和任务调度层五个部分。
底层驱动层主要负责系统硬件资源的初始化和基础数据采集，包括电机 PWM 输出、编码器数据读取、IMU 姿态信息获取、摄像头串口初始化、显示屏控制、定时器、按键和蜂鸣器等功能。系统启动后由 all_init() 函数完成各硬件模块的统一初始化，为上层控制和算法运行提供基础支持。
运动控制层主要由电机控制、PID 控制和麦克纳姆轮底盘运动控制程序组成。路径规划模块输出的移动指令经过 navigation_task() 解析后，被转换为车模的位置、速度和航向角目标值；随后通过底盘运动学解算得到各个车轮的目标速度，并由 chassis_motor_vel_pid_control() 根据编码器反馈完成电机速度闭环控制，从而实现车模对规划路径的跟踪。
视觉通信层负责主控与视觉处理端之间的数据交换。一方面，主控通过串口发送地图读取和目标识别指令，接收地图信息、箱子类别和目标类别等数据；另一方面，视觉处理端返回的位姿数据经过串口接收、数据帧解析和滤波处理后，用于修正车模的实际位置。该层主要通过 camera_uart_init()、vision_uart_rx_char() 和 vision_correct_update_task() 等函数实现通信与视觉校正功能。
路径规划层根据不同关卡的地图结构和任务要求调用对应的规划算法。第一关由 level1_path_plan.c 完成推箱路径搜索，第二关通过探索识别和推箱求解两个阶段完成路径规划，第三关则进一步加入未知目标识别、炸弹处理、墙体破坏和箱子目标配对等功能。规划结果统一保存为路径指令字符串，并由运动控制层按照指令逐步执行。
任务调度层由主循环、定时控制函数和游戏状态变量共同构成。系统利用 game.stage 区分不同关卡和任务阶段，主循环中的 update_game_state() 根据当前状态调用地图读取、识别和路径规划函数；定时控制程序则周期性执行传感器更新、视觉校正、路径解析和电机 PID 控制。整个系统形成了“外部信息获取—地图处理—路径规划—指令执行—状态反馈”的闭环工作流程，实现了软件各层之间的协调运行。
4.2运动控制与底盘执行模块设计
运动控制与底盘执行模块负责将路径规划模块生成的离散路径指令转换为车模实际运动，是连接路径规划算法与底层执行机构的关键部分。本系统采用四轮麦克纳姆轮底盘，通过分别调节四个车轮的转速，使车模能够实现前进、后退、横向移动、旋转以及斜向运动。该模块主要由电机驱动、编码器测速、姿态获取、路径解析、底盘运动学解算和闭环控制等部分组成，核心程序位于 motor.c、mecanum.c、pid.c 和 control.c 文件中。
系统启动时，all_init() 函数依次完成电机、编码器、摄像头串口、惯性测量单元和 PID 控制器等模块的初始化。其中，motor_init() 函数为四个电机配置 PWM 输出通道和方向控制引脚，并初始化四路正交编码器。当前程序中电机 PWM 频率设置为 20 kHz，能够在保证电机响应速度的同时减小驱动过程中的噪声。编码器用于采集四个车轮的转动脉冲，为电机速度闭环控制和车模位置估计提供反馈数据。
在电机输出过程中，motor_control() 函数负责向四个电机输出控制量，并根据电机安装方向对部分通道进行正负号转换。程序对 PWM 输出进行幅值限制，避免控制量超过电机驱动模块的最大允许范围。当系统检测到路径执行结束、任务失败或停止标志 stop_flag 有效时，调用 car_stop() 函数将四个电机的输出置零，同时清除电机速度 PID 和底盘角度 PID 的积分项及历史误差，防止车模重新启动时出现较大的控制冲击。
车模实际运动状态由编码器和 IMU 共同获得。在 update_speed() 函数中，系统周期性读取四个编码器的脉冲数，并根据编码器分辨率换算为各车轮的位移和速度。程序中使用比例系数 K = 0.0828 将编码器脉冲转换为位移，并以 T = 0.005 s 作为速度计算周期，计算每个车轮的实际速度。由于四个电机的安装方向不同，程序对部分编码器数据进行了符号修正。随后，系统通过低通滤波器对四路速度进行平滑处理，以降低编码器脉冲波动和机械振动对控制效果的影响。
根据麦克纳姆轮底盘的运动关系，四个车轮的速度反馈可以进一步换算为车体坐标系下的纵向速度、横向速度和旋转速度。程序使用 ture_chassis_speed.vx、ture_chassis_speed.vy 和 ture_chassis_speed.vw 分别表示车体的前后运动速度、横向运动速度和角速度。车体位移经过 IMU 提供的航向角修正后，被转换到全局坐标系，并累加更新 car_ture_state.x、car_ture_state.y 和 car_ture_state.yaw，从而获得车模的实际位置和姿态。
路径执行由 navigation_task() 函数完成。系统将路径规划模块输出的路径保存到 game.final_path 数组中，并利用 game.cur_index 表示当前待执行的路径字符。对于 u、d、l 和 r 等移动指令，程序首先根据当前网格位置和移动方向计算目标位置，然后将目标位置保存到 car_target_state 中。为了减少路径指令频繁切换带来的启停误差，程序会对连续的相同方向指令进行合并，并按照连续移动的格数一次性计算目标距离。
除基本移动指令外，路径字符串中还包含识别、视觉校正和阶段切换等控制指令。当程序解析到字符 1、2、3 或 4 时，车模会调整到对应的目标航向角，并通过航向角 PID 保持车身方向稳定，随后配合视觉处理端完成箱子或目标点识别。当解析到字符 5 时，系统启动视觉位置校正；字符 6 用于在炸弹处理后延时重新启动视觉校正；字符 h 用于执行返回初始位置操作；字符 e 表示当前阶段路径执行结束，系统停止平移运动并将控制状态切换到下一阶段。
为了提高车模运动的连续性和定位精度，navigation_task() 中没有采用简单的“到达一个格点后立即停止”的控制方式，而是设计了带有速度规划和误差修正的连续运动控制方法。程序使用 rabbit_x、rabbit_y 和 rabbit_v 表示虚拟参考点及其运动速度，根据目标距离、当前速度和最大减速度计算减速距离。当车模接近目标位置时，系统进入减速阶段；在距离较长时，车模按照加速、匀速和减速过程运行，在距离较短时则自动降低最大速度，避免车模冲过目标位置。
车模运动控制采用“前馈加 PD 误差修正”的方式。程序首先根据虚拟参考点的运动速度生成前馈速度，再利用车模实际位置与参考位置之间的误差进行比例和微分修正。对于沿网格主方向的运动，系统将误差分为运动方向误差和横向偏差，并分别设置对应的控制增益；对于斜向运动，程序将目标速度分解到全局坐标系的两个方向上，实现两个方向的同步跟踪。最终得到的全局速度控制量保存在 absolute_speed.vx、absolute_speed.vy 和 absolute_speed.vw 中。

四个车轮的速度闭环控制由 chassis_motor_vel_pid_control() 函数完成。该函数首先读取 IMU 航向角并执行坐标变换，然后调用 get_motor_targetSpeed() 获取各电机的目标速度，再将目标速度与编码器反馈的实际速度输入 PidIncCtrl() 进行增量式 PID 运算。当前程序中四个电机速度环使用相同的 PID 参数，比例系数 Kp 为 1.918，积分系数 Ki 为 0.054，微分系数 Kd 为 0。PID 输出与电机死区补偿量相加后，作为最终 PWM 控制量输出到四个电机。
为了改善低速运行和停车过程中的控制效果，程序在速度环中加入了死区补偿和制动补偿。当目标速度大于一定阈值时，系统根据电机正反转方向加入对应的死区补偿；当目标速度已经较小但实际速度仍然较大时，程序增加反向制动量，使车模能够更快地降低速度并稳定在目标位置附近。该方法可以降低电机在低速区间因静摩擦和驱动死区造成的运动不连续问题。
车模航向角控制由 chassis_angle_pid_control() 函数实现。系统将目标航向角与 IMU 实际航向角作差，并将误差限制在 -180° 至 180° 范围内，避免角度跨越边界时产生过大的控制误差。当前航向角 PID 参数为 Kp = 15.73、Ki = 0.002、Kd = 10.46，其输出作为底盘旋转速度 vw 的控制量。当车模执行直线移动或视觉识别动作时，航向角控制器持续工作，使车模保持目标方向；当车模接近识别位置时，程序会停止平移速度，仅保留航向角调节，以提高识别时的姿态稳定性。
系统采用定时任务的方式协调各控制环节。control() 函数以 1 ms 为基础周期运行，负责计时、视觉校正延时处理和位姿历史数据记录；每隔 5 ms 执行一次 update_data()，更新 IMU 航向角和编码器速度信息，同时执行电机速度 PID 控制；每隔 10 ms 调用一次 navigation_task()，解析当前路径指令并更新目标运动状态。通过路径规划、运动轨迹控制、姿态校正和电机速度闭环之间的周期性配合，系统能够将离散路径稳定地转换为连续底盘运动，实现车模对规划路径的准确执行。
4.3视觉识别与通信模块设计
视觉识别与通信模块主要负责主控系统与外部视觉处理端之间的数据交互，同时完成比赛地图读取、箱子与目标类别识别以及车模运动过程中的视觉位置校正。该模块由主控端通信程序和视觉处理端分类程序两部分组成，主控端相关代码主要位于 camera.c、camera.h 和 control.c 中，视觉处理端程序位main.py。系统通过两个独立的 UART 通道分别完成地图和位姿数据通信、箱子与目标类别识别通信，从而避免不同类型数据在同一通信通道中相互干扰。
主控端通过 camera_uart_init() 函数完成通信接口初始化。其中，UART1 主要用于接收比赛地图以及视觉处理端返回的车模位姿数据，UART4 主要用于向视觉处理端发送箱子或目标识别请求，并接收对应的类别识别结果。两个串口均开启接收中断，接收到的数据首先在中断服务函数中进行缓存，再由主控程序中的任务函数进行解析和处理。通过中断接收方式，系统不需要持续阻塞等待串口数据，可以在通信过程中同时执行运动控制和路径规划任务。
4.3.1 地图数据通信与解析
在每一关开始前，主控程序首先停止视觉位置校正，并通过 UART1 向视觉处理端发送 "start" 指令，请求获取当前比赛地图。随后，程序调用 wait_read_map() 函数等待完整地图数据到达。在 control.c 中，第一关、第二关和第三关均采用了相同的地图读取流程：发送开始指令、等待地图数据、验证地图内容、转换地图格式，并将地图传递给对应的路径规划算法。
地图通信协议采用固定长度的数据帧格式。数据帧以字符 ! 作为帧头，后续包含 192 个地图字符，因此完整数据帧长度为 193 个字节，对应 12 行、16 列的比赛地图。主控端接收到数据后，首先判断帧头和数据长度是否正确，然后调用 map_payload_char_valid() 函数检查地图字符是否合法。当前程序允许的地图字符包括墙体 #、空地 -、起点 @、箱子 $、目标点 .、炸弹 * 以及表示不同类别的大小写字母。
为了避免串口传输过程中出现数据丢失或误码，wait_read_map() 函数并不会直接采用第一次接收到的地图数据，而是将当前数据保存到 map_candidate 缓冲区中，并与下一次接收到的完整数据帧进行比较。只有当连续接收到两次完全一致的有效地图数据时，程序才会将其复制到最终的 map 数组中。如果帧格式错误、地图字符非法或长时间未接收到有效数据，程序会清空当前接收缓存，并重新向视觉端发送 "start" 指令。当前程序中每经过 25 次等待调用，便会重新发起一次地图读取请求。
地图接收完成后，主控端通过 convert_1d_to_2d() 函数将一维字符数组转换为二维地图数组。由于串口传输过程中地图以长度为 192 的一维字符串形式存在，而路径规划算法使用 12 行、16 列的二维数组进行搜索，因此转换后的地图分别保存为 level1_map、level2_original_map、level2_final_map、level3_original_map、level3_bomb_map 和 level3_final_map。对于部分地图，程序还会清除视觉端传输的起点标记，并按照车模实际初始位置重新设置起点坐标，以保证规划算法中的地图状态与实际场地一致。
4.3.2 箱子与目标类别识别通信
在第二关和第三关中，地图中可能存在尚未确定类别的箱子和目标点，因此车模需要在运动过程中到达指定位置后，利用视觉处理端完成局部识别。主控程序在 navigation_task() 中解析到识别指令后，首先调整车模航向角，使摄像头朝向待识别对象，然后根据当前地图字符向视觉处理端发送识别请求。
当待识别对象为箱子时，主控端通过 UART4 发送字符串 "box"；当待识别对象为目标点时，发送字符串 "target"。视觉处理端接收到不同指令后，调用对应的分类模型进行图像识别。视觉端程序在启动时加载 cartoon_best_int8.tflite 和 num_best_int8.tflite 两个量化模型，分别用于箱子类别识别和目标类别识别，同时加载对应的标签文件。摄像头采集 RGB 图像后，经过去自动增益、自动白平衡、图像翻转和感兴趣区域设置，再送入 TensorFlow Lite 模型进行分类。
视觉端对模型输出结果进行 softmax 处理，并按照分类概率进行排序。当最高类别的置信度达到 0.88 以上时，程序认为识别结果有效。对于箱子类别，视觉端将识别结果转换为小写字母发送给主控端；对于目标类别，则转换为大写字母发送给主控端。视觉端通过 rela 列表保存已经建立的类别对应关系，使同一类别的箱子和目标能够使用相同的编号进行匹配。主控端接收到类别字符后，由 camera2_rx_interrupt() 读取单字节识别结果，并将其保存到 detect_data 中，同时置位 detect_end_flag，通知路径执行程序识别已经完成。
在 navigation_task() 中，当车模到达识别位置且航向角误差满足要求后，程序会根据当前地图字符发送 "box" 或 "target" 请求。识别结果返回后，主控端将 detect_data 写回当前地图对应的网格，并根据识别结果更新运行时地图信息。如果识别结果为目标类别，程序还会同步更新目标点状态，为后续箱子与目标匹配及推箱路径规划提供准确的数据基础。识别完成后，系统清除检测标志、停止平移运动并恢复正常路径指令解析。
4.3.3 视觉位姿数据接收与解析
除箱子和目标类别识别外，视觉处理端还会向主控端发送车模的二维位姿信息，用于修正编码器积分产生的累计误差。视觉位姿数据采用文本格式传输，主控程序支持解析类似 x数值y数值 或 X数值Y数值 的数据帧，数据帧以换行符或回车符作为结束标志。
在 camera1_rx_interrupt() 中，程序根据 correct_flag 的状态选择当前 UART1 数据的解析方式。当系统处于地图读取阶段时，UART1 接收数据按照固定长度地图帧进行缓存；当系统进入视觉校正阶段时，接收数据则交由 vision_uart_rx_char() 进行位姿数据解析。vision_uart_rx_char() 以字符 x 或 X 作为一帧数据的起始标志，将后续字符缓存到 vision_rx_buf 中，直到接收到换行符或回车符后形成一个完整数据帧。
为了避免在串口接收中断中直接执行浮点解析和位姿修正，程序将接收到的完整数据帧复制到 vision_pending_buf 中，并记录当前的 vision_cnt。之后由周期任务 vision_correct_update_task() 读取待处理数据，并使用 sscanf() 解析视觉坐标。当数据格式解析成功且包含两个有效坐标值时，系统才会进入后续的视觉误差计算流程。
4.3.4 视觉位置校正算法
视觉校正功能由 vision_correct_start()、vision_correct_stop()、vision_correct_update_task() 和 vision_process_at() 等函数共同实现。系统并不是简单地将视觉坐标直接覆盖编码器计算的位置，而是先将视觉测量结果与带时间标记的历史位姿进行匹配，再计算视觉位置与历史估计位置之间的误差。
在 control() 函数中，系统按照 vision_cnt 对当前车模位置进行循环缓存，形成 pose_history 历史位姿数组。由于视觉数据从采集、传输到主控解析存在一定延迟，程序根据接收数据对应的采样计数值，回溯查找视觉数据实际对应时刻的历史位姿。这样可以避免直接使用当前时刻位置与延迟视觉位置进行比较所造成的误差。
视觉误差计算完成后，程序首先进行异常值剔除。当视觉测量位置与历史位姿之间的误差超过 VISION_ERR_REJECT_MM 设定的范围时，系统认为该帧数据可能存在误识别或通信异常，不对车模位置进行修正。对于有效误差，程序使用低通滤波器进行平滑处理，当前视觉误差滤波系数为 VISION_ERR_LPF_ALPHA = 0.35。经过滤波后，修正量按照 VISION_CORR_GAIN = 0.5 进行比例缩放，并通过 VISION_CORR_LIMIT_MM 限制最大修正幅度，防止单次视觉数据突变导致车模位置产生过大的跳变。
视觉校正结果通过 vision_apply_correction_from() 函数同时作用于当前位置和位姿历史缓存。这样既能够修正当前的 car_ture_state.x、car_ture_state.y，又能够保持历史位姿数据与修正后的位置状态一致，避免后续视觉数据匹配时产生新的系统误差。该处理方式将编码器的连续性与视觉测量的绝对位置优势结合起来，提高了车模长距离运行过程中的定位稳定性。
4.3.5 通信异常处理与视觉校正控制
为保证视觉通信过程不会影响底盘运动，系统设计了视觉校正启动、暂停和延时重启机制。当路径指令中出现字符 5 时，系统调用 vision_correct_start() 开启视觉校正；当炸弹处理或其他特殊动作导致视觉数据暂时不稳定时，程序通过 vision_correct_restart_after() 暂停视觉数据处理，并设置延时时间；之后由 vision_correct_delay_task_1ms() 进行倒计时，延时结束后重新启动视觉校正。
视觉校正重新启动时，程序会清空接收缓存、重置滤波器状态和待处理数据，同时忽略重新启动后的若干帧视觉数据，避免摄像头刚恢复工作时的不稳定数据参与位置修正。对于无效数据帧、超长数据帧和无法解析的数据，系统直接丢弃当前数据并重新等待下一帧有效数据。在地图读取阶段，程序还通过固定帧头、固定长度、字符合法性检查和重复帧确认等机制提高地图数据的可靠性。
总体来看，视觉识别与通信模块形成了“主控请求—视觉处理—串口返回—数据解析—地图或位姿更新”的闭环流程。地图通信为路径规划提供初始环境信息，箱子和目标识别为动态地图更新及目标匹配提供类别信息，视觉位姿校正则对运动控制过程进行实时反馈。通过上述模块的协同工作，系统能够在复杂地图和连续运动条件下完成可靠的信息获取与位置修正。
4.4路径规划算法设计与实现
路径规划算法是车模软件系统的核心部分，主要负责根据比赛地图、箱子位置、目标位置、炸弹位置以及车模当前状态，生成能够完成关卡任务的运动路径。本系统将比赛场地抽象为 12 行 16 列的二维栅格地图，地图中的每个字符表示一种场地元素，其中 # 表示墙体，- 表示可通行区域，@ 表示车模位置，$ 表示未识别箱子，. 表示未识别目标，* 表示炸弹，小写字母表示不同类别的箱子，大写字母或数字表示不同类别的目标。
路径规划程序主要由 level1_path_plan.c、level2_path_plan.c 和 level3_path_plan.c 组成，并通过 level1_get_path()、level2_explore_path()、level2_push_box_path()、bomb_solve() 以及 level3_solve_stage2_with_bombs() 等接口与主控状态机连接。规划结果统一保存到 game.final_path 数组中，路径中的 u、d、l、r 表示移动方向，1 至 4 表示识别方向，5 和 6 表示视觉校正控制，h 表示返回初始位置，e 表示当前阶段结束。这样，路径规划算法只负责生成指令序列，具体的路径解析和底盘执行由运动控制模块完成。
4.4.1 地图建模与状态表示
在路径搜索过程中，程序并不直接复制完整的字符地图，而是将地图转换为适合搜索的状态结构。状态主要包括车模位置、箱子位置、目标位置、箱子数量、已完成目标信息以及当前可达区域等内容。墙体信息保存为布尔数组，箱子和目标则使用栅格编号表示，栅格编号通过行列坐标计算得到：

在箱子推动过程中，车模并不是只能从当前格直接进行下一次推动，而是需要先判断车模能否绕行到箱子的后方。因此，程序会先以车模当前位置为起点进行 BFS 搜索，计算在当前箱子和墙体布局下车模能够到达的所有位置，再判断箱子周围四个方向是否存在合法的推动动作。该方法将车模的普通行走和箱子的推动动作分开处理，减少了无效状态数量。
为避免同一箱子布局下车模在可达区域内不同位置产生大量重复状态，程序对车模位置进行归一化处理。对于箱子位置相同且车模处于同一连通区域的状态，可以使用统一的代表位置进行搜索。这种状态压缩方式能够减少搜索节点数量，同时保留箱子推动所需要的可达性信息。
4.4.2 第一关推箱路径规划
第一关的任务主要是将普通箱子推动到目标点，level1_path_plan.c 中采用了 BFS、优先队列搜索、启发式评价和有限宽度搜索相结合的方法完成规划。
程序首先解析地图中的墙体、箱子、目标和车模起点，并调用 compute_dead_squares() 计算静态死锁位置。对于同时邻接墙体的角落位置，箱子一旦进入通常无法再被推出，因此程序将这些位置标记为不可进入区域。此外，程序还通过 is_2x2_deadlock() 检测箱子进入 2×2 封闭区域的情况。当某次推动会造成静态死锁或 2×2 死锁时，该状态会被直接舍弃，不再进入后续搜索。
为了提高启发式评价的准确性，程序调用 precompute_reverse_push() 从每个目标点反向计算箱子到达该目标所需的最少推动次数。反向搜索不仅考虑箱子与目标之间的距离，还检查箱子在推动过程中是否需要站立位置，从而比简单的曼哈顿距离更符合推箱问题的实际约束。
在 stage_heuristic() 中，程序使用动态规划对当前箱子和目标进行匹配，计算所有箱子完成任务所需的估计推动代价。搜索节点的评价函数为：

在状态扩展过程中，程序首先通过 BFS 找到车模到达箱子推动位置的行走路径，然后执行一次箱子推动动作，并更新箱子、目标和车模状态。当箱子被推入对应目标点后，该箱子和目标会从当前搜索状态中移除，使后续搜索只关注尚未完成的箱子。为了兼顾搜索质量和单片机内存限制，第一关还采用宽度为 4 的有限宽度搜索，对不同箱子完成顺序保留若干个候选状态，最终从候选结果中选择总代价较小的路径。
4.4.3 第二关探索识别与推箱规划
第二关的特点是部分箱子和目标点初始状态未知，因此路径规划被划分为探索识别阶段和推箱求解阶段。第一阶段由 level2_explore_path() 完成，主要任务是规划车模的探索路线，并在合适的位置插入识别指令。程序通过 BFS 计算车模在当前地图中的可达区域，结合箱子和目标点的位置选择识别顺序，使车模能够尽量减少无效移动。

探索阶段结束后，deduce_remaining_info() 函数会对地图中未识别的箱子和目标进行补全。当某一类别的箱子数量多于对应目标数量时，程序将未识别目标补充为该类别目标；当目标数量多于箱子数量时，则将未识别箱子补充为对应类别。如果箱子和目标同时存在成对未识别对象，程序会为其分配新的类别编号，保证后续规划中箱子与目标数量和类别关系保持一致。
第二阶段由 level2_push_box_path() 完成。程序首先将不同类别的箱子和目标分别保存到数组中，并调用 precompute_push_distances2() 计算每个目标点到各个栅格位置的反向推动距离。在启发式函数 heuristic_all_boxes() 中，程序通过递归匹配方式，仅允许箱子与相同类别的目标进行匹配，并将所有箱子的最小匹配代价作为当前状态的启发式值。
第二关推箱搜索同样采用优先队列和启发式搜索。对于每一个候选推动动作，程序需要同时满足以下条件：车模能够到达箱子后方，箱子的目标位置不是墙体，目标位置不存在其他箱子，并且推动后剩余箱子仍然具有可行的匹配目标。满足条件的状态才会加入搜索队列。
为降低搜索空间，第二关采用分阶段推箱策略。程序每次搜索若干个可能完成的箱子，将完成一个箱子后的状态作为下一阶段的输入，并通过宽度为 6 的有限宽度搜索保留多个候选箱子完成顺序。最终，程序将各阶段路径拼接成完整推箱路径，并交给主控端执行。
4.4.4 第三关识别、炸弹处理与路径规划
第三关在第二关基础上增加了未知箱子、未知目标和炸弹等动态因素，路径规划过程更加复杂。第三关规划程序将任务分为 Stage1 和 Stage2 两个阶段。Stage1 负责地图探索、箱子和目标识别以及炸弹处理，Stage2 负责根据识别结果完成箱子与目标的匹配和推箱。
在 bomb_solve() 函数中，程序首先解析地图中的箱子、目标、炸弹和车模起点，并对未知对象进行统一处理。随后调用 level3_explore_path() 生成探索路径。Stage1 搜索不仅考虑车模的移动和箱子推动，还将炸弹推动作为一种特殊状态转移。当炸弹被推动到指定墙体位置时，程序根据炸弹爆炸规则更新墙体状态，从而形成新的可通行区域。
第三关的 Stage1 搜索使用启发式函数评价识别收益、炸弹收益、可达性和路径代价。程序会综合考虑以下因素：当前车模到未识别箱子和目标的距离；识别动作能够获得的信息量；炸弹爆炸后能够清除的墙体数量；爆炸后箱子和目标之间的可达性变化；炸弹推动距离和路径长度；是否会产生箱子死锁或目标不可达状态。
为避免炸弹过早使用导致后续推箱阶段缺少必要的通路，程序设置了炸弹保留策略，包括 BOMB_STAGE1_SAVE_THRESHOLD 和 BOMB_MAX_LEFT_FOR_STAGE2 等参数。当某个炸弹在探索阶段带来的收益不足时，程序可以选择暂时保留该炸弹，将其留到 Stage2 继续处理。
Stage1 生成初始路径后，程序还会执行路径简化和有效性验证。level3_explore_path() 中依次进行取消无效往返动作、在识别信息足够时截断路径、优化连续识别动作等处理，并通过 validate_stage1_finish_path() 对优化后的路径重新进行状态模拟。只有通过验证的路径才会被写入 game.final_path，从而避免路径优化破坏炸弹、箱子或目标的实际状态。
第三关 Stage2 首先调用 deduce_remaining_info_level3() 补全尚未确定的箱子和目标类别，然后进入推箱规划。目前工程中的实际 Stage2 入口为 level3_solve_stage2_with_bombs()，该函数进一步调用 level3_push_with_level2_solver()，复用第二关已经实现的分阶段推箱求解器。这样可以避免重复设计箱子与目标匹配、推箱搜索和路径回溯逻辑，同时保证第二关和第三关在类别匹配规则上的一致性。
对于正常 Stage2 求解失败的情况，程序还保留了 solve_stage2_core() 和 Stage5 直接推箱路径等备用方案。当主搜索无法在当前节点数量或内存限制下得到结果时，系统可以尝试备用路径规划方式；如果所有方案均失败，主控程序会清空当前路径并停止车模，避免继续执行上一阶段残留路径。
4.4.5 路径生成与算法执行约束
路径规划算法最终输出的并不是单纯的箱子推动序列，而是包含车模行走、推动、识别、视觉校正和阶段切换在内的完整动作字符串。搜索过程中，普通行走路径由 BFS 回溯得到，推动动作使用 u、d、l、r 表示。第一关和第二关主要输出移动与推动指令，第二关探索阶段还会插入识别方向指令，第三关则在阶段路径前后追加视觉校正、返回初始位置和结束指令。
由于算法运行在 RT1064 单片机上，搜索过程受到内存容量、搜索节点数量和路径缓存长度的限制。程序将搜索状态池、优先队列、BFS 队列和路径缓冲区统一放置在 Super_RAM 中，并通过固定大小的内存池管理搜索节点，避免动态内存分配造成的碎片问题。同时，第一关和第二关使用访问状态哈希表判断重复状态，第三关则通过阶段节点上限和超时检测控制搜索规模。
综上，本系统的路径规划算法采用“地图建模、可达性搜索、推动状态扩展、启发式评价、死锁剪枝和有限宽度保留”相结合的设计方法。第一关重点解决普通推箱和死锁问题，第二关重点解决未知信息探索和类别匹配问题，第三关则进一步扩展到炸弹爆炸、墙体更新和动态地图规划。不同关卡的算法最终均通过统一路径字符串与运动控制模块连接，形成从地图输入到车模执行的完整规划流程。
4.5系统状态机与任务调度设计
系统状态机与任务调度模块负责协调地图读取、路径规划、视觉识别、运动控制和关卡切换等功能，是整个软件系统的运行管理中心。本系统采用主循环与定时中断相结合的任务调度方式，通过 game.stage 记录当前任务阶段，通过 game.final_path 保存当前阶段需要执行的路径指令，并由 control() 和 update_game_state() 分别完成实时控制任务和关卡状态管理。
系统的主要状态信息定义在 GAME_STATE 结构体中，包括当前阶段 stage、阶段计数 end_time、路径索引 cur_index、路径数组 final_path 以及当前地图指针 map。其中，stage 用于区分不同关卡和任务阶段，cur_index 用于记录路径执行进度，final_path 用于保存路径规划算法输出的移动、识别和控制指令，map 则指向当前阶段使用的二维地图。
4.5.1 系统初始化与主循环
系统启动后，首先在 main() 函数中完成系统时钟配置，并调用 all_init() 完成各个软硬件模块的初始化。all_init() 依次初始化电机和编码器、显示屏、摄像头串口、ICM42688 惯性测量单元、无线通信、PID 控制器、按键和蜂鸣器等模块。同时，程序启动两个定时器，其中 PIT_CH0 设置为 1 ms 周期，用于执行实时控制任务；PIT_CH1 设置为 50 ms 周期，用于处理其他周期性数据任务。
初始化完成后，程序将车模实际位置清零，并设置初始状态：
game.end_time = 1；game.stage = 1。
主程序进入无限循环，依次执行 ips_show()、update_game_state()、vofa_process() 和 key_process() 等函数，并通过 delay_ms(20) 降低主循环运行频率。主循环主要负责状态判断、显示刷新、按键处理和调试通信，不直接承担高频率的电机控制任务，从而避免路径规划或显示操作影响底盘控制的实时性。
4.5.2 基于定时中断的实时任务调度
实时控制任务由 PIT_IRQHandler() 中断服务函数触发。当检测到 PIT_CH0 定时标志后，系统调用 control() 函数完成一次控制周期。control() 函数以 1 ms 为基础周期，内部根据计数器 timer_cnt 对不同任务进行分频调度。
每个 1 ms 周期执行的任务包括视觉校正延时处理、视觉计数更新和当前位姿历史数据保存。程序通过 vision_correct_delay_task_1ms() 处理视觉校正重启倒计时，同时将 car_ture_state.x 和 car_ture_state.y 保存到 pose_history 数组中，为后续视觉延迟补偿提供历史位置数据。
每隔 5 ms，系统调用 update_data() 更新 IMU 航向角和编码器速度信息。该函数通过 get_imudata() 获取当前姿态，并通过 update_speed() 计算四个电机的实际速度以及车模在全局坐标系中的位置变化。同样在 5 ms 周期内，系统调用 chassis_motor_vel_pid_control() 完成四个电机的速度闭环控制。
每隔 10 ms，系统调用 navigation_task() 解析当前路径指令，并更新车模的目标位置、目标速度和目标航向角。路径解析结果会传递给底盘控制程序，由底盘控制程序进一步完成坐标变换、麦克纳姆轮速度解算和电机输出。
因此，系统的任务调度关系可以概括为：1 ms：视觉延时处理、位姿记录；5 ms：传感器数据更新、电机速度 PID 控制；10 ms：路径指令解析、导航目标更新；20 ms：主循环状态管理、显示刷新和按键处理；50 ms：周期性数据存储和辅助任务。
通过不同周期任务的分层调度，系统能够将路径规划、状态管理和底盘运动控制分开执行，保证实时控制任务具有较高的执行优先级。
4.5.3 多阶段状态机设计
系统采用 game.stage 作为核心状态变量，在 update_game_state() 函数中使用 switch 语句对不同状态进行处理。根据当前工程代码，状态机主要包括以下阶段：stage = 0：空闲或等待状态；stage = 1：初始阶段或阶段过渡动作；stage = 2：第一关地图读取和路径规划；stage = 3：第一关结束后的阶段过渡；stage = 4：第二关探索识别阶段；stage = 5：第二关信息补全和推箱阶段；stage = 6：第二关结束后的阶段过渡；stage = 7：第三关探索、识别和炸弹处理阶段；stage = 8：第三关最终推箱阶段。
在第一关状态中，系统首先停止视觉校正，通过 UART1 发送 "start" 指令读取地图。地图接收完成后，程序将一维地图转换为二维数组，设置车模起点，并调用 level1_get_path() 生成第一关路径。路径生成成功后，程序将当前地图指针指向 level1_map，清零路径索引，并将 stop_flag 置为 0，允许底盘开始执行路径。
第二关采用两个连续状态完成。进入 stage = 4 后，系统读取并保存原始地图，调用 level2_explore_path() 生成探索识别路径，并将探索后的地图保存为 level2_final_map。探索阶段结束后，系统进入 stage = 5，调用 deduce_remaining_info() 补全未识别的箱子和目标类别，然后调用 level2_push_box_path() 生成最终推箱路径。
第三关同样采用两个阶段完成。进入 stage = 7 后，系统读取第三关地图，并分别建立原始地图、炸弹地图和最终地图。随后调用 bomb_solve() 完成未知对象识别、炸弹处理和墙体更新，并将结果写入第三关最终地图。进入 stage = 8 后，系统调用 level3_solve_stage2_with_bombs() 完成最终推箱规划。如果规划成功，则清零路径索引并允许车模执行；如果规划失败，则清空 game.final_path，保持 stop_flag = 1，调用 car_stop() 停车，并在显示屏上输出错误提示。
4.5.4 路径执行与状态切换
状态机与路径执行模块通过 game.final_path 建立联系。路径规划模块生成路径后，系统将路径保存到 game.final_path，并将 game.cur_index 设置为 0。随后，navigation_task() 按照路径索引逐个读取指令并执行。
当路径指令为移动字符时，系统更新车模目标位置并执行底盘运动；当路径指令为识别字符时，系统调整车模航向角并启动视觉识别；当路径指令为 5 或 6 时，系统启动或延时重启视觉校正；当路径指令为 h 时，系统执行返回初始位置操作。
当 navigation_task() 解析到 e 指令时，首先判断车模是否仍在平移。如果车模仍处于运动状态，程序会先停止平移并保持当前航向，待车模稳定后再完成阶段切换。随后，程序将 stop_flag 置为 1，增加 game.end_time，并将 game.stage 更新为下一个阶段编号。这样，当前路径执行完成后，主循环会在下一次调用 update_game_state() 时进入新的状态，完成下一关或下一任务阶段的初始化。
当阶段路径执行完成时，程序还会清除对角运动状态、重置路径记录标志，并将底盘平移速度置零，仅保留必要的航向角控制。该处理能够避免上一阶段的速度状态影响下一阶段的地图读取和路径规划。
4.5.5 异常处理与安全停止机制
为了防止路径规划失败或通信异常导致车模继续执行错误指令，系统设置了多种安全保护机制。当 stop_flag 有效时，control() 函数会直接调用 car_stop()，停止四个电机并清除 PID 状态，不再执行导航和速度控制。
在地图读取阶段，如果连续接收到无效数据，程序会清空接收缓存并重新发送地图请求；在视觉识别阶段，如果接收到的数据格式错误或识别结果无效，系统会丢弃当前数据，等待下一次有效数据；在路径规划阶段，如果搜索失败或路径长度超过缓存限制，系统不会直接执行不完整路径，而是清空路径缓存并保持停车状态。
此外，系统在 PIT_IRQHandler() 中对各个定时器的中断标志进行独立判断和清除，防止同一中断标志被重复处理。UART1 和 UART4 则分别通过独立的串口中断函数接收地图、位姿和目标类别数据，从而避免通信数据阻塞主循环和底盘控制任务。
综上，系统通过 game.stage 状态机实现关卡任务和功能模块之间的有序切换，通过 1 ms 定时中断保证底盘运动控制的实时性，通过 5 ms 和 10 ms 周期任务完成传感器更新、PID 控制和路径解析，并利用路径结束标志、异常停车和数据校验机制提高系统运行的可靠性。整个任务调度流程形成了“系统初始化—地图读取—路径规划—路径执行—阶段切换—异常处理”的闭环运行结构。


结  论
自报名参加全国大学生智能汽车竞赛以来，我们小组成员从查找资料、设计机械结构、组装车模、视觉识别、编写程序一步一步的进行，最后终于完成了最初目标，定下了现在这个设计方案。
在此份技术报告中，我们主要介绍了准备比赛时的硬件迭代、结构探索、方案寻找，软件程序编写，技术创新等成果。
在车模迭代方面，我们经历了从购买现成方案，到尝试自制3D打印件，再到最终自主设计稳定结构的全过程。每一次迭代，我们都针对结构强度、整车效果、调试便携性和系统稳定性进行了不断优化，最终实现了结构合理、性能优良、适应性强的车模设计。
在电路方面，我们根据实际需求，设计了高集成度、低功耗的硬件系统。采用了RT1064作为主控芯片，配合DRV8701E实现有刷电机的高效驱动。电源管理、信号采集、传感器接口等模块合理布局，既保证了系统的稳定性，也为后续功能扩展提供了支持。
在软件与视觉系统方面，我们结合整车行驶需求，搭建了结构清晰、便于调试优化的软件程序框架。为避免程序杂乱、调试困难，我们将整体程序进行模块化拆分，分别对应硬件驱动、数据采集、视觉处理、车辆控制、异常处理等核心功能，各模块分工明确、相互配合，让程序逻辑更加清晰，极大降低了后期调试、修改和功能升级的难度。我们逐一对传感器、电机、串口等硬件设备编写适配驱动程序，保障主控芯片与各类硬件稳定通信、正常工作，为整车自主运行提供基础软件支撑。同时对车辆采集的各类数据进行简单校准、去杂处理，剔除赛场环境带来的无效干扰数据，为视觉识别和车辆控制提供可靠的数据支撑。
在车辆控制与程序优化方面，我们结合车辆行驶状态和赛道识别数据，编写对应的整车控制程序。根据赛道实时路况，实现比赛要求功能，同时根据行驶偏差及时调整转向角度，修正车辆行驶姿态，避免车辆偏离赛道。为提升整车运行稳定性，我们持续开展实地赛道调试工作，反复测试程序运行效果，排查程序卡顿、响应延迟等问题，不断精简优化程序内容，剔除冗余代码，提升程序运行效率。同时针对调试中出现的传感器异常、行驶不稳等问题，完善程序应急处理逻辑，降低车辆失控、冲出赛道的风险，经过多轮迭代调试，最终实现整车行驶稳定、响应及时的运行效果。
现在，面对即将到来的大赛，在历时近五个月的充分准备之后，我们有信心在比赛中取得优异成绩。也许我们的知识还不够丰富，考虑问题也不够全面，但是这份技术报告作为我们五个月辛勤汗水的结晶，凝聚着我们小组每个人的心血和智慧。随着它的诞生，这份经验将永伴我们一生，成为我们最珍贵的回忆。

#include "control.h"
volatile uint32_t timer_cnt;
volatile uint32_t vision_cnt;
uint8_t stop_flag = 1;
GAME_STATE game;
PoseHistory_t vision;
PoseHistory_t pose_history[POSE_HISTORY_SIZE];
void control(void){
    timer_cnt++;
    vision_correct_delay_task_1ms();

    uint16_t index = vision_cnt % POSE_HISTORY_SIZE;
    pose_history[index].x = car_ture_state.x;
    pose_history[index].y = car_ture_state.y;   
    vision_cnt++;
    vision_correct_update_task();
    
    if(timer_cnt % 5 == 0)  
        update_data();
    if(stop_flag){
        car_stop(); return;
    }
    
    if(timer_cnt % 10 == 0)
        navigation_task();
    if(timer_cnt % 5 == 0)
        chassis_motor_vel_pid_control();
    
}
void update_game_state(void){   // 放while(1)里
    switch(game.stage){
        case 0: break;
        case 1:{
            game.final_path[0]='f';
            game.final_path[1]='r';
            game.final_path[2]='r';
            game.final_path[3]='5';
            game.final_path[4]='e';
            game.cur_index = 0;
            game.stage = 0;         
        } break;        
        case 2: {  // 第一关
            delay_ms(500);
            vision_correct_stop();
            uart_write_string(UART1_INDEX, "start");
            while(wait_read_map()){ 
                ips200_show_string(0, 160, "wait_map......");
                delay_ms(20); 
            }   
            
            for(int i = 0; i<192;i++)
                if(map[i]=='@')
                    map[i] = '-';
            convert_1d_to_2d(map, level1_map);
            level1_map[6][2] = '@'; 
            ips_show_map(map);
            while(!level1_get_path(level1_map)) delay_ms(60);   
            game.stage = 0;
            game.map = level1_map;
            game.cur_index = 0;
            stop_flag = 0;          
        } break;
        case 3: {
            game.final_path[0]='r';
            game.final_path[1]='5';
            game.final_path[2]='e';
            stop_flag = 0;
            game.cur_index = 0;
            game.stage = 0;                     
        } break;        
        case 4: {  // 第二关的识别阶段
            delay_ms(500);
            vision_correct_stop();
            uart_write_string(UART1_INDEX, "start");
            while(wait_read_map()){ 
                ips200_show_string(0, 160, "wait_map......");
                delay_ms(20); 
            }
            for(int i = 0; i<192;i++)
                if(map[i]=='@')
                    map[i] = '-';
            convert_1d_to_2d(map, level2_original_map);
            ips_show_2d_map(level2_original_map);
            convert_1d_to_2d(map, level2_final_map);
            level2_explore_path(level2_original_map);
            game.stage = 0;
            game.cur_index = 0;
            game.map = level2_final_map;    
            stop_flag = 0;
        } break;
        
        case 5:{
            deduce_remaining_info();
            level2_final_map[6][1] = '-';       
            ips_show_2d_map(level2_final_map);
            game.stage = 0;
            level2_push_box_path(level2_final_map);
            game.cur_index = 0;
            stop_flag = 0;
        } break;
        case 6:{    
            game.final_path[0]='r';
            game.final_path[1]='5';
            game.final_path[2]='e';
            stop_flag = 0;
            game.cur_index = 0;
            game.stage = 0;             
        } break;        
        case 7: {  // 第三关识别阶段
            delay_ms(500);
            vision_correct_stop();
            uart_write_string(UART1_INDEX, "start");
            while (wait_read_map()) {
                ips200_show_string(0, 160, "wait_map......");
                delay_ms(20);
            }
            for (int i = 0; i < 192; i++) {
                if (map[i] == '@') {
                    map[i] = '-';
                }
            }
            convert_1d_to_2d(map, level3_original_map);
            level3_original_map[6][2] = '@';
            convert_1d_to_2d(map, level3_bomb_map);
            convert_1d_to_2d(map, level3_final_map);
           game.final_path[0] = '\0';
            ips_show_2d_map(level3_original_map);
            bomb_solve(level3_original_map);
            convert_1d_to_2d(map, level3_final_map);
            
            game.cur_index = 0;
            game.stage = 0;
            game.map = level3_final_map;
            stop_flag = 0;
        } break;
case 8: {  // 第三关推箱阶段
    if (level3_solve_stage2_with_bombs(level3_final_map)) {
        game.cur_index = 0;
        game.stage = 0;
        game.map = level3_final_map;
        stop_flag = 0;
    } else {
        // Stage2 求解失败，停车，避免继续执行上一阶段的旧路径。
        game.final_path[0] = '\0';
        game.cur_index = 0;
        stop_flag = 1;
        car_stop();
        ips200_show_string(0, 192, "L3 Stage2 Fail");
    }
} break;        
        default: break;     
    }
}

        pid_clear(motor_vel_pid+i);

}
