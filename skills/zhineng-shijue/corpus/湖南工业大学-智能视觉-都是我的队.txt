摘要
面向全国大学生智能汽车竞赛智能视觉组任务，设计并制作了一套基于 OpenART Plus 与 RT1064 的四驱麦克纳姆轮模型车。整车以 M 车模为基础，采用 3D 打印中央壳体完成两套 OpenART Plus、5 英寸无线屏、RT1064 主控板和电池的分层安装；其中一套视觉模块完成地图与车辆位置识别，另一套视觉模块按需完成箱子和终点图片 ID 分类。RT1064 通过串口接收结构化视觉结果，完成任务状态管理、延迟补偿位置融合、麦克纳姆轮闭环控制、方向状态路径搜索、车—箱联合推送、多箱任务分解、观察位 TSP 扫描、动态软墙炸弹规划及扫描折叠。
针对无线屏画面存在透视、遮挡和传输延迟的问题，地图视觉模块采用固定四角透视校正、LAB 颜色分割、网格中心 ROI 和四帧投票建图；ID 模块以置信度阈值和连续三帧一致机制确认分类结果。底盘控制结合四路编码器、IMU 和视觉位置，使用固定延迟补偿获得位置估计，并以分段速度规划、姿态控制和四轮速度闭环执行路径。实测记录表明，系统静态物体识别精度约为 98%，车辆动态检测位置误差约为 2 cm，视觉模块工作频率约为 50 帧/s；华南赛区三关计时总计为 99.395 s。
关键词：智能汽车；OpenART Plus；麦克纳姆轮；路径规划；推箱任务；视觉识别

第一章 引言
1.1 竞赛任务与系统问题
智能视觉组的模型车需要在比赛场地中获取地图、车辆位置、箱子和终点信息，并根据关卡规则完成移动、识别、推箱和炸弹预处理等连续任务。与只执行固定轨迹的小车不同，本系统面对的是一个会随箱子和软墙状态变化的离散场地：车辆需要先理解当前地图，再判断哪些位置可以到达、哪个箱子应当匹配哪个终点，最后把规划结果转换为底盘能够稳定执行的动作。[1]
任务的困难主要来自三个方面。第一，视觉端观察的是无线屏上的比赛画面，图像存在透视、颜色、遮挡和传输延迟，地图与车辆位置必须经过筛选才能用于控制。第二，麦克纳姆轮底盘能够前后、横向和旋转复合运动，但四个车轮的速度误差、地面摩擦和车体惯性会使离散路径不能直接等同于实际轨迹。第三，COMPLEX 和 BOMB 场景不是静态最短路问题，ID 扫描顺序、箱子推送顺序和炸弹爆破顺序都会影响后续地图的可执行性。
本项目将上述问题拆分为“视觉识别—串口传输—任务调度—地图求解—动作计划—底盘闭环”六个环节。OpenART Plus 负责从无线屏画面中提取结构化信息，RT1064 负责实时决策和控制，底盘通过编码器和 IMU 反馈运动状态。各环节之间使用明确的数据接口连接，避免让图像处理、任务流程和电机控制互相侵入。
1.1.1 相关技术方案与文献综述
智能视觉组的实现通常围绕屏幕画面结构化识别、嵌入式实时控制和离散地图求解展开。固定相机观察显示屏的方案能够将视场、光照和地图尺度约束在可控范围内，再通过透视校正、颜色分割和多帧确认输出栅格地图。与直接将原始图像交给主控不同，本车将地图、车位和目标 ID 分由两套 OpenART Plus 模块完成，主控只接收结构化串口结果，从而把图像处理与实时运动控制解耦。
在移动与任务求解层面，麦克纳姆轮底盘需要处理横移、转向和轮速闭环的耦合，离散关卡还需要考虑可达路径、箱子推送顺序和炸弹改变地图后的可执行性。方向状态搜索、真实可达距离排序与状态空间搜索为这些问题提供了可实现的工程方法。本车在此基础上，将视觉延迟补偿、动作分段、观察位排序和炸后重规划组合为闭环执行流程。
1.2 整车设计目标
整车以四驱麦克纳姆轮 M 车模为基础，在保留原车电机、传动和编码器的前提下增加视觉、主控、电源和显示结构。设计目标不是单纯提高某一个模块的速度，而是在有限车体空间和有限主控资源下，形成一套能够重复完成比赛任务的系统。
具体目标包括：
1. 在中央壳体内完成两套 OpenART Plus 和两颗摄像头的稳定安装，使摄像头能够观察下方 5 英寸无线屏显示的地图和第一人称画面；
2. 使用 RT1064 统一接收地图、车位和目标 ID，完成 SIMPLE、COMPLEX 和三关 CONTINUE 流程；
3. 利用 IMU660RB、四路 1024 线迷你正交编码器和视觉位置构成可用于运动控制的位置状态；
4. 对普通移动、推箱、观察位访问和炸弹动作分别建立可验证的路径计划；
5. 在主控板 OLED 上显示菜单、状态和调试信息，同时不影响无线屏对比赛画面的显示和识别；
6. 在满足尺寸、质量和供电约束的情况下，获得可用于比赛记录的整车计时结果。
1.3 总体硬件方案
整车外形约为 282 mm × 120 mm × 150 mm，质量约 2.1 kg。底盘四角布置四个麦克纳姆轮，保留原车四个有刷电机和编码器。车体中央增加大壳体，壳体内部上方悬挂两套 OpenART Plus，每套模块配有一颗摄像头，摄像头朝下观察壳体下方的无线屏画面；5 英寸无线屏位于摄像头下方，是比赛系统画面的显示和识别对象。
RT1064 主控板固定在中央壳体上方，负责串口数据接收、任务调度、路径计算和底盘控制。主控板上的 OLED 与无线屏承担不同功能：无线屏显示游戏系统的地图和第一人称画面，供摄像头识别；OLED 由本车程序控制，用于菜单、运行状态和调试信息。3S 2200 mAh 电池通过魔术贴固定在壳体侧面，便于拆装并为主控、视觉和电机驱动提供电源。
电机驱动采用前后两块有刷电机驱动板，每块板负责两路电机 H 桥功率输出。主控板提供 PWM、方向和使能控制，驱动板完成大电流开关；编码器反馈回主控用于轮速闭环。IMU660RB 安装在主控板上，提供偏航角和角速度信息。整车新增伺服或电机数量为 0，机械动作全部由原车四驱麦克纳姆轮完成。
1.4 总体数据流与软件分工
地图视觉模块从无线屏图像中识别墙、终点、箱子、炸弹和车辆位置，目标识别模块在主控请求后读取箱子或终点的图片 ID。两路结果通过 UART 发送至 RT1064，主控在前台解析完整帧后更新任务输入。
RT1064 的软件按照 APP、MID 和 BSP 分层。APP 层管理任务状态、三关流程、识别请求和动作推进；MID 层负责地图建模、路径规划、推箱分解、TSP 扫描、炸弹搜索、位置融合和速度计算；BSP 层负责 UART、编码器、IMU、电机驱动和显示接口。规划器输出的是路径点、观察位或子任务，动作层将其转换为目标栅格和最终朝向，底盘控制再生成四轮目标角速度和 PWM。
系统的主数据流可以概括为：
视觉画面 → OpenART 结构化识别 → UART 帧 → RT1064 地图与任务上下文 → 路径/任务求解 → 动作计划 → 位置、姿态和轮速闭环 → 麦克纳姆轮运动。
编码器和 IMU 的反馈沿相反方向进入控制层，视觉位置则通过延迟补偿参与绝对位置修正。任务状态机只根据输入快照、规划结果和动作结果转移，不直接操作电机寄存器。
1.5 比赛任务组织
SIMPLE 是不依赖图片 ID 的基础推箱任务。车辆获得地图后，规划器在自由匹配条件下为箱子和终点生成子任务，动作层依次完成接近、推送和回车。COMPLEX 在此基础上增加箱子与终点的 ID 识别，车辆先访问观察位、请求视觉识别，再根据匹配关系规划推箱顺序。
CONTINUE 负责三关切换，第 0 关下发 SIMPLE，第 1、2 关下发 COMPLEX。每关完成后，车辆停车并等待下一关画面刷新，再重新建立地图和任务上下文。CONTINUE 不与 SIMPLE、COMPLEX 并列承担具体推箱业务，而是负责关卡索引、关间等待以及炸弹阶段结束后的任务恢复。
BOMB 是可插入的预处理阶段。当当前地图中存在需要先清除的软墙时，SIMPLE 或 COMPLEX 向顶层返回切换请求，炸弹规划器计算可执行的爆破顺序。爆破完成后，系统以更新后的地图恢复原任务；已经取得的 ID 和已经完成的扫描不重复执行。
1.6 主要技术特点
本项目的技术特点集中在视觉、规划和执行三者的结合。
第一，双 OpenART Plus 采用职责分工：一套持续提供地图和车位，另一套按需执行数字或卡通 ID 识别，减少单个视觉模块在地图检测和分类识别之间切换的负担。第二，RT1064 使用带朝向的方向状态 Dijkstra、车—箱联合搜索和真实可达距离 TSP，规划结果不以几何直线距离代替车辆实际可达性。第三，炸弹阶段维护动态软墙状态，并将部分 ID 扫描折叠到炸弹接近路径，在炸后仅补扫未完成节点。第四，动作层对规划结果进行路径拼接、到位确认和失败回退，使算法输出能够适应车辆实际位置变化。
1.7 本章小结
本章确定了整车的总体组成和任务链路：中央壳体内布置双 OpenART Plus 与无线屏，壳体上方安装 RT1064 主控板，侧面固定电池，底盘保留四驱麦克纳姆轮和四路编码器；视觉端负责结构化识别，主控端负责任务、规划和控制，OLED 负责本车状态显示。后续章节将分别说明机械与电路实现、视觉处理与通信、控制软件与算法、制作调试和实测结果。

第二章 机械结构、传感器与电路设计
2.1 设计要求与实现原则
智能视觉组模型车同时承载视觉采集、游戏系统画面显示、运动控制、功率驱动和供电部件。器件安装不仅影响整车重心，也直接决定摄像头视场、无线屏可视性、排线受力以及强弱电之间的干扰情况。整车机械和电路设计以结构紧凑、重心居中、强弱电分区和便于调试为原则：
1. 在不改变原车传动机构的前提下，为主控、视觉模块、显示屏和电池提供独立且可靠的安装位置；
2. 将两套视觉模块和 5 英寸无线屏集中安装在中央壳体内，缩短信号线和排线长度；
3. 将大电流驱动板布置在靠近电机的位置，减少动力线压降和回路面积；
4. 对主控、视觉和功率驱动分别进行供电、接地和线束管理，降低电机启动、制动和换向对控制侧的影响；
5. 保证电池、主控板和驱动板可拆装，便于进行上电检查、接口排故和比赛现场维护。
整车外形尺寸约为 282 mm × 120 mm × 150 mm，质量约为 2.1 kg。底盘采用四驱麦克纳姆轮结构，原车自带直流电机、传动齿轮和编码器；本次改造未增加额外伺服电机。车体前后各设置一块有刷电机驱动板。中央壳体内部安装两套 OpenART Plus 和 5 英寸无线屏，RT1064 主控板固定在壳体上方，电池通过魔术贴固定在壳体侧面。

2.2 车模底盘与改造结构
2.2.1 四驱麦克纳姆轮底盘
底盘采用四个麦克纳姆轮。与普通差速底盘相比，麦克纳姆轮外缘滚子具有斜向布置特征，四个轮子的速度组合能够产生纵向、横向和绕车体中心的转动运动。该结构适合在栅格化场地中完成前进、后退、横移和姿态调整等动作，但同时对四路轮速一致性、底盘刚度、重心位置和控制参数更为敏感。
原车的电机、编码器和传动机构均保留使用。编码器安装在电机或传动机构附近，能够输出与车轮运动相关的脉冲信息；软件侧读取四路脉冲后形成速度反馈。保留原车机械传动有两个优点：一是底盘驱动关系明确，不需要重新设计车轮与电机的机械接口；二是可将改造重点集中在控制、视觉和供电系统集成上。
在车体下部，轮组和传动系统保持相对独立。所有新增结构均安装在底盘上方，避免支架、排线或电源线进入车轮和齿轮活动范围。动力线经过固定后沿车架边缘布置，视觉排线和显示排线则尽量从支架内部或侧面通过，减少与大电流电机线的交叉。

2.2.3 重心与电池位置
电池是整车质量最大的单个部件之一。电池采用魔术贴固定在中央壳体侧面，既便于拆装和充电，也避免占用壳体内部的视觉与显示空间。侧挂位置尽量靠近车体中部，以减小前后轮法向载荷差异和横移时的侧倾趋势。主控板、视觉模块和无线屏质量相对较小，集中在壳体区域内，能够避免整车重心明显偏向车头或车尾。
实际装配时，电池通过绑带、魔术贴或固定件约束在支架平台上。动力电源使用较粗导线，并采用可插拔连接器，便于充电和维护。电池与主控板之间保持必要的绝缘和间隙，避免金属外壳、焊点或连接器在车辆振动时发生摩擦或短路。

2.3 传感器与视觉模块安装
2.3.1 双 OpenART Plus 视觉模块
整车配置两套 OpenART Plus，每套模块配有一颗摄像头。两套模块并非重复采集同一数据，而是按任务数据类型分工：一套用于获取场地栅格地图和车位信息，另一套用于获取箱子与终点的图片 ID。两颗摄像头均朝下观察 5 英寸无线屏显示的游戏系统画面。视觉识别后的结构化结果经串口发送给 RT1064，主控端不直接接收或处理原始视频帧。
两套视觉模块均安装在中央壳体内部上部，镜头朝下对准无线屏。安装时重点控制以下因素：
1. 屏幕画面完整进入视场。 支架边缘、排线和屏幕边框不得遮挡镜头主要视场；必要时通过调整镜头高度、间距和支架开孔位置使无线屏有效画面完整可见。
2. 相对位置稳定。 视觉模块与车体的相对姿态在运行中应保持不变，否则车辆振动会使外参发生变化，导致动态检测误差增大。
3. 排线受力小。 模块排线从壳体内部引出，避免折弯半径过小或被主控板、电池和板边压住；排线两端连接器应有固定和应力释放措施。
4. 显示与采集方向固定。 摄像头与无线屏之间的相对位置、间距和旋转角度在运行中不应改变，便于将识别结果稳定解释为地图、车位或目标位置。

图 2.4 展示了视觉模块和无线屏在壳体内的相对位置。两个摄像头位于上方，镜头朝下；5 英寸无线屏位于其下方，显示游戏系统的地图和第一人称画面。主控板上的 OLED 位于壳体上方的主控板区域，只用于本车菜单和调试信息显示。
2.3.2 IMU 与编码器
IMU660RB 集成在主控板上。陀螺仪和加速度相关数据对安装姿态和机械振动较敏感，因此主控板固定应避免松动：主板通过螺钉、铜柱或支撑件与支架连接，板底与支架之间保留绝缘距离；安装方向与车辆坐标方向对应，便于软件侧统一解释偏航角和角速度符号。由于 IMU 不能单独决定车辆的平移距离，其输出主要用于姿态观察、转向过程修正和与编码器信息配合使用。
四路 1024 线迷你正交编码器与原车四个驱动单元配合。正交编码器通常输出 A、B 两相信号，主控根据脉冲计数和相位关系获得轮速及方向信息。编码器在本车中的作用包括：
• 为各车轮速度闭环提供反馈；
• 检查轮组运动方向和实际速度是否与指令一致；
• 辅助估计车辆的相对行驶距离；
• 在前进、横移和转向过程中发现明显的轮速偏差；
• 与 IMU 姿态数据共同支持运动状态判断。
编码器线束属于弱电信号线，应与电机动力线保持适当距离。连接器装配后需核对电源、地线、A 相和 B 相对应关系；若 A/B 相接反或轮速符号设置错误，会直接影响闭环方向和里程估计结果。

2.4 主控板电路设计
2.4.1 主控板功能划分
主控板以 RT1064 核心板为核心，承担视觉数据接收、编码器读取、IMU 数据获取、OLED 显示、按键处理以及电机控制信号输出等任务。根据原理图，主板可划分为主控核心、视觉接口、OLED 接口、IMU、编码器接口、按键接口、无线预留接口、电源输入与稳压、电机控制信号引出等功能区域。[2,3]
主控核心模块向外引出多组 GPIO、串口和供电接口。对于本项目，接口设计的重点不在于将所有引脚都用于功能扩展，而在于保证视觉数据、编码器反馈和电机控制三个关键链路各自具备稳定、明确的连接关系。视觉侧向主控提供结构化结果，编码器侧向主控提供脉冲反馈，主控侧则向驱动板输出 PWM、方向和使能等控制量。

2.4.2 电源输入与稳压支路
电池为 3S 2200 mAh 锂电池，标称电压为 11.1 V，工作状态下记录的供电电压约为 12.4 V。电池输出进入主控板和电机驱动板：电机驱动侧使用接近 12 V 的动力电源，主控板侧经过稳压后形成 5 V 与 3.3 V 逻辑电源。
主控板电源输入处设置开关和电源指示，便于在不拔插电池连接器的情况下进行上电和断电操作。5 V 支路为外设及后级稳压提供输入，3.3 V 支路为 RT1064 核心、IMU、OLED、编码器接口和其他逻辑电路提供工作电压。视觉模块设置独立的 5 V 供电支路，以减少其工作电流波动直接叠加到其他敏感逻辑支路上。
各稳压支路附近配置输入、输出电容和去耦电容。大容量电容用于缓冲负载变化，较小的高频去耦电容用于抑制开关和数字芯片产生的高频扰动。按主板和两块驱动板上可辨认的电容值进行粗略统计，整车电容总容量暂记为约 0.7 mF；该值属于设计资料统计值，不代替电容实际容量测量。
在约 12 V 工作电压下，整车静态电流约为 0.35 A，对应输入功率约为 4.2 W；电机开始运动时电流通常约为 0.74 A，对应输入功率约为 8.9 W。后者反映了起步阶段的典型电流量级，实际动态运行电流仍会随加速度、地面摩擦、轮组受力和任务动作变化而改变。
从电源路径看，电机是最主要的动态负载。车辆起步、横移、制动和换向时，驱动板电流变化会在动力线和公共地上产生压降；若这一扰动直接传入主控和视觉支路，可能表现为串口错帧、画面丢失或控制器复位。因此，电池至驱动板的动力路径保持短而直接，低压稳压、滤波和去耦集中在主控与视觉侧附近，使高频开关电流尽量在驱动板局部回路内闭合。
小容量去耦电容和较大容量储能电容承担不同作用。前者靠近芯片电源引脚，补偿数字逻辑和传感器的高频瞬态电流；后者靠近电源和驱动输入端，缓冲电机启动、PWM 调制和换向引起的低频电压变化。按主控板与两块驱动板中可辨认的元件值统计，整车电容总容量约为 0.7 mF。该值为板级标称容量之和，不等同于电机瞬态时的有效储能，后续应以 BOM 复核。
2.4.3 视觉、显示与编码器接口
主板设置两路视觉模块接口。每路接口包含相应的电源、地线和通信信号，分别连接两套 OpenART Plus。视觉模块完成识别后，主控通过 UART 接收地图、车位和 ID 等结构化数据。双视觉模块采用独立数据链路，可以避免将不同任务数据混在同一串口协议中，也使地图识别与 ID 识别能够分别进行调试。
主板上的 OLED 接口用于连接调试显示屏。OLED 不参与游戏画面显示，也不参与任务决策；它用于呈现当前模式、视觉通信状态、菜单参数、编码器速度、姿态信息或任务执行进度，使现场调试时无需连接外部上位机即可判断程序状态。壳体内部的 5 英寸无线屏则是游戏系统画面的显示终端，供两套 OpenART Plus 摄像头识别地图和第一人称信息。
编码器接口向四路正交编码器提供电源和信号连接。对于速度反馈，接口的可靠性比排线长度更重要：编码器信号若因连接松动而丢脉冲，主控会误判轮速，进而使速度环输出异常。因此编码器线应避开动力线的大电流回路，并在接头处完成拉力释放和绝缘处理。
2.4.4 控制信号引出
主控板向前、后两块驱动板引出控制信号。每组信号包括 PWM 调速、方向控制、驱动使能和公共参考地。PWM 用于调节电机平均驱动电压，方向信号决定 H 桥输出极性，使能信号用于控制驱动板是否处于工作状态。前后两组控制线分别接入对应位置的驱动板，构成“主控计算—驱动板功率放大—电机执行”的闭环链路。
尽管控制信号幅值较低，但其参考地与连接完整性直接影响驱动板对 PWM 和方向信号的判定。装配时应首先确认主控地与驱动板控制侧地的连接关系，再检查 PWM、方向和使能线的插针定义。动力地的回流路径、控制地的参考关系以及信号隔离电路需要共同考虑，不能仅凭“线已接通”判断系统可靠。
2.5 有刷电机驱动板设计
2.5.1 双 H 桥功率结构
前后各一块电机驱动板，每块板包含电机 A、电机 B 两路驱动，因此可覆盖四个有刷直流电机。每一路使用 MOS 管 H 桥：上、下桥臂按控制时序导通，使电机两端形成正向或反向电压，从而实现正转、反转、制动、停止和 PWM 调速。
H 桥的功率回路直接连接电机电源和电机绕组，工作时电流变化较快。电机在起动、急停和换向时会产生较大的反电动势和电流波动，若缺少合理的驱动与滤波设计，可能导致电源跌落、主控复位或通信异常。因此驱动板将功率器件、栅极驱动、输入滤波和控制隔离集中布置，并通过较粗动力线连接电池和电机。

图 2.6 智能视觉驱动板电路原理图
2.5.2 栅极驱动与使能控制
主控的 GPIO 和 PWM 输出电流有限，不能直接快速驱动大功率 MOS 管栅极。驱动板采用专用栅极驱动芯片，将来自主控的逻辑控制信号转换为适合桥臂 MOS 管开关的栅极驱动信号。栅极驱动电路的作用包括提高开关速度、减少开关损耗、避免桥臂长期处于不完全导通状态，并在使能控制下实现驱动输出的统一开闭。
驱动板设置芯片使能相关电路。当系统上电、通信尚未建立或任务处于停止状态时，使能控制可使功率桥保持关闭，避免电机在控制信号未确定时出现误动作。正常运行后，主控根据任务状态和速度环输出逐步调整 PWM 与方向信号，驱动板再将逻辑控制量转换为电机端的实际功率输出。
2.5.3 控制信号隔离与抗干扰
电机驱动侧存在大电流开关和较强的电磁干扰，控制侧则包含 RT1064、视觉模块和传感器接口。为降低两侧相互影响，驱动板在控制信号输入处设置隔离电路。隔离并不意味着系统各部分完全没有电气联系，而是通过受控的信号传递和参考关系，降低功率侧噪声对主控弱电信号的直接耦合。
除隔离外，整车抗干扰还依赖于以下工程细节：
• 动力线采用较粗导线，缩短电池至驱动板、驱动板至电机的路径；
• 编码器、视觉排线和其他低电平信号线尽量不与动力线长距离平行；
• 连接器、开关、电源线和电机线均进行固定，减少机械振动造成的瞬时接触不良；
• 主板和驱动板上的滤波、去耦电容靠近相应电源和芯片布置；
• 先验证控制信号逻辑和空载方向，再进行整车带负载测试。
编码器信号虽然不直接承载大电流，却直接影响轮速闭环和位置估计。连接时需要同时确认供电、公共地、A/B 相和计数方向；若只在软件中临时修改某一路符号而没有排查实际方向，前进测试可能暂时正常，但横移和旋转组合运动会出现轮速关系错误。编码器方向确认应在四轮运动学参数进入整车测试前完成。
2.5.4 驱动板安装与电机连接
两块驱动板分别布置在车体前、后区域，靠近相应轮组和电机。这样能够缩短电机线，减少线束在底盘上反复折返。驱动板通过螺钉、支撑件或固定结构安装在车架上，板边与轮组、传动齿轮及可能发生挤压的位置保持距离。

2.6 整车接口关系与布线
整车的关键连接可概括为四类：
1. 电源链路。 3S 电池分别向主控板和两块驱动板供电；主控板再生成 5 V、3.3 V 和视觉模块独立供电支路。
2. 视觉通信链路。 两套 OpenART Plus 分别通过 UART 与 RT1064 连接，发送地图、车位与目标 ID 等结构化数据。
3. 反馈链路。 四路编码器和主控板上的 IMU660RB 向 RT1064 提供运动状态信息。
4. 执行链路。 RT1064 向前后驱动板输出 PWM、方向和使能信号，驱动板控制四个有刷直流电机，最终带动车轮运动。

2.6.1 结构与电路的协同约束
中央壳体的分层结构并非只为容纳器件。摄像头与无线屏之间的相对位置决定透视校正角点是否长期有效；主控板与 IMU 的固定方式决定姿态数据是否受支架振动影响；电池侧挂位置会改变横移时的重心偏移；驱动板与电机的距离影响动力线长度和压降。因此，机械改造完成后仍需在上电、视觉标定和底盘运动三个阶段分别检查结构是否保持稳定。
装配时还应预留维护空间。电池需要能够快速拆装，驱动板电源端和电机端应能在不拆下中央壳体的情况下检查，视觉排线和串口线则不应成为拆装电池时的受力点。对比赛系统而言，便于复现和现场维护的布线方式通常比极端紧凑的布线更可靠。
2.7 本章小结
车体以原有四驱麦克纳姆轮底盘为基础。中央壳体内上置两套 OpenART Plus、下置 5 英寸无线屏；RT1064 主控板固定在壳体上方，OLED 用于菜单和调试显示，电池通过魔术贴固定在壳体侧面。四路编码器与 IMU660RB 为底盘控制提供速度和姿态反馈。电路部分采用主控板与前后两块有刷电机驱动板的组合：主控板负责多电压供电、接口扩展和控制信号输出，驱动板通过双 H 桥、栅极驱动、滤波和隔离将控制量转换为四路电机功率输出。

第三章 视觉处理与串口通信设计
3.1 视觉系统任务与双模块分工
智能视觉组的场地信息并不直接来自外部摄像头或上位机文件，而是由游戏系统在 5 英寸无线屏上显示地图和第一人称画面。两套 OpenART Plus 安装在中央壳体内部上方，摄像头朝下对准无线屏；无线屏位于壳体内部下方。这样，摄像头、屏幕和支架之间的相对位置固定，视觉模块能够持续读取同一显示平面上的任务画面。[4]
两套 OpenART Plus 分别运行独立程序，避免将地图解析、车辆定位和目标 ID 分类塞入同一视觉循环。
表 3.1 两套 OpenART Plus独立程序 

OpenART Plus 1 处理规则性较强的地图画面，主要利用透视校正、颜色分割和网格统计获得可规划地图；OpenART Plus 2 处理数字和卡通类别等目标图像，使用两套 MobileNet 模型进行分类。RT1064 不接收原始图像，而是接收视觉模块整理后的地图、位置和 ID 数据。这种职责划分使视觉端负责“看清画面”，主控端负责“理解任务并驱动车辆”。
3.2 OpenART Plus 1 地图与车位识别
3.2.1 图像采集与固定视场
地图识别程序采用 RGB565 像素格式和 QVGA 分辨率，图像尺寸为 320×240。采集端关闭自动增益和自动白平衡，使在相同无线屏亮度、相机高度和壳体遮光条件下的颜色数据保持相对稳定；相机帧率设置为 60 帧/s。[4]
无线屏、摄像头和支架构成固定的近距离采集系统。与直接拍摄实际赛场不同，主要误差来源集中在屏幕亮度、反光、相机安装角度、镜头到屏幕的距离和屏幕边框遮挡。因此，视觉程序不需要在每帧重新寻找完整场地边界，而是使用经安装调试得到的四个固定角点：左上、右上、右下、左下。代码中的固定角点为 (33,27)、(290,33)、(291,213)、(33,222)，用于将屏幕内的有效地图区域映射到标准矩形。
3.2.2 透视校正与单应矩阵
即使摄像头与无线屏大致平行，镜头安装误差也会使屏幕中的矩形地图表现为梯形。若直接按原始像素坐标切分网格，屏幕边缘处的格子宽高会发生变化，容易将墙、终点或箱子映射到相邻格。为此，地图模块使用四点透视校正，将采集图像中的有效地图区域转换为 320×240 的标准场地平面。

3.2.3 LAB 颜色阈值与网格判定
校正后，程序在 LAB 色彩空间内按类别分割颜色。地图模块定义了灰色墙、紫色终点、黄色箱子、红色炸弹、绿色车体标记和青色车体标记的阈值。相比直接使用 RGB 阈值，LAB 的亮度与色度分量相对独立，更适合在无线屏亮度存在轻微波动时维持颜色分类的稳定性。
静态地图识别不直接统计整格像素，而是使用网格中心区域作为 ROI。代码将中心采样区域设为网格宽高的 70%，用以减小相邻格边界、粗线条和显示锯齿对判定的影响。墙格和终点格的颜色占比分别达到设定阈值后，才被写入静态地图：

箱子和炸弹属于动态物体。建图时，若某格中黄色、红色、绿色或青色色块占比超过动态遮挡阈值，程序不会用该帧对墙和终点进行判定，以免被目标物遮挡的格子被错误写入静态地图。对于跨越多个网格的大色块，程序不会简单按一个连通域只记一个格子，而是对色块覆盖范围内的每个格子重新检查中心 ROI，以降低相邻箱子被合并后漏检的概率。
3.2.4 四帧投票建图
单帧画面可能受到无线屏刷新、屏幕反光、瞬时模糊和颜色边界锯齿影响。地图模块在收到 RT1064 的地图请求后连续采集 4 帧。每帧分别统计墙、终点、箱子和炸弹在各网格中的出现次数，再按照有效帧数和全局帧数计算通过门槛。对于最外圈格子，程序直接强制写为墙，以保持比赛地图边界一致。
多帧投票的处理顺序为炸弹、箱子、终点、墙、空地。动态物体优先于静态要素写入，能够避免黄色箱子或红色炸弹覆盖在终点格上时，将当前任务状态错误解释为仅有终点。投票后的结果存入全局二维数组，并在需要发送时复制一份临时地图；车辆位置在复制图上叠加为数值 12，不破坏原始静态地图。
3.2.5 车辆位置识别
车辆位置由绿色和青色两类标记共同确定。程序分别提取两类色块，并从每类候选中选择像素数最大的色块，排除屏幕边缘小面积噪点或反光区域。当两类标记均存在时，取两个中心点的平均位置；当只有其中一类存在时，使用该类中心点。所得像素坐标经单应矩阵映射到校正场地坐标。
位置数据以 16 位坐标形式发送。若当前帧未检测到有效车辆标记，程序将当前位置置为空，并在回复时发送零值坐标。该处理使主控能够区分“位置未更新”与“存在一个有效的零坐标”，后续状态机可据此决定是否继续执行动作或进入保护处理。
3.2.6 地图结果的有效性约束
地图识别输出并不把每个颜色像素都当作有效场地信息。静态颜色只在中心 ROI 达到比例门槛、并经过四帧投票后写入地图；黄色、红色和车体颜色作为动态遮挡信号，会阻止同一帧把被遮挡格误判为墙或终点。动态对象优先叠加到静态地图，保证规划器首先看到当前可推动的箱子和炸弹，而不会只看到其下方被遮挡的终点。
边界格采用固定墙体语义，避免无线屏边缘、透视残差或图像裁剪导致车辆规划到场地外。输出地图在发送时与当前车位分开管理：静态/动态地图作为任务快照，车位作为叠加信息。这样，主控刷新车辆位置时不会改变墙、终点、箱子和炸弹的原始识别结果。
当颜色阈值、透视角点或屏幕亮度发生变化时，系统首先表现为投票结果不稳定、某些格反复在空地和目标之间切换，而不是立即由底盘表现为路径错误。因此，视觉调试先在图像端检查校正画面、ROI 覆盖范围和色块占比，再检查主控端的地图编码与路径结果。该顺序能够减少把视觉问题误归因于规划器的情况。
3.3 OpenART Plus 2 目标 ID 识别
3.3.1 模型加载与识别模式
目标 ID 模块启动后加载两套 MobileNet 分类模型，并读取对应标签文件。两套模型分别服务于数字类和卡通类识别请求，避免用同一分类器处理视觉特征差异较大的目标。
摄像头同样使用 QVGA 图像。程序在初始化阶段启用水平镜像，在主循环中启用垂直翻转，使摄像头朝下安装时的画面方向与无线屏内容一致。RT1064 不要求 ID 模块持续进行神经网络推理：模块在空闲状态只刷新图像并等待请求，接收到识别命令后才选择对应模型执行分类。该按需推理方式减少了无效计算，也使主控能够在需要扫描某类目标时明确控制识别时机。

3.3.2 分类结果筛选
收到有效请求后，模块执行滑窗分类。当前配置采用最小缩放比例 1.0、缩放倍数 0.5，且不设置窗口重叠。每次推理后，程序将标签与输出概率按从高到低排序，取置信度最高的类别；只有最高置信度大于 0.9 时，该帧结果才作为候选 ID。标签名称以数字前缀表示类别编号，程序从标签首部提取连续数字得到待发送 ID。
某些类别或低置信度画面不应作为有效任务 ID。程序将不满足阈值的结果标记为无效值，并对特定保留类别进行过滤。这样，ID 模块不会因为一帧模糊、屏幕切换或模型低置信度输出而立即把错误类别发送给主控。
3.3.3 连续三帧确认
单帧分类受无线屏刷新、相机轻微抖动、画面缩放和目标遮挡影响。为提高结果稳定性，程序维护长度为 3 的历史队列。只有连续 3 帧候选 ID 完全一致时，才确认该结果并结束本轮识别；随后以 0x13 帧返回 RT1064。
连续 3 帧确认相当于在时间维度上增加了一层抗抖动滤波。它不会改变模型本身的类别边界，却能降低偶发误分类直接进入任务规划的风险。每次 ID 查询需要等待至少 3 帧，扫描排序和状态机因此应为视觉确认预留时间，而不应在发出请求后立即假设数据已经有效。
3.3.4 无效分类与按需重试
当最高置信度未达到 0.9，或者连续帧结果不能形成一致序列时，ID 模块不发送一个未经确认的类别。主控侧将该节点保留为未识别状态，而不是用上一次查询的旧结果覆盖它。任务状态机可以在等待超时后重试、跳过当前节点并在后续扫描阶段补扫，避免一帧错误 ID 直接造成箱子和终点的错误匹配。
按需触发识别也使两类目标的模型切换具有明确的边界。主控在车辆到达观察位并完成朝向确认后，才发送相应类别的请求；视觉模块返回确认结果后结束当前事务。这样可以避免车辆仍在行驶、摄像头画面尚未稳定时持续分类并产生无法对应到具体目标位置的结果。
3.4 串口帧与数据交换
3.4.1 统一帧格式
两套视觉程序均使用同一帧格式：
AA 55 | Len | Cmd | Payload | Checksum | 0D 0A
其中，AA 55 为帧头，Len 表示命令字和有效载荷的总长度，Cmd 为命令字，Payload 为数据区，校验和为从 Len 到 Payload 的逐字节求和后取低 8 位，0D 0A 为帧尾。统一帧格式使 RT1064 的通用串口解析器能够使用相同的帧同步、长度检查、帧尾检查和校验和逻辑处理两套视觉数据。
视觉模块接收数据时使用字节缓冲区。若缓冲区首字节不是 AA 或第二字节不是 55，程序丢弃一个字节后继续寻找帧头；若长度不足，则等待后续字节到达；若帧尾或校验和不匹配，同样丢弃一个字节后重新同步。该策略能够处理串口传输中可能出现的丢字节、错位或不完整帧，而不会因一次异常永久停止解析。
3.4.2 地图与车位数据
OpenART Plus 1 使用 UART4，波特率为 115200 bit/s。RT1064 发送 0x01 请求地图时，模块完成四帧投票建图并以 0x11 回复；地图数据按列优先顺序依次写入 16×12 个格子，共 192 B。地图中空地、墙、终点、箱子、炸弹和小车分别使用预先约定的数值编码，RT1064 接收后可直接写入规划器使用的二维数组。
RT1064 发送 0x02 请求车位时，地图模块以 0x12 回复。位置数据由 X、Y 两个 16 位无符号值组成，采用高字节在前的顺序发送：
Payload = XH XL YH YL
地图模块主循环还会持续更新当前车位。这样，车辆位置既可以在主控请求时回复，也可作为地图帧叠加的一部分传递。地图和车位分开定义命令，能够避免主控仅想刷新位置时重复请求完整 192 B 地图。
3.4.3 ID 数据
OpenART Plus 2 使用 UART1，波特率同为 115200 bit/s。RT1064 发送 0x03 或 0x04 选择识别类型后，ID 模块完成模型分类和三帧确认，再以 0x13 回复一个字节的 ID。与地图数据不同，ID 查询采用“请求—识别—应答”的事务式流程：主控明确提出本次需要识别的类别，视觉模块在确认结果前不回复临时分类值。

3.4.4 前台解析与异常帧恢复
视觉串口采用“中断收字节、前台组帧”的方式。接收中断不执行颜色判断、地图复制或任务跳转，只把字节放入 FIFO；前台主循环再根据帧头、长度、帧尾和校验和组装完整消息。该设计缩短了中断执行时间，避免一次地图帧解析占用控制周期。
帧恢复采用逐字节重新同步策略。收到非帧头字节时继续移动窗口；长度异常时不按该长度等待；校验和或帧尾错误时仅丢弃当前同步起点，再寻找下一组合法帧头。这样即使串口中出现丢字节、噪声或半帧，后续完整帧仍可进入主控，而不会要求重启视觉模块或清空全部接收缓冲。
3.5 视觉指标、误差与调试方法
当前系统的静态物体识别精度约为 98%，小车动态检测位置误差约为 2 cm，视觉模块工作频率约为 50 帧/s。代码中的地图相机初始化帧率为 60 帧/s；50 帧/s 为系统在实际工作条件下记录的视觉运行频率，两者不应混作同一指标。
视觉误差主要来自以下方面：
• 无线屏亮度、色彩模式或环境反光变化，使 LAB 颜色分割边界发生偏移；
• 摄像头或无线屏在壳体内的相对位置变化，使固定四角和单应矩阵不再匹配；
• 屏幕边框、排线或支架边缘进入视场，遮挡有效地图区域；
• 车辆、箱子或炸弹遮挡静态墙和终点，导致单帧地图不完整；
• ID 画面模糊、切换过快或置信度不足，使分类结果不能在 3 帧内稳定确认；
• UART 接收异常导致帧头、长度或校验和不匹配。
针对上述误差，调试时应先检查中央壳体内的机械关系：镜头是否朝下对准无线屏、屏幕有效画面是否完整进入视场、排线是否拉扯摄像头；再检查固定四角和透视校正后的网格是否与屏幕地图对齐。颜色阈值的调整应以校正后的图像为对象，分别观察墙、终点、箱子、炸弹和车体标记的 ROI 占比。ID 模块应分别用数字和卡通画面验证模型选择、置信度阈值和三帧确认逻辑。最后再用串口日志或 OLED 状态确认请求命令、回复命令、数据长度和校验和是否一致。
3.6 本章小结
两套 OpenART Plus 以无线屏画面为视觉输入，分别完成地图/车位与目标 ID 的识别。地图模块通过固定四角透视校正、LAB 颜色分割、网格中心 ROI 和四帧投票生成 16×12 栅格地图，并以颜色标记估计车辆位置；ID 模块使用两套 MobileNet 模型，在主控命令触发后以 0.9 置信度阈值和连续三帧一致规则确认类别。两套模块均采用统一帧格式与 RT1064 通信，为后续任务状态机、路径规划和底盘控制提供结构化视觉数据。

第四章 RT1064 控制软件与算法设计
4.1 软件分层与控制任务
RT1064 控制程序需要同时处理视觉输入、任务规划和底盘运动。视觉端返回的是地图、车辆位置和目标 ID，规划器处理的是离散栅格和任务约束，底盘最终需要的是四个车轮的目标角速度。若这些工作混在同一循环中，视觉延迟、路径不可达和电机跟踪误差会相互掩盖，难以定位问题。因此，软件按数据流划分为应用层、中间算法层和硬件抽象层。
应用层负责比赛流程和动作编排。它根据当前关卡选择 SIMPLE、COMPLEX 或 BOMB 任务，保存箱子、终点、ID 和子任务状态，并通过动作层启动或推进运动。应用层不直接写电机输出，也不修改规划器内部状态。
中间层包含地图求解、炸弹求解、位置融合和底盘控制计算。地图求解只接收地图、车辆位置和任务参数，返回路径或子任务；炸弹求解在临时地图状态上产生炸弹顺序和扫描折叠计划；速度控制模块将位置和姿态误差转换为车体速度，再由运动学模块转换为四轮目标角速度。中间层不读取按键、串口命令或任务状态。
硬件抽象层负责串口、编码器、IMU、电机和显示器件的驱动。串口中断只把接收字节放入 FIFO，完整帧的解析放在前台；编码器和 IMU 提供测量值，电机驱动只接收已经计算好的 PWM 或目标角速度。这样的依赖方向使任务流程、算法计算和硬件输出保持边界清晰。

4.2 初始化、时间基准与主循环
上电后，系统依次完成 OLED、按键、调试输出、电机、IMU、编码器和视觉串口的初始化。IMU 准备完成后进行静止零偏校准；四个速度环分别装载控制参数，并设置低速死区和积分限幅；随后清空位置融合历史缓冲区，启动两个周期定时器。这样可以避免上一次运行残留的编码器轨迹参与本次位置计算。
系统存在两个不同的时间尺度。PIT 通道 1 每 6 ms 产生一次控制 tick，用于编码器里程更新、位置控制、任务超时和部分底盘调度；PIT 通道 2 每 5 ms 更新 IMU。前台主循环不是固定 6 ms 周期，而是持续轮询视觉串口、解析完整帧、更新车辆位置并推进任务。任务中的等待时间统一换算为 6 ms tick，避免把前台循环执行时间误当作控制周期。

这种异步安排避免了两个常见问题：若在串口中断内执行地图复制和路径搜索，控制周期可能被长帧处理打断；若只按固定控制 tick 假定视觉已经更新，又可能在旧车位上提前进入下一动作。前台只负责尽快把可用视觉数据交给控制与任务层，控制周期仍由定时器保证。
主循环遵循“先更新输入，再推进任务，最后推进动作”的顺序。每轮先轮询两路视觉串口，获得地图、车辆位置或 ID 后更新应用上下文；任务状态机根据最新输入决定是否请求地图、规划路径、发起识别或进入回车阶段；动作层再推进当前路径点。电机控制在定时控制流程中运行，不依赖主循环恰好执行了多少次。
4.3 任务状态机与三关调度
比赛任务按具体业务分为 SIMPLE 和 COMPLEX。SIMPLE 直接根据地图完成箱子与终点的规划和推送；COMPLEX 在此基础上增加箱子和终点 ID 的观察、匹配与扫描排序。BOMB 是可插入的公共预处理任务，用于先改变软墙状态，之后再恢复原任务继续执行。
CONTINUE 是三关流程的调度器，不是新的箱子处理算法。启动后，第 0 关下发 SIMPLE，第 1、2 关下发 COMPLEX，形成 SIMPLE—COMPLEX—COMPLEX 的比赛流程。每一关的具体路径、识别和推送仍由对应任务模块负责。当前关完成后，车辆先停止并等待场地画面刷新，再进入下一关；等待期间不沿用上一关的地图和路径。
当 SIMPLE 或 COMPLEX 判断当前地图必须先处理炸弹时，任务向顶层返回切换结果，顶层进入 BOMB。BOMB 完成后只更新地图、车辆位置和已经获得的 ID，原任务从炸后对应阶段恢复，不重复执行已经完成的准备工作。任务结果分为运行中、完成、切换和异常四类：运行中继续推进，完成返回上层，切换进入炸弹阶段，异常关闭运动使能并停车。
这种安排把“关卡切换”和“具体任务执行”分开。CONTINUE 只决定下一关使用 SIMPLE 还是 COMPLEX，以及炸弹阶段结束后恢复哪一个任务；它不直接生成推箱路径，也不绕过规划器向底盘下发动作。
4.4 位置估计与视觉延迟补偿
视觉模块以约 50 帧/s 更新车辆位置，而编码器里程在控制周期内连续变化。视觉坐标反映了场地中的绝对位置，但存在图像处理、无线屏传输和串口传输延迟；编码器更新及时，却会受到轮胎打滑和麦克纳姆轮横移误差影响。控制程序因此保留一段带时间戳的编码器位置历史，用于将视觉帧与其采集时刻附近的车辆状态对齐。
当前使用固定延迟匹配。收到一帧视觉坐标时，先在历史缓冲区中找到约 280 ms 之前的编码器位置，再用下式修正到当前时刻：
融合位置 = 视觉位置 +（当前编码器位置 - 延迟时刻编码器位置）。
该计算保留视觉坐标的绝对参考，同时利用编码器补上从图像采集到当前控制时刻之间的位移。历史缓冲区按 6 ms 控制周期写入，长度足以覆盖视觉链路的延迟范围。首次获得视觉帧时，程序用视觉坐标初始化编码器位置起点，并清空旧历史，避免上电前的里程数据污染融合结果。
设视觉帧反映的是时刻 t-delta 的位置，当前编码器积分位置为 p_enc(t)，历史缓冲区中与视觉帧对应的编码器位置为 p_enc(t-delta)，视觉测量为 p_vis(t-delta)，则融合位置可写为：
p_fuse(t) = p_vis(t-delta) + p_enc(t) - p_enc(t-delta)。
这一关系并不假设编码器长期无误差，而是只利用较短延迟区间内的相对位移补偿视觉滞后。视觉负责消除长期累计漂移，编码器负责填补视觉帧之间的连续运动。对于麦克纳姆轮横移和转向过程中可能产生的滑移，系统仍需要依靠实车标定和后续视觉帧进行校正。
融合位置不可用时，控制模块按照输入有效性回退到当前视觉位置或编码器累计位置。车辆栅格位置也由同一位置来源转换得到，规划器和动作层不会分别维护两套互相独立的车位。融合模块还比较视觉帧间位移和编码器位移，检测“画面几乎不动而车轮持续运动”的冻结现象，并保留该诊断结果供调试使用。
4.5 动作计划与离散路径执行
规划器输出的是栅格路径，动作层负责将其变成可以逐段执行的运动计划。一个计划包含路径点序列、当前点索引、是否需要最终朝向以及动作状态。任务层只能启动计划、轮询计划结果或复位计划，不能直接修改路径数组、路径索引和底盘控制状态。
普通移动先由地图求解得到逐格路径，再提取起点、转折点和终点。动作层向速度控制模块逐个设置目标栅格；当前位置到达并稳定后，才推进到下一个路径点。观察任务在路径末点还要确认朝向，推箱任务则由联合状态搜索同时给出车辆接近段和推送段。每个动作结束后返回运行中、完成或异常，任务模块据此进入下一阶段。
多个箱子连续执行时，系统先分别为每个子任务生成经过真实地图验证的路径，再尝试拼接。相邻子任务的重复端点会被删除，跨边界的同向共线点通过叉积为零、点积为正的条件判断后删除；转弯、掉头和推送接触点仍然保留。若某一段无解、拼接后超过动作缓冲容量或拼接结果无法复核，则退回逐子任务执行，不影响任务正确性。
动作计划的基本状态为“路径执行—转向命令—转向等待—完成”。路径点全部到达后，若任务要求观察方向，则先执行原地转向并等待姿态到位；否则直接结束。动作层不把“已经没有待执行点”直接解释为成功，只有在计划成功装载的前提下才向上层报告完成。
路径执行阶段始终只推进一个当前点。每轮控制中，动作层重复确认该点仍是当前目标；速度控制返回到位后，路径索引才加一。这样的设计避免视觉位置短时波动使动作层一次跨过多个格点。观察位、推箱和推弹任务虽然都使用同一动作计划骨架，但其路径来源不同：观察位来自目标周围的可达站位，推箱来自车—箱联合搜索，推弹来自炸弹联合搜索。动作层只负责执行，不重新解释这些任务的业务语义。
4.6 坐标变换与麦克纳姆轮运动学

编码器里程反向使用相同的轮速关系计算车体纵、横向速度，再依据 IMU 偏航角旋转到地图坐标并积分。不同方向的横移和直行使用独立的滑移补偿系数，以减小麦克纳姆轮滚轮接触造成的轴向累计误差。视觉融合对绝对位置进行校正，编码器则提供控制周期内的连续变化。
4.7 速度闭环、姿态控制与到位判定
4.7.1 四轮速度闭环
运动学模块给出每个车轮的目标角速度，编码器测得实际角速度。轮速控制采用前馈与 PID 修正叠加的方式：前馈项根据目标角速度的正反方向估计所需 PWM，PID 项根据目标与实际角速度误差补偿负载、摩擦和电池电压变化。四个车轮分别使用独立参数，停车时清零 PWM 并复位积分项，避免下一次动作继承上一段运动的累积误差。
低速死区用于抑制电机在目标值接近零时的来回抖动，积分限幅用于避免长时间偏差造成积分饱和。速度环只关心轮速跟踪，不判断箱子是否完成或当前处于哪一关；任务语义由上层状态机保持。
4.7.2 姿态控制
车辆朝向控制以目标偏航角和 IMU 当前角度之差为输入。角度误差先归一化到负 180° 至正 180° 范围，避免跨越角度边界时选择大于半周的旋转方向。姿态控制由比例项和角速度阻尼项组成，输出车体角速度，并进行上下限限制。
姿态控制设置两个不同阈值：较小的死区用于停止微弱修正，较大的到位容差用于判断动作是否可以进入下一阶段。观察位动作要求车辆在位置到达后保持目标朝向，只有位置和姿态都满足条件才请求视觉 ID；推箱动作不在箱子移动段中插入独立姿态动作，推送方向由路径序列确定。

位置误差被分解为目标方向上的速度向量后，再依照当前偏航角转换到车体纵横向。对于横移主导和前后主导的动作，控制器分别采用不同的速度增长步长，以适应麦克纳姆轮在两个方向上的响应差异。速度分量小于设定阈值时被置零，防止车辆在已经接近目标时因极小速度指令持续爬行。
当融合位置与目标距离小于约 3 cm，位置环将平移速度置零、停止电机并复位四轮速度环。随后连续保持若干个控制周期，确认车辆没有因惯性重新离开目标区域，才将该点标记为到达。动作层收到到达结果后推进路径索引；若需要最终朝向，则转入姿态等待，否则结束当前动作。
本部分小结
当前控制软件形成了从视觉输入到车轮输出的完整链路：应用层管理 SIMPLE、COMPLEX、CONTINUE 和 BOMB，位置模块用固定延迟匹配融合视觉与编码器，动作层管理路径点和转向阶段，位置环生成车体速度，麦克纳姆运动学分配四轮目标角速度，轮速 PID 最终输出电机 PWM。下一部分将在这一执行基础上展开栅格路径、LOS、推箱分解、观察位 TSP、炸弹搜索和扫描折叠算法。
4.8 栅格地图与求解边界
视觉模块返回的场地被转换为 16 列、12 行的栅格地图，每格约 20 cm。地图中的空地、墙、终点、箱子、炸弹和车辆位置使用统一的坐标表示，规划器只在这一坐标系中工作。地图进入求解器后会被复制为当前任务的快照，任务规划过程中产生的临时箱位、软墙状态和车辆位置不会反向修改视觉输入。
不同对象的通行语义需要分开处理。车辆可以在空地和终点格之间移动，经过终点不会触发箱子消失；墙、箱子和未处理炸弹会阻断车辆路径。推箱时，箱子前方必须是空地，或者是当前子任务分配给它的目标终点；其他终点不能被箱子占用，否则会提前改变后续匹配关系。炸弹规划还要额外维护软墙存活状态，炸弹清除软墙后，新的地板立即对车辆和后续炸弹生效。
求解器容量按最多 8 个箱子和 8 个子任务组织，原始路径和后处理路径均受单条路径长度上限约束。规划结果明确区分三种情况：已经得到可执行方案、在完整搜索空间内确认无解、搜索预算耗尽但尚未证明无解。只有第一种情况进入动作层；预算耗尽会交给上层决定是否切换快速策略或保留诊断信息。
4.9 带朝向的方向状态 Dijkstra
4.9.1 状态和扩展
普通空车路径采用带朝向的方向状态搜索。状态由车辆所在栅格 (x, y) 和进入该格时的朝向 h 组成。每次只沿上、下、左、右扩展到相邻格，扩展前检查目标格是否在地图内、是否被墙、箱子或炸弹占用，并根据当前任务决定终点格是否允许车辆通过。[6]
与只记录位置的 BFS 相比，带朝向状态能够区分“从北侧进入同一格”和“从西侧进入同一格”这两种后续转向代价不同的情况。候选路径的代价按字典序比较：第一关键字是移动步数，第二关键字是方向变化次数。只有步数相同，才优先选择转弯较少的路线，因此不会为了少转一次弯主动增加明显的行驶距离。
4.9.2 回溯和执行化
搜索过程中为每个状态保存前驱状态和累计代价。目标位置第一次从优先队列中稳定取出后，程序回溯得到逐格路径，再提取起点、终点和方向改变点。动作层不直接执行所有逐格点，而是把连续同向的点压缩为一个目标段；转折点和需要最终对准的终点保留。
如果车辆已经因为上一段动作或地图变化偏离原起点，旧路径不继续使用，而是用最新车辆位置和地图快照重新搜索。这样路径的有效条件始终与实际执行时的地图状态一致。
4.9.3 代价比较与不可达处理
方向状态搜索中的每个状态保存二元代价 (s, t)，其中 s 是累计步数，t 是累计转向次数。由状态 (x, y, h) 向相邻方向 h_new 扩展时，候选代价为：
s_new = s + 1
t_new = t + 0，当 h_new = h；否则 t_new = t + 1。
更新规则先比较 s_new，步数相同时再比较 t_new。因此，在同一地图上，算法不会为减少一次转弯而主动走更长路线；但当两条路线经过相同数量的栅格时，优先使用对底盘更平顺的方案。车辆初始朝向未知或刚完成复杂动作时，可以以多个初始方向参与比较，最终仍由同一代价规则选出路径。
搜索队列为空而目标未被稳定取出时，说明在当前地图快照和通行语义下目标不可达。此时动作层不装载半条路径，也不会以直线距离替代路径；上层需要先处理阻挡物、刷新地图或调整任务顺序。这个约束把“规划器找不到路线”和“底盘尚未运动”明确分开。
4.10 LOS 视线简化与路径安全
LOS 是在轴向路径已经通过搜索验证后进行的路径后处理，不替代基础可达性搜索。其目的在于利用麦克纳姆底盘可以斜向运动的特点，删除空旷区域中不必要的直角转折。算法从当前保留点开始，向路径末端反向寻找最远的可直连点；如果直连失败，就退回更近的点，保证每次至少向前推进一个路径点。[7]
直连判定采用 supercover 网格遍历。线段不仅检查经过的中心格，还检查斜线贴角时同时擦过的两个旁侧格，从而避免用普通 Bresenham 近似时漏掉非 45° 斜线的碰撞格。墙、箱子和炸弹均视为阻挡；起点和最终要停靠的目标格按照车辆可站立条件处理。
由于车辆具有实际尺寸，箱子和炸弹周围还要进行八邻域障碍膨胀。膨胀只用于否决可能擦过实体角的斜线，不改变基础 BFS 已经验证的轴向可达性；如果膨胀使某条斜线无法通过，算法退回原轴向转折路径。推箱任务进一步将路径分为箱子静止的接近段和箱子移动的推送段：前者可以做 LOS 简化，后者只保留轴向推送转折，禁止用斜线替代正交推箱动作。
LOS 的实现已完成几何单测和实车冒烟验证，但正式比赛配置仍使用经过验证的轴向转折路径。因此，报告将 LOS 作为已完成的路径优化设计和安全验证写入，不把它表述为当前比赛计时成绩中的默认执行路径。
为了便于说明 supercover 的必要性，可将一条从栅格中心到栅格中心的斜线看作依次穿越若干纵向、横向网格边界。当下一条纵向边界和下一条横向边界在同一参数位置被穿过时，车辆轨迹会同时擦过两个旁侧格；只检查对角落点会遗漏其中一个障碍。supercover 在这种贴角情形下同时检查两个旁侧格和对角格，因此不会把“中心轨迹看似没有进入墙格、实际却从箱子角边擦过”的路线误判为安全路线。
LOS 只删除中间点，不生成新的绕行点，也不改变起点、终点和推送方向。它的收益来自减少不必要的停车、起步和转向，而安全失败时的代价仅是恢复到已经由 Dijkstra 或推箱搜索验证过的原始路径。这种单向优化使路径简化不会扩大任务的不可执行风险。
4.11 单箱推送与死锁控制
4.11.1 车—箱联合状态
推箱不能只搜索箱子从起点到终点的移动路线。对每个箱子状态，车辆必须先到达箱子后方的推送位，箱子前方还必须有可进入的目标格。因此单箱求解同时记录车辆位置和箱子位置，车辆绕行和箱子推进共同决定下一状态。
每次扩展枚举四个正交推送方向。候选动作成立需要满足：车辆能够绕到箱子后方；箱子前方不越界；箱子前方不是墙、炸弹或其他箱子；箱子不会进入其他子任务的终点；推送后车辆与箱子位置能够继续形成合法状态。车辆接近箱子后方的路径使用普通空车搜索得到，不能用两点的直线距离代替。
4.11.2 路径输出与终点规则
单箱求解输出车辆接近段、推送段和箱子位置变化的对应关系。动作层按“接近推送位—对准—连续推送—重新绕行”的顺序执行，每次推送完成后再使用更新后的车辆位置和箱子位置验证下一段。若视觉刷新发现箱子或车辆状态与规划快照不一致，动作层停止剩余路径并请求重新规划。
车辆可以经过任意终点格，但箱子只能进入当前分配的目标终点。这条规则避免一个箱子在搜索过程中经过其他终点后提前消失，导致剩余箱子和终点数量不一致。对墙角、无后方接近空间的通道末端等明显死锁位置，候选会优先被排除；无法仅凭局部规则证明安全的状态，则继续交给真实联合搜索复核。
联合状态搜索的前驱记录同时保留“上一车位、上一箱位和本次移动方向”。回溯时，车位连续变化而箱位不变的区间被识别为接近段；箱位发生一格变化的时刻被识别为推送段。这样动作层不需要根据路径形状猜测何时接触箱子，而能按搜索结果装载完整序列。对同一箱子连续推送时，车辆位置会自然跟随到箱子原位置；若下一次推送方向改变，求解器必须再次证明车辆能绕到新的后方位置。
单箱求解的成功条件不是“箱子离终点更近”，而是箱子实际到达已分配目标格；失败条件也不是某一个方向被堵住，而是所有车—箱联合状态都无法继续扩展。这个区别使上层可以把单箱失败用于否定某个匹配或排序，而不是错误地认定整张地图无解。
4.12 多箱任务分解与路径拼接
4.12.1 候选匹配
多箱任务先建立箱子与终点的候选匹配表。表中的代价不是箱子坐标到终点坐标的几何距离，而是箱子推进下界、车辆到首个推送位的真实可达距离以及必要的方向变化。候选表用于排除没有目标的箱子和没有来源的终点，同时为后续顺序搜索提供下界；最终方案仍需逐个调用真实车—箱搜索确认。
4.12.2 小规模方向 B
箱子数量较少时，系统先用贪心方式得到一条完整可执行序列，作为当前上界。随后进行深度优先搜索，每个节点保存已经完成的箱子集合、剩余匹配、车辆位置和当前地图。每选择一个箱子—终点匹配，就运行单箱求解；成功后更新车辆和箱子状态，再进入下一层。
搜索使用匹配下界剪枝：剩余箱子各自最小候选代价之和与当前已用代价相加，如果已经不可能优于上界，就停止展开。节点数量设有上限，避免复杂地图长期占用主控计算时间。预算内找到的序列必须全部通过真实单箱路径回放，不能将估计距离直接当作执行路径。
4.12.3 大规模快速分解
箱子较多或自由匹配终点较多时，系统采用快速分解。它先按照候选数量、推送代价和对通道的影响选择较优匹配，逐项进行真实单箱验证；若贪心方案失败，只对最近的有限决策做 early-exit 回退。单箱回退搜索设置独立次数预算，预算用尽返回“未证明”，不返回“确认无解”。
4.12.4 子任务拼接
分解器输出的是有序子任务，每个子任务包含箱子起点、目标终点、子地图和全图箱子位置。动作层先逐个生成已验证路径，再尝试合并为一条连续运动计划。合并只删除重复端点和跨子任务边界的同向共线停顿点，不删除转向、掉头和推送接触点；合并失败则退回逐子任务模式。
多箱求解特别强调“估计代价”和“执行代价”的区别。候选匹配表和匹配下界只服务于排序搜索，帮助尽早排除明显差的分支；真正进入动作计划的每个子任务仍需从当时的车位重新运行联合搜索。若一个排序在估计模型下较短、但因前一个箱子改变通道后无法通过真实搜索，它不会被装载到运动计划。由此，优化目标可以追求时间效率，但可执行性始终是先决条件。
对于预算耗尽，任务模块保留的是“尚未证明”而非“确认无解”。这在比赛地图较大、自由匹配组合较多时尤为重要：提高预算可能得到方案，调整任务顺序也可能恢复可行性。将预算耗尽、单箱不可达和完整搜索无解分别返回，有助于调试时定位是计算量、地图识别还是规则约束导致的问题。
4.13 观察位选择与 TSP 扫描排序
4.13.1 观察位选择
目标 ID 不能在目标所在格直接读取。规划器枚举目标上、下、左、右的相邻候选观察位，检查候选格是否可站立、车辆能否到达，以及到位后车辆朝向是否能指向目标。当前观察位策略先计算四个候选的真实路径长度，再在不超过最短路径 3 格的容差范围内，优先选择与当前车头转向差较小的候选；若没有候选满足容差，则回到最短路径观察位。[8]
这种选择不是单纯追求少走几格。观察任务通常需要停车、转向、等待视觉识别，适当增加少量行驶距离换取较少的原地旋转，整体时间可能更短。观察位一旦确定，动作层必须驶向该具体格并保持对应朝向，不能在执行阶段重新选择另一个“最近观察位”。
4.13.2 真实距离矩阵
TSP 节点代表待扫描的箱子或终点，节点间距离由车辆从一个节点的可站观察位到另一个节点的可站观察位的真实地图路径计算。起点到第一个节点也用同样规则计算。墙体、箱子和炸弹造成的绕行会直接反映在距离矩阵中，因此不会把被墙隔开的两个近邻坐标错误地当成低代价相邻节点。
4.13.3 精确与有界求解
节点不超过 10 个时，系统先用多起点最近邻生成可行上界，再进行 DFS 分支定界。搜索中的当前路径代价加上已知下一条边代价作为下界；当该值已经不小于当前最优解时剪枝。得到的最优路径是固定起点、无需回到起点的开放路径，符合扫描任务的实际流程。
节点超过 10 个时，完整排列会明显增加主控计算时间，系统改用多起点最近邻，并对每个候选执行有限轮 best-improvement 2-opt。2-opt 每轮尝试反转一段节点顺序，只接受能降低真实路径代价的结果，最多执行 16 轮。该策略不保证大规模全局最优，但会明确限制计算量，且不会生成不可达边。
扫描顺序确定后，任务模块并不一次性把所有 ID 标记为已知，而是逐节点执行“移动到观察位—确认朝向—请求相应类别—等待确认结果”的事务。只有视觉模块返回经过连续确认的 ID，才写入当前箱子或终点记录；请求超时、低置信度或动作异常时，该节点仍保持未识别状态。这样，TSP 负责缩短可达节点的访问顺序，ID 的有效性仍由视觉确认和任务状态机共同保证。
4.14 炸弹序列与动态地图搜索
4.14.1 动态状态
炸弹处理采用独立的动态状态副本。状态包含软墙存活位图、箱子和终点状态、剩余炸弹、车辆位置以及已执行的炸弹序列。每个候选序列在自己的状态副本上模拟爆破，清除的软墙只影响该候选，不会污染同层的其他候选。
炸弹候选必须满足车辆可以到达炸弹后方、炸弹可以沿正交方向被推入规则允许的墙格，且推送完成后新的状态仍能被表示。车辆经过终点格不构成障碍，但炸弹和箱子的占用关系必须按动态状态重新判断。
4.14.2 Beam 搜索与收益评价
多个炸弹的顺序会改变后续可达区域，完整枚举容易超出主控时间。因此每一层只保留评分靠前的 4 个部分序列。评分不简单统计清除墙的数量，而综合考虑焦点箱是否获得新的推送方向、其他箱子是否被解锁、原本不可达的终点是否被打通、新炸弹是否可用、车辆可达区域是否扩大，以及车辆接近和推送代价。
评分后的候选按照“炸后地图、箱子布局、终点状态、剩余炸弹和车辆位置”组成的终态去重。若多个历史顺序得到相同终态，只保留收益较高或接近距离较短的一项。对评分靠前的状态，规划器进一步调用普通多箱分解，优先采用炸后仍能生成可执行推箱子任务的状态。没有物理候选、炸后无法分解和搜索预算耗尽分别作为不同结果保留。
当常规两弹搜索因短视评分全部失败时，系统允许一次有界铺垫回退，尝试先打开后续动作需要的通道，再重新评价收益。该回退不是无限扩大搜索，而是受限的补救分支，防止“先铺路、后产生收益”的有效顺序被第一步局部评分淘汰。
炸弹阶段的核心判断是“爆破是否改变后续任务的可执行性”，而不是“本次爆破清除了多少个墙格”。例如，清除一面无关软墙即使视觉上变化明显，也不一定增加任何箱子的推送位；相反，打通一个死终点附近的窄口可能只清除少量墙格，却能让多个箱子重新获得匹配和接近机会。因此，收益评价和炸后普通推箱复核必须同时存在：前者缩小搜索空间，后者确认最终结果不会破坏完整任务。
4.15 炸弹路径扫描折叠与 skip-pair
4.15.1 接近段与推送段划分
COMPLEX 任务的 ID 扫描可以与炸弹路径合并。对每个炸弹任务，先将车辆路径划分为自由接近段和车辆与炸弹耦合的推送段。接近段允许车辆为观察 ID 做有限绕行；车辆进入炸弹起始格后进入连续推送段，此后不插入观察站，避免改变推弹动作的连续性。
4.15.2 爆破窗口和观察站机会
第 k 个炸弹任务使用第 k 个炸弹尚未爆破时的地图窗口。规划器从该窗口的接近段所有路径格进行多源 BFS，得到车辆从接近路线到各候选观察站的距离。观察站必须能够站立并且相邻于至少一个待扫描箱子或终点；一处观察站可以停下后通过不同朝向扫描多个相邻节点。
所有窗口的观察站机会先统一收集，再做集合覆盖选择，而不是在每个窗口内遇到第一个可行位置就立即分配。每轮优先选择“新增扫描节点多、代价小”的机会，剩余节点交给炸后普通 TSP。这样可以利用后续软墙清除后出现的新观察位，也能利用车辆本来就要经过的推送站位。
4.15.3 真实行驶代价约束
仅使用“观察站到接近段的往返距离”会低估真实代价，因为车辆可能需要从上一站继续走到下一站，再前往炸弹。当前选站评分同时加入三部分：理论绕路、上一站到当前站的真实 BFS 距离、当前站到炸弹推送位的真实距离。前两项用于抑制站点分散和累计绕路，后一项用于避免选择虽然靠近窗口起点、却远离最终推弹位置的观察站。
每个窗口还限制观察站数量和累计额外绕路。若下一站会使累计绕路超过限制，则不再接受该站，未覆盖节点保留给炸后扫描。扫描请求失败或观察站不可达时，节点保持未识别状态，不影响炸弹动作继续执行。
4.15.4 skip-pair 和炸后补扫
在炸弹计划确定后，系统以最后一个炸弹任务的预计车位和炸后地图为输入，枚举每个“箱子—终点”保留组合。对每个组合，从全体箱子和终点中移除这一箱一终，再复用同一距离矩阵和有界 TSP 计算剩余节点的扫描代价，选择代价最小的组合。这样跳过的是对整体扫描路线影响最大的一对，而不是固定跳过某个编号。
扫描折叠阶段不扫描保留对，炸后只为仍未获得 ID 的节点建立 TSP。其余节点完成扫描后，利用箱子侧和终点侧的 ID 出现次数差推断保留对：箱子侧多出的 ID 对应被跳过的终点，终点侧多出的 ID 对应被跳过的箱子；若两侧计数全部相同，则检查是否存在只在保留对中出现的共同 ID。计数不满足一对一匹配条件时放弃推断并回退完整扫描，避免把不确定结果交给推箱匹配。
这一策略成立的前提是当前关卡中箱子和终点数量相等，且每个 ID 在箱子侧和终点侧均遵循一对一对应关系。若对象数量不足以可靠推断、炸后地图不可达或剩余节点的 TSP 无法建立，系统不启用保留对，而是退化为扫描全部节点。保守回退保证时间优化失败时只增加行驶量，不改变任务匹配的正确性。
4.16 规划—控制执行闭环
规划器的输出都必须经过动作层转换。空车路径变成目标栅格序列，单箱求解变成接近和推送交替的路径，TSP 变成观察位访问顺序，炸弹搜索变成推弹子任务和炸后地图，扫描折叠变成具体观察站、朝向和 ID 请求。动作层每完成一个关键点，都重新读取实际车辆位置并检查下一段是否仍处于原规划地图中。
如果路径点到达、朝向到位或 ID 返回失败，任务状态机按对应结果推进；如果动作异常、地图刷新或车辆实际位置与计划差异过大，则停止剩余计划并重新求解。炸弹完成后不沿用爆破前路径，而是以炸后地图和当前车辆位置重新生成普通推箱或剩余扫描任务。由此，算法输出不是一次性固定轨迹，而是可以在关键状态变化后重新验证的执行计划。
4.17 本章小结
本章的控制与算法形成四层闭环。底层以 IMU、编码器和视觉融合结果估计车辆状态，位置控制和麦克纳姆逆运动学生成四轮目标，轮速 PID 完成实际驱动；动作层将离散路径转成带到位和姿态确认的运动计划；求解器通过方向状态 Dijkstra、车—箱联合搜索、多箱分解和 TSP 生成普通任务；炸弹规划再以动态软墙、Beam 搜索、扫描折叠和 skip-pair 处理复杂地图。每一层都以真实可达性和失败可诊断为约束，避免将几何上较短但车辆无法执行的路线交给底盘。

第五章 制作调试与实测结果
5.1 制作与调试方法
整车调试采用由局部到整体的顺序。先确认电源和单个硬件模块，再检查视觉通信与传感器数据，随后进行底盘单向运动、位置控制和任务算法测试，最后才进行连续关卡运行。这样可以把“不能上电”“数据没有到达”“路径不可执行”和“电机没有按目标运动”等问题分开定位。
调试过程中，主控 OLED 用于查看菜单、当前任务和状态信息，串口调试信息用于观察地图、车位、ID 和规划结果，视觉屏继续承担比赛画面显示。算法调试则使用保存的地图和测试模块复现路径、TSP、炸弹和扫描折叠过程，再把通过复核的方案放回整车运行。
5.2 机械与电源联调
机械安装首先检查中央壳体的刚度和视觉模块的相对位置。两套摄像头需要保持朝下，且镜头、无线屏和壳体之间不能出现遮挡；主控板固定在壳体上方，避免与摄像头支架互相干涉；电池用魔术贴固定在壳体侧面，既便于更换，也避免电池在线束拉扯下移动。四个车轮和编码器线束沿底盘边缘固定，不能进入麦克纳姆轮滚轮的运动范围。
电源调试按输入端、稳压支路和驱动支路分级进行。上电后先确认主控板逻辑电源和 OLED 工作，再接入视觉模块，最后使能电机驱动。实测约 12 V 工作电压下，整车静态电流约为 0.35 A，输入功率约 4.2 W；电机开始运动时，电流通常约为 0.74 A，输入功率约 8.9 W。运动电流会随地面摩擦、加速和负载变化，因此该数值用于记录典型状态，不作为整车最大电流。
主控板和两块驱动板的电容总容量根据原理图中可辨认器件值粗略估计约为 0.7 mF。该数值尚未以完整 BOM 复核，报告中将其标记为估算值。电源联调重点观察电机启动和换向时逻辑电源是否稳定、视觉串口是否出现连续错误帧以及 OLED 是否异常复位。
5.3 视觉与串口联调
视觉联调先分别验证地图模块和 ID 模块，再验证两路 UART 与主控的联合运行。地图模块需要确认四角透视校正后场地网格边界稳定，墙、终点、箱子和炸弹的颜色分割结果能够映射到正确栅格；车辆位置识别需要检查绿色和青色标记中心计算是否随车辆移动连续变化。ID 模块则先分别发送数字类和卡通类识别请求，确认模型选择、置信度筛选和连续三帧一致确认逻辑有效。
串口调试按帧头、长度、命令、负载、校验和和帧尾逐项检查。地图请求和车位请求分别验证返回数据长度，ID 请求验证返回的目标类型和单字节 ID。遇到半帧、错帧或校验失败时，解析器丢弃当前错误帧并继续寻找下一组帧头，避免一次通信异常使任务状态长期停留在等待阶段。
视觉测试记录的静态物体识别精度约为 98%，车辆动态检测位置误差约为 2 cm，视觉处理频率约为 50 帧/s。误差主要可能来自无线屏画面变化、摄像头安装角度、车体振动、标记遮挡和串口传输延迟。位置控制使用视觉与编码器的延迟补偿结果，减小单帧视觉坐标滞后对运动过程的影响。
5.4 传感器与底盘调试
四路编码器调试首先确认计数方向和电机编号对应关系，再分别给出低速前进、后退、横移和转向指令，观察实际轮速与目标轮速是否方向一致。若某一路方向相反，先修正轮子安装或信号符号，再进行速度环参数调整。IMU 调试在静止状态下完成零偏校准，之后检查车辆原地旋转时偏航角变化方向和角度连续性。
底盘控制调试分为轮速环、姿态环和位置环。轮速环先让四个车轮独立跟踪目标角速度，再叠加纵向、横向和角速度命令；姿态环检查原地转向时是否能够在目标角附近稳定；位置环最后接入视觉和编码器融合位置，检查车辆到达栅格中心后是否减速、停止并保持稳定。观察位测试还要确认车辆停下后朝向正确，才能向视觉模块发送 ID 请求。
调试中重点关注两个问题：一是麦克纳姆轮横移时四轮速度组合容易产生方向偏差，二是目标点附近若仍保持高速，车辆会因惯性越过观察位或推送位。系统采用分段速度和制动距离控制，在接近目标时降低速度，并在位置误差进入容差后复位轮速环积分，减少下一动作受到上一动作残差的影响。
5.5 路径与任务算法调试
算法调试先使用固定地图验证空车路径和单箱推送，再加入多箱匹配、TSP 扫描和炸弹状态变化。空车路径重点检查车辆朝向是否参与代价比较，以及转折点压缩后是否仍保持可达；推箱任务重点检查车辆是否能够绕到箱子后方，以及非目标终点是否被错误占用。
多箱任务调试同时观察可执行性和计算时间。小规模场景使用带上界和下界的搜索，确认剪枝不会删除已知可行顺序；箱子较多时使用快速分解，并检查预算耗尽是否与确认无解区分。TSP 调试使用真实地图距离矩阵，检查观察位不可达时不会生成虚假短边。
炸弹调试在临时状态副本上进行。每次候选推弹都检查车辆后方可达性、炸弹前方墙格、爆破后软墙变化和普通推箱可分解性。扫描折叠调试进一步检查接近段与推送段的边界、观察站覆盖节点、站间距离和累计绕路。若观察站不可达或 ID 请求失败，节点保留为未识别状态，炸后再由剩余扫描计划补齐。

第六章 结论
6.1 设计成果
本项目完成了一套面向智能视觉竞赛的麦克纳姆轮模型车。整车以四驱 M 车模为基础，采用中央大壳体承载两套 OpenART Plus、两颗摄像头和 5 英寸无线屏，RT1064 主控板安装在壳体上方，3S 2200 mAh 电池通过魔术贴固定在侧面。主控板上的 OLED 独立承担菜单和调试显示，和用于比赛画面显示及视觉识别的无线屏相互分工。
视觉端完成地图、车辆位置和目标图片 ID 的结构化识别，主控端通过 UART 接收结果并执行任务调度。软件将 SIMPLE、COMPLEX、CONTINUE 和 BOMB 组织为可恢复的任务状态，算法层完成地图建模、方向状态路径搜索、车—箱联合推送、多箱分解、观察位 TSP、炸弹动态规划和扫描折叠，动作层再将这些结果转换为底盘运动计划。
6.2 技术指标与运行结果
当前资料能够确认的系统指标包括：整车质量约 2.1 kg，外形尺寸约 282 mm × 120 mm × 150 mm；静态物体识别精度约 98%，动态车辆检测位置误差约 2 cm，视觉模块频率约 50 帧/s；约 12 V 工作电压下静态电流约 0.35 A，电机开始运动时通常约 0.74 A；主控板与两块驱动板总电容容量根据原理图粗略估算约 0.7 mF。
华南赛区比赛计时截图记录三关用时分别为 18.363 s、41.267 s 和 39.765 s，总计 99.395 s。该结果表明整车已经完成过连续三关的实际运行，视觉、任务规划和底盘执行能够在同一系统中协同工作。
6.3 局限与改进方向
系统仍有以下限制。复杂地图中多箱任务的搜索时间会随箱子和终点数量增长，需要进一步改善分解策略和计算预算；炸弹规划虽然已经加入动态软墙、有限宽度搜索和炸后可分解性验证，但困难地图仍需要更充分的回归覆盖；扫描折叠当前不能将终点格作为观察位，可能使部分节点无法在推弹接近段完成识别；电容总容量仍是原理图估算值，应使用 BOM 或完整设计文件复核；任务异常停车已有保护路径，但独立人工急停和错误回程的最终策略仍需完善。
后续改进可以从四个方向展开：一是补充不同地面、负载和电池电压下的底盘标定数据，建立更稳定的轮速和滑移补偿；二是增加复杂箱子数量和多炸弹地图的离线回归，进一步压缩搜索时间；三是完善视觉失效、串口异常和任务超时的安全收敛；四是根据正式比赛记录补充多次重复测试，形成更完整的统计结果。
6.4 本章小结
本项目形成了从视觉识别、通信传输、任务调度、路径算法到麦克纳姆轮闭环控制的完整智能车系统，并取得了可核验的视觉指标和三关计时结果。现阶段系统的主要矛盾已从“各模块能否工作”转向“复杂场景下能否更快、更稳定、更易诊断”。后续工作将围绕求解效率、视觉与底盘协同标定、电气参数复核和安全机制完善继续进行。

    }
    if (Task_GetMode() == TASK_SIMPLE) SimpleTask_Tick();
    if (Task_GetMode() == TASK_COMPLEX) ComplexTask_Tick();
}
A.2 路径点闭环控制
bool Motion_TrackGridPoint(const Pose *target)
{
    float ex = target->x - g_pose.x;
    float ey = target->y - g_pose.y;
    float yaw_error = AngleNormalize(target->yaw - g_pose.yaw);

    if (fabsf(ex) < POS_EPS && fabsf(ey) < POS_EPS &&
        fabsf(yaw_error) < YAW_EPS) {
        Motion_Stop();
        return true;
    }

    float vx = PID_Update(&g_x_pid, ex);
    float vy = PID_Update(&g_y_pid, ey);
    float wz = PID_Update(&g_yaw_pid, yaw_error);
    LimitVector(&vx, &vy, MAX_TRANSLATION_SPEED);
    wz = Clamp(wz, -MAX_YAW_SPEED, MAX_YAW_SPEED);

    Motion_SetBodyVelocity(vx, vy, wz);
    return false;
}
A.3 麦克纳姆轮逆运动学
void MEC_Update(void)
{
    const float k = MEC_LX + MEC_LY;
    float w_fl = (s_vx - s_vy - k * s_wz) / MEC_R;
    float w_fr = (s_vx + s_vy + k * s_wz) / MEC_R;
    float w_rl = (s_vx + s_vy - k * s_wz) / MEC_R;
    float w_rr = (s_vx - s_vy + k * s_wz) / MEC_R;
    Motor_SetTargetOmega(MEC_FL, apply_inv(MEC_FL, w_fl));
    Motor_SetTargetOmega(MEC_FR, apply_inv(MEC_FR, w_fr));
    Motor_SetTargetOmega(MEC_RL, apply_inv(MEC_RL, w_rl));
    Motor_SetTargetOmega(MEC_RR, apply_inv(MEC_RR, w_rr));
}
A.4 视觉数据帧有效性检查
bool Vision_FrameValid(const uint8_t *buf, uint16_t len)
{
    if (buf == NULL || len < FRAME_MIN_LEN) return false;
    if (buf[0] != FRAME_HEAD_0 || buf[1] != FRAME_HEAD_1) return false;
    if (buf[len - 1] != FRAME_TAIL) return false;
    return Vision_Checksum(buf, len - 2) == buf[len - 2];
}
A.5 带朝向状态的路径扩展
void Search_ExpandState(const SearchState *cur, SearchQueue *queue)
{
    for (uint8_t next_dir = 0; next_dir < 4; next_dir++) {
        Point next = PointStep(cur->pos, next_dir);
        if (!Map_IsPassable(next, g_search_map)) continue;

        SearchState candidate = *cur;
        candidate.pos = next;
        candidate.heading = next_dir;
        candidate.steps = cur->steps + 1;
        candidate.turns = cur->turns + (next_dir != cur->heading);

        int index = SearchStateIndex(next, next_dir);
        if (!g_closed[index] ||
            CostLess(candidate.steps, candidate.turns,
                     g_best[index].steps, g_best[index].turns)) {
            g_best[index] = candidate;
            g_prev[index] = cur->index;
            Queue_Push(queue, &candidate);
        }
    }
}

bool Search_BuildPath(Point start, Point goal, Path *out_path)
{
    Search_Reset();
    Search_PushStartStates(start);
    while (!Queue_Empty(&g_open)) {
        SearchState cur = Queue_PopBest(&g_open);
        if (g_closed[cur.index]) continue;
        g_closed[cur.index] = true;
        if (PointEqual(cur.pos, goal))
            return Search_Backtrack(cur.index, out_path);
        Search_ExpandState(&cur, &g_open);
    }
    return false;
}
A.6 开放路径 TSP 扫描顺序
void TSP_Dfs(uint16_t visited, uint8_t last, int cost)
{
    if (cost >= g_tsp_best_cost) return;
    if (visited == g_tsp_all_mask) {
        g_tsp_best_cost = cost;
        memcpy(g_tsp_best_order, g_tsp_order, g_tsp_count);
        return;
    }

    for (uint8_t next = 0; next < g_tsp_count; next++) {
        if (visited & (1u << next)) continue;
        int edge = g_tsp_distance[last][next];
        if (edge >= OPTIMAL_INF) continue;
        int lower_bound = cost + edge + TSP_RemainingLowerBound(visited, next);
        if (lower_bound >= g_tsp_best_cost) continue;
        g_tsp_order[PopCount(visited)] = next;
        TSP_Dfs(visited | (1u << next), next, cost + edge);
    }
}

bool TSP_SolveOpenPath(uint8_t start_node, uint8_t *out_order)
{
    TSP_InitUpperBound(start_node);
    TSP_Dfs(1u << start_node, start_node, 0);
    if (g_tsp_best_cost >= OPTIMAL_INF) return false;
    memcpy(out_order, g_tsp_best_order, g_tsp_count);
    return true;
}
A.7 可达观察位选择
bool Solver_FindNearestPointIndex(Point current_pos,
                                  const Point *points, int point_count,
                                  uint8_t map[MAP_ROWS][MAP_COLS],
                                  uint8_t *out_index)
{
    int best_distance = OPTIMAL_INF;
    int best_index = -1;
    for (int i = 0; i < point_count; i++) {
        int distance = calc_distance_bfs(current_pos, points[i], map);
        if (distance < best_distance) {
            best_distance = distance;
            best_index = i;
        }
    }
    if (best_index < 0) return false;
    *out_index = (uint8_t)best_index;
    return true;
}
A.8 炸弹状态到工作地图导出
void BombSolver_ExportWorkMapFromState(
        const BombState *state, uint8_t out_map[MAP_ROWS][MAP_COLS])
{
    if (state == 0 || out_map == 0) return;
    memset(out_map, MAP_CELL_EMPTY, MAP_ROWS * MAP_COLS);
    for (int y = 0; y < (int)MAP_H; y++) {
        for (int x = 0; x < (int)MAP_W; x++) {
            if (state->base[y][x] == CELL_WALL)
                out_map[y][x] = MAP_CELL_WALL;
            else if (state->base[y][x] == CELL_GOAL)
                out_map[y][x] = MAP_CELL_GOAL;
            else if (Is_Soft_Wall_Alive(state, x, y))
                out_map[y][x] = MAP_CELL_WALL;
        }
    }
}
