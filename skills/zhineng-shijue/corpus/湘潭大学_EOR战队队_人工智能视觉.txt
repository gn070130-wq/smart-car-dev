摘要
本车以恩智浦 32 位单片机 i.MX RT1064 为核心控制器，依托其高内核处理速度提供卓越 CPU 性能与实时响应。以双 Open-ART Mini 为核心视觉传感器：Open-ART1 完成场地地图采集、单应逆透视校正及车体视觉定位；Open-ART2 对数字（0–9）及米老鼠、大头儿子等 10 类卡通人物进行分类识别。主控融合视觉坐标、编码器轮速与 IMU 偏航角，形成“视觉定位 + 陀螺航向 + 编码器测速”的组合导航闭环，经麦克纳姆轮逆运动学与增量式 PID 实现全向运动控制。路径规划针对 12×16 栅格地图中的箱、目标、炸弹与墙体约束，采用 A* 完成观测阶段（P1）与推箱阶段（P2）求解，并以切线拉线压缩路径。整个系统设计包括了车模机械结构设计和软/硬件系统设计。车体机械结构设计主要包括 Open-ART 摄像头识别数字与卡通图像、前后轮的调节、车模重心调节、主控板和驱动板的安装、各传感器的安装、舵机以及编码器的安装等；硬件部分的设计契合智能车的功能需求，遵循低功耗、高转化率、高安全性、高耐用性以及操作简便等。为了提高模型车的速度和稳定性，使用 Matlab、VOFA+ 上位机、虚拟示波器、OpenMV IDE、Keil5 等工具，进行了大量硬件与软件测试。实验结果表明，该系统设计方案确实可行。
关键词：路径规划，A*，PID，Open-ART，智能视觉，图像分类


引言
随着现代科技的飞速发展，人们对智能化的要求日益渐增，智能车辆是一个 
集环境感知、规划决策、多等级辅助驾驶等功能于一体的综合系统，它集中运用了计算机、现代传感、信息融合、通讯、人工智能及自动控制等技术，是典型的高新技术综合体。目前对智能车辆的研究主要致力于提高汽车的安全性、舒适性，以及提供优良的人车交互界面。近年来，智能车辆己经成为世界车辆工程领域研究的热点和汽车工业增长的新动力，很多发达国家都将其纳入到各自重点发展的智能交通系统当中。
全国大学生智能汽车竞赛是以“立足培养、重在参与、鼓励探索、追求卓越”为指导思想，鼓励创新的一项科技竞赛活动。竞赛要求在规定的汽车模型平台上，使用恩智浦半导体公司的微控制器作为核心控制模块，通过增加摄像头、惯性传感器、电机驱动模块以及编写相应控制程序，制作完成一个能够自主读取场地地图、识别数字与卡通目标，并完成排雷、分类匹配与推箱任务的模型汽车。参赛队员的目标是使模型汽车按照规则以尽可能短的时间完成地图解析、目标识别与路径执行。
该竞赛以恩智浦半导体公司为协办方，得到了教育部相关领导、恩智浦公司领导与各高校师生的高度评价，已发展成全国 30 个省市自治区 400 余高校的全国大学生智能汽车竞赛。

第一章 系统整体设计

车模的系统组成框图如图1所示。 


图1 车模系统组成框图

我们采用“RT1064 主核 + 双 Open-ART 协处理”的方案：主核执行传感器信息融合、车模位姿维护、电机控制与比赛状态机；Open-ART1 独立完成运算量较大的地图识别与视觉定位，Open-ART2 独立完成目标分类推理。IMU 获取车模运行时 yaw 轴角速度，经零偏标定与低通滤波后积分得到航向；电机磁编码器测得四轮转速，经增量式 PID 实现轮速闭环，并与视觉坐标共同构成车体平面运动反馈。基于当前视觉位姿、航向角以及规划器给出的栅格路径点，可求解车体在地图系下的期望速度，再经坐标旋转变换与麦克纳姆轮逆运动学得到四轮速度指令，使用 PWM 经由电机驱动对转速进行控制。Open-ART2 识别到箱子或目标的类别后，主控据此完成箱–目标配对，并执行推箱路径。

第二章 智能车机械结构设计

智能车中的控制都是在一定的机械结构基础上实现的，因此在设计整个软件架构和算法之前一定要对整个车模的机械结构有一个感性的认识，然后建立相应的数学模型。从而再针对具体的设计方案来调整赛车的机械结构，并在实际的调试过程中不断的改进和提高。本章将主要介绍智能车车模的机械结构。
此次比赛选用的赛车车模采用 M 型车模。赛车机械结构只使用竞赛提供车模的底盘部分及转向和驱动部分。整车由4个麦克纳姆轮进行驱动。

图2 车模

整车机械机构从前到后以此由电磁铁、机械臂、前置双电机驱动、目标板存放装置、后置双电机驱动、主控板、电池以及摄像头支架构成。
电磁铁采用的是逐飞科技直径2.5cm的电磁铁。机械臂由3个RDS3218舵机和连接件组成，支撑底板采用亚克力板切割而成，存放目标板的卡盒用3D打印制作。前置部分的任务是拾取地面的卡片并将其精准投放到指定的收集框中。在此部分上有安装摄像头框架的孔位。
前置电机驱动安装亚克力支架板下，利用车模自有孔位安装电机以及编码器。 车模收集框之后还应装有带有挡板的舵机，用于控制收集框的开关，实现装载和卸下目标卡片。
车模尾部亚克力板搭载有后置电机驱动以及主控板。主控板和电机驱动板交错安装。主控板通过铜柱加高并且使用立方体螺母直立安装。电池用胶水固定在主控板底部并于主板相连。摄像头支架采用十字架形式，支撑架做的足够粗，使七尽可能稳定不摇摆，使摄像头尽可能不受震动的影响。 


第三章 硬件电路设计

为满足使用需要，硬件电路主要需要设计一个主板和连个电机驱动板。主板的作用是连接RT1064单片机核心板和智能车所需的各种外设，从而使单片机可以对编码器、Open-ART、电磁铁、舵机、摄像头、电机、陀螺仪等设备进行通信和控制；同时，其也对电源电压进行稳压，从而为不同外设提供所需的工作电压。驱动板的作用是为电机提供驱动电压，并接受来自主板的单片机控制信号，并将控制信号转化为电机的转速和转动方向。

3.1 供电系统设计 
智能车系统由3块锂电池并联供电，锂电池固定在车模上。主板对电池提供的电压进行稳压。本主板中存在如下几种电压：
电池电压11.1v~12v。在电路原理图中的标识为VBAT。其连接到驱动板、开关及稳压电路，当开关接通时稳压二极管驱动 MOS 管导通，使电池正极与VBAT相连，实现电路通电。此处MOS管采用HY19P03。
主板上用于稳压到其他的电压的5V电压。在电路原理图中的标识为5V。通过DC-DC稳压芯片SY8205FCC将12V稳压得到5V。采用DC-DC方案进行稳压而不是采用线性稳压器的原因是DC-DC方案进行稳压功耗小，对主板散热的要求相对没有那么高，但是它的电路设计起来要麻烦一些。
主板上的3.3V电源。在电路原理图中的标识为3V3。通过LDO芯片RT9013-33将5V稳压得到3.3V。用于给除摄像头外，连接到主板的需要3.3V电源的设备供电，如RT1064单片机核心板、编码器、蜂鸣器、姿态传感器、IPS屏幕等。
主板上的5V外设电源。在电路原理图中的标识为5V_EXT。由5V经过电源负载开关SY6280得到5V_EXT。
主板上的5V~6V舵机电源。在电路原理图中的标识为VServo。通过DC-DC稳压芯片SY8205FCC将12V稳压得到舵机电源。
主板上的24V舵机电源。在电路原理图中的标识为24V。通过DC-DC升压芯片SX1308将12V进行升压得到24V电源。

第四章 软件系统设计及实现
软件系统采用裸机加周期中断的架构，不依赖实时操作系统线程调度。按时间尺度划分，主要任务如下：
1 ms 周期中断（PIT_CH2）：读取 IMU 原始角速度；每 5 ms 完成一次零偏补偿、一阶低通滤波与偏航角积分。上电约 1 s 后锁定初始航向并允许发车。
2 ms 周期中断（PIT_CH0）：读取四路编码器，完成轮速增量式 PID、航向 Turn_PID、视觉位置 PID，以及麦克纳姆轮逆运动学解算与 PWM 输出。
串口中断：分别接收 Open-ART1 的地图/坐标数据、Open-ART2 的分类结果，以及无线串口调参指令。
主循环：以有限状态机调度读图停靠、取图、路径规划、路径跟踪、看方向识别与关卡切换。
调试任务：无线调参、IMU 数据流与空跑测图可在编译开关下独立进入，不干扰正式比赛流程。
下面将介绍上述模块的实现细节。

4.1 周期中断与轮速闭环
编码器测速采用 M 法。在 2 ms 控制周期中，用本次计数值减去上次计数值，除以时间间隔并乘以车模标定系数，得到车轮实际转速。四路编码器均做窗口滤波，以抑制量化噪声对闭环的影响。
轮速控制采用增量式 PID。根据直线加速/减速工况切换两套参数：加速段提高比例系数以增强跟随能力，减速段增大积分作用以抑制稳态误差。控制器输出 PWM 至驱动板，使各轮快速达到并稳定在期望转速。
四轮期望转速由麦克纳姆轮逆运动学由车体速度（vx, vy, ω）解算得到。其中 vx、vy 来自视觉位置环，ω 来自航向环。将四轮实际转速作为内环反馈，构成“位置/航向外环 + 轮速内环”的串级结构。

4.2 IMU 航向解算与串口通信
姿态解算在 1 ms 中断中读取陀螺仪，并在 5 ms 节拍执行完整解算流水线，以避免高频积分被噪声主导。上电后采集若干帧静止数据求取三轴零偏；运行时先减去零偏，再以一阶低通滤波器平滑角速度，对超过死区的 z 轴角速度进行积分，得到偏航角 yaw，供转向闭环使用。
该流程等价于“零偏补偿 + 一阶互补/低通 + 航向积分”的简化姿态解算。由于比赛场地为平面运动，主要关心 yaw，因此不引入完整欧拉角与磁力计融合，以降低计算量并避免磁场干扰。
串口方面，Open-ART1 以较高波特率回传地图栅格与车体视觉坐标，Open-ART2 回传分类编号；无线串口用于在线修改速度、PID 与开关量。接收均在中断中写入缓冲区，主循环与控制中断按标志位取用，避免阻塞。

4.3 主循环初始化与系统指示
主函数完成时钟、屏幕、按键、电机、编码器、无线串口、IMU、双 Open-ART 串口及 PIT 的初始化。
初始化 IMU 后先进行陀螺零偏标定，再等待两路 Open-ART 就绪标志。随后根据编译开关进入正式比赛、无线调参或空跑测图。核心板 LED 与蜂鸣器用于指示系统运行与关键事件，屏幕用于显示关卡与调试信息。
与基于 RT-Thread 的多线程方案相比，本设计将强实时控制全部放入 PIT，主循环只做逻辑调度，时序更确定，也便于在 Keil 中断点调试。

4.4 视觉伺服、航向闭环与运动学解算
路径跟踪在地图坐标系下进行。Open-ART1 给出车体像素坐标后，与当前栅格目标点比较得到位置误差。外环采用视觉 PID，并根据剩余距离构造停车型速度曲线 v=√(2as)，在近目标处降低加速度，避免过冲。
航向外环以 IMU 积分解算的 yaw 为反馈、以 spin_angle 为给定，经 Turn_PID 输出角速度 ω。看方向识别时将 spin_angle 锁到 ±90° 或 180°；识别完成后默认不旋回，后续速度指令按该航向做地图系到车体系的旋转变换，减少无效原地转向。
得到地图系速度后，按当前航向变换到车体系，再调用麦克纳姆轮逆运动学得到四轮转速给定。视觉定位提供平面位置，陀螺仪提供航向，编码器保证轮速跟踪，三者在控制层完成数据融合。
接近目标时还设置位移容差与速度门槛，连续多拍满足条件才判定到站，以抑制视觉坐标抖动导致的反复加减速。

4.5 任务逻辑调度
用户交互（按键、屏幕）与比赛状态机在主循环中执行，优先级低于 1 ms/2 ms 控制中断，从而保证运动控制不受逻辑分支影响。
发车后状态机依次执行：驶向读图点、获取地图、P1 观测规划、路径跟踪与看方向识别、箱–目标匹配、P2 推箱规划、返回起点并切换关卡。
具体的比赛任务逻辑将放在第六章进行说明。

第五章 视觉识别算法介绍
5.1 双 Open-ART 任务划分
为降低单模块算力压力并提高实时性，视觉系统采用双机分工。Open-ART1 负责全局地图识别与车体定位，Open-ART2 负责近距目标分类。两路结果经 UART 汇总至 RT1064。
Open-ART1 采集分辨率约 578×418 的场地图像，经逆透视变换（IPM）校正为 640×480 的地图坐标系图像，与上位机及主控栅格定义一致。主控将场地划分为 12 行×16 列，格点中心由 ROI 尺寸均匀映射得到。
地图语义编码为：0 空地、1 墙、2 目标、3 箱子、4 炸弹、5 车体。主控收到地图后先校验是否存在车体格；若不存在则重新取图，避免在错误地图上规划。
定位方面，Open-ART1 持续回传车体在校正图像中的坐标。主控将其作为视觉里程计，用于路径点跟踪、到站判断以及看方向时推算被观察物体所在格点。
5.1.1 地图坐标系与栅格映射
记校正图像宽高为 W、H，则第 c 列、第 r 行格点中心为 x=(W/(2C))+c·(W/C)，y=(H/(2R))+r·(H/R)，其中 C=16、R=12。该映射保证规划器使用的离散格点与视觉伺服使用的连续坐标一一对应。
视觉 PID 的误差在地图像素系计算，再按格宽换算到厘米量纲，以便与速度曲线 v=√(2as) 中的加速度参数统一。直线方向允许更高速度，斜向运动则按方向系数降速，减少麦克纳姆轮侧移时的打滑。
当需要“看方向”时，根据当前车格与动作（上看/下看/左看/右看）得到被观察物体格点，再由相对位置决定原地转向方向，使 Open-ART2 光轴对准目标后再触发分类。
该分工避免了在同一摄像头上同时做大视野建图与近距分类：建图需要俯视全局，分类需要目标充满画面，二者视场矛盾。

5.2 AprilTag 锁定与逆透视变换
分类相机工作于近距、斜视条件，直接把原图送入网络会因透视变形导致类间混淆。因此在推理前先估计场地平面到模型输入平面的单应矩阵，将 ROI 校正为近似正视图像。
系统优先使用 AprilTag（TAG16H5）检测四枚定位码，按预定角点对应关系提取透视源四边形。为抑制抖动，要求连续多帧四边形位移小于阈值才锁定；预热阶段仅用于曝光与检测稳定，不进入锁定。
若连续多帧无法得到合法四边形（数量不足、角点越界、宽高过小或顺序异常），则回退到预先标定的固定四角，保证在个别标签被遮挡时仍能进行分类，只是几何精度有所下降。
5.2.1 单应矩阵求解
由四组对应点建立 8 参数单应方程，采用列主元高斯消元求解。推理时对 120×80 模型坐标系中的每个像素反变换到原图像素并最近邻采样，一次完成透视校正与尺度归一，避免二次拉伸。
与“先旋转校正再拷贝缩放”的两步法相比，直接单应映射减少插值次数，更适合 Open-ART 的 CPU 算力约束。校正后的图像同时保存至 SD 卡，便于复盘误识别样本并迭代训练。
5.2.2 与主控的时序配合
AprilTag 锁定完成后，Open-ART 通过串口发送锁定完成帧，主控据此认为分类相机已就绪。此后仅在收到分类命令时才进行拍照、校正与推理，空闲期只轮询串口，降低平均功耗与发热。

5.3 数字与卡通分类网络
分类任务包含两类标签空间：数字 0–9，以及米老鼠、皮卡丘、海绵宝宝、喜羊羊、唐老鸭、哪吒、大头儿子、猪猪侠、葫芦娃、灰太狼共 10 类卡通。赛图约束为：数字 i 与卡通（10+i）构成配对类，同类最多重复出现有限次数。
端侧部署采用 TFLite 轻量化分类模型。箱子命令调用卡通模型，目标命令调用数字模型。对输出向量取最大置信度，若高于阈值则回传类别编号，否则回传无效码，由主控按未识别处理。

5.3.1 训练与量化
因推理前已做逆透视，训练数据只需覆盖光照、色彩、轻微模糊及 90° 倍数旋转，不必进行大范围随机透视增广。网络骨干采用 MobileNet 类深度可分离卷积结构，在 PC 端完成训练后导出 int8 TFLite，以满足 Open-ART 内存与时延约束。
定位与分类解耦：全局目标位置由地图栅格给出，分类网络只解决“是哪一类”，而不在端侧再做一次通用目标检测。这与“先定位后分类”的两阶段思想一致，能够在嵌入式平台上同时保证准确率与实时性。

5.3.2 串口协议与失败处理
主控发送帧格式为帧头 + 命令字 + 帧尾。命令 0x03 请求卡通（箱子）分类，0x04 请求数字（目标）分类。
Open-ART 返回帧头 + 类别编号 + 帧尾。识别失败返回 255，主控记录 vis_id=-1，不参与强制配对，避免一次误识别污染整局规划。
看方向识别设有超时重发：若超过一定时间未收到结果，主控重发分类命令；仍失败则跳过该观测点，后续匹配算法允许在部分观测下做约束求解。
调试模式下可在原图上绘制透视源四边形与类别文字，便于现场判断是几何校正问题还是分类阈值问题。
5.4 分类结果到规划器的映射
主控将 0–9 视为数字目标，10–19 视为卡通箱子，并以 vis_class=id%10 映射到同一配对类。P1 路径上每个“看”动作到达后，把分类结果绑定到对应箱或目标索引；全部必要观测完成后进入匹配求解。
匹配并非简单的“看到谁就推谁”。由于同类可重复，需要在可行 1:1 分配下选择使 P2 推箱代价更小的配对。项数较少时穷举排列，项数较多时采用贪心分配并结合爬山搜索，以控制求解时延。
若识别信息不足以唯一确定配对，状态机报错并停在安全态，而不是盲目推箱。关卡 1 可配置为跳过看方向，直接按地图几何求解推箱顺序，用于无视觉约束的基准测试。
通过上述流程，视觉模块向规划模块提供的不是原始图像，而是带置信处理的离散符号（地图栅格 + 类别 ID），从而把深度学习的不确定性隔离在识别层，保证后续组合搜索的确定性。

5.5 视觉算法小结
本章方法的核心是“几何校正保证可分性、轻量网络保证实时性、协议层保证可恢复性”。AprilTag/IPM 解决透视畸变，双模型分类解决数字与卡通两类语义，超时重发与无效码解决现场丢包和低置信问题。
实验与完赛调试表明，在校正锁定稳定的前提下，端侧分类足以支撑 8 箱规模的配对与推箱；主要失败模式来自标签未锁定、目标未充满画面或运动模糊，而非网络结构本身。

第六章 比赛任务逻辑的实现
比赛任务由主循环状态机调度，控制中断始终维持轮速与航向闭环。总体流程为：
1、上电完成 IMU 零偏标定，等待双 Open-ART 就绪；PIT 计时约 1 s 后锁定起始航向并允许运动。
2、驶向读图停靠格点。到位后停止视觉跟踪，向 Open-ART1 发送取图命令。
3、校验地图中是否存在车体；若无则重新取图。通过后进入路径规划。
4、P1 阶段：规划“看方向/排雷”动作序列，用 A* 在含墙、箱、雷的栅格中搜索观测路径，并以切线拉线压缩纯行走段。
5、路径跟踪过程中，若路点动作为看方向，则原地转向并对准目标，发送分类命令，记录箱或目标的视觉 ID。
6、P1 结束后根据观测结果求解箱–目标配对；再进入 P2，用 A* 搜索推箱顺序与路径，同样进行切线优化，并追加返回起点。
7、P2 执行完毕后，若尚未完成全部关卡，则再次前往读图点开始下一关；否则进入空闲停车。
关卡 1 可跳过看方向，直接以几何可达性规划推箱，用于检验求解器；关卡 2/3 必须依赖视觉分类结果。
下面分别介绍两阶段路径求解、切线优化以及箱–目标匹配方法。

6.1 基于 A* 的两阶段栅格路径规划
场地为 12×16 栅格。实体包括墙、箱子、数字目标、炸弹和车体。炸弹需在推箱前处理，箱子必须推到对应类别的目标格。该问题具有高维离散状态（车位、箱位、雷是否已爆），不能一次性暴力搜索全部动作。
因此将任务分解为 P1 与 P2。P1 的目标是生成一条能够完成必要观测与排雷的路径，并得到更新后的地图；P2 的目标是在给定箱–目标配对后，生成代价尽可能小的推箱路径。
P1 以车体位置为状态，结合炸弹爆炸掩码进行图搜索。需要看的对象作为必须访问的动作点，炸弹作为必须触发的动作。搜索在限定时限内先返回可行解，若仍有余量则继续改进。
P2 将“推哪一只箱子、推到哪一个目标、以何种顺序”组合起来。箱数不超过设定阈值时对顺序做全排列并调用推箱 A*；超过阈值则先以贪心种子解尽快压低上界，再通过两两交换爬山与迭代局部搜索改进。
单次推箱采用 A*：g 为已走路程，h 为箱子到目标的启发距离。为加快完赛，可对启发项加权，使搜索更接近最佳优先搜索，从而在数秒时限内给出可执行路径。
求解器将地图与节点缓冲置于高速内存段，并对重复状态做哈希判重。找到第一组可行解后开启改进时间窗，超时则返回当前最优，以保证比赛节拍不被规划拖死。
6.1.1 切线拉线后处理
A* 输出的是四邻域栅格动作。纯行走段存在大量“先走格子再转弯”的冗余。后处理将看/炸动作作为不可跨越的锚点，在锚点之间做代价感知的 string-pulling（切线拉线），用全向直线连接可视点。
推箱段不参与拉线，必须沿格心推进，以免箱子轨迹偏离通道。拉线后再做共线压缩：连续同向行走合并，仅保留拐点与看/炸动作，从而减少视觉 PID 的中间停靠次数。
路径代价近似为步长加上拐点惩罚。切线优化通常能同时减小距离与转向次数，使麦克纳姆轮更多处于直线或固定斜向工况，速度曲线更容易打满。
若切线优化失败，则回退为按栅格动作逐点展开的路径，保证功能完备性。P2 路径末尾追加返回读图/起点格，便于多关卡连续执行。
该“组合搜索求可行语义路径 + 几何后处理求可执行轨迹”的两层结构，把 NP 难的推箱问题限制在离散层，把连续层交给视觉伺服，工程上更稳定。
6.2 看方向识别与箱–目标匹配
P1 路点若标记为看方向，运动控制先把该点当作普通目标驶入，到站后进入识别子状态机：按车格与物体格的相对位置选择左转、右转、掉头或不转；Turn_PID 将航向对准后发送分类命令。
Open-ART2 返回类别后，主控判断当前看的是箱子还是目标，写入对应 vis_id。默认识别后不转回原航向，而是锁定 spin_angle，后续速度做旋转变换，以节省时间。
全部观测完成后，匹配算法在“数字 i ↔ 卡通 10+i”的类约束下寻找 1:1 分配。同类重复时，在类内排列中选择使后续 P2 推箱代价更小的方案，而不是固定“先看到的先推”。
炸弹路点到站后延时触发排雷动作，再继续后续路径。跟踪过程中的转弯点不停车识别，只切换下一目标点，以保持速度连续性。
若匹配失败或 P2 无解，状态机进入错误/空闲，避免在不确定语义下推动箱子造成不可逆局面。三关完成后停止跟踪并停车。

总结与展望
大学生智能汽车比赛在大学生各类学科竞赛中算得上是战线拉得非常长的了。经过长期准备，在调车过程中我们也发现了不少问题和困难，例如视觉坐标抖动、推箱时打滑、规划超时与分类漏检等，然后一步一步地解决和改进，尝试了不同的方案。在比赛中，我们看到了其他优秀的方案，看到了别人的优点和自己的不足，通过改正调整解决了各种问题。
一个队伍中的三个人各自分工不同，但这并不代表我们不需要关注和了解其他人的工作。软件和硬件是相互依存的关系。硬件是软件赖以工作的物质基础，而软件的正常运行又是硬件发挥作用的唯一途径。因此，程序员了解硬件能更好地发现程序上的问题，也能更好地了解对硬件的需求，帮助硬件负责人更好地工作。
智能车不仅仅是我们的回忆，更承载着我们的梦想驶向远方。无论最后比赛成绩如何，我们做智能车的初心不会改变，我们对智能车的热爱也不会改变。希望智能车越办越好，希望我们变得更强！

void icm42688_att_calibrate_gyro_bias(void)
{
    for (uint16_t i = 0; i < ICM42688_ATT_CALIB_N; ++i) {
        icm42688_att_fetch_raw();
        icm42688_att_apply_scale();
        g_icm42688_att_gyro_bias.Xdata += s_icm42688_phys_gyro_dps[0];
        g_icm42688_att_gyro_bias.Ydata += s_icm42688_phys_gyro_dps[1];
        g_icm42688_att_gyro_bias.Zdata += s_icm42688_phys_gyro_dps[2];
        system_delay_ms(5);
    }
    icm42688_att_bias_div_n(&g_icm42688_att_gyro_bias);
}

void icm42688_att_filter_gyro(void)
{
    const float ga = ICM42688_ATT_GYRO_LP_ALPHA;
    for (int i = 0; i < 3; ++i) {
        const double raw_mb = s_icm42688_phys_gyro_dps[i] - gb[i];
        s_icm42688_gyro_lp_dps[i] = raw_mb * ga + s_icm42688_gyro_lp_dps[i] * (1.0f - ga);
    }
}

void icm42688_att_update_yaw(void)
{
    const double gyro_z = s_icm42688_gyro_lp_dps[2];
    if (fabs(gyro_z) > ICM42688_ATT_GYRO_DEADZONE)
        g_icm42688_att_euler.yaw += gyro_z * ICM42688_ATT_DT_READ_S;
}

void icm42688_att_pipeline_tick(void)
{
    icm42688_att_read_sensors();
    icm42688_att_filter_gyro();
    icm42688_att_update_yaw();
}

enum RESULT_STATE Task_Path_Plan(void)
{
    switch (Plan_TASK_STATE) {
    case Plan_TASK_STATE_IDLE:
        Task_GMapToTrackMap(raw_map);
        if (!track_find_robot(raw_map, &cx, &cy))
            return ERR;
        skip_classify = (level_num == 1) ? TRACK_SKIP_LOOK : 0;
        Plan_TASK_STATE = Plan_TASK_STATE_1;
        return NO;
    case Plan_TASK_STATE_1:
        if (!run_phase1(raw_map, &p1_res, 4, skip_classify))
            return NO;
        if (track_tangent_optimize(raw_map, cx, cy, p1_res.path, p1_res.path_length, 0.0f, false, tg))
            n = track_tangent_plan_to_points(tg, path_pts, MAX_PATH_LEN);
        else
            n = track_append_waypoints(p1_res.path, p1_res.path_length, &cx, &cy, path_pts, 0, MAX_PATH_LEN, 1);
        Task_Set_Path(path_pts, n);
        Plan_TASK_STATE = Plan_TASK_STATE_MATCH;
        return YES;
    case Plan_TASK_STATE_MATCH:
        if (level_num != 1 && !Task_Vision_TrySolve(box_ids, target_ids))
            return ERR;
        Task_Vision_UpdateBoxTargetMap(box_ids, target_ids);
        Plan_TASK_STATE = Plan_TASK_STATE_2;
        /* fall through */
    case Plan_TASK_STATE_2:
        if (!run_phase2(box_ids, target_ids, &p2_res))
            return ERR;
        track_tangent_optimize(p2_map, cx, cy, p2_res.path, p2_res.path_length, 0.0f, false, tg);
        task_append_home_base(path_pts, &n2, MAX_PATH_LEN);
        Task_Set_Path(path_pts, n2);
        return YES;
    default:
        return ERR;
    }
}
