摘  要
第二十一届全国大学生智能汽车竞赛人工智能视觉组采用“真实车模+虚拟游戏系统”的虚实融合比赛方式。真实车模在约3.2 m×2.4 m的平面场地内运动，虚拟系统依据车模方位标识牌获得位置与方向，并将全局俯视图和第一视角画面通过无线屏幕提供给车载视觉系统。车模需要独立完成视觉感知、地图建模、目标身份识别、推箱规划、运动控制以及三关连续比赛。
本文在往届智能视觉组技术报告写作结构的基础上，结合第二十一届人工智能视觉组最新比赛细则和计分方式，对参赛车模的机械结构、硬件电路、双视觉模块、分类模型、地图建模、推箱搜索、炸药资源规划、运动控制与调试方法进行系统设计。主控采用NXP i.MX RT1064，视觉侧采用OpenART Plus与OpenART Mini协同方案：前者负责无线屏幕全局画面的几何校正与地图元素识别，后者负责第二、三关中的数字和图像分类。决策层将虚拟场景离散为栅格地图，以玩家可达区域BFS、推箱状态BFS、死锁检测和状态去重为核心，针对三种比赛模式分别建立传统推箱、身份匹配推箱和随机目的地/炸药约束推箱流程。第三关训练方案将可用炸药数作为搜索状态的一部分，并按2次资源约束进行规划。
为提高工程可用性，软件采用显式车头方向状态与动作编译机制，将规划器的离散位移转换为UDLR平移动作以及E/Q/B原地转向动作，并允许通过小写动作在指定时机触发身份识别。报告还建立了复杂地图压力测试、重复元素测试、炸药资源测试、各关求解时间统计和三关连续运行测试方法。文中所有尚需由实车测量得到的重量、功耗、识别准确率、运动误差与最终耗时均采用“待实测”标记，避免用估计值替代比赛提交数据。
关键词：人工智能视觉；虚实融合；OpenART；推箱子；广度优先搜索；路径规划；i.MX RT1064

第1章  引言
1.1  竞赛背景与任务特点
全国大学生智能汽车竞赛是一项强调多学科交叉和工程实践的科技竞赛。第二十一届竞赛中的人工智能视觉组不再以固定赛道或电磁引导线作为唯一环境信息，而是把真实车模运动与虚拟游戏任务耦合起来：比赛系统通过场地全局摄像头识别车模顶部方位标识牌，获得车模在真实场地中的位置和方向；虚拟软件据此实时更新游戏状态，并通过车载无线屏幕向参赛车模输出全局俯视图和第一视角图像。车模只能依赖自身合法传感器和车载图像处理平台完成闭环决策[2]。
这种“硬件在环”结构使比赛核心由传统的高速循迹转向“感知—理解—规划—执行”。车模需要先从屏幕图像中获取墙体、可移动箱子、目的地、炸药等虚拟元素，再根据不同关卡要求识别箱体图案与目的地数字，最终把离散规划动作转化为实车可执行的平移、转向和推箱动作。算法正确性、识别可靠性、实车控制精度和系统实时性必须同时满足，任何一个子系统不稳定都会放大为任务失败。
1.2  第二十一届人工智能视觉组规则分析
根据第二十一届人工智能视觉组比赛细则，允许使用B、C、F、G、M、H、Y、Z等指定成品车模，车模及其附属物地面投影应限制在35 cm×35 cm范围内；车模顶部需要安装比赛现场提供的方位标识牌，标识牌采用磁吸结构，安装中心间距和高度需要符合统一要求。主控限定为NXP MCU，含MCU的视觉平台限定在比赛规则允许的NXP生态图像处理模块范围内[2][5]。
正式比赛采用三个关卡连续进行，地图由比赛系统随机选择。每关需要至少完成该关箱子数量的50%才记为有效完成；有效关卡中每遗漏一个箱子加罚30 s，每少完成一个关卡加罚300 s。每一关单独显示计时，但关卡切换、返回车库的时间仍计入总成绩[3]。因此，系统策略不能只追求“单幅地图最短路径”，而应同时考虑求解时间、执行稳定性、关卡切换效率和在难图上的保底完成率。

1.3  关键技术难点
• 屏幕图像受视角、反光、曝光和无线投屏延迟影响，必须先稳定提取全局视图与第一视角ROI，再进行语义识别。
• 推箱问题存在不可逆动作和大量死锁，普通“车到目标点”的路径规划不能直接解决箱子推动顺序问题。
• 第二、三关中箱子图案与目的地数字存在身份关系，且目标可能随机摆放，要求先探索、识别和匹配，再执行推动。
• 炸药会改变可通行墙体结构；第三关训练版本仅允许两次炸药资源，使用时机直接影响后续可达性与总代价。
• 真实麦克纳姆底盘的轮径误差、侧向滑移和转向误差会导致离散栅格动作累积偏差，因此必须建立可重复的动作原语和闭环校正。
• RT1064端同时承担任务管理、搜索规划和运动控制，需要严格限制状态结构大小、哈希表容量和临时缓冲区。
1.4  本队总体设计思路与主要工作
本方案以“模块解耦、状态统一、优先保证完赛”为总体原则。感知层负责把车载屏幕图像转换为可供算法使用的栅格地图和身份标签；规划层以统一状态结构表示玩家、箱子、目的地、墙体、识别状态和炸药资源；执行层只接收离散动作序列，并通过编码器、IMU和视觉信息将离散动作转换为实车位移。这样可将算法错误与控制误差分离，便于逐层调试。
• 以实际识别到的箱子数量作为所有状态数组和循环边界，避免把箱数写死在程序中。
• 采用“玩家可达区域BFS + 推箱状态BFS”的两层搜索，主搜索只在发生有效推动或爆破时扩展新状态。
• 加入角落、墙边和局部互锁等死锁检测，并以哈希表完成状态去重，降低高难地图的无效扩展。
• 第二关采用“观察点规划—触发识别—身份映射—正式推箱”的分阶段方法；第三关在此基础上加入随机目的地探索和炸药资源状态。
• 建立UDLR/EQB动作协议和显式车头方向状态，小写动作可表示“执行后识别”，从而把搜索结果稳定映射到实车执行。
1.5  本文结构
第二章分析比赛系统和总体方案；第三章介绍机械结构；第四章说明硬件电路；第五章重点介绍视觉感知、分类模型及识别可靠性；第六章给出三关推箱规划算法和搜索优化；第七章介绍麦克纳姆底盘运动控制与动作执行；第八章说明软件架构、内存组织和调试工具；第九章给出实验设计、压力测试与数据记录表；第十章总结系统现状及进一步优化方向。

第2章  比赛系统与总体方案设计
2.1  比赛系统组成与信息闭环
比赛系统由真实车模、平面比赛场地、场地全局定位摄像头、车载无线屏幕和虚拟游戏软件组成。全局摄像头并不是参赛车模的直接传感器，而是比赛系统用于将真实车模映射到虚拟世界的外部测量环节。参赛车模最终获得的是车载屏幕上的虚拟画面，因此车载算法仍需完成完整的视觉感知与自主决策[2]。

2.2  分层软硬件架构
车载系统采用感知层、决策层、执行层和调试层四层结构。OpenART Plus负责全局画面、地图元素与几何关系，OpenART Mini负责第二、三关中的精细分类；RT1064负责地图状态管理、推箱搜索、动作编译和系统调度；底层运动控制负责四轮速度闭环、姿态控制和离散动作落地；调试层通过串口/SWD输出地图、路径、动作数量、求解耗时和异常状态。

2.4  关卡状态机与计时策略
三关连续比赛不能用三个彼此完全独立的“测试函数”简单拼接。系统启动后首先完成传感器与视觉模块初始化，确认车模处于车库和正确初始方向；关卡开始后按照“感知—求解—执行—校验”循环工作。当本关满足结束条件时，立即冻结本关统计数据，生成返回车库路径，同时释放或重置本关地图、哈希表、识别缓存和动作队列；回到车库后等待系统进入下一关。
1. 关卡开始：记录算法起始时间与关卡编号，清零本关统计量。
2. 视觉构图：读取全局视角，建立墙体、箱子、目的地、炸药和车辆位置。
3. 任务求解：根据关卡类型选择第一/二/三关求解器，记录求解时间、扩展状态数和路径长度。
4. 动作执行：按照动作协议运行，必要时在指定观察动作后触发分类识别。
5. 结果确认：确认箱子消失、关卡完成比例以及车辆位置；若异常则进入恢复流程。
6. 关卡结束：保存统计，返回车库，切换下一关；第三关结束后停止总流程。
2.5  总体设计目标与指标体系
技术报告要求必须给出整车重量、尺寸、功耗、电容总容量、传感器种类与数量、检测精度和频率等参数[1]。本报告将指标分为“规则硬约束”“算法指标”“实车指标”三类。规则硬约束可以依据赛题直接确认；算法和实车指标必须由最终版本实测得到。
第3章  机械结构设计与安装
3.1  M型麦克纳姆轮车模平台
根据当前方案，车模采用M型四轮独立驱动平台。麦克纳姆轮能够在不改变车体朝向的情况下实现纵向、横向和平面合成运动，这一点与规则中的平面虚拟任务高度匹配：规划器可以把栅格上的U/D/L/R平移直接映射为底盘平移，而不必在每次转向后才能侧向靠近箱子。
机械设计的第一目标并非最高速度，而是“动作重复性”。推箱任务要求车模多次接触箱体、横移和原地转向；如果支架刚度不足、轮组装配角度偏差过大或重心过高，控制误差会在连续动作中快速累积。因此底盘改装应优先保证四轮同高、轮轴平行、结构对称和重心居中。
  

图3.1  车模侧视、后视与俯视实物图
3.2  电机、编码器与轮组安装
四个驱动电机分别对应一个编码器通道，便于进行四轮独立速度闭环。安装时应检查编码器同一计数周期下的方向符号、每圈脉冲数和减速比配置，避免软件中出现“同样前进命令但某轮反馈为负”的符号不一致。麦克纳姆轮的左右轮辊方向必须按车模结构成镜像布置，否则横移和旋转解算会发生方向耦合。
3.3  车载无线屏幕固定结构
规则给出的无线屏幕约4英寸，并同时显示俯视角与第一视角画面[2]。屏幕支架必须保证屏幕相对于车体的姿态固定，否则视觉标定参数会随振动改变。设计时应同时考虑屏幕拆装、供电线束弯折半径、OpenART摄像头视场和标识牌安装空间。
• 屏幕平面固定后应做机械限位，防止比赛碰撞或推箱反力导致角度变化。
• 摄像头与屏幕之间的距离和夹角在正式训练中固定，不使用手持式临时支架。
• 屏幕表面不得擅自粘贴可能违反现场规定的材料；光学抗反光优先通过安装角度、遮光罩与曝光策略处理。
• 供电和投屏线束应远离轮胎、麦克纳姆滚子和电机转轴。

第5章  视觉感知与分类模型
5.1  视觉任务划分
人工智能视觉组的视觉任务可分为“全局结构感知”和“局部身份识别”。前者关心墙、箱子、目的地、炸药和车模在虚拟地图中的位置关系，要求稳定和完整；后者关心箱体图案、目的地数字等细节，要求较高分类准确率。将两类任务拆分到OpenART Plus和OpenART Mini，有利于降低单模块同时处理大视野和细分类任务造成的算力冲突。
5.2  屏幕ROI提取与几何校正
摄像头首先确定无线屏幕有效区域，去除支架、黑边和环境背景。若摄像头并非完全垂直于屏幕，可通过四角特征点计算单应性矩阵H，将原始图像变换到标准矩形坐标系。对俯视图和第一视角分别建立固定ROI后，后续识别阈值和模型输入尺度才能保持一致。
	s · [u  v  1]ᵀ = H · [x  y  1]ᵀ	（式1）
其中(x,y)为原始图像坐标，(u,v)为校正后的标准坐标，s为尺度因子。由于屏幕与相机属于车载固定结构，H可在机械安装完成后离线标定，并在运行中仅进行小范围自检。

5.3  全局地图元素识别
全局俯视图中的元素具有固定语义，可优先采用颜色、形状和连通域方法提取。处理流程为：颜色空间转换→阈值分割→形态学滤波→连通域提取→面积/宽高比筛选→中心点计算→栅格坐标量化。对相邻目标和边缘目标，加入邻域一致性检查，避免两个目标粘连或目标被切分成多个候选。

5.4  车模位置与车头方向识别
比赛系统使用方位标识牌完成全局定位；在车载屏幕俯视图中，车模也可通过两个颜色相近但可区分的色块判断自身位置和方向[2]。本队软件同时维护视觉方向和动作历史方向：视觉结果作为绝对校验，动作历史作为高频状态来源。当两者不一致时不立即执行下一次推箱，而是先进入方向复核和重定位。

5.8  置信度、多帧融合与重识别

第6章  地图建模与多关卡推箱规划算法
6.1  栅格地图与坐标表示
为将视觉场景转换为可计算的离散规划问题，本队将当前训练地图表示为二维栅格。每个栅格记录地形类型和动态对象：空地、不可爆破外围墙、可爆破内部墙、玩家、箱子、目的地、炸药等。视觉输出的像素中心坐标通过标定关系量化为栅格坐标，所有搜索算法只在该离散地图上工作。
栅格宽高和箱子数量不写死在算法核心中，而是通过地图配置和识别结果初始化。这样既可兼容当前16×12级别训练地图，也能在后续规则或测试地图规模变化时复用同一套算法。
6.2  搜索状态定义
传统推箱状态至少包含玩家位置p和箱子集合B。第二、三关还需记录箱子身份、目的地身份和已识别状态；第三关加入剩余炸药资源r以及必要的可爆破墙状态Wb。为了避免玩家在同一箱子布局下不同空地位置造成大量等价状态，主搜索可把玩家位置压缩为“在当前箱子布局下可达区域的规范代表点”。
	S = (p, B, M_id, G_id, W_b, r)	（式2）
其中M_id、G_id分别表示箱子和目的地的身份映射，W_b表示尚未被爆破的内部墙集合，r表示剩余炸药次数。第一关可退化为S=(p,B)，第二关不使用W_b和r，第三关使用完整状态。
6.3  玩家可达区域BFS
在固定箱子和墙体布局下，玩家普通行走是一个无权栅格最短路问题。程序使用BFS从当前玩家位置出发，标记所有可达空格，同时记录父节点用于恢复从玩家当前位置到某个箱子背后“支撑格”的最短行走路径。只有支撑格可达且箱子前方落点合法时，才生成一次推动动作。
6.4  以“推动”为边的主搜索
若把玩家每一步行走都作为主搜索节点，状态数量会急剧增加。更有效的做法是：对每个箱子枚举四个推动方向，先调用可达区域BFS判断玩家能否到达箱子背后，再判断箱子前方是否为空地或合法目的地；若可推动，则生成新箱子布局，并把这一次推动视为主搜索的一条边。
这种表示把“玩家在空地中走很多步”从主搜索中剥离，主搜索规模主要由箱子推动组合决定。路径恢复阶段再利用局部BFS的parent数组补齐推动之间的普通行走路径。
6.5  死锁检测
推箱问题中最危险的不是“走远路”，而是把箱子推入无法恢复的死锁。基础死锁包括：非目标角落、沿墙无目标区域、两个箱子互相堵塞、箱子被推入目标身份不匹配且无法离开的位置等。系统在生成新状态后立即检查死锁，死锁状态不进入开放队列。
表6.1  主要死锁规则
6.6  状态编码、哈希与去重
状态去重的核心是使“同一逻辑局面”得到相同哈希键。箱子位置应排序或使用位图/紧凑数组编码，玩家位置采用可达区域规范点，第三关还需加入剩余炸药数与内部墙破坏状态。哈希表采用固定容量开放地址或其他可控内存结构，避免RT1064上频繁动态分配。
6.7  第一关：传统推箱求解
第一关只需要依据颜色和位置完成传统推箱。视觉构图完成后直接进入推箱状态搜索。搜索目标为全部箱子到达任意合法目的地；若比赛策略需要兼顾时间，可以在多个可行解之间比较推动次数、玩家移动长度和转向次数，选择更适合实车执行的方案。
6.8  第二关：识别—匹配—推箱
第二关的新增难点是“可移动箱子的图案”和“目的地数字”之间存在固定映射关系。若一开始没有完整身份信息，直接推箱可能把箱子送到错误目的地。因此求解分为观察阶段和正式推动阶段。
6.9  第三关：随机目的地与两次炸药资源
第三关在第二关基础上将目的地随机摆放，车模必须主动前往目标附近识别数字，探索成本明显增加。与此同时，地图中可能出现炸药；规则允许炸药炸除场地中间的围墙，但外围围墙不能炸除[2]。本队当前训练策略按“最多2次炸药”建模，把剩余次数r∈{0,1,2}加入搜索状态。
炸药不是“看到墙就用”的局部动作，而是改变后续拓扑的全局资源。使用一次炸药后，需要更新墙体集合并重新计算玩家可达区域、箱子可推动方向和死锁信息。搜索中只有当爆破能够提高任务可达性或明显降低总代价时才扩展该动作，并对无意义爆破进行剪枝。
	r_new = r - 1,   W_b,new = W_b \ {w}	（式3）
6.10  炸药动作的候选生成与剪枝
• 只允许对规则定义的内部可爆破墙生成炸药动作，外围墙始终不可改变。
• 若炸墙后没有新增可达格、没有新增箱子推动方向，也没有缩短关键通道，则认为该爆破无收益。
• 在只剩1次炸药时，提高资源保守程度，优先保证仍有办法完成主要箱子。
• 若某状态已在更高剩余炸药数下以不更差代价访问，则低资源同构状态可进行支配剪枝。
6.11  身份匹配与重复元素处理
对第二、三关，完成条件不是“箱子在任意目的地上”，而是“箱子身份与目的地身份匹配”。当同一类别存在多个实例时，可将匹配问题表示为一个小规模二分图：左侧为箱子实例，右侧为与其类别合法的目的地实例，边权为推箱估计代价。匹配结果作为启发信息，不强制一次确定，避免某个局部最短匹配导致整体死锁。
6.12  动作恢复与UDLR/EQB编译
搜索层输出的是地图坐标中的普通移动和推动方向，并不直接等价于实车车头动作。本队定义UDLR为四个平移方向，平移本身不修改逻辑车头；E表示右转90°，Q表示左转90°，B表示掉头180°。动作编译器根据当前车头方向和下一动作需要补充转向指令。第二、三关中，小写u/d/l/r/e/q/b表示“完成对应动作并停稳后触发一次识别”。

6.13  求解时间与内存优化
复杂地图的求解时间不仅取决于箱子数量，还与可推动方向、死锁密度、身份约束和炸药拓扑分支有关。优化时先测量“扩展节点数、哈希冲突、局部BFS次数、峰值队列长度”，再决定是否需要更强启发式。工程中优先使用静态工作区和对象复用，避免频繁malloc/free造成碎片。
6.14  超级难地图压力测试
为避免算法只在简单地图上表现良好，测试阶段需要专门构造高难地图：狭窄通道、多箱互相遮挡、多个角落伪目标、重复类别、多处可爆破墙和必须精打细算两次炸药的地图。压力测试不要求每张地图都追求最短动作，而是检查算法是否能在给定时间和内存上限内稳定返回“最优/可行/无解/超时”中的明确结果。
















第7章  运动控制与推箱执行
7.1  麦克纳姆轮运动学
设车体坐标系纵向速度为v_x，横向速度为v_y，角速度为ω，四轮线速度可由麦克纳姆轮运动学矩阵分配。不同厂家轮序和滚子方向可能不同，因此正式公式中的正负号必须以本队实际轮序标定结果为准。
	[v1 v2 v3 v4]ᵀ = A · [v_x  v_y  ω]ᵀ	（式4）
控制实现中将“前进、后退、左移、右移、原地旋转”封装为动作原语，上层规划不直接操作四个PWM。这样能够在更换轮径、调整速度环参数或增加前馈时保持规划层代码不变。
7.2  四轮速度闭环
每个车轮独立运行速度PID，编码器反馈经过方向统一和低通处理后与目标轮速比较。速度环周期固定，避免因主搜索执行时间变化而改变控制器离散采样周期。
	u(k)=K_p e(k)+K_i Σe(k)+K_d[e(k)-e(k-1)]	（式5）
7.3  位置与航向外环
离散动作结束条件不能只依赖固定延时。平移时根据编码器累计位移与视觉/地图坐标进行停止判断；原地转向根据IMU航向角变化作为主要反馈，必要时用屏幕中的车头方向进行绝对校验。外环输出期望速度或角速度，内环完成四轮跟踪。
7.4  编码器、IMU与视觉融合
编码器短时响应快，但麦克纳姆轮横移时容易打滑；IMU对角速度和转向变化敏感，但长时间积分会漂移；视觉定位更新频率相对较低，但可提供绝对位置或方向校验。因此采用“高频里程计+IMU、低频视觉修正”的互补策略：动作过程中使用编码器/IMU闭环，动作结束后利用视觉结果校验是否仍落在预期栅格附近。

7.6  推箱对准控制
推箱动作必须保证车体中心线、箱体中心和目标推动方向尽量一致。执行前先到达箱子背后的支撑格，然后用低速微调车体位置和方向；接触箱体后降低速度，避免冲击造成箱体偏转。推动结束后等待车体和箱子稳定，再读取新一帧屏幕确认箱子是否进入预期栅格。
7.7  显式车头方向状态
规划层把车头方向维护为四值状态head∈{U,D,L,R}。UDLR平移不改变head；E/Q/B根据旋转方向更新head。若视觉方向校验与head不同，则将本次状态标记为“方向不可信”，不继续执行下一推动。显式状态使动作序列可检查、可回放，也便于第二、三关在指定朝向下进行分类识别。
7.8  识别动作与运动协同
小写动作的执行流程为：完成位移/转向→速度降为零→等待短暂曝光稳定→触发Mini采样→接收分类结果→判断置信度→继续或重识别。这样可以避免“车还在动就拍照”导致运动模糊，同时将观察位置精确绑定到规划动作。
7.9  异常恢复与重定位
异常恢复分为三级：一级为局部修正，如平移不足时补偿少量位移；二级为视觉重定位，重新读取车模栅格和方向并重编译剩余路径；三级为重新规划，当箱子位置与预测状态不同、身份信息被更新或炸药动作改变拓扑时，从当前真实状态重新调用关卡求解器。
7.10  关卡切换与返回车库
比赛计时规则决定返回车库同样计时[3]。因此关卡结束后不能进行冗长的数据保存或重复标定。程序仅保存必要统计量，立即生成返库路径；返库过程中不再执行无关识别。进入下一关前清空上一关地图和哈希表，但保留底盘标定参数、车头校验模块和全局错误计数。

第10章  结论
本次围绕智能汽车竞赛虚实融合赛题的技术方案设计与落地，是一场“感知-决策-执行”全链路技术整合的实践。从硬件选型（以NXP i.MX RT1064为主控，OpenART Plus/Mini分工处理视觉）到算法设计（BFS搜索、死锁检测、哈希去重等规划逻辑），再到关卡差异化策略（三关从“传统推箱”到“身份匹配”再到“资源动态纳入状态搜索”的递进），每一步都需紧扣赛题需求做针对性优化。
过程中深刻体会到“模块化协作”的价值：视觉模块负责“看懂环境”，规划模块专注“想清路径”，执行模块保障“精准动作”，三者通过UDLR/EQB协议、车头方向状态等接口无缝衔接，让算法能转化为实车可解释、可调试的动作。同时，“鲁棒性设计”是关键——多帧视觉确认、动作结束校验、异常重规划等机制，有效降低了单次识别误差或控制偏差对全局任务的冲击，让系统在复杂场景中更具稳定性
赛题驱动下的能力跃迁：竞赛不是“纸上谈兵”，而是倒逼我们把理论知识（如BFS算法、哈希表应用）转化为解决真实问题的工具。比如“推箱状态BFS+死锁检测”，需先理解推箱游戏的数学本质（状态空间搜索），再结合实车运动约束（如转向半径、动作时序）做工程化改造，这种“理论→场景→落地”的闭环训练，极大提升了技术迁移能力。
团队协作的“齿轮效应”：从硬件调试到视觉算法调优，从规划逻辑验证到实车联调，每个环节都依赖队友的专业互补。有人专攻底层驱动，有人深耕视觉模型，有人死磕路径规划……就像精密齿轮组，只有咬合紧密才能推动项目前进。过程中也学会了“用对方语言沟通”——给硬件同学讲视觉延迟的影响，给算法同学解释底盘执行的物理限制，这种跨领域协作能力是课堂难以赋予的。
挫折里的“迭代思维”：实车调试时，曾遇到“视觉识别正确但推箱失败”“规划路径理论上可行但实车卡壳”等问题。每一次故障都是“系统漏洞”的信号：可能是视觉帧率与规划频率不匹配，可能是动作协议对车头方向的描述不够精准……通过“问题定位→假设验证→方案迭代”的循环，我们逐渐养成“不迷信理论，只相信实测”的工程思维，也更懂“细节决定成败”——一个像素的识别偏差、一次动作时序的错位，都可能让全局任务崩盘。
这次竞赛让我们触摸到智能系统落地的“最后一公里”挑战：如何让算法在算力有限的嵌入式端高效运行？如何让多模块在复杂干扰下保持协同？这些思考也为后续学习指明方向——既要深耕算法原理（如强化学习在动态场景的应用），也要强化工程素养（如实时系统调度、硬件资源优化）。
智能汽车的征程才刚刚开始，而这次竞赛教会我们的“全链路思维”“鲁棒性意识”“协作精神”，将成为未来探索更复杂智能系统时的底气。愿我们带着这份收获，在技术与创新的道路上继续破浪前行！

void mecanum_cascade_control(float raw_target_y, float raw_target_x, float raw_target_angle,
                             float curr_y, float curr_x, float curr_angle)
{
    static float smoothed_target_angle = 0.0f;
    static int is_first_run = 1;

    static float filtered_vel_x_robot = 0.0f;
    static float filtered_vel_y_robot = 0.0f;

    if (is_first_run)
    {
        smoothed_target_angle = curr_angle;
        is_first_run = 0;
    }

    float err = atan2f(sinf(raw_target_angle - smoothed_target_angle),
                       cosf(raw_target_angle - smoothed_target_angle));

    float max_step = MAX_ANGLE_SPEED * CONTROL_DT;
    float step = err * 0.2f;
    step = fclip(step, -max_step, max_step);

    smoothed_target_angle += step;

    vel_w_cmd = PidLocCtrl(&gyro, curr_angle, smoothed_target_angle);

    float vel_y_world;
    float vel_x_world;

    vel_y_world = PidLocCtrl(&Y, curr_y, raw_target_y);
    vel_x_world = PidLocCtrl(&X, curr_x, raw_target_x);

    vel_y_world = fclip(vel_y_world, -20.0f, 20.0f);
    vel_x_world = fclip(vel_x_world, -20.0f, 20.0f);

    float cos_theta = cosf(curr_angle);
    float sin_theta = sinf(curr_angle);

    float raw_vel_x_robot =
        vel_x_world * cos_theta + vel_y_world * sin_theta;

    float raw_vel_y_robot =
       -vel_x_world * sin_theta + vel_y_world * cos_theta;

    const float alpha = 0.25f;

    filtered_vel_x_robot +=
        alpha * (raw_vel_x_robot - filtered_vel_x_robot);

    filtered_vel_y_robot +=
        alpha * (raw_vel_y_robot - filtered_vel_y_robot);

    vel_x_robot = filtered_vel_x_robot;
    vel_y_robot = filtered_vel_y_robot;
}

/*
 * 技术报告附录：栅格最短路径规划子程序
 *
 * 说明：本代码展示路径规划层使用的基本 BFS 可达路径搜索。完整工程中的
 * 多箱联合状态、任务排序、启发式代价、死锁剪枝和缓存优化不在本节公开。
 */

#include <stdint.h>
#include <string.h>

#define REPORT_MAP_ROWS 12
#define REPORT_MAP_COLS 16
#define REPORT_MAP_CELLS (REPORT_MAP_ROWS * REPORT_MAP_COLS)

typedef struct {
    int8_t x;
    int8_t y;
} ReportGridPoint;

static int report_inside(int x, int y)
{
    return x >= 0 && x < REPORT_MAP_COLS &&
           y >= 0 && y < REPORT_MAP_ROWS;
}

static int report_blocked(char cell)
{
    return cell == '#' || cell == '$' ||
           (cell >= 'A' && cell <= 'Z');
}

/**
 * @brief 在 12x16 栅格地图上搜索一条无权最短路径。
 *
 */
int report_plan_grid_path(const char map[REPORT_MAP_ROWS][REPORT_MAP_COLS],
                          ReportGridPoint start,
                          ReportGridPoint goal,
                          char *out_path,
                          uint16_t out_capacity)
{
    static const int8_t dx[4] = {0, 0, -1, 1};
    static const int8_t dy[4] = {-1, 1, 0, 0};
    static const char command[4] = {'U', 'D', 'L', 'R'};
    int16_t parent[REPORT_MAP_CELLS];
    char parent_command[REPORT_MAP_CELLS];
    uint16_t queue[REPORT_MAP_CELLS];
    char reverse_path[REPORT_MAP_CELLS];
    uint16_t head = 0;
    uint16_t tail = 0;
    uint16_t path_length = 0;
    int start_cell;
    int goal_cell;

    if (map == 0 || out_path == 0 || out_capacity == 0u ||
        !report_inside(start.x, start.y) ||
        !report_inside(goal.x, goal.y)) {
        return -1;
    }

    start_cell = start.y * REPORT_MAP_COLS + start.x;
    goal_cell = goal.y * REPORT_MAP_COLS + goal.x;
    memset(parent, 0xFF, sizeof(parent));
    parent[start_cell] = (int16_t)start_cell;
    queue[tail++] = (uint16_t)start_cell;

    while (head < tail && parent[goal_cell] < 0) {
        int current = queue[head++];
        int x = current % REPORT_MAP_COLS;
        int y = current / REPORT_MAP_COLS;

        for (int direction = 0; direction < 4; ++direction) {
            int next_x = x + dx[direction];
            int next_y = y + dy[direction];
            int next_cell;

            if (!report_inside(next_x, next_y)) continue;
            next_cell = next_y * REPORT_MAP_COLS + next_x;
            if (parent[next_cell] >= 0) continue;
            if (report_blocked(map[next_y][next_x]) &&
                next_cell != goal_cell) continue;

            parent[next_cell] = (int16_t)current;
            parent_command[next_cell] = command[direction];
            queue[tail++] = (uint16_t)next_cell;
        }
    }

    if (parent[goal_cell] < 0) return -1;

    for (int cell = goal_cell; cell != start_cell; cell = parent[cell]) {
        if (path_length >= REPORT_MAP_CELLS) return -1;
        reverse_path[path_length++] = parent_command[cell];
    }
    if ((uint32_t)path_length + 1u > out_capacity) return -1;

    for (uint16_t i = 0; i < path_length; ++i) {
        out_path[i] = reverse_path[path_length - 1u - i];
    }
    out_path[path_length] = '\0';
    return (int)path_length;
}

    d1 = (float)cnt1 / ENCODER_COUNT_PER_PIXEL;
    d2 = (float)cnt2 / ENCODER_COUNT_PER_PIXEL;
    d3 = (float)cnt3 / ENCODER_COUNT_PER_PIXEL;
    d4 = (float)cnt4 / ENCODER_COUNT_PER_PIXEL;

    dy_robot =
        (d1 + d2 + d3 + d4) * 0.25f;

    dx_robot =
        (-d1 + d2 - d3 + d4) * 0.25f;
		
		dx_robot*=ODOM_SCALE_X;
		dy_robot*=ODOM_SCALE_Y;
    cos_gyro = cosf(gyro);
    sin_gyro = sinf(gyro);

    delta_x_world =
        dx_robot * cos_gyro -
        dy_robot * sin_gyro;

    delta_y_world =
        dx_robot * sin_gyro +
        dy_robot * cos_gyro;
				
		    if (!fusion->initialized)
    {
        return;
    }

    fusion->x += delta_x_world;
    fusion->y -= delta_y_world;
}
B.4  运动控制
void mecanum_cascade_control(float raw_target_y, float raw_target_x, float raw_target_angle,
                             float curr_y, float curr_x, float curr_angle)
{
    static float smoothed_target_angle = 0.0f;
    static int is_first_run = 1;

    static float filtered_vel_x_robot = 0.0f;
    static float filtered_vel_y_robot = 0.0f;

    if (is_first_run)
    {
        smoothed_target_angle = curr_angle;
        is_first_run = 0;
    }

    float err = atan2f(sinf(raw_target_angle - smoothed_target_angle),
                       cosf(raw_target_angle - smoothed_target_angle));

    float max_step = MAX_ANGLE_SPEED * CONTROL_DT;
    float step = err * 0.2f;
    step = fclip(step, -max_step, max_step);

    smoothed_target_angle += step;

    vel_w_cmd = PidLocCtrl(&gyro, curr_angle, smoothed_target_angle);

    float vel_y_world;
    float vel_x_world;

    vel_y_world = PidLocCtrl(&Y, curr_y, raw_target_y);
    vel_x_world = PidLocCtrl(&X, curr_x, raw_target_x);

    vel_y_world = fclip(vel_y_world, -20.0f, 20.0f);
    vel_x_world = fclip(vel_x_world, -20.0f, 20.0f);

    float cos_theta = cosf(curr_angle);
    float sin_theta = sinf(curr_angle);

    float raw_vel_x_robot =
        vel_x_world * cos_theta + vel_y_world * sin_theta;

    float raw_vel_y_robot =
       -vel_x_world * sin_theta + vel_y_world * cos_theta;

    const float alpha = 0.25f;

    filtered_vel_x_robot +=
        alpha * (raw_vel_x_robot - filtered_vel_x_robot);

    filtered_vel_y_robot +=
        alpha * (raw_vel_y_robot - filtered_vel_y_robot);

    vel_x_robot = filtered_vel_x_robot;
    vel_y_robot = filtered_vel_y_robot;
}
