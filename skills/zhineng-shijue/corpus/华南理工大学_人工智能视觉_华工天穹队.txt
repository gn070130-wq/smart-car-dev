摘要
本报告系统阐述了华南理工大学华工天穹队参加第二十一届全国大学生智能汽车竞赛智能视觉组的技术方案。本届比赛采用“虚实融合”模式，要求车模在约3.2m×2.4m的实体场地内，通过车载无线屏幕显示的虚拟地图，完成“推箱子”闯关任务。场地划分为16×12的虚拟网格，设有三个难度递增的关卡：基础推箱子、分类推箱子及复杂推箱子（含墙壁、炸弹等障碍），车模需识别目标、规划路径并自主推动箱子至指定区域，按完成度与用时综合计分。
总体采用“视觉感知—决策规划—运动控制”分层框架。主控选用NXP i.MX RT1064核心板，视觉系统由两块OpenART Plus模块构成：一块负责全局地图识别与车模定位，另一块执行箱子和目标区域的分类检测。各模块通过UART串口通信，实现感知信息与控制指令的实时交互。
视觉部分地图识别模块通过颜色阈值提取场地角点，采用双线性插值进行透视校正，划分16×12网格，识别围墙、箱子、目标点及障碍物，生成二维地图数组。车模定位利用蓝绿色标识，经色块检测、坐标转换、多点标定及滤波算法，获取稳定的亚网格级位置信息，为闭环控制提供视觉反馈。分类模块采用MobileNetV2轻量化网络，经数据增强、裁剪量化后部署至OpenART Plus，对10类“动漫人物”箱子图像进行推理，模型准确率超99%，推理帧率达10-12帧，满足实时性要求。
控制与规划部分RT1064集成了路径规划、运动控制及辅助校正模块。路径规划采用分层策略：普通行驶使用BFS搜索，兼顾路径最短与转向最少；推箱任务采用IDA*与A*混合算法，状态包含“箱子位置+车模位置”，通过哈希表去重、最小堆管理，结合可达性预判，确保高效求解。控制系统结合编码器、陀螺仪（ICM42688）及视觉定位，形成多源融合闭环。特别地，系统设计了“纯视觉为主、编码器补偿延迟”的定位方案，利用全局视觉修正累计误差，并实现路径终点单轴校准（Route校准），有效抑制长距离漂移。运动控制包含直线跟踪、转向及推箱专项策略，确保动作精确稳定。
硬件与机械部分硬件采用模块化设计，包括集成主控板、DRV8701双路电机驱动、TPS5450降压模块（12V→5V/8.4V）、分电板及开关板，各模块通过插接件连接，便于更换维护。机械结构将无线屏幕朝上固定于车模中部，两块OpenART Plus平行布置于上方，由碳素杆支撑，屏幕四周加装遮光板防干扰。电池、主控板及驱动板均通过打印件稳固固定，整体布局紧凑，重心合理。
辅助调试系统：开发了基于WiFi-SPI模块的无线调试上位机，支持“文本模式”实时输出状态日志、彩色地图及“示波器模式”显示多路传感器曲线（如位置、速度、航向角），大幅提升了现场调试效率。
关键词：智能车竞赛；虚实融合；推箱子；视觉定位；路径规划；A*算法；MobileNetV2；RT1064




























第一章 引言
1.1 第二十一届智能视觉组比赛任务
1.1.1 比赛场地
比赛场地为矩形平面场地。根据官方规则，场地尺寸约为3.2米 × 2.4米。场地内铺设普通蓝色广告布作为背景，与普通赛道组背景材质一致。场地边界使用宽度为5厘米的黄色布基胶带或黄色封箱胶带进行固定并标示车模可活动范围。正式比赛时，会在黄色胶带外侧额外贴一圈高度为1厘米的路肩，避免小车冲出比赛区域。场地四个角落贴有数字为15、16、17、18的Apriltag码，用于系统自动定位场地位置并对全局图像进行逆透视校正。场地左侧留有30*30厘米大小的车库，小车要从车库出发开始比赛，每通过一关后，需要返回车库以开始下一关的比赛。场地外需要安置彩钻风摄像头，用于识别比赛场地与小车位置。

1.1.2 任务要求
第21届全国大学生智能汽车竞赛人工智能视觉组的核心任务是制作一个车模，在室内场地上完成“推箱子”游戏。该组别采用“虚实融合”的全新模式，车模并非在实体赛道上竞速，而是在一个约3.2米×2.4米的真实平面场地内，通过车模上屏幕显示的虚拟游戏界面来完成交互任务。比赛场地以20厘米为间隔划分出16×12的虚拟网格坐标系统，车模需要利用视觉模块实时识别并理解虚拟地图上各类箱子和障碍物的分布。
比赛的核心操作是在虚拟网格地图上自主完成一系列复杂任务。车模首先需要通过摄像头识别不同类别的箱子，随后规划出将箱子推动到指定目标区域的最优路径。在推动过程中，车模还需具备自主导航与避障能力，能够绕开墙壁等障碍物，同时地图上可能存在的“炸弹”等特殊元素也要求车模具备识别并合理应对的能力。
比赛采用关卡制进行计分和晋级。分为三个连续且难度递增的关卡。
第一关：基础推箱子。这一关是比赛的基础，要求车模在16×12的虚拟网格地图上，识别并推动箱子。只要推动的箱子数量超过该关卡总数的一半（大于等于50%），即视为有效完成。
第二关：分类推箱子。这一关在推箱子的基础上增加了难度，车模需要识
别箱子上的不同图片或标识，并按照特定的类别将其推到对应的目标区域。
第三关：复杂推箱子。地图会包含更多的箱子以及墙壁、炸弹等障碍和特殊元素。车模需要在更复杂的环境中，高效地规划路径。
在每个关卡中，车模必须成功推动超过该关卡总数50%的箱子才视为有效完成，若未能完成将被罚时300秒。对于成功完成的关卡，每遗漏一个箱子也会被罚时30秒，比赛总用时为三个关卡计时与所有罚时之和。
1.1.3 游戏系统
第21届全国大学生智能汽车竞赛人工智能视觉组的游戏系统，是一个构建在物理车模与虚拟世界之上的“虚实融合”交互平台。该系统的核心是让车模在一块屏幕上与一个虚拟的二维世界进行互动，完成“推箱子”的闯关任务。比赛时，车模上会放置一部手机或无线投屏器，用于显示这个虚拟游戏系统的实时画面。系统通过场地上的Apriltag码对车模进行全局定位，再结合车模上安装的特定标识牌，就能精确追踪车模在场地内的位置和方向。
游戏系统的核心是虚拟地图与游戏元素。地图是一个16×12的虚拟网格，与现实场地中以20厘米为单位的坐标网格相对应。游戏中的所有元素，如箱子、墙壁和目标点，都分布在这个虚拟网格上。本届比赛使用的元素图片数据集以“动漫人物周边”为主题，包含皮卡丘、喜羊羊、哪吒、葫芦娃等10个类别，共1571张图片。比赛前，系统会将这些图片预加载，并在游戏中随机显示。参赛队伍需要训练模型来识别这些图片，将其对应为游戏中的不同“箱子”。
整个比赛由三个难度递增的关卡组成，并按顺序连续进行。系统会从地图库中随机抽取三个关卡的地图方案。每个关卡中，车模都需要自主识别并推动一定数量的箱子到目标区域。
系统的计时与判罚是全自动的。车模从唯一保留的左侧车库出发时，计时开始。每个关卡都有独立计时，并在关卡结束时自动结算成绩。比赛的总成绩由三个关卡的计时与所有罚时累加得出。

第二章 系统设计框架介绍
2.1整体框架与方案设计
本系统采用“视觉感知—决策规划—运动控制”的整体设计框架。系统主要由两块OpenART Plus视觉模块和一块RT1064主控板组成，其中一块OpenART Plus 负责比赛地图识别及车模位置识别，另一块OpenART Plus负责箱子和目标区域的分类检测；RT1064 主控板负责接收视觉识别结果，并完成任务决策、路径规划以及车模运动控制。
比赛过程中，视觉模块首先获取场地地图、车模位置及各类目标信息，并通过串口发送至主控板。主控板根据当前关卡和地图信息进行任务分析与路径规划，随后控制车模按照规划路径移动和完成推箱操作。同时，在运动过程中持续利用视觉定位结果对车模位置进行校正，从而形成从环境感知、路径规划到运动执行的闭环控制系统。
2.2 智能车各个模块总体介绍
(1)主控模块：恩智浦 i.MX RT1064 单片机，对采集的传感器信息进行处理和计算，对电机进行控制，进行路径规划。 
(2)传感器模块：包括两个智能摄像头模块 OpenArt Plus，六轴陀螺仪ICM42688和四路编码器。 
(3)电源管理模块：电源为3S锂电，提供12V转8.4V、12V转5V模块以及5V转3V3模块分别为各个模块提供合适的电压电源。 
(4)电机驱动模块：为处理器控制电机提供接口。
(5)模式开关模块：根据人机交互要求，开关模块用于车模运动模式的调整。 
第三章 智能车视觉框架设计
3.1 地图识别设计思路陈述
地图识别主要由一块 OpenART Plus 完成。根据比赛场地为 16×12 虚拟网格的特点，首先对摄像头采集到的场地图像进行预处理，通过颜色阈值搜索场地区域，并获得地图的四个角点位置。结合四个角点建立图像区域与虚拟网格之间的对应关系，将实际拍摄到的场地图像划分为 16×12 个网格区域。比赛地图本身也是按照 20 cm 间隔建立的 16×12 虚拟网格，因此识别结果可以直接用于后续路径规划。
由于摄像头拍摄时存在一定的透视变形，程序根据检测得到的左上、右上、右下和左下四个角点，采用双线性插值的方法计算每个网格中心在图像中的实际位置，并在网格中心附近选取局部ROI区域进行识别。这样可以减小透视变化对网格划分准确性的影响。
在地图元素识别方面，根据不同游戏元素在画面中的颜色特征设置相应的颜色阈值，通过色块检测区分道路、围墙、箱子、目的地以及炸弹等元素。其中地图最外层直接按照围墙处理，其余网格分别进行元素检测。最终将识别结果转换为一个 16×12 的二维数组，不同数值分别代表不同地图元素，并将该地图信息发送给 RT1064 主控板，为后续任务决策和路径规划提供基础数据。

3.2 车模位置识别算法实现
车模位置识别由负责地图与定位的 OpenART Plus 完成。系统在获取场地图像后，依次进行平场校正、干扰区域掩蔽、定位色块检测以及坐标转换，最终得到车模在 16×12 网格地图中的实时位置，并将结果发送至 RT1064 主控板，用于路径规划和运动控制。该视觉模块在整体方案中同时承担地图和车模位置识别任务。
3.2.1 位置识别
程序利用车模上的蓝绿色定位标识进行位置识别。首先在地图四个角点限定的ROI区域内，根据蓝绿色的LAB颜色阈值进行色块搜索，并从检测结果中选择主要定位色块，以其中心坐标作为车模在图像中的像素位置。
获得像素坐标后，通过地图角点建立图像坐标与实际网格坐标之间的映射关系，并结合四点、八点或十六点标定数据进行位置修正，以减小摄像头透视畸变和安装误差带来的影响。最终将像素坐标转换为 16×12 地图中的实际位置坐标。
为了减少单帧检测抖动，程序还对连续位置数据依次进行三点中值滤波和低通滤波，使输出位置更加平滑稳定。处理后的坐标作为车模实时视觉位置，为主控系统进行运动控制、路径跟踪及位置校正提供依据。
3.3 分类模型设计思路陈述
按照21届智能视觉组的规则，第二关第三关都需要进行分类识别，如果对每个箱子都进行分类，那么分类错误一次就会少一个箱子推到目的地，如果为了减少路径少识别一个箱子，那错误一次很有可能有两个箱子无法推到目的地，对于没推完的箱子，一个给予 30s 的罚时。对于想要取得较好成绩的队伍，30s 的罚时是个沉重的打击。因此，对于视觉组的成员而言，训练出高精度的分类模型是很有必要的。因为分类是根据无线屏幕上的图像进行的，所以场地环境带来的干扰比较有限，同时为了缩短路径和节省识别时间，我们需要帧率高且准确度高的模型，最终我们训练出的两个模型都达到了99%以上的准确率，且帧率分别达到10帧和12帧。
3.4 分类模型训练实现
分类模型训练主要包括数据集预处理、数据增强、模型训练以及模型量化部署四个步骤。比赛提供的图像数据共包含 10 个类别，系统需要将识别结果转换为对应的 0～9 类别编号，因此训练时按照类别分别建立数据集目录，并保证训练类别与车模通信协议中的类别编号一一对应。比赛数据集本身包含 10 个类别、共 1571 张图片。
在模型训练前，首先对原始图片进行预处理。为了使训练图片更加接近 OpenART Plus 实际拍摄到的画面，将目标图片进行裁剪和旋转处理，再按照实际显示区域的比例缩放，并随机叠加到采集的背景图片上，以模拟目标在实际画面中的不同位置。生成后的图片统一调整为 160×160 像素，同时随机打乱图片顺序后按照类别保存。预处理程序中还通过随机选择背景和随机纵向位置的方式增加训练样本的多样性。 最终生成的训练图片统一缩放至 160×160 像素。
模型训练采用 TensorFlow/Keras 实现。对于箱子图片的十分类任务，采用轻量化 MobileNetV2 作为特征提取网络，并根据 OpenART Plus 的计算性能对网络进行截短和简化，输入图像尺寸设置为 128×128 RGB。训练过程中使用旋转、平移、缩放以及亮度变化等在线数据增强方法，提高模型对目标位置变化和光照变化的适应能力。训练采用 Adam 优化器和交叉熵损失函数，初始学习率设置为 (1\times10^{-4})，Batch Size 为 32，并划分部分数据作为验证集。训练过程中根据验证集准确率保存最佳模型，同时在模型长期不收敛时降低学习率并提前停止训练，以避免出现过拟合。
完成训练后，将得到的模型转换为 TFLite 格式。为减少模型存储空间和提高 OpenART Plus 上的推理速度，采用完整 UINT8 整数量化方式，将模型的输入、权重及输出转换为 8 位整数。量化完成后再次利用验证集对模型进行准确率测试，并检查模型输入尺寸及数据类型。最终得到 10class.tflite 等模型文件，部署到 OpenART Plus 中完成实际分类识别。

3.5 与控制的通讯
两块 OpenART Plus 与 RT1064 主控板之间均采用 UART 串口进行通信，通信波特率设置为 115200 bit/s。其中，ART1 主要负责向主控发送地图信息和车模实时位置信息，ART2 主要负责向主控返回箱子及目标区域的分类识别结果。RT1064 根据当前任务状态向对应视觉模块发送识别请求，从而实现视觉感知与运动控制之间的信息交互。
ART1 与主控之间采用带帧头、命令字、数据长度、数据区、校验字节和帧尾的数据帧格式。地图识别完成后，ART1 将 16×12 网格地图发送至主控；进行位置识别时，则将经过校准和滤波后的车模坐标发送给主控。主控接收数据后进行帧格式和校验判断，接收正确则返回应答信息，出现数据异常时可要求重新发送，从而提高通信可靠性。
ART2 采用按需识别方式工作。当主控需要识别箱子或目标区域时，向 ART2 发送对应的分类请求。ART2 接收到指令后调用相应分类模型进行推理，并将识别得到的类别编号返回主控，其中 0～9 表示不同类别，10 表示当前画面中未检测到有效目标。
通过上述通信方式，视觉模块只负责完成地图、位置及类别等信息的获取，而 RT1064 负责根据视觉结果完成任务状态判断、路径规划和运动控制，使视觉识别与主控决策相互独立，同时能够进行实时数据交互，构成完整的智能车视觉控制系统。

5.2 控制系统的设计及实现
本系统的控制部分运行于 RT1064 主控板，其核心任务是根据视觉模块提供的地图、位置和分类信息，完成任务决策后的路径执行与车模稳定运动控制。整体上，控制系统采用“任务层—规划层—执行层”的分层设计：上层根据比赛状态确定当前目标，中层根据地图和目标位置生成行驶路径，下层则负责将路径点转换为电机控制量，驱动车模完成前进、转向、推箱和返航等动作。
在具体实现中，控制系统以周期任务方式运行。主控在固定周期内持续更新比赛状态，读取当前视觉坐标、编码器反馈和惯性传感器数据，并结合路径规划结果计算当前的目标点、目标航向和运动速度。对于普通行驶任务，系统按照规划路径依次跟踪关键路径点；对于推箱任务，则根据箱子与目标区域的相对关系，调整车模的接近方向和推进路径，保证推箱过程稳定可靠；在返航阶段，则重新规划从当前位置到车库的最优路径，完成任务结束后的自主回库。
为了提高运动过程中的稳定性和精度，控制系统并不完全依赖单一传感器，而是综合利用编码器、陀螺仪以及视觉定位结果进行闭环修正。其中，编码器用于反映车轮运动状态，陀螺仪用于提供实时航向变化信息，视觉模块则用于对全局位置进行校正。通过上述多源信息融合，系统能够在路径跟踪、转向控制和终点停车过程中保持较好的精度与鲁棒性。
5.2.1 车模运动控制实现
车模运动控制的目标是使主控规划得到的路径能够准确转化为车模的实际运动。程序实现时，首先将路径规划模块输出的目标路径离散为若干关键点，再根据当前车模位置与目标点之间的偏差，计算位置误差和航向误差，并进一步生成对应的速度控制指令。
在直线行驶过程中，系统主要根据当前位置与目标点之间的距离误差进行位置控制，同时结合目标航向与当前航向之间的差值进行方向修正，使车模能够沿着给定路径稳定前进。在转向或姿态调整过程中，则重点控制航向误差，使车模尽快转到目标方向后再进入下一阶段运动。对于推箱动作，控制系统会在接近箱体时降低速度，并对推进方向进行更严格的约束，以避免因姿态偏差导致箱子偏移或脱离预定路线。
底层执行时，主控将计算得到的目标速度和转向控制量分配给各个车轮驱动电机，并结合编码器反馈形成闭环调节。这样可以实时补偿电机响应不一致、地面摩擦变化及外部干扰带来的误差，提高路径跟踪精度。与此同时，程序还设置了目标点到达判定条件，当车模进入设定误差范围后，认为当前路径点到达，并自动切换至下一个控制目标。
此外，在实际比赛过程中，系统还会结合视觉定位结果对运动轨迹进行修正。当编码器累计误差增大或车模位置与规划轨迹偏离较明显时，主控利用视觉返回的全局位置重新校准当前位置，再继续执行后续运动控制，从而兼顾运动连续性与定位准确性。
5.3.2 陀螺仪数据的处理
陀螺仪数据主要用于反映车模的实时角速度信息，并进一步计算车模航向角，为转向控制、路径跟踪和姿态稳定提供依据。由于车模在比赛过程中需要频繁转向、修正方向和执行推箱动作，航向信息的准确性直接影响整体控制效果，因此陀螺仪数据处理是控制系统中的重要环节。
程序初始化时，首先对陀螺仪进行零偏校准。由于传感器在静止状态下仍可能存在小幅偏置，如果不进行校准，角速度积分后会引起明显航向漂移。因此，系统在上电初期采集若干组静止数据，计算平均值作为零偏补偿项，在后续运行中对原始角速度进行修正。
在运行过程中，主控周期性读取陀螺仪角速度数据，并通过滤波抑制高频噪声和瞬时抖动，使角速度信号更加平滑稳定。经过滤波和零偏补偿后的角速度数据再进行积分，得到车模当前的航向角变化量。该航向角一方面参与底层转向闭环控制，另一方面也可与编码器或视觉信息进行联合校正，以减小纯积分方式带来的累计误差。
在具体控制应用中，陀螺仪数据主要体现在两个方面：其一是在路径跟踪过程中提供实时航向反馈，使车模能够根据目标航向不断修正转向误差；其二是在推箱、转向及原地调整姿态时，帮助系统快速、稳定地完成角度控制。尤其在视觉更新频率较低或短时无法获取稳定位置时，陀螺仪能够提供连续的姿态信息，保证控制过程不中断。
因此，陀螺仪数据处理并不是简单地读取传感器数值，而是经过零偏校准、滤波处理、角度积分和控制融合后的完整过程。通过这些处理，系统能够获得较为稳定可靠的航向信息，为智能车的平稳运动和精确控制提供支撑。
5.4 route校准
在车模运动过程中，仅依靠编码器和惯性导航进行位置估计会产生一定的累计误差。为提高长距离运动及多次转向后的定位精度，本系统设计了 Route 校准机制，利用 OpenART Plus 提供的全局视觉位置对主控内部的定位结果进行周期性修正。
主控完成路径规划后，首先将完整路径按照连续直线段进行压缩，并将各段的终点坐标、运动方向以及需要校准的坐标轴发送给 ART1。由于比赛地图采用 16×12 网格，每个网格对应实际场地中的 20 cm，因此路径节点可以直接建立网格坐标与实际位置之间的对应关系。
Route 校准主要采用与运动方向垂直的单轴校准方式。当车模沿 X 方向左右运动时，主要对 Y 方向的位置进行校准；当车模沿 Y 方向上下运动时，则主要校准 X 方向的位置。这样可以重点修正车模偏离规划路线的横向误差，同时避免由于视觉识别延迟而对车辆前进方向的位置产生不必要的修正。
当车模进入指定 Route 目标附近时，ART1 根据视觉定位结果采集多帧位置数据，并对有效样本进行平均处理，得到当前目标点对应的视觉坐标。同时，RT1064 保存车模到达该位置时的 INS 定位结果。主控将两者进行比较，得到位置校准量.
对于斜向运动路径，程序还支持根据路径方向建立局部坐标系，并在路径法向方向上进行位置修正。此外，较长直线路径产生的横向偏差还可以用于估计车模航向角误差，并对地图航向偏置进行修正，从而进一步减小后续行驶过程中的累计偏差。
当前程序主要采用“路径终点单轴视觉校准”的方式，即在关键 Route 节点利用视觉定位对 INS 进行修正。通过这种方式，在不影响车模连续运动的前提下，可以有效抑制编码器和惯性导航产生的累计误差，提高后续路径跟踪及推箱操作的位置精度。
5.5 纯视觉算法
为了减小编码器累计误差对车模长距离运动的影响，系统设计了以 OpenART Plus 全局视觉坐标为主要定位依据的纯视觉定位方案。需要说明的是，本系统中的“纯视觉”并不是完全舍弃编码器，而是以视觉测得的绝对位置作为主定位信息，编码器主要用于补偿视觉处理和通信产生的时间延迟，并在视觉数据短时间丢失时提供位置外推，从而兼顾视觉定位的全局准确性与运动过程的连续性。
OpenART Plus 持续识别车模定位标识，并将车模在场地中的二维位置以及对应的图像帧时间信息发送给 RT1064。主控接收到视觉坐标后，首先进行坐标范围判断，排除超出比赛场地范围的异常数据，再根据视觉帧的采集时刻计算该帧对应的位置。由于图像采集、处理以及串口发送均会产生一定延迟，如果直接将接收到的视觉位置作为车模当前位置，会使车模高速运动时产生明显的位置滞后，因此程序利用编码器保存的历史里程信息进行延迟补偿。
其中，编码器只用于计算从图像采集时刻到当前时刻之间车模实际产生的位移，最终位置仍以视觉测量结果作为基准。程序同时保存一段历史里程数据，通过视觉帧龄和系统残余延迟反推出图像采集时刻，并从历史数据中寻找对应位置。系统还设计了视觉延迟在线估计机制，用于减小不同运行状态下视觉处理延迟变化造成的定位误差。
得到补偿后的视觉坐标后，系统不会立即使用单帧数据直接覆盖当前坐标，而是首先计算视觉候选位置与当前估计位置之间的偏差。当偏差超过允许范围时，认为该帧可能受到识别错误、遮挡或数据跳变影响，将其舍弃；对于正常数据，则采用低通方式逐步修正当前位置。同时对单帧最大修正距离进行限制，防止视觉坐标突然跳变造成车模控制指令突变。
考虑到比赛过程中可能出现车模被遮挡、定位色块识别失败或视觉画面冻结等情况，系统还增加了视觉有效性判断。当检测到车模实际处于运动状态，而连续多帧视觉坐标保持完全不变时，将该情况判断为视觉冻帧，此时暂停使用异常视觉数据，并利用短时间里程信息维持位置连续性。当连续获得多帧变化方向一致且可信的视觉坐标后，再恢复视觉主定位。
因此，纯视觉定位的整体过程可以概括为“视觉坐标获取—时间延迟补偿—异常数据判断—平滑位置修正—视觉失效保护”。这种方式能够利用场外摄像头提供的全局绝对坐标抑制编码器累计误差，同时通过短时里程补偿解决视觉数据存在延迟和更新频率较低的问题，为路径跟踪和返航提供较为稳定的位置反馈。
5.6 路径规划
路径规划是整个智能车软件中的核心决策部分，其主要任务是根据视觉识别得到的 16×12 栅格地图、车模当前位置、箱子位置、目的地位置以及 TNT 等障碍信息，计算车模从当前位置到目标位置的可执行运动路径。由于比赛任务不仅要求车模自身能够绕开障碍物，还需要考虑箱子的移动过程，因此系统将路径规划划分为“车模行驶路径规划”和“推箱任务规划”两个层次。
5.6.1 普通行驶路径规划
对于不涉及推动箱子的普通运动，如车模前往观察位置、箱子侧面、目的地区域以及返回车库等，系统主要采用 BFS 广度优先搜索算法进行路径规划。
BFS 从车模当前栅格开始，将周围可通行栅格依次加入搜索队列，并逐层向外扩展。墙壁始终作为不可通过区域，箱子和 TNT 是否作为障碍则根据当前任务进行设置。当搜索到目标位置后，通过保存的距离关系反向恢复从起点到终点的完整路径。
普通 BFS 可以保证获得栅格意义下的最短路径。但实际车模运动时，即使两条路径长度相同，转弯次数较多的路径仍会消耗更多时间，并产生更大的控制误差。因此程序在获得最短距离后，又增加了“最少转向”作为第二优化目标。在所有等长最短路径中进一步比较方向变化次数，优先选择转弯次数较少的路径。
当前程序还支持八方向路径搜索，即除上下左右运动外，在满足安全条件时允许规划斜向路径。对于斜向移动，必须同时检查斜线两侧相邻栅格是否存在障碍，防止车模在对角运动时从墙角或箱子边缘擦过。
5.6.2 箱子与目的地选择
推箱任务比普通导航更加复杂，因为不仅要考虑箱子能否到达目的地，还要考虑车模能否移动到箱子后方完成每一次推动。因此系统不会简单地按照距离最近原则选择箱子，而是首先根据当前地图建立所有可行的“箱子—目的地”候选组合。
在分类关卡中，ART2 识别出的类别信息用于建立箱子与目的地之间的匹配关系，只有类别相符的箱子与目的地才进入候选集合；在不需要分类的情况下，则允许根据位置关系建立候选组合。
随后对每组候选进行综合评分。评分不仅考虑箱子与目的地之间的曼哈顿距离，还考虑以下因素：
1、箱子推到该目的地后是否容易形成死锁；
2、剩余箱子与剩余目的地之间的总体距离；
3、箱子周围可推动方向的数量，即箱子的运动自由度；
4、当前方案是否会堵塞其他箱子的运动空间；
5、规划路径的总长度及转弯次数。
对于剩余箱子与目的地的匹配问题，当对象数量较小时，程序采用位掩码动态规划计算剩余箱子和目的地之间的最小匹配代价，而不是仅使用简单的最近邻匹配。这样可以避免当前箱子选择最短目的地后，使后续箱子出现大范围绕行甚至无法完成的问题。
因此系统选择的并不一定是“当前最近的箱子”，而是综合考虑当前路径以及后续任务后代价较低的箱子。
5.6.3 推箱路径搜索
确定候选箱子和目的地后，系统采用针对推箱子问题设计的 IDA* 与 A* 混合搜索算法生成真正可执行的推箱路径。
与普通路径规划只需要记录车模位置不同，推箱搜索中的一个状态同时包含箱子当前的位置和车模当前的位置。这是因为即使箱子处于同一个位置，如果车模位于箱子的不同方向，下一步能够执行的推动动作也可能完全不同。
每扩展一个状态时，程序分别尝试箱子的上、下、左、右四个推动方向。假设箱子需要向右推动，则首先检查箱子右侧栅格是否允许箱子进入，同时检查车模能否到达箱子左侧的“推前位”。只有这两个条件同时成立，该推动动作才是有效动作。
为了快速判断车模是否能够到达推前位，系统在每个推箱状态下首先进行一次 BFS，生成车模到所有可达栅格的距离图。之后四个方向的推前位均可以直接通过距离图判断是否可达，避免针对四个方向分别进行多次 BFS，从而降低搜索时间。
A*搜索的总代价定义为f(n)=g(n)+h(n)
其中，g(n) 主要由车模走到推前位的距离、已经完成的推箱步数以及推箱方向变化产生的附加代价组成；h(n) 使用箱子当前位置到目标位置的曼哈顿距离作为启发函数。
通过这种设计，搜索不仅希望减少推箱步数，同时也会倾向于选择车模绕行距离更短、箱子换向次数更少的方案。
在 A* 外层又加入 IDA* 的迭代深化思想。搜索开始时根据启发函数设置一个较小的代价阈值，只搜索总代价不超过该阈值的状态；如果本轮没有找到可行路径，则根据本轮搜索过程中超过阈值的最小代价值逐步提高搜索范围，再进行下一轮搜索。这样可以在保证求解能力的同时限制 MCU 上的节点数量和计算时间。
5.6.4 状态去重与搜索优化
由于一个推箱地图中可能产生大量重复状态，如果不进行处理，会造成搜索节点数量迅速增加。程序采用哈希表保存已经搜索过的“箱子位置+车模位置”状态。
当新状态产生时，首先通过哈希表判断该状态是否已经存在。如果不存在，则加入搜索队列；如果已经存在，则比较新路径与原路径的累计代价。当新路径代价更小时，更新该状态并重新加入搜索队列。
A*开放列表采用最小堆进行管理，每次优先展开 (f(n)) 最小的节点，从而避免每次遍历全部候选节点寻找最优状态，提高 RT1064 上的搜索效率。
5.6.5 路径生成与执行
当 IDA* 与 A* 搜索到箱子到目的地的可行解后，系统通过父节点关系从目标状态逐级回溯，得到箱子的推动顺序。对于相邻两次推动之间车模需要绕到箱子另一侧的情况，再利用 BFS 补充车模从当前位置到下一个推前位的行驶路径。
因此最终输出的并不是单纯的“箱子移动路径”，而是一条车模能够直接执行的完整路径，其中同时包含：
“车模绕行到推箱位置 → 推动箱子 → 再次绕行 → 再次推动箱子”。
生成完整路径后，程序还会重新模拟一次推箱过程，对路径进行合法性验证，确认整个路径中不存在越界、穿墙、无法到达推前位以及错误推动等情况。验证成功后才将路径交给运动控制模块。
最终，栅格路径被转换为实际场地坐标并按照直线段进行简化，运动控制模块依次跟踪各目标点。在执行过程中不断更新车模实际位置，当一个路径点到达后自动进入下一个路径点，直到箱子到达目的地。完成一次推箱后更新地图状态，再重新进行下一轮候选选择和路径规划。

7.2 WiFi模块与上位机
为了方便智能车程序调试以及比赛过程中运行状态的观察，本系统设计了 WiFi 无线调试模块，将 RT1064 主控板运行过程中产生的地图、位置、传感器及控制状态等信息实时发送至电脑上位机。WiFi 模块主要作为调试和数据监测通道使用，不参与智能车的核心任务决策和运动控制，因此即使关闭 WiFi，车模仍能够独立完成比赛任务。
系统采用 WiFi-SPI 模块与 RT1064 进行通信。程序启动后，首先读取拨码开关状态判断是否启用 WiFi 调试功能。开启后，主控通过 SPI 初始化 WiFi 模块并连接指定无线网络，随后建立 UDP 通信，将调试数据发送至电脑端。程序中的通信端口设置为 8086，并采用 UDP 方式传输，以降低无线调试数据对主控制程序实时性的影响。
根据调试需求，系统设计了“文本输出”和“示波器输出”两种工作模式，并在上电时通过拨码开关进行选择。两种模式在运行过程中互斥，避免不同类型的数据同时发送导致上位机解析错误。
在文本模式下，主控可以将比赛状态、当前网格坐标、目标位置、路径执行进度以及程序运行日志等信息发送至上位机。例如，在任务运行过程中，可以实时观察车模当前处于地图获取、目标探测、分类匹配、路径规划、路径执行还是返航等状态。同时，程序还可以将 OpenART 识别得到的 16×12 地图转换为彩色地图发送至上位机，不同颜色分别表示墙壁、道路、箱子、目的地以及车模当前位置，使调试人员能够更加直观地检查视觉地图识别结果。
在示波器模式下，系统最多同时发送 8 路浮点型数据。根据当前调试内容，可以选择不同的数据组合，例如三轴加速度、三轴角速度、航向角、车模位置、目标位置、编码器速度、视觉位置、INS 位置以及视觉定位延迟等。上位机将接收到的数据以实时曲线形式显示，通过对不同曲线进行对比，可以分析车模运动过程中位置误差、速度响应、航向变化以及视觉校准效果。
为了提高调试数据传输的可靠性，示波器数据帧中还加入了发送序号、时间信息以及 SPI 和 UDP 发送异常标志。电脑端能够根据连续的数据帧判断是否出现丢包或发送异常，为分析视觉延迟和控制数据提供依据。

def Map_Rec(img, corners, rows=16, cols=12, outer_rings=3):
    # 地图四角：左上、右上、右下、左下
    top_left, top_right, bottom_right, bottom_left = corners

    # 估算网格尺寸
    grid_width = (
        top_right[0] - top_left[0] +
        bottom_right[0] - bottom_left[0]
    ) / 2 / cols

    grid_height = (
        bottom_left[1] - top_left[1] +
        bottom_right[1] - top_right[1]
    ) / 2 / rows

    map_grid = [[-1 for _ in range(cols)] for _ in range(rows)]

    # 以网格中心附近区域作为颜色识别 ROI
    sample_size = int(min(grid_width, grid_height) * 0.5)

    for row in range(rows):
        for col in range(cols):

            # 网格中心在标准地图中的归一化坐标
            row_ratio = (row + 0.5) / rows
            col_ratio = (col + 0.5) / cols

            # 在地图上边缘进行插值
            top_x = top_left[0] + \
                    (top_right[0] - top_left[0]) * col_ratio
            top_y = top_left[1] + \
                    (top_right[1] - top_left[1]) * col_ratio

            # 在地图下边缘进行插值
            bottom_x = bottom_left[0] + \
                       (bottom_right[0] - bottom_left[0]) * col_ratio
            bottom_y = bottom_left[1] + \
                       (bottom_right[1] - bottom_left[1]) * col_ratio

            # 双线性插值得到当前网格中心
            center_x = int(top_x + (bottom_x - top_x) * row_ratio)
            center_y = int(top_y + (bottom_y - top_y) * row_ratio)

            sample_x = center_x - sample_size // 2
            sample_y = center_y - sample_size // 2
            sample_roi = (
                sample_x,
                sample_y,
                sample_size,
                sample_size
            )

            if (sample_x >= 0 and sample_y >= 0 and
                sample_x + sample_size < img.width() and
                sample_y + sample_size < img.height()):

                # 判断当前网格处于地图第几圈
                ring_index = min(
                    row,
                    rows - 1 - row,
                    col,
                    cols - 1 - col
                )

                # 最外圈直接作为墙处理
                if ring_index < 1:
                    element_type = 1

                # 外层区域采用单独识别函数
                elif ring_index < outer_rings:
                    element_type = Element_Rec_Outer(
                        img,
                        roi=sample_roi
                    )

                # 内部区域正常识别
                else:
                    element_type = Element_Rec(
                        img,
                        roi=sample_roi
                    )

                map_grid[row][col] = element_type

return map_grid
def Element_Rec(img, roi=None):

    thresholds = {
        'road':        (19, 48, 44, 83, -112, -70),
        'wall':        (0, 100, -7, 38, -112, -4),
        'start':       (57, 100, -86, -7, -53, 97),
        'box':         (61, 100, -38, -3, 23, 127),
        'destination': (55, 68, 76, 127, -128, -29),
        'bomb':        (42, 59, 35, 96, -39, 44)
    }

    # 箱子
    if img.find_blobs(
        [thresholds['box']],
        roi=roi,
        area_threshold=15,
        pixels_threshold=10,
        merge=True
    ):
        return 3

    # TNT
    if img.find_blobs(
        [thresholds['bomb']],
        roi=roi,
        area_threshold=15,
        pixels_threshold=15,
        merge=True
    ):
        return 5

    # 目的地
    if img.find_blobs(
        [thresholds['destination']],
        roi=roi,
        area_threshold=15,
        pixels_threshold=15
    ):
        return 4

    # 道路
    if img.find_blobs(
        [thresholds['road']],
        roi=roi,
        area_threshold=15,
        pixels_threshold=15
    ):
        return 0

    # 围墙
    if img.find_blobs(
        [thresholds['wall']],
        roi=roi,
        area_threshold=10,
        pixels_threshold=10
    ):
        return 1

return -1

    static uint16 visited[MAP_MAX_HEIGHT][MAP_MAX_WIDTH];
    static uint16 distance[MAP_MAX_HEIGHT][MAP_MAX_WIDTH];

    static uint8 qx[MAP_MAX_WIDTH * MAP_MAX_HEIGHT];
    static uint8 qy[MAP_MAX_WIDTH * MAP_MAX_HEIGHT];

    static uint16 bfs_gen = 0;

    bfs_gen++;

    if (bfs_gen == 0)
    {
        memset(visited, 0, sizeof(visited));
        bfs_gen = 1;
    }

    uint16 head = 0;
    uint16 tail = 0;

    /* 起点加入队列 */
    qx[tail] = sx;
    qy[tail] = sy;
    tail++;

    visited[sy][sx] = bfs_gen;
    distance[sy][sx] = 0;

    uint8 found = 0;
    uint16 goal_dist = 0xFFFF;

    while (head < tail)
    {
        uint8 cx = qx[head];
        uint8 cy = qy[head];
        head++;

        if (found && distance[cy][cx] >= goal_dist)
        {
            break;
        }

        /* 搜索当前位置周围所有方向 */
        for (uint8 i = 0;
             i < PATHPLAN_ROUTE_DIR_COUNT;
             i++)
        {
            int16 nx = (int16)cx + s_route_dx[i];
            int16 ny = (int16)cy + s_route_dy[i];

            /* 越界 */
            if (nx < 0 || ny < 0 ||
                nx >= map_w || ny >= map_h)
            {
                continue;
            }

            /* 已访问 */
            if (visited[ny][nx] == bfs_gen)
            {
                continue;
            }

            /* 判断斜向移动是否安全 */
            if (!pathplan_diagonal_step_clear(
                    map,
                    cx,
                    cy,
                    (uint8)nx,
                    (uint8)ny))
            {
                continue;
            }

            uint8 is_goal =
                ((uint8)nx == ex &&
                 (uint8)ny == ey);

            if (!is_goal)
            {
                uint8 cell = map[ny][nx];

                /* 墙壁不可通过 */
                if (cell == MAP_WALL)
                    continue;

                /* 根据任务决定箱子、TNT是否作为障碍 */
                if (block_box && cell == MAP_BOX)
                    continue;

                if (block_bomb && cell == MAP_BOMB)
                    continue;
            }

            /* 记录最短距离 */
            visited[ny][nx] = bfs_gen;
            distance[ny][nx] =
                distance[cy][cx] + 1;

            /* 新节点入队 */
            qx[tail] = (uint8)nx;
            qy[tail] = (uint8)ny;
            tail++;

            if (is_goal)
            {
                found = 1;
                goal_dist = distance[ny][nx];
            }
        }
    }

    if (!found)
    {
        return 0;
    }

    if (out_steps != NULL)
    {
        *out_steps = distance[ey][ex];
    }

    return 1;
}
IDA和A*混合算法
/* IDA* + A* 混合搜索核心 */

uint16 root_h = game_task_push_heuristic(
    box_x, box_y, dest_x, dest_y);

uint16 ida_bound = root_h;     // IDA* 初始搜索阈值

for (uint8 ida_round = 0;
     ida_round < GAME_TASK_IDA_MAX_ROUNDS;
     ida_round++)
{
    uint16 min_over_bound = 0xFFFF;

    /* 将初始状态加入 A* 开放列表 */
    nodes[0].ox = box_x;
    nodes[0].oy = box_y;
    nodes[0].cx = car_x;
    nodes[0].cy = car_y;
    nodes[0].g_score = 0;
    nodes[0].f_score = root_h;

    game_task_heap_push(heap, &heap_size, nodes, 0);

    /* A* 搜索 */
    while (heap_size > 0)
    {
        /* 每次取出 f = g + h 最小的节点 */
        uint16 nid =
            game_task_heap_pop(heap, &heap_size, nodes);

        /* 到达目标 */
        if (nodes[nid].ox == dest_x &&
            nodes[nid].oy == dest_y)
        {
            return 1;
        }

        /* 扩展四个推箱方向 */
        for (uint8 k = 0; k < 4; k++)
        {
            uint8 next_x = nodes[nid].ox + dx4[k];
            uint8 next_y = nodes[nid].oy + dy4[k];

            if (!push_is_valid(next_x, next_y))
                continue;

            /* A* 代价 */
            uint16 new_g =
                nodes[nid].g_score + 1;

            uint16 new_h =
                game_task_push_heuristic(
                    next_x, next_y,
                    dest_x, dest_y);

            uint16 new_f = new_g + new_h;

            /*
             * IDA* 阈值限制：
             * 超出本轮阈值的节点暂时不展开
             */
            if (new_f > ida_bound)
            {
                if (new_f < min_over_bound)
                    min_over_bound = new_f;

                continue;
            }

            /* 满足阈值则加入 A* 开放列表 */
            nodes[node_count].ox = next_x;
            nodes[node_count].oy = next_y;
            nodes[node_count].g_score = new_g;
            nodes[node_count].f_score = new_f;
            nodes[node_count].parent_idx = nid;

            game_task_heap_push(
                heap,
                &heap_size,
                nodes,
                node_count);

            node_count++;
        }
    }

    /* 本轮没有找到路径，提高 IDA* 搜索阈值 */
    if (min_over_bound == 0xFFFF)
        break;

    ida_bound = min_over_bound;
}

return 0;
