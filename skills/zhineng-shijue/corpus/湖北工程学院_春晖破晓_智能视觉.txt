第一章 引言
智能视觉组是本届竞赛室内赛道的核心组别之一，也是技术挑战最为突出的组别之一。该组别要求参赛队伍制作一辆可在平面比赛场地内自由运动的智能车模，车模在场地内的位置与方向由比赛系统根据车模上安装的标识牌进行识别与定位。与传统的竞速类组别不同，智能视觉组采用“虚实结合”的全新比赛模式，车模上放置无线屏幕，屏幕上显示虚拟现实仿真系统投影的实时动态图像，包括比赛场地的全局俯视图和车模的第一视角图像。车模通过识别屏幕中的虚拟场景信息来完成相应的游戏任务。本届智能视觉组的竞赛任务以推箱子游戏为基本框架，要求车模从发车区出发，通过识别虚拟场景中的可移动箱子与目的地，将箱子逐一推至指定位置。这种虚实融合的比赛形式既考验车模的运动控制精度与稳定性，也对视觉识别、目标检测、路径规划与决策算法的综合能力提出了极高要求。
围绕智能视觉组的技术挑战，近年来已有大量相关研究与实践探索。在视觉感知方面，基于深度学习的图像分类与目标检测算法已被广泛应用于移动机器人的环境感知与任务理解；在运动控制方面，PID控制、模型预测控制及强化学习方法为车模的精准定位与路径跟踪提供了有效手段。在智能汽车竞赛的历届文献中，针对摄像头组、电磁组等传统组别的技术方案已有较为系统的总结，但针对虚实结合场景下智能视觉组的技术实现路径，可供参考的公开文献仍相对有限。本报告正是在这一背景下，结合第二十一届竞赛规则与智能视觉组比赛细则的具体要求，系统阐述本队参赛车模的设计与实现过程。
本报告后续内容安排如下：第一章为总体设计方案，概述模型车设计制作的主要思路与实现的技术方案；第二章介绍机械结构与安装，包括车模的选型、改造、传感器安装及电路板固定等内容；第三章阐述硬件电路设计，给出系统电路板的原理图与设计说明；第四章介绍软件控制算法，重点说明视觉识别、路径规划与运动控制的核心算法；第五章叙述开发与调试过程，包括开发工具及调试中遇到的问题与解决方案；第六章列出车模的主要技术参数；最后为结论与展望，总结整体工作情况并指出可进一步改进的方向。

第二章 总体设计方案
2.1模型车设计制作的主要思路
	2.1.1车模选型
	根据赛题要求，车模需在3.2m×2.4m的比赛场地内自由移动，能够在平面内实现任意方向的平移与旋转，因此首选全向移动车模。本届竞赛智能视觉组可供选用的车模型号包括M车、M1车和Y车。
在车模结构选型方面，主要考量因素包括车顶方位标识牌的安装适配性、车模整体稳定性以及维护便利性。M车综合性能稳定，车体结构与官方的车顶方位标识牌直接适配，为本队首选方案。M1车与M车整车结构相同，主要区别在于轮圈材质：M车采用航空铝金属材料轮圈，坚固耐用；M1车采用一体化注塑成型轮圈，整车重量有所减轻，成本亦相应降低。若后续考虑使用负压结构以增加车模下压力，则可选用M1车模，通过减轻整车重量来降低运动惯性，从而提升车模的机动性与响应速度；在常规状态下，优先选用结构强度更高的M车。Y车整车为全金属结构，强度高、重心低，但在第二十届竞赛中使用Y车的实际经验表明，其编码器与电机安装复杂耗时，且电机寿命相对较短。由于赛事规定不可随意更换非原厂型号电机，当电机性能衰减时只能更换同型号电机，增加了车模的日常维护难度，故将Y车仅作为备选项。
在运动控制方面，M车与M1车均为四轮驱动结构，控制算法成熟、实现简便、运行稳定性好；Y车为三轮结构，在平移运动时的稳定性不及四轮结构。综合考虑上述因素，本队确定以M车模为主力平台，M1车模为备选平台。
2.1.2 整车布局设计
	裁判系统通过场地内的全局摄像头采集车模位置信息，经处理后将虚拟场景图像通过无线方式传输至车模上的无线屏幕，车模则通过识别屏幕内容完成相应任务。由此，屏幕位置的确定成为整车布局的首要环节，车体各功能模块的布置均需围绕屏幕位置展开。摄像头需布置于正对屏幕的方位，其固定位置与视野范围直接受屏幕位置约束；车辆主控板及其他电路模块需避开摄像头与屏幕之间的光路，同时需注意主控板上的状态指示灯是否会进入摄像头视野，对识别造成干扰。
屏幕固定支架有两种可选方案：其一为官方售卖的成品支架，其二为自行设计并3D打印的定制支架。自行设计虽可根据整车布局灵活调整结构，但受限于实验室现有打印材料（PLA与PETG），二者质地相对较软，在车模加减速及转向过程中可能导致屏幕发生晃动，影响识别稳定性。若委托外部厂家使用光固化树脂打印，则制作成本较高，试错成本随之增大。综合考虑成本与可靠性因素，本队选用官方成品支架，其余结构件的设计均以此支架为基准进行适配。
在具体布局方面，屏幕通过官方支架固定于车模上，显示面朝车模后方。车模上安装两个摄像头，分别用于识别无线屏幕中显示的全局地图俯视图和车模第一视角图像，以实现对场地全局信息与局部细节的同步感知。车模中部沿车长方向居中竖直架设两根碳素杆，两杆中心距20cm，杆顶固定磁铁，通过磁吸结构安装车顶方位标识牌。摄像头固定于屏幕显示面一侧的碳素杆上，确保其始终正对屏幕显示区域。
车模主控板、电机驱动板、电池及各功能模块均集中布置于屏幕背面一侧，使主控板上的常亮电源指示灯及其他光源被遮挡在屏幕背面，不会进入摄像头视野干扰识别；同时，通过调整电池的安放位置可调节整车重心，使前后轮受力趋于均匀，避免因一侧过重而影响车模运动的平顺性与稳定性。
2.2实现的技术方案概要说明
2.2.1系统总体架构
	系统分为感知层、决策层与执行层。感知层采用两个OpenART Plus摄像头模块分别采集全局地图与车模第一视角图像，采用ICM42688六轴惯性测量单元读取车身姿态信息，采用4个逐飞科技的1024线正交编码器分别采集四个轮子的速度信息，为运动控制提供反馈。
2.2.2控制方案
	通过视觉识别结果解算车模在场地中的位置坐标，通过车载陀螺仪解算车模姿态角，结合任务目标规划运动路径。在路径跟踪过程中，通过运动学逆解将期望速度矢量分解为四个麦克纳姆轮各自所需的转速指令，结合各轮编码器的速度反馈实现闭环速度控制，从而达成车模位置与姿态的精确控制。
2.2.3通信与系统协同方案
	主控芯片与两个OpenART Plus摄像头分别通过两路独立串口进行通信，与ICM42688陀螺仪通过SPI总线通信。主板预留一路SPI接口与一路串口接口，供功能扩展使用；另设计有一路10pin FPC软排线串口监控接口，将两路摄像头串口与预留串口接口的TX信号引出，可外接RT1064核心板对各路数据进行只读监听，实现数据采集与记录功能。该核心板将汇总后的数据通过高波特率串口发送至串口数据记录仪，存储于TF卡中；同时其TX引脚可通过杜邦线连接至串口透传模块，实时将数据传输至PC端进行显示与调试。
2.2.4关键技术与创新点
	针对虚实结合场景下视觉识别稳定性的问题，本队采用双摄像头分工协同的策略：摄像头一固定对准无线屏幕中的全局地图区域，用于解算场地信息并实时计算车模在场地中的位置坐标；摄像头二固定对准无线屏幕中的第一视角区域，用于识别虚拟场景中待推动箱体上的图案类别以及对应目标点位的编号。两者协同工作，实现全局定位与任务识别的并行处理。此外，串口监控接口的设计可在不干扰主控与摄像头正常通信的前提下实时监听数据交互过程，便于快速定位通信异常与识别错误问题，提升了开发调试效率。

第三章 机械结构与安装
3.1模型车机械部分的安装及改造
	在机械结构设计之前，首先对M车进行了整车建模（如图3.1.1），为后续各项结构件的设计提供尺寸基准与安装依据。本队在机械结构上主要加装了M车补强板、摄像头稳固支架、电池仓及主板支架、屏幕稳定杆以及遮光罩，具体设计如下。
图3.1.1 整车建模
M车补强板（如图3.1.2）安装于车模底部，由本队自行设计，委托外部厂商使用碳纤维材料加工制作。该补强板旨在弥补M车注塑结构底盘刚性不足的问题，减小车身在加减速及转向过程中产生的轻微形变，提升整车结构的稳定性与一致性。
图3.1.2 M车补强板
摄像头稳固支架（如图3.1.3）安装于屏幕显示面所朝向一侧的碳素杆上，整体套于碳素杆外部，底部通过螺丝固定于车底盘，同时嵌入电机后侧的横杆中，形成多点固定，确保支架在车辆运行中不会产生晃动。两个摄像头分别固定于支架两侧，分别对准无线屏幕中的全局地图区域与第一视角区域。
图3.1.3 摄像头稳固支架
电池仓及主板支架（如图3.1.4）安装于屏幕支架的后方。电池仓在横向上预留有一定的移动空间，电池可在其中沿横向滑动以调节整车重心位置。电池表面贴有魔术贴，与仓壁之间产生适度阻尼，使得电池在非严丝合缝固定的情况下，仍能在车辆加减速与转向过程中保持位置不变。电池仓上下两端均预埋热熔螺母，分别用于与车底盘和主控板进行螺纹连接，保证结构稳固且便于拆装。
图3.1.4 电池仓及主板支架
屏幕稳定杆（如图3.1.5）安装于两根碳素杆中间、屏幕支架的上方，通过螺丝与屏幕支架连接。该结构旨在弥补官方成品屏幕支架仅在底部单点固定、上方无约束的不足，有效抑制车辆运动中屏幕的轻微晃动。同时，屏幕稳定杆使屏幕与碳素杆之间的距离保持恒定，进一步抵消了因车底轻微形变导致两根碳素杆顶端间距偏离20cm中心距的影响。
图3.1.5 屏幕稳定杆
遮光罩（如图3.1.6）安装于屏幕稳定杆上方，采用卡扣方式固定，与稳定杆连接屏幕支架共用同一颗螺丝。当场地环境光线对摄像头识别造成干扰时，可加装遮光罩以降低杂散光影响，提升图像采集的稳定性。
图3.1.6 遮光罩
3.2传感器的设计安装
	本车模搭载的传感器主要包括图像传感器、编码器与陀螺仪三类。
图像传感器采用两个OpenART Plus视觉模块，分别固定于摄像头稳固支架的两侧，一个对准无线屏幕中的全局地图区域，用于解算场地信息并实时计算车模位置坐标；另一个对准无线屏幕中的第一视角区域，用于识别虚拟场景中箱体上的图案类别与目标点位编号。
编码器采用四个逐飞科技的1024线正交编码器，分别安装于车模底盘四个电机旁边，使用齿轮传动，用于采集各轮转速信息，为闭环速度控制提供反馈信号。
陀螺仪采用ICM42688六轴惯性测量单元，其裸片直接焊接于主控电路板上，随主板一同固定于屏幕背面一侧的电池仓及主板支架上，用于采集车模的姿态角信息。
3.3系统电路板的固定及连接
	系统电路板采用拼接式设计，分为一块主控板和两块驱动板。主控板接入电池供电、四路编码器反馈信号以及两路摄像头串口信号。两块驱动板分别插接于主控板上，其供电与通信信号均由主控板统一提供；每块驱动板输出两个电机控制方波信号，分别驱动对应电机的动作，两块驱动板共同实现四轮独立驱动控制。

第四章 硬件电路设计
系统电路板采用拼接式设计，分为一块主控板和两块驱动板。核心板采用逐飞科技成品RT1064核心板，整车供电采用3S锂电池。
4.1主控板设计
4.1.1供电网络
供电网络主要由VIN、VOUT、5V、5V_EXT及3V3五路电源构成。
VIN与VOUT各受一颗HY19P03D功率MOS管控制（如图4.1.1.1），其中VIN由主板自锁开关控制，VOUT由驱动开关控制。VOUT为驱动部分的供电网络，虽然驱动控制引脚已通过电阻默认下拉，但为防止因不可预知的情况意外触发驱动而导致电机不受控运行，采用串联供电结构，即主控板未上电时，驱动供电不能独立开启；同时，驱动供电可独立关闭，便于调试过程中的安全操作。
图4.1.1.1 供电部分电子开关电路原理图
5V电源采用SCT2450 DC-DC降压芯片提供（如图4.1.1.2），该芯片输入电压范围宽（3.8V~36V），输出电压可调（0.8V~36V），输出电流可达5A，满足本主板及各外设模块的供电需求。
图4.1.1.2 5V供电电路原理图

第五章 软件控制算法
5.1微处理器控制软件主要理论及算法说明
本智能车控制系统是一个多传感器强耦合、软硬件高度协同的复杂实时系统。为满足复杂场地下的精准全向移动、高鲁棒性目标识别以及多箱子最优路径求解需求，微处理器控制软件的底层理论被划分为底盘运动控制、双目机器视觉感知、启发式路径规划三大核心矩阵。
5.1.1底盘运动控制与多级闭环融合理论
底盘是物理动作的最终执行单元，系统基于麦克纳姆轮运动学解算构建了全向移动模型，并设计了以增量式 PI 速度环、位置式 PD 角度环及限幅位置 PID 组成的多级闭环控制网络。
	IMU自适应滤波与 ZUPT 互补里程计：针对高速运行时的姿态漂移与车轮打滑问题，系统对六轴姿态传感器提取的数据引入了一阶低通滤波（LPF），并独创了基于滑动窗口的动态零偏校准算法——通过实时统计角速度均值与方差，在严格的极低阈值下精准捕捉“绝对静止”时刻并动态更新零偏，从根源上抑制了温漂误差。此外，在里程计推算中引入 ZUPT（零速修正）算法，将编码器低频稳态速度与 IMU 高频突变加速度进行互补滤波融合，有效解决了急刹车和盲跑阶段因打滑导致的里程计失真。
	视觉导引梯形速度规划与软着陆：在接收视觉反馈时，摒弃了传统的线性跟随，设计了基于查表法（Look-up Table）与软着陆机制的梯形速度规划。根据 X/Y 轴映射到机体坐标系的绝对欧拉距离，在非线性区间动态输出限幅速度；当误差进入死区缓冲区时触发按比例衰减的“软着陆”调节，最终通过矢量合速度圆形限幅（Circular Limit）与步长平滑，实现了寻迹过程中的柔性起停与完美轨迹拟合。
5.1.2双目机器视觉与轻量化深度学习理论
系统的环境感知基于逐飞科技 OpenART Plus 的双目协同架构，左目主导全局网格重构与闭环导引，右目专注于车载视角的目标分类，两者通过自定义状态机串口协议与主控实现微秒级交互。
	多区域自适应色彩分割与动态解黏连：左目图像处理充分利用 LAB 颜色空间对光照的鲁棒性，根据小车在画面的空间位置（中心、边缘、四角）动态映射不同的阈值组，彻底消除了边缘暗角干扰。面对密集的箱体色块黏连难题，系统基于网格长宽比特征引入几何尺度切分算法，精准剥离并提取各箱体中心点；建立屏幕图像与 16×12 栅格的映射模型后，左目可实时解算小车与目标拐点的像素级偏差 (Δx, Δy)，为主控构建高精度的位置外环。
	端侧轻量化网络与 INT8 量化部署：右目视觉搭载了优化后的 MobileNetV2轻量化深度学习模型。在本地训练阶段，构建了包含高斯噪声、对比度、亮度及色相扰动的复合数据增强管道，并配置早停（Early Stopping）与动态学习率衰减机制以极大化模型泛化能力；在端侧部署阶段，利用代表性数据集进行全整型 INT8 PTQ（训练后量化）压缩，成功在算力受限的微处理器上实现了高准确率、极低延迟的目标分类。
5.1.3启发式路径规划与全局防死锁求解理论
针对多目标推箱子任务极易引发的维度爆炸与状态死锁，软件集成了一套具备双重保底机制的 A* 启发式图搜与全局规划算法。
	分层模块化设计与内存极限优化： 算法架构划分为地图数据、死锁检测、路径巡视、求解器与调试交互五大模块，高度解耦。为突破 MCU 片上 RAM 的资源瓶颈，利用 GridState、Pos、Goals 等结构体并大量复用 uint8_t 类型极致压缩内存，同时将庞大的搜索树状态数组强制映射至外部 SDRAM 缓存段。
	哈希状态去重与高精度死锁剪枝： 底层 A* 寻路采用曼哈顿距离作为基础启发函数，并巧妙叠加了推箱子与转向代价惩罚。算法引入 FNV-1a-64 强哈希散列算法实现全局状态的 O(1) 复杂度去重，有效遏制了搜索空间的指数级爆炸。高层规划通过回溯机制循环分配单箱任务。寻路期间，依靠 BFS（广度优先搜索）建立极严格的死锁检测模型，细分为静态箱子、动态箱子、炸弹及目标死锁四类，配合缓存失效机制为搜索树实时剪枝；必要时可触发“炸弹爆破仿真”算法消除内墙死锁。
	双模式策略与 Bresenham 轨迹后处理： 业务逻辑提供了两套互补策略：“普通模式”允许箱子任意就近分配目标，作为高鲁棒性的保底求解；“匹配模式”则通过调用巡视预处理，模仿人类贪心探图策略采集点位，随后执行严格的字母-数字一一绑定求解。在输出物理路径前，后处理链路采用 Bresenham 直线采样算法执行斜向通行校验与轨迹拐点化简，最终仅将极致精简的网格坐标序列交予底层驱动执行，彻底打通了从顶层逻辑算力到物理空间的业务闭环。
5.2代码设计介绍
本系统的代码架构遵循“高内聚、低耦合”的模块化设计原则，将底盘运动、视觉交互与路径规划无缝衔接。系统以全局状态机和自定义通信协议为驱动中枢，实现了从顶层逻辑算力到物理空间运动的完整业务闭环。
5.2.1底盘运动控制与状态机流转设计 
底盘控制软件以全局状态机变量 car_state 为核心主线，驱动小车完成完整工作流：
	启动发车阶段 (CAR_IDLE 至 CAR_START_Y)： 系统上电后利用里程计目标坐标 (target_odometer_x, target_odometer_y) 结合位置 PID 驶出发车区。当位移误差在多帧内均小于设定阈值（ERR_THRE）时确认发车完毕，随后开启视觉地图识别并进入待命状态（CAR_WAIT_ERR）。 
	视觉导航枢纽 (CAR_NAVIGATE)： 该状态为系统常态，主控实时接收左目回传的像素偏差 axis_err_x 与 axis_err_y。系统自适应评估误差权重并切换 MODE_DIAGONAL、MODE_X_MAJOR 等运行模式。此状态同时充当多任务调度枢纽，实时监听转向、停车及编码器盲跑（encoder_receive_done）等外部中断标志。 
	里程计盲跑穿越 (CAR_ENCODER)： 接收到无视觉引导区域的指令时，系统中断视觉闭环，以当前真实里程计坐标为基准 (target_odometer_x = odometer.x) 开启盲跑。底层运动学依赖融合了 ZUPT 零速修正的 Encoder_Integral_Calculate_Fused 模块推算机体位移。指令集执行完毕后，小车向视觉模块发送到达标志 (send_arrive_flag_W) 并无缝切回CAR_NAVIGATE。
5.2.2双目视觉状态机与通信交互设计
视觉感知建立在严格的自定义状态机串口协议之上：
	左目闭环导引链路： 交互由主控发起请求（下发 K 标志），左目端 main.py 程序随即锁定感光与白平衡，遍历子 ROI 生成并回传 16×12 栅格地图。随后主控通过 +..- 协议分批下发解算出的坐标拐点。左目进入动态追踪模式，实时解算小车中心至目标的相对位置，持续发送格式为 (+xx-yy..) 的像素误差报文，支持与底层编码器深度解耦的混合导引。 
	右目推理识别链路： 当小车抵达最终终点并完成姿态校正后，主控下发触发标志 !L?。唤醒右目摄像头捕获当前帧，加载 INT8 量化后的 MobileNetV2 模型完成目标分类推理，并将识别结果回传主控以完结整个任务链。
5.2.3路径规划内存管理与双轨求解设计
路径规划采用纯 C 语言开发，划分为地图数据层、死锁检测层、路径巡视层、求解器层与调试交互层。
	内存资源调度：为规避 MCU 片上 RAM 瓶颈，系统利用 GridState、Pos、Goals 等精简类型（如大量使用 uint8_t）构建结构体描述局面，并将庞大的状态空间哈希数组统一部署于 SDRAM 缓存段，确保高层回溯与低层 A* 嵌套时的栈堆安全。
	业务逻辑双轨入口：核心求解链路在 parameter.c 中被统一封装。系统设计了两套相互保底的执行流：第一套为载入地图后直接调用的 solve_puzzle()，执行无限制匹配的普通全局求解；第二套为匹配模式，先调用 patrol_map() 激活巡视预处理，基于贪心策略控制底盘采集地图信息后置位 patrol_continue_flag，随后拉起 solve_puzzle_match() 执行字母与数字的一一绑定求解。最终轨迹经过 Bresenham 斜向验证与化简后，输出至底层供 CAR_SOLVE_TASK 调度执行。

6.1开发工具说明
本智能车控制系统的开发是一个跨平台、软硬件高度耦合的协同工程。为保证底层驱动的高效编译、视觉算法的快速迭代以及 AI 模型的精准部署，项目中主要采用了以下几款核心开发与调试工具：
集成开发环境（Keil MDK）：用于主控软件的核心 C 语言代码编写、工程管理、编译与链接。Keil 提供了优秀的编译器和丰富的底层外设支持库，极大地提高了代码执行效率。
逐飞 DAP 下载器与示波器：DAP 下载器支持高速 SWD 接口，不仅用于日常程序烧录，更在复杂算法排查中提供了断点设置与全局变量在线监控功能；示波器则用于精准捕捉底层 PWM 波形与编码器正交解码信号，确保硬件底层逻辑无误。
逐飞助手（上位机调试软件）：利用其内置的虚拟示波器功能，将电机的目标/实际速度、视觉回传的像素误差实时绘制成波形，为 PID 闭环参数（Kp、Ki、Kd）的精细化微调提供了直观的数据支撑。
OpenMV IDE：专为端侧视觉模块开发的集成环境。项目中主要依托其进行 MicroPython 脚本编写、多区域 LAB 色彩阈值的动态调谐，以及端侧实时画面的监控与 ROI 取景框校验。
PyCharm：作为深度学习算法开发的算力中枢，在 PC 端运行 TensorFlow 框架。主要负责 MobileNet-V2 模型的搭建、迁移学习训练迭代，以及关键的 INT8 离线量化压缩流程。
6.2制作、安装、调试过程说明
在完成车模底盘装配与 PCB 主板固定后，软硬件联调工作全面展开。调试过程遵循“由底向上、单点突破至全局联调”的原则，在实际下地试车与测试中，系统攻克了光照干扰、高频振动、端侧算力瓶颈等多项技术难点，具体过程有以下几点：机械安装与视觉光照标定，底层姿态融合与里程计抗滑调试，视觉预处理优化与端侧 AI 部署，通信闭环与双模混合导航联调。
6.2.1机械安装与视觉光照标定
在传感器布局方面，为最大化感知视野，左目摄像头采用倾斜支架安装，以全面覆盖屏幕网格区；右目摄像头则保持水平正对，专门负责前方的目标识别区。 在赛道实测初期，屏幕反光对色彩分割造成了严重干扰。为此，我们在底层寄存器级别强制关闭了相机的自动白平衡（AWB）与自动曝光（AE），通过手动标定锁定增益与曝光时间，彻底消除了反光与外界光线突变带来的阈值漂移。
6.2.2底层姿态融合与里程计抗滑调试
高频振动干扰： 底盘开环测试时，电机震动导致 IMU6050 产生严重的高频毛刺与零偏。为此引入了一阶低通滤波，并设计了动态零偏校准算法。系统通过实时统计角速度均值与方差，在严格阈值下捕捉“绝对静止”时刻并动态更新零偏，保障了长直道航向角的绝对稳定。
打滑与盲跑失真： 针对高速大角度寻迹时的车轮打滑问题，控制端引入了柔和的梯形速度规划与软着陆；定位端开发了 ZUPT（零速修正）互补滤波里程计。将编码器稳态速度与 IMU 加速度积分融合，成功规避了急刹车滑行带来的“虚假位移”，解决了盲跑阶段的位置丢失难题。
6.2.3视觉预处理优化与端侧 AI 部署
网格预计算与帧率优化： 在左目建图阶段，大量像素级浮点除法运算曾导致画面卡顿。经过优化，我们建立了全局网格坐标的静态查找表（Look-up Table），大幅削减了主循环的算力开销，使得左目视觉闭环运行帧率稳定突破 50 FPS 以上。
模型训练与量化微调： 针对右目目标分类，我们在真实赛道工况下采集了大量多角度、多样光照的样本。在 PyCharm 端经 60轮迭代训练，模型在验证集上的准确率飙升至 99.9% 以上。为部署到资源受限的端侧，我们精心挑选了 2 万张典型图片作为校准集执行 INT8 全整型量化，将量化过程中的精度损失严格控制在了 0.4% 以内，实现了性能与速度的完美平衡。
6.2.4通信闭环与双模混合导航联调

第八章 结论与改进方向
8.1结论
本文围绕第二十一届全国大学生智能汽车竞赛智能视觉组的赛题要求，设计并制作了一台基于M车模的全向移动智能车模。在车模选型方面，综合考量了M车、M1车与Y车在结构强度、标识牌适配性、控制复杂度与维护便利性等方面的差异，最终确定以M车模为主力平台、M1车模为备选平台，并明确了在负压应用场景下选用M1车的技术考量。在整车布局方面，以无线屏幕的安装位置为核心，采用双摄像头分工协同方案，分别识别全局地图与第一视角图像，各功能模块集中布置于屏幕背面，避免了指示灯等光源对视觉识别的干扰，同时通过电池位置可调实现重心优化。
在机械结构设计方面，通过对M车进行整车建模，针对性设计了碳纤维补强板、摄像头稳固支架、电池仓及主板支架、屏幕稳定杆和遮光罩等结构件，有效弥补了原车注塑底盘刚性不足、屏幕固定不稳定等问题，为系统稳定运行提供了结构保障。
在硬件电路设计方面，采用主控板与驱动板拼接式架构，主控板基于RT1064核心板，设计了完善的供电网络，满足核心板时序要求及各类外设供电需求。地平面采用功率地与逻辑地分离设计，抑制了驱动电路对主控电路的干扰，实现了可靠的四路电机独立驱动。
在软件算法方面，通过视觉识别结果解算车模在场地中的坐标，结合陀螺仪姿态信息规划运动路径，经运动学逆解将期望速度分解为四轮转速指令，结合编码器速度环反馈实现位置与姿态的精确控制。板载蜂鸣器、五向按键等外设为调试与状态反馈提供了便利，串口监控接口可在不干扰正常通信的前提下实时监听系统数据，有效提升了开发和调试效率。
本车模在3.2m×2.4m的比赛场地内能够实现全向自由移动，视觉识别与运动控制协同工作，完成了虚实结合场景下的推箱子任务。通过一系列结构加固与电路优化措施，系统的识别稳定性与控制精度得到了有效保障，达到了赛题所要求的基本性能指标。

8.2存在的问题与改进方向
尽管本车模在现有方案下实现了基本功能并达到了预期的性能指标，但在实际调试与比赛过程中仍暴露出若干可改进之处：
8.2.1摄像头帧率限制
本系统采用的OpenART Plus摄像头最高帧率为60fps。在当前速度条件下，该帧率基本满足视觉识别与定位需求，但若希望进一步提升车模运行速度，更高帧率的图像传感器将更为必要。帧率不足会导致车模在高速运动过程中图像采集的实时性下降，进而影响位置解算的精度与控制响应的及时性，成为速度提升的瓶颈之一。
8.2.2可升级为负压结构
在方案设计阶段曾考虑并实装测试过加装负压装置以增加车模下压力、提升速度，但综合考虑车载摄像头的帧率与分辨率限制后，本队认为优化路径规划算法所带来的速度增益更为显著和直接，因此将负压方案优先级后置，未在本代车模中实施。
8.2.3裁判系统延迟
由于竞赛采用“虚实结合”的赛制，裁判系统需通过全局摄像头采集场地信息，经上位机处理后将虚拟场景通过无线网络传输至车模屏幕。受限于官方裁判系统的性能，画面传输存在固有延迟，且屏幕画面与实际场地状态之间存在一定的时间差。当车模速度过快时，可能导致裁判系统响应滞后甚至出现画面跳变，影响虚拟场景中目标元素的位置准确性，进而干扰识别与决策。由于裁判系统由组委会统一提供，参赛队伍无法对其进行任何修改或优化，因此只能通过优化车模运动路径与控制策略来规避延迟带来的不利影响，在现有系统框架内寻求速度与稳定性的最佳平衡。

static void collect_line_pass_cells(Pos start, Pos end, uint8_t vis[12][16], Pos out_cells[], int *out_cnt){
    int x0 = start.x, y0 = start.y;
    int x1 = end.x, y1 = end.y;
    int stepX = x1>x0 ? 1 : (x1<x0 ? -1 : 0);
    int stepY = y1>y0 ? 1 : (y1<y0 ? -1 : 0);
    int gx = stepX >=0 ? x0 : x0-1;
    int gy = stepY >=0 ? y0 : y0-1;
    int targetX = stepX >=0 ? x1 : x1-1;
    int targetY = stepY >=0 ? y1 : y1-1;
    int dx = abs(x1-x0);
    int dy = abs(y1-y0);
    float tMaxX = 1e6f, tMaxY = 1e6f;
    float tDeltaX = 1e6f, tDeltaY = 1e6f;
    const float eps = 1e-6f;
    if(stepX != 0) { tMaxX = 1.0f/dx; tDeltaX = 1.0f/dx; }
    if(stepY != 0) { tMaxY = 1.0f/dy; tDeltaY = 1.0f/dy; }
    if(gx>=0&&gx<16&&gy>=0&&gy<12 && !vis[gy][gx]){
        vis[gy][gx]=1;
        if(*out_cnt<256) out_cells[(*out_cnt)++] = (Pos){gy,gx};
    }
    while(gx!=targetX || gy!=targetY){
        if(tMaxX < tMaxY - eps){
            gx += stepX; tMaxX += tDeltaX;
        }else if(tMaxY < tMaxX - eps){
            gy += stepY; tMaxY += tDeltaY;
        }else{
            gx += stepX; gy += stepY;
            tMaxX += tDeltaX; tMaxY += tDeltaY;
        }
        if(gx==targetX && gy==targetY) continue;
        if(gx>=0&&gx<16&&gy>=0&&gy<12 && !vis[gy][gx]){
            vis[gy][gx]=1;
            if(*out_cnt<256) out_cells[(*out_cnt)++] = (Pos){gy,gx};
        }
    }
}

void complete_match_arrays(char target_nums[], int* target_cnt,char box_nums[], int* box_cnt){
    char debug[200];
    sprintf(debug, "complete enter: target=%d, box=%d\r\n", *target_cnt, *box_cnt);
    uart_write_string(UART_4, debug);
    int count_digit[10] = {0};
    int count_letter[10] = {0};
    for (int i = 0; i < *target_cnt; i++) {
        if (target_nums[i] >= '0' && target_nums[i] <= '9')
            count_digit[target_nums[i] - '0']++;
    }
    for (int i = 0; i < *box_cnt; i++) {
        if (box_nums[i] >= 'a' && box_nums[i] <= 'j')
            count_letter[box_nums[i] - 'a']++;
    }
    int did_fix = 0; 
    for (int i = 0; i < 10; i++) {
        int max_cnt = (count_digit[i] > count_letter[i]) ? count_digit[i] : count_letter[i];
        while (count_digit[i] < max_cnt) {
            target_nums[*target_cnt] = '0' + i;
            count_digit[i]++;
            (*target_cnt)++;
            did_fix = 1;
        }
        while (count_letter[i] < max_cnt) {
            box_nums[*box_cnt] = 'a' + i;
            count_letter[i]++;
            (*box_cnt)++;
            did_fix = 1;
        }
    }
    if (!did_fix && *target_cnt == *box_cnt) {
        for (int i = 0; i < 10; i++) {
            if (count_digit[i] == 0 && count_letter[i] == 0) {
                target_nums[*target_cnt] = '0' + i;
                box_nums[*box_cnt] = 'a' + i;
                (*target_cnt)++;
                (*box_cnt)++;
                break;
            }
        }
    }
    sprintf(debug, "Post target(%d): ", *target_cnt);
    for(int i = 0; i < *target_cnt; i++) 
    printf(debug + strlen(debug), "%c ", target_nums[i]);
    strcat(debug, "\r\n");
    uart_write_string(UART_4, debug);
    sprintf(debug, "Post box(%d): ", *box_cnt);

    printf(debug + strlen(debug), "%c ", box_nums[i]);

    uart_write_string(UART_4, debug);
}

int load_map_from_array(char map_lines[H][W+1], GridState* st, Goals* goals) {

    goals->n = 0;
    int found_agent = 0;
    for (int y = 0; y < H; y++) {
        const char* line = map_lines[y];
        for (int x = 0; x < W; x++) {
            char c = line[x];
            if (c == BOX) box_count++;
            if (c == GOAL) goal_count++;
        }
    }

//    if (box_count != goal_count || goal_count > MAX_GOALS) return 0;
        if (goal_count > MAX_GOALS) return 0;
    for (int y = 0; y < H; y++) {
        const char* line = map_lines[y];
        for (int x = 0; x < W; x++) {
            char c = line[x];
            if (c == GOAL) {
                goals->goal[goals->n++] = (Pos){ (uint8_t)y, (uint8_t)x };
                st->g[y][x] = EMPTY;
            } else {
                st->g[y][x] = c;
            }
            if (c == AGENT) {
                st->agent = (Pos){ (uint8_t)y, (uint8_t)x };
                found_agent = 1;
            }
        }
    }
    if (!found_agent) {
        st->agent = (Pos){ 5, 1 };
        st->g[5][1] = AGENT;
    }
        st->resolved_goals_mask = 0;
    return 1;
}

def detect_cell_color(img, cell_roi, row, col):
    """基于色块占比识别单元格颜色"""
    x, y, w, h = cell_roi
    color_pixels = {name: 0 for name in COLOR_THRESHOLDS.keys()}
    # 检测每个颜色的色块
    for color_name, threshold in COLOR_THRESHOLDS.items():
        blobs = img.find_blobs(
            [threshold],
            roi=cell_roi,
            pixels_threshold=5,  # 过滤微小噪声
            area_threshold=5
        )
        for blob in blobs:
            color_pixels[color_name] += blob.pixels()
    # 计算各颜色的像素占比
    total_pixels = w * h
    max_pixels = max(color_pixels.values())
    if max_pixels < total_pixels * 0.1:  # 占比过低则判为空地
        return "empty"
    return max(color_pixels, key=color_pixels.get)
